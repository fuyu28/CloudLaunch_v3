# objstore

- 日時: 2026-10-23 01:53 (JST)

## 当初の要求 / 背景

M1（walking skeleton）の 2 つ目の作業として、リモートに読み書きできるようにする。コアはリモートを、キーを指定して Get / Put / List / Delete を行う汎用のオブジェクトストアとして扱い、`internal/objstore` は S3 API の薄いラッパーにする（2026-10-23_00-30_remote-object-store.md）。

objstore と、テストで使う偽物の振る舞いがずれないよう、両方に同じ契約テストを走らせ、本物の側は S3 互換のサーバーで確かめることにしていた（AGENTS.md「テスト」）。そのサーバーには MinIO を想定していたが、MinIO の GitHub リポジトリ（`minio/minio`）は 2026 年 4 月にアーカイブされている。

本番の接続先は R2 で、HTTPS で接続する。手元と CI のテスト用のサーバーは、HTTP で立てる。

## 仕様

- パッケージの構成
- 契約テストに使う S3 互換のサーバー
- 「キーがない」ことの表し方
- 各操作の引数と振る舞い
- S3 クライアントの設定
- 偽物で失敗を仕込む方法
- 契約テストを本物のサーバーに対して走らせる条件

## 決定事項

### パッケージの構成

- 事項: 本物・偽物・契約テストの置き場所
- 決定内容: `internal/objstore` に S3 API の実装、`internal/objstore/memstore` にメモリ上の偽物、`internal/objstore/objstoretest` に契約テストの本体（本物と偽物の両方から呼ぶ関数）を置く。偽物と契約テストは、他のパッケージのテストから使うため、テストファイルではなく通常のパッケージにする。objstoretest は、契約テストのためだけの小さなインターフェースを自分で持つ
- 判断理由: Go の標準ライブラリにも、本体（`net/http`、`io/fs`）とテスト用の部品（`net/http/httptest`、`testing/fstest` の `MapFS` と `TestFS`）を分ける前例があり、同じ分け方にした。使う側のインターフェースは syncore と metasync が定義するので（2026-10-23_00-30_package-structure.md）、objstore はインターフェースを公開しない

### 契約テストに使うサーバー

- 事項: 本物の側の契約テストで使う S3 互換のサーバー
- 決定内容: versitygw（`versity/versitygw:v1.9.0`）を、ローカルのディレクトリをそのまま見せる posix のバックエンドで使う。合わなければ RustFS に替える
- 判断理由: 契約テストで確かめたいのは、objstore が S3 API を正しく使えているか（往復しても内容が変わらない、ページングで取りこぼさない、「キーがない」の変換、署名・パス形式・チェックサムの設定でリクエストが拒否されない）であり、保存したデータが失われないこと（耐久性）はサーバーの性質なので対象外である。versitygw は単体で動く軽いゲートウェイで、Apache-2.0 で更新が続いている。RustFS は S3 互換のオブジェクトストアそのもので R2 に振る舞いが近い見込みがあるが、そのぶん重い。versitygw はファイルシステムに変換するため、特殊な文字のキーや一覧の細部が R2 と違う可能性があり、その違いは本物の R2 に対する手動のテストで確かめる

### 「キーがない」ことの表し方

- 事項: Get でキーがないときのエラー
- 決定内容: 標準ライブラリの `fs.ErrNotExist` で包んだエラーを返す
- 判断理由: syncore は HEAD がないこと（仕様書 4 章の「remote なし」）を判別する必要がある。objstore が独自のセンチネルエラーを持つと、syncore と metasync が objstore を import することになり、依存の向きに反する。`fs.ErrNotExist` なら、どちらも標準ライブラリを参照するだけで済む

### 各操作の引数と振る舞い

- 事項: Get / Put / List / Delete の形
- 決定内容:
  - `Get(ctx, key) (io.ReadCloser, error)`
  - `Put(ctx, key, body io.ReadSeeker, size int64) error`。同じキーへの Put は上書きになる
  - `List(ctx, prefix) ([]string, error)`。prefix で始まるキーを、すべて辞書順で返す。1,000 件を超えるページングは objstore の中で処理する
  - `Delete(ctx, key) error`。キーがなくてもエラーにしない
- 判断理由: Put の本文を `io.Reader` ではなく `io.ReadSeeker` にするのは、AWS SDK の PutObject が、HTTP の接続では署名のために本文を読んで sha256 を計算し、先頭に巻き戻してから送るためである（`aws-sdk-go-v2/aws/signer/v4/middleware.go` の `dynamicPayloadSigningMiddleware` と `ComputePayloadSHA256`、`smithy-go/transport/http/request.go` の `RewindStream`）。巻き戻せない本文では、HTTP で立てたテスト用のサーバーへの Put が失敗する。HTTPS では本文を署名に含めない（`UNSIGNED-PAYLOAD`）ので R2 では動くが、テストを HTTPS で立てるには自己署名の証明書の扱いが要る。巻き戻せないものをメモリに読み込んで送る方法は、セーブの大きいゲームでファイル全体がメモリに載る。syncore が Put に渡すのはファイル（`*os.File`）か、manifest などのバイト列（`bytes.Reader`）で、どちらも巻き戻せる。Delete でキーがなくてもエラーにしないのは、S3 の DeleteObject の振る舞いに合わせるためで、リモート削除（仕様書 8 章）の消し残りの掃除のように、同じ削除をやり直しても失敗しないようにする。区切り文字を使った一覧（仕様書 8 章の取り込み）とまとめての削除（GC）は、使う段階（M3、M2）で足す

### S3 クライアントの設定

- 事項: AWS SDK のクライアントの設定
- 決定内容: エンドポイントを指定し、パス形式（`UsePathStyle`）を有効にする。リージョンは設定（`Config.Region`）で指定でき、空なら `auto` にする。テスト用の versitygw は `--region auto` で立て、リージョンを空のまま接続する。リクエストとレスポンスの追加のチェックサムは、必要なときだけにする（`RequestChecksumCalculation` と `ResponseChecksumValidation` を `WhenRequired`）。再試行は SDK の既定に任せる
- 判断理由: R2 も versitygw もパス形式に対応しているので、1 つの設定で両方につながる。つなぎ先を R2 に絞る必要はなく、AWS S3 や Wasabi などの S3 互換のサービスは、署名に正しいリージョンがないとリクエストを拒否するので、リージョンを設定で指定できるようにする。空のときの `auto` は R2 が指定するリージョンで、R2 では値を選ぶ余地がない（EU などのジュリスディクションはエンドポイントで選ぶ）ため、R2 の利用者は指定しなくて済む。versitygw は署名のリージョンを検査し、既定の `us-east-1` 以外を `AuthorizationHeaderMalformed` で拒否するので、サーバーの側を `auto` に合わせる。AWS SDK は 2025 年から既定で CRC32 のチェックサムを付けるようになり、S3 互換のサーバーで拒否される例があった。内容の正しさは仕様書のとおり sha256 で検証するので、SDK のチェックサムには頼らない。チェックサムを必要なときだけにすると、PutObject はチェックサムの計算の経路を通らない（`aws-sdk-go-v2/service/internal/checksum` の `ComputeInputPayloadChecksum`）

### 偽物で失敗を仕込む方法

- 事項: memstore で任意の操作を失敗させる仕組み
- 決定内容: memstore に、各操作の前に呼ばれるフック `Before func(op Op, key string) error` を持たせる。フックがエラーを返せば、その操作は実行されずにそのエラーで失敗する
- 判断理由: 中止のテスト（AGENTS.md「テスト」）では、「HEAD の Put だけ」「3 回目の object の Put」のように、失敗させる操作を細かく選ぶ必要がある。フックを 1 つ持たせれば、選び方をテストの側で自由に書ける

### 契約テストを本物のサーバーに対して走らせる条件

- 事項: 本物のサーバーに対する契約テストを、いつ走らせるか
- 決定内容: 環境変数 `CLOUDLAUNCH_TEST_S3_ENDPOINT`・`CLOUDLAUNCH_TEST_S3_BUCKET`・`CLOUDLAUNCH_TEST_S3_ACCESS_KEY_ID`・`CLOUDLAUNCH_TEST_S3_SECRET_ACCESS_KEY` があるときだけ走らせ、ないときは skip する。versitygw は `compose.yaml` で定義し、手元でも CI の Ubuntu のジョブでも `docker compose up -d --wait` で立てる。本物の R2 に対しては、ビルドタグ `r2` を付けたときだけ走らせる（#9 で入れる）
- 判断理由: GitHub Actions の service コンテナには起動の引数を渡せず、versitygw はバックエンドの指定などを引数で受け取るので、手順の中で立てる。CI でも `compose.yaml` を使えば、手元と CI でサーバーの設定が 1 か所にまとまる。`--wait` が待ち受けの開始まで待てるよう、compose にヘルスチェックを置く。Windows のランナーでは Linux のコンテナを動かせないため、Ubuntu だけで行う。環境変数がないときに skip すれば、サーバーを立てていない手元でも `go test ./...` が通る

## 結果 / 影響

- 契約テストの 8 ケースが、memstore と versitygw の両方で通る。versitygw に対しては約 4 秒で、そのうち 1,001 件を Put して List するケースが約 3 秒を占める
- HTTP の接続で、巻き戻せない本文を PutObject に渡すと `failed to seek body to start, request stream is not seekable` で失敗することを、versitygw に対して確かめた。Put を `io.ReadSeeker` にした根拠が実物でも成り立つ
- memstore の Put は、`size` と本文の長さが違えば失敗する。S3 が Content-Length と本文のずれたリクエストを拒否するのに合わせたもので、契約テストには含めていない
- S3 の List が辞書順で返すことに頼らず、objstore の中で並べ替える。キーの数だけ並べ替えの手間が増える
- 依存に AWS SDK（`service/s3`・`credentials` と、その間接的な依存）が加わった
- 本物の R2 との振る舞いの違いは、まだ確かめていない（#9 で確かめる）
