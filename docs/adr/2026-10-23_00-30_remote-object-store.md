# remote-object-store

- 日時: 2026-10-23 00:30 (JST)

## 当初の要求 / 背景

同期コア（syncore・metasync）は、R2 上のデータを読み書きする。コアはリモートとのやり取りをインターフェースで受け取る（2026-10-23_00-30_package-structure.md）。そのインターフェースの粒度と、並列に転送するときの責任の分担を決める必要がある。

リモートのキーの形（`games/{gameId}/HEAD` など）は、仕様書 2 章で定めた振る舞いの一部である。同期コアのテストでは、リモートを偽物に差し替え、任意の手順で失敗させて中止・中断を確かめる（AGENTS.md「テスト」）。

## 仕様

- リモートのインターフェースの粒度
- キーの形をどこが持つか
- 大きなファイルの受け渡し方
- 並列実行の制御をどこが持つか

## 決定事項

### インターフェースの粒度とキーの形

- 事項: コアが使うリモートのインターフェース
- 決定内容: キーを指定して Get / Put / List / Delete を行う汎用のオブジェクトストアとする。キーの形はコア（syncore・metasync）が持ち、`internal/objstore` は S3 API の薄いラッパーにする
- 判断理由: `ReadHEAD` や `PutManifest` のような同期専用の高水準なインターフェースにすると、キーの形がアダプタの実装の中に入り、偽物を使うテストからは見えなくなる。汎用のオブジェクトストアなら、テストの偽物は「キー → 中身」の対応表で済み、「`games/x/HEAD` が書かれた」ことを確かめられる。キー単位で失敗を仕込めるので、中止のテストも書きやすい。ゲーム情報やプレイ履歴も同じ 4 つの操作で足りるので、metasync とも共用できる

### 受け渡しの型

- 事項: Get と Put でデータをどう受け渡すか
- 決定内容: `[]byte` ではなく `io.Reader`（Get は `io.ReadCloser`）で受け渡す
- 判断理由: セーブの大きいゲームでも、ファイル全体をメモリに載せずに転送するため

### 並列実行の分担

- 事項: 並列の転送を、どこがどう制御するか
- 決定内容: objstore の実装は、複数の goroutine から同時に呼んでも安全にする。並列数は呼び出す側のコアが `golang.org/x/sync/errgroup` の `SetLimit` で制御し、objstore の側では制御しない。転送は 8 並列、ハッシュ計算は CPU の数を上限とする。1 つが失敗したら残りをキャンセルし、再試行は AWS SDK に任せる。進捗はコアが直列化したコールバックで通知する
- 判断理由: 両方で並列数を制御すると、実際の並列数が掛け算になり読めなくなる。AWS SDK のクライアントは同時に呼んでも安全なので、本物の実装には追加の作業が要らない。CloudLaunch_Go は、最初のエラーの記録とキャンセルを `sync.WaitGroup`・`sync.Once`・`context.WithCancel` の組み合わせで手書きしていた（`internal/infrastructure/storage/blob_store.go`）。errgroup はこれを置き換える。`github.com/sourcegraph/conc` は goroutine 内の panic を呼び出し元へ伝えられるが、panic はバグであり、その後の復旧は Pull ジャーナルと判定表が担うので（仕様書 4・6 章）、差にならない。errgroup は Go チームが保守する準標準ライブラリで、依存が小さい。失敗時に残りの転送を中止しても、Push では参照されない object が残るだけで、Pull では stage を削除するので安全である（仕様書 5・6 章）

## 結果 / 影響

- キーの形をコアのテストで守れる
- objstore と偽物の振る舞いがずれる恐れがあるので、両方に同じ契約テストを走らせる（本物の側は MinIO）
- 並列数 8 は固定の値で、回線の遅い環境で調整できない
