# セーブ同期仕様

このファイルが同期の振る舞いの唯一の正。振る舞いを変えるときは、実装より先にこのファイルを変える PR を通す。

---

## 1. 目的と範囲

- CloudLaunch は複数 PC 間でセーブデータを安全に持ち運ぶツール
- 同期対象: セーブフォルダ配下の全ファイル（除外パターンは v1 では持たない）

### 保証すること

ユーザーが明示的に上書きを選ばない限り、どの PC のセーブも失われない。
同期が途中で失敗しても、ローカルのセーブフォルダとリモートの最新 manifest は、それぞれ「同期前」か「同期後」の完全な状態にある。

### 保証しないこと

- 同時 push の排他。後から HEAD を書いた方が勝ち、先の push は最新でなくなる
- 同時 push と GC が重なったとき、最新 manifest が欠損 object を参照しうる（5 章）。この場合も Pull の検証で失敗するためローカルは壊れず、再 Push で直る

### 対象外（v1）

- reset / branch / 履歴閲覧 / ファイル単位マージ
- 既存のローカル登録をクラウド上のゲームへ後から紐付ける（ID 付け替え）
- ゲーム情報の項目単位の後勝ち
- 画像の縮小・サムネイル生成
- 削除したゲームの取り消し、削除済み gameId の再利用
- プレイ履歴の編集・削除、セーブのリセット、使われていない画像の削除（10 章、v1 後に実装）

### 用語

- **manifest**: ある時点のセーブフォルダの内容一覧（2 章）
- **manifest ハッシュ**: manifest の `entries` だけから計算するハッシュ。同期状態の比較はすべてこれで行う
- **object**: ファイル実体。sha256 をキーに不変で保存する
- **世代**: リモートに保存された 1 つの manifest。UUIDv7 で識別する
- **HEAD**: リモートの最新世代を指すポインタ
- **base**: この PC で、ローカルとリモートが一致したと最後に確認できた manifest ハッシュ
- **local**: 現在のセーブフォルダから計算した manifest ハッシュ
- **remote**: HEAD が指す世代の manifest ハッシュ
- **tombstone**: ゲームがリモートで削除されたことを示す印

## 2. リモートのデータ構造（R2）

### キーのレイアウト

```
games/{gameId}/HEAD                     最新世代の UUIDv7（テキスト）
games/{gameId}/manifests/{UUIDv7}.json  manifest（不変）
games/{gameId}/objects/{sha256}         セーブファイル実体（不変）
games/{gameId}/game.json                ゲーム情報（8 章）
games/{gameId}/sessions/{sessionId}.json プレイ履歴 1 件（不変、8 章）
games/{gameId}/images/{sha256}          ゲーム画像（不変、8 章）
games/{gameId}/deleted.json             tombstone（8 章）
games/{gameId}/saves-reset.json         セーブのリセット記録（10 章、v1 後）
games/{gameId}/sessions/{sessionId}.deleted.json プレイ履歴の tombstone（10 章、v1 後）
```

### manifest

```json
{
  "version": 1,
  "createdAt": "2026-10-22T12:00:00.000Z",
  "deviceName": "Desktop",
  "entries": [{ "path": "slot1.sav", "sha256": "...", "size": 1234 }]
}
```

- `path` はセーブフォルダからの相対パス、区切りは `/` に正規化、大文字小文字は区別
- `entries` は `path` の昇順
- mtime は含めない
- 対象は通常ファイルのみ。空ディレクトリは保存・復元しない
- `createdAt` / `deviceName` は確認ダイアログの表示用

### manifest ハッシュ

- `entries` だけを正規化 JSON にした sha256。`version` / `createdAt` / `deviceName` は含めない
- 別の PC が同じ内容を push すれば同じハッシュになる

### 世代の保持と削除

- 直近 10 世代を保持する。新しさは世代キー（UUIDv7）の順で決める
- HEAD 差し替え成功後、`manifests/` を一覧し、新しい 10 件を残して残りを削除する
- HEAD が指す世代は、10 件に入らなくても削除しない（時計のずれた PC の push で最新を消さないため）
- GC: 削除後に残った全世代のどれからも参照されない object を削除する

## 3. ローカルの状態

- base: ゲームごとに SQLite に保存。初回は未設定（判定表の「なし」）
- ハッシュキャッシュ: `(gameId, path)` ごとに size・mtime と sha256 を SQLite に保存。size と mtime が一致すれば再計算しない。消えても正しさに影響しない
- セーブフォルダ・実行ファイルのパスは PC ごとのローカル設定で、同期しない
- deviceName: 初期値は OS のホスト名。ローカル設定で変更でき、同期しない
- Pull 用の作業ディレクトリ: セーブフォルダの親に `.cloudlaunch-stage-{opId}` と `.cloudlaunch-old-{opId}` を作る（同じボリューム内のリネームで入れ替えるため）。セーブフォルダ内には作業用ファイルを置かない
- Pull 前バックアップ: `%LOCALAPPDATA%\CloudLaunch\backups\{gameId}\{UTC 日時}-{opId}\`。ゲームごとに直近 3 世代

### 保存先

- SQLite: `%LOCALAPPDATA%\CloudLaunch\cloudlaunch.db` を 1 つだけ置き、GUI と CLI で共有する（WAL、busy_timeout あり）
- R2 のアクセスキー: Windows 資格情報マネージャー。バケット名・エンドポイントは DB の設定に置く
- 日時は RFC3339 の UTC・ミリ秒固定長（`2026-10-22T12:00:00.000Z`）で保存する。R2 上の JSON も同じ形式

### DB に持つもの

テーブル定義は最初の migration の SQL を正とする。ここでは何を持ち、いつ書くかだけを定める。

- ゲーム情報: game.json と同じ項目。同期しない項目とは別の表に置く
- ゲームのローカル情報: セーブフォルダ・実行ファイルのパス、base、tombstone を見つけた記録（deletedAt / deviceName）
- プレイ履歴: `{ id, gameId, playedAt, durationSec }`。同期済みフラグは持たず、毎回リモートの一覧と突き合わせる
- ハッシュキャッシュ: `(gameId, path)` ごとに size・mtime（ナノ秒）・sha256
- Pull ジャーナル: 実行中の Pull 1 件につき 1 行（6 章）。ジャーナルが残っているゲームは削除できない
- 旧版の未紐付けの履歴（9 章）
- 設定（deviceName など）

ゲームを削除すると、そのゲームのローカル情報・プレイ履歴・ハッシュキャッシュも消える。

### 排他

Push / Pull の実行中は、`%LOCALAPPDATA%\CloudLaunch\sync.lock` を OS のファイルロックで握る。同時に実行できる同期は PC 全体で 1 つ。ロックが取れなければ「別の同期が実行中です」として中止する。

## 4. 状態判定

- 入力は base / local / remote の 3 つの manifest ハッシュ
- 出力は `変更なし` / `Push` / `Pull` / `競合` の 4 値
- local の「なし」は、ファイルが 1 つもない（セーブフォルダが存在しない場合を含む）かつ、base が空 manifest のハッシュでないことを指す。base が空 manifest のハッシュなら、ファイル 0 件の local はそのハッシュとして比べる
- remote の「なし」は HEAD が存在しないことだけを指す。`entries` が空の manifest は「あり」
- 判定の前に tombstone を確認し、あれば判定しない（8 章）

### 判定表

| base | local | remote | 結果 |
|---|---|---|---|
| なし | なし | なし | 変更なし |
| なし | あり | なし | Push |
| なし | なし | あり | Pull |
| なし | あり | あり（local と同じ） | 変更なし（base を記録） |
| なし | あり | あり（local と異なる） | 競合 |
| B | B | B | 変更なし |
| B | 変化 | B | Push |
| B | B | 変化 | Pull |
| B | 変化 | 変化（同じ内容） | 変更なし（base を更新） |
| B | 変化 | 変化（異なる内容） | 競合 |
| B | なし | B または変化 | 競合（「ローカルにセーブが見つかりません」と警告） |
| B | B または変化 | なし | Push |
| B | なし | なし | 変更なし |

- 「base を記録 / 更新」の行は、Push / Pull の途中で落ちたあとの自動復旧も兼ねる
- 判定は副作用を持たない。base の記録・更新は別の操作で行い、データが動かないため確認は取らない

---

## 5. Push 手順

1. local の manifest を計算し、HEAD を読んで判定し、ユーザーに確認する
2. 承認時点の remote の世代と local のハッシュを控える
3. 不足 object をアップロードする。存在確認は `objects/` の一覧で行う。アップロード時に読みながら sha256 を再計算し、manifest と違えば中止する
4. `manifests/{UUIDv7}.json` を PUT する
5. HEAD を読み直し、2 で控えた世代から変わっていれば中止して判定からやり直す
6. HEAD を PUT する
7. base を更新する
8. 世代削除と GC を行う。失敗しても Push は成功とする

### 落ちたときに残るもの

- 3〜4 で落ちた: 参照されない object / manifest が残るだけ。次回の GC で消える
- 6 と 7 の間で落ちた: 次回の判定が「B / 変化 / 変化（同じ内容）」になり、base が更新される
- 8 で落ちた: 古い世代や不要な object が残るだけ。次回の Push で消える

### GC と同時 push

別の PC が「既に存在する」と判断してアップロードを省いた object を、GC が同時に削除しうる。同時 push は保証の外とし、このとき最新 manifest は欠損 object を参照する。Pull は検証で欠損を検出して安全に失敗する。

---

## 6. Pull 手順

1. HEAD と manifest を取得して判定し、ユーザーに確認する
2. Pull ジャーナルに `{ opId, gameId, live のパス, stage のパス, old のパス }` を書く
3. ステージング `.cloudlaunch-stage-{opId}` に全ファイルを取得する
4. 検証する: 全エントリの sha256 と size が一致すること、manifest にないファイルがないこと、manifest が不正でないこと
5. live をハッシュし直し、承認時点から変わっていれば中止する
6. live を `.cloudlaunch-old-{opId}` にリネームし、stage を live にリネームする（live が存在しなければ前半は飛ばす）
7. base を書き込む
8. old をバックアップへ移し、古いバックアップを削除して 3 世代に保つ（old が無ければ飛ばす）
9. ジャーナルを削除する

中止したとき（4・5 で失敗したときを含む）は、stage を削除してからジャーナルを削除する。

### 不正な manifest

`entries` の `path` が次のいずれかに当たれば、その manifest を不正として拒否する。

- 空である
- 絶対パスである（`/` や `\` で始まる、ドライブレター `X:` を含む、UNC パス）
- `/` で区切った要素に `..`・`.`・空要素がある
- `\` を含む
- 大文字小文字の違いだけで重複する path がある

### 起動時の復旧

Pull ジャーナルに残っている行ごとに、記録されたパスの状態を見て復旧する。復旧が終わったらジャーナルを削除する。

| 残っているもの | 処理 |
|---|---|
| stage のみ（old がない） | stage を削除する。live は無傷 |
| old があり live がない | old を live に戻し、stage を削除する |
| old と live の両方（stage はない） | 入れ替え済み。old をバックアップへ移す。base が未書き込みでも、ここでは書かず次の判定で記録させる |
| stage も old もない | 手順 3 より前で落ちたか、手順 8 まで終わっている。ジャーナルを削除するだけ |

## 7. 確認フロー

- Push / Pull は必ずユーザー確認を取る
- 確認を出すタイミング
  - ゲーム起動前: Pull が必要 or 競合のときだけ
  - ゲーム終了後: Push が必要なときだけ
  - 手動: 一覧からいつでも状態確認・Push / Pull
- 競合時はゲーム単位で「アップロードで上書き / ダウンロードで上書き」を選ぶ
- 承認後、実行前に判定結果や local / remote のハッシュが変わっていれば、実行せず中止して確認し直す
- ゲームのプロセスが実行中なら Push も Pull も拒否する（ローカル設定の実行ファイルパスで判定。CLI も同じ）

### 確認ダイアログに出す情報

- 方向（アップロード / ダウンロード）
- 追加・変更・削除されるファイル数
- 転送サイズ
- remote の deviceName と createdAt
- local の最終更新（ファイル mtime の最大値）
- 競合時は local と remote を並べて出す

### 見送り・オフライン

同期できないことを理由にゲームの起動は止めない。

- 起動前に Pull を見送った: 起動を続行し、「このまま遊ぶと終了後に競合になります」と警告する
- 起動前にオフラインで判定できない: 警告して起動を続行する
- 終了後に Push を見送った / オフライン: 何もしない。次回の判定で再び Push になる

## 8. メタ情報の同期

- 判定とは別の操作として、確認なしで同期する
  - GUI: 状態確認のタイミング（起動前・終了後・手動）で判定と並べて行う。セーブの Push を見送ってもプレイ履歴は上がる
  - CLI: `push` / `pull` のときに行う。`status` は読み取りのみで同期しない
- 失敗してもセーブ同期の結果に影響させず、通知とログだけ残す

### ゲーム情報

- `games/{gameId}/game.json`: `{ id, title, brand?, imageSha256?, createdAt, updatedAt }`
- 文書全体の後勝ち（`updatedAt` が大きい方）
- 総プレイ時間・最終プレイ日時などの集計値は持たず、プレイ履歴から計算する

### 画像

- `games/{gameId}/images/{sha256}` に置く。セーブの `objects/` とは独立に扱う
- 変更時は新しい画像を PUT してから game.json を PUT する。古い画像は削除しない（別の PC の game.json が後勝ちで古い画像を参照し直すことがあるため）。画像を消すのは、リモート削除と使われていない画像の削除（10 章）のときだけ
- 変換せずに保存する。上限 10 MB、形式は PNG / JPEG / WebP
- ローカルではアプリデータフォルダに sha256 キーでキャッシュする

### プレイ履歴

- `games/{gameId}/sessions/{sessionId}.json` に 1 セッション 1 オブジェクト。不変
- 和集合は、互いに無いものを PUT / 取得するだけで作る

### ゲーム ID

- UUIDv7。ゲームを登録した PC が採番し、以後変えない

### 2 台目の PC での取り込み

1. `games/` を区切り文字つきで一覧し、各 `game.json` を読む。tombstone のあるゲームは除く
2. この PC に未登録のゲームを一覧で出し、ユーザーが選ぶ
3. 同じ gameId でローカルに登録し、セーブフォルダと実行ファイルのパスを入力してもらう
4. base なしの状態で通常の判定に乗る

### ゲームの削除

- この PC の登録解除だけを行うか、リモートも削除するかを選べる
- リモート削除
  1. ゲーム名の入力などの強い確認を取り、この PC のセーブをバックアップへ退避する
  2. `games/{gameId}/deleted.json`（`{ deletedAt, deviceName }`）を PUT する
  3. `games/{gameId}/` 配下の tombstone 以外をすべて削除する
  4. 3 が終わってから、この PC の登録を解除する
- 3 の途中で落ちても tombstone があるため削除済みに見える。登録が残っているので、次回この PC が tombstone を見つけたときに掃除が再開される
- tombstone は残し続ける

### tombstone を見つけた PC

- 確認なしで `games/{gameId}/` 配下の tombstone 以外を削除する（消し残りの掃除。tombstone があればどの PC が消しても安全）
- そのゲームは「別の PC で削除されました（deviceName・deletedAt）」の状態になり、Push / Pull はできない
- ゲームの起動は可能
- ユーザーが次のどちらかを選ぶ。自動では行わない
  - この PC でも登録を解除する（セーブフォルダには触れない）
  - 新しいゲームとして上げ直す（新しい UUIDv7、ゲーム情報とプレイ履歴を引き継ぎ、base なしから始める）

## 9. 旧版からのプレイ履歴取り込み

- 旧版（CloudLaunch_Go）のデータエクスポート JSON（`cloudlaunch_export_*.json`）をそのまま読み込む
- 読み込んだ内容はローカル DB に「未紐付けの旧履歴」として保持し、ゲーム登録時に照合する
- 照合: `games[].title` と v3 のゲーム名を、前後の空白を除いた完全一致で比べる
  - 1 件一致: 取り込みを提案する（確認を取る）
  - 0 件 / 複数件一致: 旧ゲームの候補一覧から手動で選ぶか、スキップする
- 取り込んだ `sessionRows` は通常のプレイ履歴になり、8 章の形で同期する
- セッション ID は旧版のものを使い、既にあれば取り込まない（何度取り込んでも結果は同じ）
- それ以外（ゲーム一覧・旧リモート）は引き継がない

## 10. クラウド上のデータの削除（v1 後に実装）

この章の内容は v1 では実装しない。v1 の同期コア・CLI・GUI がそろった後の最初の追加として実装する。v1 の設計は、これらを後から足せる形にしておく。

### セーブのリセット（クラウド上の写しを捨てる）

どの PC のローカルセーブも消さずに、クラウド上のセーブだけを捨てる。

1. 確認を取る
2. `games/{gameId}/saves-reset.json`（`{ resetAt, deviceName }`）を PUT する。リセットのたびに上書きする
3. `HEAD` → `manifests/` → `objects/` の順に削除する
4. この PC の base を消し、`resetAt` を記録する

- 判定の前に `saves-reset.json` を確認し、`resetAt` がこの PC の記録より新しければ、base を消して `resetAt` を記録してから判定する
- base を消した PC では、次の判定は「base なし」の行になる。最初に Push した PC のセーブが新しいクラウドの写しになり、他の PC は内容が違えば競合になる
- 3 の途中で落ちて object が残っても、次の Push の GC で消える

### プレイ履歴の削除

- 1 件ずつ、確認を取って削除する
- `games/{gameId}/sessions/{id}.deleted.json`（`{ deletedAt, deviceName }`）を PUT してから、セッション本体を削除する
- 和集合を取るとき、tombstone のあるセッションはどちらにあっても消す。ローカルにも削除の記録を持ち、後から届いた本体を取り込まない
- 編集はできない。時間を直すときは、削除してから新しい ID で追加する

### 使われていない画像の削除

- 手動の操作として、現在の game.json が参照していない `images/` 配下を削除する
- 別の PC の古い game.json が後勝ちで削除済みの画像を参照し直すことがある。その場合はエラーにせず、画像なしとして表示する。確認ダイアログでこのことを警告する
