# game-reupload

- 日時: 2026-11-14 22:38 (JST)

## 当初の要求 / 背景

仕様書 8 章「リモートで削除されたゲーム」は、ゲームの tombstone を見つけた PC で、登録の解除（8-U1）か、新しいゲームとしての上げ直しをユーザーが選ぶとしている。上げ直しは、同期ロックを握り（8-U2）、Pull ジャーナルが残っていれば何も変える前に拒否し（8-U3）、新しい UUIDv7 のゲーム情報を作ってプレイ履歴とローカル情報を移し、base とゲームの tombstone の記録を消し、古い gameId のゲーム情報を消すまでを、DB の 1 つのトランザクションで行う（8-U4）。画像がローカルのキャッシュになければ、`imageSha256` を引き継がない（8-U5）。上げ直した後は base なしから判定し、次のメタ情報の同期で、新しい gameId の下に画像・game.json・プレイ履歴が PUT される。

登録の解除（8-U1）は、2026-11-14_20-30_game-delete.md で `game delete`（`--remote` なし）として作った。同期ロックと Pull ジャーナルの確認は syncore にあり（`acquire`・`ensureNoPullJournal`）、外からは呼べない。ゲーム情報・プレイ履歴・ゲームの tombstone の記録・画像のキャッシュは metasync が扱う。syncore と metasync は互いに import しない（2026-10-23_00-30_package-structure.md）。store にはゲームの ID を付け替える関数がなく、CLI にも上げ直しのコマンドがない。AGENTS.md の CLI の一覧には `game reupload` がある。

## 決定事項

### 扱う仕様書の ID の範囲

- 事項: この作業で、どの項目を満たすか
- 決定内容: 8-U2〜8-U5 と、ID のない「上げ直した後は base なしから判定し、次のメタ情報の同期で新しい gameId の下に PUT される」を扱う。8-U1 は扱わない。古い gameId のバックアップを残すことは、上げ直しがファイルに触れないことで満たし、テストを書かない
- 判断理由: 8-U1 は #101 で `game delete` として作り、残るテストは #102 が持つ。上げ直しはファイルシステムに触れないので、バックアップを残すための処理がない

### 上げ直せるゲームの条件

- 事項: DB にゲームの tombstone の記録がないゲームを、上げ直してよいか
- 決定内容: 記録があるゲームだけを上げ直す。記録がなければ、何も変えずにセンチネルエラー `metasync.ErrNotRemoteDeleted` を返す。記録の有無は、リモートを読まずに DB だけで確かめる。metasync が画像のキャッシュを読む前に確かめ、store がトランザクションの中でも確かめる
- 判断理由: 仕様書は、上げ直しを「リモートで削除されたゲーム」の選択肢としてだけ書いている。記録のないゲームを上げ直すと、リモートに残る古い gameId のデータとは別に、同じゲームが新しい gameId で 2 つになる。リモートの `deleted.json` を読んで判断する案は、上げ直しの手順（8-U4）が DB だけで完結するのにリモートへの接続が要るようになり、`deleted.json` があって記録がないときは、`push`・`pull` か GUI の状態の確認が先に記録する（8-T2）ので、採らない。画像を読む前に確かめるのは、記録のないゲームで画像を読めないときに、`ErrNotRemoteDeleted` ではないエラーを返さないためである。トランザクションの中でも確かめるのは、ロックを握らない登録の解除（3 章「排他」）と重なっても、記録を確かめた後に消えた行を移さないためである

### syncore と metasync の分担

- 事項: 同期ロックと Pull ジャーナルの確認（syncore）と、ゲーム情報・プレイ履歴・画像のキャッシュの扱い（metasync）を、どうつなぐか
- 決定内容: syncore に `ReuploadGame(ctx, gameID string, reupload func(ctx context.Context) error) error` を置き、同期ロックを取り（8-U2）、Pull ジャーナルを確かめ（8-U3）、`reupload` を呼ぶ。ゲームの実行中は確かめない。`reupload` のエラーは `%w` で包んで返す。DB の書き換えは metasync の `ReuploadGame` に置き、cmd がそれを閉包に包んで `reupload` として渡す
- 判断理由: 2026-11-14_20-30_game-delete.md の `DeleteGame` と同じ形で、ロックを外に開けずに済み、ロックとジャーナルの順を syncore のテストで確かめられる。8-U2 は、セーブフォルダに触れないので実行中でもできるとしている。画像のキャッシュのパスと、ゲーム情報の形は metasync が持つので、8-U5 の判断と新しいゲーム情報の組み立ては metasync に置く

### 8-U5 の「キャッシュにある」の判定

- 事項: `imageSha256` の画像がキャッシュにあるかを、どう確かめるか
- 決定内容: キャッシュのファイルを読み、中身の sha256 が `imageSha256` と一致したときだけ、キャッシュにあるとする。ファイルがない・一致しないときは、`imageSha256` を引き継がない。一致しないファイルは消さない。読めない（ファイルがない以外のエラー）ときは、何も変えずにエラーを返す
- 判断理由: 次の同期の画像の PUT（`uploadImage`）は、一致しないファイルを壊れたものとして消し、画像を PUT せずに `imageSha256` を入れたまま game.json を PUT する（8-I4）。上げ直しでファイルがあるだけで引き継ぐと、新しい gameId の下に、どの PC も取得できない `imageSha256` が残る。壊れたファイルの削除は `uploadImage` の役目で、上げ直しで消すと、書き込みが DB のトランザクションの外に増える。読めないときに画像なしで進める案は、一時的な失敗で画像を失うので採らない

### DB のトランザクション

- 事項: 8-U4 の書き換えを、store でどう行うか
- 決定内容: store に `ReuploadGame(ctx, oldID string, g metasync.GameInfo) error` を置く。1 つのトランザクションで、次の順に行う
  0. 古い gameId の `pull_operations` の行があれば、`store.ErrPullInProgress` を返す
  1. `g` の項目で games の行を作る
  2. 古い gameId の game_locals の行が、ゲームの tombstone の記録を持つときだけ、セーブフォルダと実行ファイルのパスを写した行を新しい gameId で作る。base とゲームの tombstone の記録は写さない。作れなければ `metasync.ErrNotRemoteDeleted` を返す
  3. 古い gameId の play_sessions の行の game_id を、新しい gameId に書き換える
  4. 古い gameId の games の行を消し、`ON DELETE CASCADE` で古い game_locals の行を消す
  - `g` は `ReplaceGameInfo` と同じく検証し、合わなければ何も書かずにエラーを返す
- 判断理由: 行を作ってから古い行を消すので、どこで失敗しても、ロールバックで上げ直す前に戻る（8-U4）。Pull ジャーナルは syncore が確かめる（8-U3）が、store でも 0 で確かめる。`DeleteGame` と同じく、4 の `ON DELETE RESTRICT` に任せると返るのは制約違反のエラーで、syncore を通らない配線（GUI など）で CLI が `recover` を案内できないためである。RESTRICT は最後の安全網として残る。古い gameId のゲーム情報は metasync がトランザクションの前に読む。その間に書き換えうるのは同じ PC の `game edit` だけで（メタ情報の同期は 8-M4 で記録のあるゲームを書き換えない）、利用者が同時に行う操作なので、読み直しの仕掛けは作らない

### 新しい gameId の採番

- 事項: 新しい UUIDv7 をどこで振るか
- 決定内容: cmd が振り、metasync の `ReuploadGame` に引数で渡す。metasync は UUIDv7 の形（`game import` と同じ検査）でなければ、何も変えずにエラーを返す
- 判断理由: `game add` の採番（`resolveGameID`）が cmd にある。metasync に採番の口を足すと、テストのために差し替えの設定が要る。引数で渡せば、テストが新しい gameId を決めて確かめられる

### API の形

- 事項: 各パッケージに何を足すか
- 決定内容:
  - syncore: `Core.ReuploadGame`
  - metasync: `Core.ReuploadGame(ctx, gameID, newGameID string, now time.Time) (ReuploadResult, error)`、`ReuploadResult`（`ImageDropped`: 8-U5 で `imageSha256` を引き継がなかったか）、`ErrNotRemoteDeleted`。`LocalStore` に `ReuploadGame(ctx, oldID string, g GameInfo) error` を足す
  - store: `ReuploadGame`
  - migration は足さない
- 判断理由: `createdAt`・`updatedAt` の今の時刻は、`DeleteRemoteGame` の tombstone と同じく、cmd が引数で渡す。`ImageDropped` を返すのは、CLI が画像を設定し直すよう案内するためである。syncore の `LocalStore` には足さない。syncore は DB を書き換えないためである

### CLI の振る舞い

- 事項: `game reupload` の形と出力
- 決定内容:
  - `game reupload --game <id> [--data-dir <dir>]`。リモートには接続しない
  - 成功したら、新しい gameId と、次の `push`・`pull` で新しい gameId の下にアップロードされることを出す。`ImageDropped` なら、画像を引き継がなかったので `game set-image` で設定し直すよう出す
  - エラーは `explainSyncError` に、`ErrNotRemoteDeleted`（記録がないので上げ直さない。`status` で確かめ、削除されていれば `push`・`pull` で記録してから実行する）、`syncore.ErrPullPending`・`store.ErrPullInProgress`（`recover` の案内）、`sql.ErrNoRows`（登録していない gameId）を足して説明する
  - `push`・`pull` がゲームの tombstone で止まったときは、登録の解除（`game delete`）と上げ直し（`game reupload`）のコマンドを、`--data-dir` を引き継いで出す
  - AGENTS.md の CLI の一覧には `game reupload` が既にあるので、直さない
- 判断理由: 上げ直しは DB の書き換えだけで、リモートへの PUT は次のメタ情報の同期が行う（8 章）。リモートに接続しなければ、環境変数がなくても実行でき、オフラインでも上げ直せる。ゲームを消す操作ではないので、`game delete --remote` のような強い確認は取らない。`push`・`pull` で案内するのは、仕様書 8 章がそこで利用者に解除か上げ直しを選ばせるとしており、案内がなければ usage を読まない限り `game reupload` にたどり着けないためである。`status` では案内しない。記録をしないので、そのままでは上げ直せないためである

### テスト

- 事項: どう確かめるか
- 決定内容:
  - syncore（`reupload_test.go`、`package syncore_test`）: `reupload` を偽物にし、8-U2（ロックを握ったまま呼ぶ・ロックが取れなければ呼ばない・実行中でも呼ぶ）、8-U3、`reupload` のエラーを返してロックを外すこと、`reupload` がないときを書く
  - metasync（`reupload_test.go`）: 本物の SQLite と memstore で、8-U4（ゲーム情報・ローカル情報・プレイ履歴が新しい gameId に移り、base と記録が消え、古い gameId が消える）、8-U5（キャッシュにない・壊れている・ある）、記録がないときの拒否、新しい gameId が UUIDv7 でないときの拒否、上げ直した後の `Sync` で画像・game.json・プレイ履歴が新しい gameId の下に PUT されることを書く
  - store（`game_test.go`）: 8-U4 の途中の失敗（games の削除で失敗するトリガーを置き、4 の削除で止める）で DB が上げ直す前のままであること、Pull ジャーナルが残るときの `ErrPullInProgress`、記録がないときの `ErrNotRemoteDeleted` を書く
  - cmd の配線にはテストを書かない
- 判断理由: AGENTS.md のテストの方針に従う。途中の失敗は、トランザクションの最後の手順で止め、それまでの書き込みが戻ることを確かめる。Pull ジャーナルの行は 0 で先に止まるので、最後の手順で止めるにはトリガーを使う。store の記録の確認は、metasync が先に確かめるので metasync のテストでは通らず、store のテストで確かめる。上げ直した後の判定が base なしになることは、新しい gameId のローカル情報の base が空であることで確かめる。判定は base の値だけで決まり（4 章）、syncore のテストに metasync を組み立てずに済む

## 結果 / 影響

- CLI の `game reupload` で、リモートで削除されたゲームを新しい gameId で上げ直せる。リモートに接続しないので、オフラインでも実行できる
- 8-U2〜8-U5 は、すべてテストのケース名に入った（`mise run spec-ids` の一覧から消えた）
- R2 を相手に CLI で確かめた。3 台の PC に見立てた別々の data-dir で、PC1 でゲームを追加して `push` し、PC2 で取り込んで `game delete --remote` した。PC1 の `push` は tombstone で止まって記録し、`game reupload` は新しい gameId を出した。新しい gameId の `status` は base なしの Push になり、`push` でセーブ・ゲーム情報・プレイ履歴 1 件をアップロードした。PC3 の `game remote` には新しい gameId だけが出て、取り込んで `pull` すると、セーブとプレイ履歴 1 件が届いた。記録のないゲームの `game reupload` は、何も変えずに拒否した。別のゲームで、tombstone で止まった `push` が、`--data-dir` を引き継いだ `game delete` と `game reupload` のコマンドを出すこと、登録していない gameId の `game reupload` が「登録されていません」と出すことも確かめた
- ゲームの実行中に上げ直すと、終了時に古い gameId で記録するプレイ履歴が失われうる。上げ直しは古い gameId のゲーム情報を消すためで、扱いは仕様書の「未決事項」に挙げた。今の CLI では、プレイ履歴は利用者が `session add` で gameId を指定して記録するので、新しい gameId を指定すれば記録できる
- 8-U5 の画像の検証は、`uploadImage` のキャッシュの読み込みと sha256 の照合と重なる。整理は、マイルストーンの前の `/simplify` で行う
- 行数は約 800 行（テスト約 460、syncore 約 30、metasync 約 70、store 約 55、CLI 約 80、ADR 約 110）で、見込みの約 450 行を超えた。超えたのは主にテストで、8-U5 の条件ごとのケース、metasync と store のそれぞれでの拒否のケース、レビューの後に足した store のジャーナルと記録のケースのため
