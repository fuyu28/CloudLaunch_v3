# fuzz-manifest-path

- 日時: 2026-11-08 00:25 (JST)

## 当初の要求 / 背景

AGENTS.md は、manifest の path の検証（仕様書 6 章「不正な manifest」）に fuzz テストを書くと決めている。CI では保存したコーパスだけを走らせ、ランダムな探索は手元で行う。

検証の規則は、2026-11-07_23-41_manifest-validation.md と 2026-11-08_00-09_manifest-validation-dirs.md で 6-M1〜6-M13 まで揃った。そのうえで、6-M5 のディレクトリの部分（`dir/a.sav` と `DIR/b.sav`）と 6-M10 の空白（`aux .sav`）は、表のテストを書いた後のコードレビューで初めて見つかった。どちらも、人が思いつかなかった入力で検証をすり抜ける穴である。fuzz テストで、この種類の穴を機械的に探す。

## 仕様

- fuzz の入り口と、確かめる性質
- 入力の形
- シードとコーパス
- 手元での探索
- Windows での探索

## 決定事項

### fuzz の入り口と、確かめる性質

- 事項: 何を通して fuzz し、何が成り立てばよいとするか
- 決定内容: `Status` → `Pull` を通す。各回で、偽のリモートに 1 世代を置いて Pull し、結果が次のどちらかであることを確かめる
  - 同期ロックを一度も取らずにエラーで止まり、セーブフォルダとジャーナルが変わらない（6-L2 で拒否した）。Pull はロックを 6-L2 の検証の後に取るので、ロックを取ったかで、検証で止まったかを見分ける。取得した object の数では見分けない。object を取得する前に stage にディレクトリを作るので、ディレクトリを作れずに失敗した穴を、拒否と取り違えるため
  - 成功し、セーブフォルダに manifest のとおりのファイルがあり、セーブフォルダの外に何も作られていない
- 判断理由: AGENTS.md は syncore のテストを公開 API 経由で書くとしている。この性質は、規則を写した検査ではなく、実際のファイルシステムに書けるかで判定する。そのため、検証を通ったのに書けない path（名前が変わって 6-L5 で失敗するなど）も、外に書いてしまう path も、規則に書いていない穴として見つかる。`export_test.go` で `validatePaths` を出し、`filepath.IsLocal` と比べる案は、速いが、公開 API 経由の方針から外れる。また、確かめられるのが「stage の外に出ない」ことだけになる

### 入力の形

- 事項: fuzz の入力を何にするか
- 決定内容: path を 2 つ（`string, string`）にする。テストの側でバイト列の昇順に並べ、等しいか、正しい UTF-8 でなければ飛ばす。object の中身は固定にする
- 判断理由: path が 1 つでは、path をまたぐ 6-M5・6-M13 を探れない。remote の manifest は JSON から読むので、正しくない UTF-8 は U+FFFD に置き換わって現れない。置き換わると 2 つの path が等しくなったり並びが変わったりして、6-M9 で拒否されるだけになる。並びの規則 6-M9 は表のテストで確かめており、並べずに渡すと多くの入力が 6-M9 で拒否されて、探索が path の規則に届かないので、fuzz の対象にしない

### シードとコーパス

- 事項: シードをどこに置き、見つけた入力をどう扱うか
- 決定内容: シードは `f.Add` でコードに書く。既存の表のケースと、境目に当たる名前（`aux .sav`・` aux.sav`・`COM10`・`a..b.sav`・`ı.sav` など）を入れる。探索で見つかり `testdata/fuzz/FuzzPull不正なmanifest/` に保存された入力は、原因を直したうえでコミットする
- 判断理由: `go test` は `-fuzz` を付けなくてもシードと `testdata/fuzz/` を走らせるので、CI の設定を変えずに「CI では保存したコーパスだけ」を満たす。シードをコードに書けば、どの入力を試しているかがコードを読んで分かる

### 手元での探索

- 事項: ランダムな探索をどう走らせるか
- 決定内容: `mise.toml` に `fuzz` タスクを足し、`go test ./internal/syncore -run NONE -fuzz FuzzPull -fuzztime 5m` を走らせる。時間は `mise run fuzz -- -fuzztime 30m` のように、後ろにフラグを足して上書きする
- 判断理由: Windows の mise はタスクを cmd で実行する。cmd では `^` がエスケープの文字で、`'` も引用符として外れないので、`-run '^$'` のような書き方では意図どおりに動かない。記号を使わない形にすれば、Linux でも Windows でも同じ書き方で動く。`-fuzz` は正規表現で、このパッケージの fuzz 関数は 1 つなので、`FuzzPull` で一意に決まる。Go のフラグは後に書いたものが勝つので、後ろに足せば上書きできる

### Windows での探索

- 事項: Windows 固有の穴（予約名や末尾の空白など、Windows のファイルシステムでだけ書けない名前）をどう探すか
- 決定内容: 必要なとき（検証の規則を変えたときなど）に、Windows の実機で `mise run fuzz` を走らせる。CI の Windows では探索しない
- 判断理由: PR の CI で探索すると、同じコードでも結果が変わり、必須チェックが不安定になる。手動や定期で走らせるワークフローを分ける案は、AGENTS.md の方針を変えることになり、規則がほぼ固まった今は、そこまで要る場面がない。限界として、手元の探索は Linux で行うので、Windows 固有の穴は、その名前がシードかコーパスに入るまで、Windows の CI でも見つからない

## 結果 / 影響

- 決定事項のとおりに実装した。`TestPull不正なmanifest` の表をパッケージの変数に移し、fuzz のシードと共有した
- 性質の検査が穴を捕まえることを、Pull の検証を一時的に外して確かめた。シード 46 個のうち、不正な 39 個がすべて「検証を通ったのに Pull が失敗した」として検出された。残る 7 個は正当な名前である
- Linux の手元で探索し、要素が 255 バイトを超える名前（`file name too long`）が、検証を通るのに手順 4 で失敗することが見つかった。仕様書に長さの規則がないので、11 章「未決事項」に挙げた（要素と path 全体の長さ）。決まるまで、fuzz の側で、要素が 255 バイトを超えるか、path 全体が PATH_MAX（4096 バイト）に近い入力を飛ばす。この入力はコーパスにコミットしていない（CI が失敗し続けるため）
- 長さの入力を飛ばしたうえで 5 分（約 83 万回）探索し、ほかの穴は見つからなかった
- 1 回ごとに DB を作り直して migration を流すので、1 秒に数百〜千数百回にとどまる。数分の探索には足りるので、DB の雛形を写すような速くする工夫はしていない
- `mise run fuzz -- -fuzztime 10s` で、後ろに足したフラグが既定の 5 分を上書きすることを Linux で確かめた。Windows での動作は、実機で確かめる
