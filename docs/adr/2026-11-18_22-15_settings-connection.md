# settings-connection

- 日時: 2026-11-18 22:15 (JST)

## 当初の要求 / 背景

仕様書 3 章は、R2 のアクセスキーを Windows 資格情報マネージャーに、秘密でないバケット名とエンドポイントを DB の設定に置くと決めている。deviceName も DB の設定に置き、初期値を OS のホスト名にして、利用者が変更できるとしている。M4 の計画（#140 の決めたこと 6）は、これらを GUI の設定画面から入れ、CLI も同じ場所から読み、環境変数があればそちらを優先すると決めている（#142）。

今のコードは、次の状態である。

- CLI と GUI は、どちらも接続情報を環境変数 `CLOUDLAUNCH_S3_ENDPOINT`・`_REGION`・`_BUCKET`・`_ACCESS_KEY_ID`・`_SECRET_ACCESS_KEY` から `os.Getenv` で読む
- deviceName は、CLI と GUI のどちらも、起動のたびに `os.Hostname()` の値を渡す
- DB には `settings` テーブル（`key`・`value`）が migration で作ってあるが、どこからも使っていない
- GUI は起動時に syncore・metasync・gamesync のコアを 1 回だけ作り、接続情報を読めなければ、その理由を `SyncService` の `setupErr` に持って確認を拒否する（`docs/adr/2026-11-17_01-30_gui-skeleton.md`）

前の版の CloudLaunch_Go は、`github.com/danieljoos/wincred` で、接続情報のすべて（キー・バケット・エンドポイント・Region）を 1 件の資格情報に入れていた。設定画面には Region の欄があり、「通常は auto」と案内していた。Region は、資格情報の値 → 環境変数 `CLOUDLAUNCH_S3_REGION` → `auto` の順で決めていた。

## 決定事項

### 資格情報マネージャーの呼び方

- 事項: Windows 資格情報マネージャーを、どのライブラリで呼ぶか
- 決定内容: `github.com/danieljoos/wincred` を使い、`internal/platform/credential_windows.go` に置く
- 判断理由: CloudLaunch_Go で同じライブラリを使っており、Windows で動いた実績がある。小さく、Windows 専用で、依存が増えない。`golang.org/x/sys/windows` から `CredWriteW`・`CredReadW` を自前で呼ぶ案は、依存は増えないが、`CREDENTIAL` 構造体と UTF-16 の変換を自分で書いて検査することになるので採らない。`github.com/zalando/go-keyring` は OS をまたいで使えるが、Linux では D-Bus の Secret Service が要り、開発用の最小限（AGENTS.md の「構成」）を超えるので採らない

### Linux での資格情報の置き場所

- 事項: Linux（開発用）で、アクセスキーをどこに置くか
- 決定内容: データディレクトリの `credential.json` に、パーミッション 0600 で置く。`internal/platform/credential_linux.go` に書く
- 判断理由: Linux の実装は開発用の最小限にとどめる（AGENTS.md の「構成」）。環境変数だけにすると、Linux で設定画面の保存と、保存した値で動く道を確かめられない。ファイルなら依存を増やさずに書ける

### 資格情報と DB に置くもの

- 事項: 資格情報マネージャーと DB の設定に、それぞれ何を置くか
- 決定内容: 資格情報は 1 件にし、ターゲット名を `CloudLaunch/R2`、UserName をアクセスキー ID、CredentialBlob をシークレットにする。DB の `settings` テーブルには、エンドポイント・バケット・Region・deviceName を置く。新しい migration は作らない
- 判断理由: 仕様書 3 章のとおり、秘密のものだけを資格情報マネージャーに置く。アクセスキー ID とシークレットは対で使うので、1 件にまとめれば片方だけが残ることがない。CloudLaunch_Go のように、全部を資格情報に入れる案は、仕様書 3 章と食い違うので採らない。`settings` テーブルは key と value の形で既にあるので、項目を足しても migration は要らない

### Region

- 事項: Region を、設定できるようにするか
- 決定内容: DB の設定に置き、設定画面に入力欄を出す。空なら `auto` として扱い、「通常は auto のままでよい」と案内する。環境変数 `CLOUDLAUNCH_S3_REGION` は、環境変数の優先（次の節）に含める
- 判断理由: R2 では常に `auto` だが、S3 互換のほかのストレージでは Region が要るものがある。CloudLaunch_Go も Region を設定でき、空のときは `auto` で動いていた。設定画面から外すと、そうしたストレージを使えなくなる

### 環境変数の優先

- 事項: 環境変数と、保存した設定のどちらを使うか
- 決定内容: `CLOUDLAUNCH_S3_*` の 5 つのうち 1 つでも空でない値があれば、接続情報はすべて環境変数から読み、DB と資格情報は見ない。このとき、環境変数で足りない項目は、未設定として扱う（Region だけは空なら `auto`）。deviceName には環境変数を設けない
- 判断理由: 環境変数は Linux と versitygw での開発用である（#140 の決めたこと 6）。項目ごとに環境変数と保存した値を混ぜると、エンドポイントは環境変数、キーは資格情報、という組み合わせで、どこから読んだかに気づきにくい。deviceName は開発でも変える必要がない

### deviceName の保存と検証

- 事項: deviceName をいつ DB に書き、どう検証するか
- 決定内容: 利用者が保存するまで DB に書かず、DB に値がなければ、読むたびに OS のホスト名を返す。保存するときは前後の空白を除き、空なら拒否する。64 文字（rune の数）を超えても拒否する。ホスト名を取れないか、ホスト名が同じ検証を通らなければ、エラーを返す
- 判断理由: 初めから DB に書くと、ホスト名を変えた PC でも古い名前が残り続ける。空の deviceName は、ゲームの tombstone で不正なものとして扱う（8-T5）ので、保存の時点で拒否する。ホスト名も manifest や tombstone に書くので、同じ検証をかける。deviceName は確認ダイアログや tombstone の表示に出るだけなので、画面に収まる長さで止める

### 接続情報の検証

- 事項: 接続情報を保存するとき、何を検証するか
- 決定内容: 次のとおりにする。文字数の上限は設けない
  - エンドポイント: `http` か `https` の URL で、ホストがある
  - バケット・アクセスキー ID: 前後の空白を除いて、空でない
  - シークレット: 前後の空白を除く。資格情報がまだなければ必須。あれば、空のときは今の値を残す
  - Region: 空なら `auto`
- 判断理由: versitygw での開発では `http` を使うので、`https` だけには絞らない。正しく書けているかは、つないでみるまで分からない。文字数の上限は、つなげない値を減らすには足りないので設けない。シークレットに貼り付けた末尾の改行や空白が入ると、保存は通っても R2 の署名が合わず、原因の分かりにくい認証エラーになる。R2 のシークレットに空白は含まれないので、除いても失うものはない

### 接続情報が揃っていないとき

- 事項: DB の値はあるが資格情報がない、のように、接続情報が揃っていないときの扱い
- 決定内容: 未設定として扱い、センチネルエラー `settings.ErrRemoteNotConfigured` を返す。環境変数から読むときも、エンドポイント・バケット・アクセスキー ID・シークレットのどれかが空なら同じにする。GUI は、今の `setupErr` と同じく一覧と起動時の復旧を使えるようにし、確認のときに「設定画面で接続情報を入れてください」と伝える。CLI は、リモートを使うコマンドを同じ文言で止める。環境変数が効いているときは、設定画面で入れ直しても直らないので、環境変数に足りない項目があることを伝える
- 判断理由: 揃っていない接続情報でつなぐと、R2 の認証のエラーなど、原因の分かりにくいエラーになる。GUI と CLI が、つなぐ前に「未設定」を見分けて同じ案内を出すために、センチネルエラーにする（AGENTS.md の「構成」のエラーの方針）。これまでの `objstore.New` は、エンドポイントとバケットだけを必須にし、キーのない（認証なしの）サーバーにもつなげた。R2 も開発の versitygw もキーを要求するので、認証なしのサーバーは受け付けない

### 設定を組み立てるコードの置き場所

- 事項: 環境変数・DB・資格情報から設定を組み立てるコードを、どこに置くか
- 決定内容: 新しいパッケージ `internal/settings` を作り、読む順番・検証・deviceName の既定値を持たせる。`internal/settings` は、必要な操作だけのインターフェース（DB の設定の読み書き、資格情報の読み書き）を定義し、store と platform がそれを実装する。環境変数とホスト名は、関数として受け取って差し替えられるようにする。`internal/settings` は TDD で書き、AGENTS.md の「構成」と「テスト」に足す
- 判断理由: CLI と GUI の両方が同じ順番で読むので、`cmd/` の 2 か所に書くと食い違う。優先の順番と検証は、テストの要るロジックである。store に置く案は、store が資格情報と環境変数を知ることになり、責務が増えるので採らない。依存の向きは、syncore と同じく、使う側がインターフェースを定義する形に揃える（AGENTS.md の「構成」）

### GUI で保存した後の反映

- 事項: 設定画面で保存した値を、いつ使い始めるか
- 決定内容: 保存したら、再起動せずに、リモートと syncore・metasync・gamesync のコアを作り直し、`SyncService` と `BackupService` が持つコアを差し替える。差し替えるときは、ゲームごとの確認済みの plan とトークンを捨てる。同期の途中（確認中・承認の待ち・転送中）のゲームが 1 つでもあれば、保存を拒否する。deviceName だけを変えたときも同じにする
- 判断理由: 初めて使うときは、接続情報がない状態で起動して設定画面で入れるので、保存の後に再起動を求めるのは不自然である。古いコアで作った plan を新しいリモートで実行すると、利用者の見ていない相手に転送することになるので、plan を捨てる。転送の途中で差し替えると、転送中のコアと表示が食い違うので、途中なら拒否する

### シークレットの表示

- 事項: 保存したシークレットを、設定画面にどう出すか
- 決定内容: シークレットはフロントへ返さず、保存してあれば「保存済み」とだけ出す。入力欄が空のまま保存したら、今の値を残す。アクセスキー ID は、入力欄に今の値を出す
- 判断理由: 画面に出す必要のない秘密を、Wails のバインディングを通じて WebView に渡さない。アクセスキー ID は単独では使えず、どのキーを使っているかを見分けるのに要る

### 環境変数が効いているときの設定画面

- 事項: 環境変数の接続情報を使っているときに、設定画面をどうするか
- 決定内容: 保存はできるようにし、「環境変数の接続情報を使っています。保存した値は、環境変数を外すまで使いません」と出す。deviceName は環境変数の対象外なので、保存したらいつもどおり使う
- 判断理由: 環境変数は開発用で、保存を止める理由がない。案内がないと、保存した値が使われない理由が分からない

### 設定画面の入り口

- 事項: 設定画面をどこから開くか
- 決定内容: 画面上部に「設定」ボタンを置き、モーダルでない別の画面に移る。接続情報が未設定（`ErrRemoteNotConfigured`）なら、一覧の上に「接続情報が未設定です」の帯を出し、設定画面へのリンクを置く
- 判断理由: 初めて起動したときは、接続情報を入れないと同期できないので、一覧から設定画面へ移れるようにする。進捗をモーダルでない画面の一部に出す方針（#140 の決めたこと 5）に合わせ、設定もモーダルにしない

### CLI

- 事項: CLI で設定をどう扱うか
- 決定内容: CLI は `internal/settings` で読むだけにし、設定を書くコマンドは足さない
- 判断理由: v1 の CLI は同期コアを確かめる道具で、ゲームと設定の管理は GUI で行う（AGENTS.md の「構成」）。Linux での開発では環境変数を使えば足りる

### 範囲外にすること

- 事項: #142 で扱わないこと
- 決定内容: 次を扱わない
  - 接続を確かめる操作（接続のテストのボタン）。#179 で扱う
  - 保存した接続情報を削除する操作
  - 仕様書の変更
- 判断理由: 誤った接続情報は、最初の状態の確認でエラーとして出るので、確かめる操作がなくても同期は壊れない。接続情報は上書きして保存すれば変えられるので、削除がなくても困らない。仕様書 3 章は置き場所と deviceName の初期値を既に決めており、環境変数の優先は開発用の振る舞いなので、仕様書には書かない

### テスト

- 事項: 何をどう検査するか
- 決定内容: `internal/settings` を、外部のテストパッケージで TDD で書く。DB は本物（一時ファイルの SQLite）、資格情報はメモリ上の偽物、環境変数とホスト名は差し替える。ケース名は「3章/接続情報/…」「3章/deviceName/…」にする。store の設定の読み書きにもテストを書く。platform の資格情報は、実装した後に、保存して読み戻すテストを書く。Windows では、テスト用のターゲット名で本物の資格情報マネージャーに書き、CI の Windows のジョブで走らせる。GUI と CLI の配線にはテストを書かない
- 判断理由: 優先の順番と検証は、CLI と GUI の両方の振る舞いを決めるので、TDD で書く（AGENTS.md の「テスト」）。platform のテストは実装した後に書き、Windows の振る舞いは Windows の CI で確かめる（AGENTS.md の「テスト」）。本番のターゲット名を使うと、開発する PC の設定を壊すので、テストではターゲット名を変える

### PR の分け方

- 事項: PR をどう切るか
- 決定内容: 2 つに分ける
  1. store・platform・`internal/settings` と、CLI がそれを読むところまで
  2. GUI の設定画面と、保存した後の反映
- 判断理由: 見込みの行数は合わせて 800 行ほどで、オーナーが全行を読める量（AGENTS.md の「設計と実装の分担」）を超える。1 つ目だけで、CLI が保存した設定から読むところまで縦に通り、R2 で確かめられる。1 つ目の時点では設定を書く手段がないが、環境変数で今までどおり動く
