# sync-lock

- 日時: 2026-11-04 15:21 (JST)

## 当初の要求 / 背景

仕様書 3 章「排他」は、Push と Pull の実行中は `%LOCALAPPDATA%\CloudLaunch\sync.lock` を OS のファイルロックで握ると決めている。同時に実行できる同期は PC 全体で 1 つだけで、ロックが取れなければ「別の同期が実行中です」として中止する。プロセスが異常終了すれば OS がロックを解放する。

M1 の Push と Pull、M2 の `Recover` は、どれもロックを握っていない（2026-11-03_01-02_push.md・2026-11-03_17-44_pull.md・2026-11-04_11-27_pull-backup-and-recover.md の「同期ロックとゲームの実行中の確認」）。CLI を手で 1 回ずつ実行する間は問題にならないが、M2 が終わると実際のセーブで CLI を使い始め、M4 では GUI と CLI が同じ DB とセーブフォルダを扱う。2 つの同期が重なると、同じゲームの Push どうしが HEAD を取り合ううえ、Pull の入れ替えの途中のセーブフォルダを、別の同期がハッシュしてしまう。

仕様書 7 章の「ゲームの実行中は Push も Pull も拒否する」も同じ Issue（#25）に挙げていたが、OS の処理がまったく違う（ファイルロックとプロセスの一覧）ので、別の Issue に分ける。

## 決定事項

### ロックの実装を置くパッケージ

- 事項: OS のファイルロックをどこに実装するか
- 決定内容: `internal/platform` を作り、ファイルロック（待たずに失敗する排他ロック）を置く。Windows は `LockFileEx`（`LOCKFILE_EXCLUSIVE_LOCK|LOCKFILE_FAIL_IMMEDIATELY`）、Linux は `flock`（`LOCK_EX|LOCK_NB`）で実装し、ファイル名の接尾辞で分ける。`internal/synclock` は作らない。AGENTS.md の「構成」から synclock を外す。`golang.org/x/sys` を直接の依存にする
- 判断理由: 2026-10-23_00-30_package-structure.md は、OS 固有の処理（ファイルロックを含む）を platform に、PC 全体の同期ロックを synclock に置くと決めていた。しかし、synclock に残る仕事は「`sync.lock` というパスでロックを取る」ことだけで、パスは配線の側が決める。synclock は中身のない層になり、OS ごとの処理が 2 つのパッケージに分かれる。ロックの実装を syncore の外に置くのは、OS ごとのコードをコアに入れず、コアのテストで偽物に差し替えるためで、platform に置けばこの目的は満たせる。この決定で、package-structure の ADR の「パッケージの分け方」のうち synclock の部分を置き換える

### syncore がロックを受け取る形

- 事項: syncore が platform を import せずに、ロックを取れたかどうかをどう知るか
- 決定内容: syncore に `Locker` インターフェース（`TryLock() (unlock func() error, ok bool, err error)`）を定義し、`Config.Locker` で受け取る。取れなかったときは `ok == false`・`err == nil`、ファイルを開けないなどの失敗は `err` で返す。syncore は `ok == false` を見て、センチネルエラー `ErrSyncInProgress` を返す
- 判断理由: 呼び出し側（CLI・GUI）は「別の同期が実行中です」と出し分けるので、センチネルエラーが要る（AGENTS.md「構成」）。platform が `syncore.ErrSyncInProgress` を返す案は、platform が syncore に依存する。cmd でエラーを変換する案は、配線の外の処理が cmd に入る。戻り値で取れたかどうかを返せば、どちらも避けられる

### ロックを握る操作と範囲

- 事項: どの操作が、いつからいつまでロックを握るか
- 決定内容: `Push`・`Pull`・`Recover` が、何かを変える前に `TryLock` を呼び、終わるまで（失敗して返るときも含む）握る。`Status` と `RecordBase` は握らない
- 判断理由: 仕様書 3 章は Push と Pull の実行中に握ると決めている。`Recover` は Pull の残骸を片付け、セーブフォルダをリネームするので、Pull と重なってはいけない。`Status` は副作用がない。`RecordBase` は base を書くだけで、セーブフォルダにもリモートにも触れない

### ロックを渡し忘れたとき

- 事項: `Config.Locker` が nil のとき、どうするか
- 決定内容: `Push`・`Pull`・`Recover` は、何も変える前にエラーを返す
- 判断理由: ロックなしで黙って動く道を作ると、配線の誤りに気づけない。`BackupsDir` が空のときと同じ扱いにする

### 解放の失敗と、CLI の表示

- 事項: `unlock` が失敗したとき、および CLI が `ErrSyncInProgress` を受け取ったときの扱い
- 決定内容: `unlock` の失敗は、同期の結果を変えずに警告のログだけを出す。CLI の `push`・`pull`・`recover` は、`ErrSyncInProgress` を受け取ったら「別の同期が実行中です」と出し、終了コード 1 で終わる
- 判断理由: 解放に失敗しても同期そのものは終わっており、プロセスが終われば OS がロックを外す（仕様書 3 章）。文言は仕様書 3 章のとおりで、表示用の文言なので CLI に置く

### テスト

- 事項: ロックをどう確かめるか
- 決定内容: platform のテストで、同じプロセスの中で 2 つ目の `TryLock` が `ok == false` になること、解放すれば取れること、ロックを握った子プロセスが終われば取れることを、Ubuntu と Windows の CI で確かめる。syncore のテストでは、ロックを偽物に差し替える。`Push`・`Pull`・`Recover` のそれぞれで、取れなければ `ErrSyncInProgress` で止まり、リモートにもローカルにも何も書かないこと、終わった後に解放していることを確かめる
- 判断理由: `LockFileEx` はハンドルごと、`flock` は開いたファイルごとにロックするので、ファイルを 2 回開けば 1 つのプロセスの中で取り合える。異常終了で外れることは仕様書 3 章の保証なので、子プロセスで確かめる。platform のテストは実装した後で書く（AGENTS.md「テストの種類」）
