# reparse-dir-in-save-folder

- 日時: 2026-11-04 14:53 (JST)

## 当初の要求 / 背景

仕様書 2 章は、セーブフォルダの中に通常のファイル以外（シンボリックリンク、ジャンクション、OneDrive のファイルのような Windows の reparse point など）があれば、manifest を計算せずにエラーにすると決めている。セーブフォルダそのものがリンクのときも同じである。

dev のコード全体のレビューで、この規則が一部のディレクトリに効いていないと分かった。Go 1.27 の `os/types_windows.go` では、reparse point のモードは次のようになる。

- シンボリックリンクとジャンクション（name surrogate の reparse point）: `ModeDir` を付けず、`ModeSymlink` か `ModeIrregular` にする
- それ以外のディレクトリの reparse point（OneDrive のクラウドのフォルダなど）: `ModeDir` を付けたうえで、`ModeIrregular` も付ける

`localEntries`（`internal/syncore/manifest.go`）は、`d.IsDir()` が真なら通常のファイルかどうかを確かめずに中へ進む。セーブフォルダそのものも `info.IsDir()` だけで確かめている。そのため、後者のディレクトリはエラーにならず、中まで読まれる。前者は今の実装でエラーになり、#33 で確かめた内容と一致する。

## 仕様

- ディレクトリをどう見分けるか
- テストを書くか

## 決定事項

### ディレクトリの見分け方

- 事項: 中へ進んでよいディレクトリを、モードのどのビットで見分けるか
- 決定内容: manifest の計算（`localEntries`）では、種類のビット（`Mode().Type()`、`DirEntry.Type()`）が `ModeDir` だけのものを、通常のディレクトリとして中へ進む。`ModeDir` にほかの種類のビットが付いていれば、エラーにする。セーブフォルダそのものも同じ規則で確かめる。Pull の手順 9 でバックアップへコピーするとき（`copyTree`）は、これまでどおり `IsDir()` で見分け、そうしたディレクトリの中もコピーする
- 判断理由: Go は、name surrogate でないディレクトリの reparse point に `ModeDir|ModeIrregular` を付ける。`IsDir()` は `ModeDir` だけを見るので、`ModeIrregular` を見落とす。`platform` パッケージで reparse point の属性を直接読む案は、Go が付けるモードで見分けられるので採らない。このモードの付け方は Go 1.23 のリリースノートに書かれた振る舞いで、このリポジトリは GODEBUG の `winsymlink` を変えていない。`copyTree` まで拒むと、別のボリュームへコピーする道で手順 9 が失敗し、復旧の 6-R3 も毎回同じところで失敗して、ジャーナルが残り続ける。バックアップは old を読んで写すだけなので、中を読めるなら写して残すほうがよい

### テスト

- 事項: この修正をテストで確かめるか
- 決定内容: テストは書かない
- 判断理由: `ModeDir|ModeIrregular` になるディレクトリは、Windows の CI でも、`FSCTL_SET_REPARSE_POINT` で独自のタグを付ければ作れる。しかし、そのタグを処理するドライバーがないので、Windows はディレクトリの中を開けない。修正の前も、`WalkDir` がそのディレクトリを開こうとして失敗し、`Status` はエラーになる。前後で違うのはエラーの文言だけで、守りたい振る舞い（OneDrive のクラウドのフォルダのように中を読めるディレクトリを、黙って読み進めないこと）は再現できない。文言だけを確かめるテストは、名前と中身が食い違う。Linux ではこのモードにならない

## 結果 / 影響

- セーブフォルダの中やセーブフォルダそのものに、OneDrive のクラウドのフォルダのようなディレクトリの reparse point があれば、`Status` が「a directory reparse point or another special directory」のエラーで止まる。これまでは黙って中を読み、仕様書 2 章の規則が効いていなかった
- セーブフォルダの親が OneDrive の管理下にあると、Pull が作る stage がクラウドのフォルダに変わり、全部ダウンロードした後の手順 5 で失敗することがありうる。OneDrive の中のセーブは v1 の対象外（仕様書 1 章）なので、手当てしない
- テストはなく、`IsDir` に戻す退行は CI で検出できない。#33 の「Windows でジャンクションを使うテストは足さない」と同じく、コメントと ADR で理由を残す
- R2 を相手に CLI で、入れ子のフォルダの Push と Pull が通ること、シンボリックリンクがあると `status` がエラーで止まることを確かめた。ディレクトリの reparse point そのものは Linux では作れないので、確かめていない
- 行数は約 70 行（本体約 15、ADR 約 55）で、見込みの約 60 行とほぼ同じだった
