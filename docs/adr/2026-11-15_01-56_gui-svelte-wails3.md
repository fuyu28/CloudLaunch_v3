# gui-svelte-wails3

- 日時: 2026-11-15 01:56 (JST)

## 当初の要求 / 背景

`docs/adr/2026-10-23_00-30_gui-frontend.md` は、GUI の枠組みを Wails とし、フロントエンドの第一候補を Go のテンプレート + htmx、次点を Svelte とした。どちらにするかは、GUI に着手するときに、進捗の表示と確認ダイアログを含む 1 画面を試作して決めるとしていた。Wails は安定版の v2 を前提とし、v3 の安定度は GUI に着手するときに確かめるとしていた。

試作は、htmx（Wails v2）、templ + htmx、templ + datastar、Svelte（Wails v2）、Svelte（Wails v3）の 5 つを作った。このうち Svelte + Wails v3 は、Windows 11（Build 26200、WebView2 157）でビルドと操作を確かめ、結果を #113 に記録した。同期は偽物で、ゲームの登録だけ本物の store を使った。

M4 の範囲と進め方は #140 で決めた。

## 決定事項

### フロントエンドの方式

- 事項: Wails の中のフロントエンド
- 決定内容: Svelte を使う。Go のテンプレート + htmx（templ・datastar を含む）は採らない
- 判断理由: GUI には、転送の進捗の通知、キャンセル、確認ダイアログ、ゲームごとの状態の表示のように、非同期に変わる表示が多い。Svelte は、非同期の結果を待って表示を変えることや、画面の一部だけを描き直すことを、フロントの状態として素直に書ける。htmx 系は、Go が HTML を返して画面の一部を差し替える方式なので、Go からの通知で画面を変えるたびに、差し替える HTML の単位と、通知を受けるための JS を別に用意することになり、フロントの状態の管理に向かない。古い ADR が htmx を第一候補にした理由の、Go の型を TS で書き直す層が要らないことは、Wails v3 のバインディングの生成で満たせる（下記「Go とフロントの分担」）

### Wails のバージョン

- 事項: Wails v2 と v3 のどちらを使うか
- 決定内容: Wails v3（3.1.0）を使う
- 判断理由: v3.1.0 で、Windows 11 でのビルド・起動・操作が通った（#113）。v3 の `wails3 generate bindings -ts` は、Go のメソッドと型に加えて、enum とイベントの型も TS に生成し、試作ではそれが `svelte-check` を通った。進捗の通知はイベントで送るので、イベントの型まで生成されると、TS で型を書き直さずに済む。v2 は安定しているが、イベントの型を生成しないので、通知の形を TS 側で書き直すことになる

### Go とフロントの分担

- 事項: 状態と画面の組み立てをどちらに置くか、Go と TS の橋渡しをどう書くか
- 決定内容: 同期の状態、判定、画面に出すデータの組み立ては Go に置く。Svelte は、Go が返したデータの表示と、表示のための状態（ダイアログの開閉、入力中の値、進捗の表示など）だけを持つ。Go の型と API は `wails3 generate bindings` で生成した TS をそのまま使い、Go の型を TS で書き直す層や、Go の API を包む層は作らない
- 判断理由: CloudLaunch_Go が肥大化した主な原因は、Go の型を TS で書き直す層と API を包む層で、Go で機能を 1 つ足すたびに TS の複数か所を書く構造だった（古い ADR）。生成したバインディングを直接呼べば、Go の変更は生成し直すだけで TS に届く。判定や同期の状態を Svelte に持たせると、Go のコアと二重に持つことになるので、表示のための状態だけに限る

### コードの置き場所

- 事項: GUI のコードをどこに置くか
- 決定内容: Wails の配線と画面に出すデータの組み立ては `cmd/cloudlaunch-gui/` に、Svelte のフロントは `cmd/cloudlaunch-gui/frontend/` に置く。フロントのビルド結果は `//go:embed` で取り込み、git には `frontend/dist/.gitkeep` だけを入れる。生成したバインディングはコミットする。テストの要るロジック（ゲームの起動と終了の待機、プレイ時間の計測）は、`internal/` の新しいパッケージに置き、TDD で書く。そのパッケージの名前と形は #146 で決める
- 判断理由: AGENTS.md は `cmd/` を配線だけの場所とし、UI と Wails の配線にはテストを書かないとしている。仕様書 8 章「プレイ時間の計測」の規則は検査できる項目なので、`cmd/` に置くとテストのない場所に規則が入る。`dist/.gitkeep` を置くと、フロントをビルドしなくても `//go:embed` の対象があるので、Go のビルド・リント・テストがフロントのビルドに依存しない。バインディングをコミットすると、Go の変更で TS がどう変わったかを差分で読め、CI で生成し直したものとの差分を確かめられる（#21）

### ツールの管理

- 事項: wails3 と bun をどう入れるか
- 決定内容: `mise.toml` の `[tools]` に、bun と、`go:github.com/wailsapp/wails/v3/cmd/wails3`（Linux 向けに `tags = "gtk3"`）を足す。フロントの依存は bun で入れ、`bun.lock` をコミットする
- 判断理由: ツールのバージョンは `mise.toml` で固定する決まりで、clone して `mise install` すれば同じ環境になる。試作でも、この形で Windows のビルドが通った（#113）。Wails v3.1.0 は Linux で既定で GTK4 を使い、`gtk3` のタグを付けると従来の GTK3 の実装を使う。`gtk3` のタグは試作の設定を引き継いだもので、GTK3 を選ぶ判断理由は根拠未確認

## 結果 / 影響

- フロントに Node の道具（bun・vite・svelte-check）が入り、CI にフロントのジョブが要る（#21）
- 画面の振る舞いの一部を TS（Svelte）に書くことになる。表示のための状態に限ることで、Go のコアと状態を二重に持たないようにする
- 転送中のダイアログを Esc で閉じるのは、Chromium の仕様で止められない（#113）。進捗の出し方は #141 で決める
- 試作のうち push したのは Svelte + Wails v3（`fuyu28/GUI-svelte-v3`）だけで、ほかの試作のコードは残していない
