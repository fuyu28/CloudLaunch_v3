## 当初の要求 / 背景

M1（walking skeleton）の 4 つ目の作業として、セーブをリモートにアップロードできるようにする（仕様書 5 章）。M1 の道は `game add` → `status` → `push` → 別のフォルダで `pull` で、判定は「base なし」の行だけを扱う（AGENTS.md「開発の進め方」）。M1 の道で `push` を実行するのは、判定が「base なし・local あり・remote なし → Push」の行に当たるときだけである。

syncore の公開 API は、`Status` が返した plan を `Push` が受け取り、承認した後に状況が変わっていればセンチネルエラーを返す形にする（AGENTS.md「構成」）。manifest の計算と `Status` は 2026-10-27_03-07_manifest-and-status.md で作った。リモートの読み書きは 2026-10-23_01-53_objstore.md で作り、`Put` は SDK が再試行のときに読み直せるよう `io.ReadSeeker` を受け取る。

## 決定事項

### 5 章の手順の範囲

- 事項: 仕様書 5 章の Push の 8 つの手順のうち、どこまでを作るか
- 決定内容: 手順 1〜7 を作る。手順 8（古い世代の削除と GC）は M2 で作る
- 判断理由: 手順 8 は失敗しても Push を成功とする手順で、行わなくても古い世代と不要な object が残るだけである（仕様書 5 章「中断したときに残るもの」）。M1 の目的はつなぎ目の問題を先に出すことで、手順 8 はつなぎ目を増やさない

### 同期ロックとゲームの実行中の確認

- 事項: 仕様書 3 章の `sync.lock` と、7 章の「ゲームの実行中は Push を拒否する」を、この作業で入れるか
- 決定内容: どちらも入れず、M2 で入れる
- 判断理由: どちらも `internal/synclock` と `internal/platform` を新しく作る必要がある。M1 の道では CLI を手で 1 回ずつ実行するので、同時の同期も、ゲームの実行中の同期も起こらない

### Push が受け付ける判定

- 事項: `Push` が、どの判定の plan を受け付けるか
- 決定内容: 判定が Push の plan だけを受け付ける。ほかの判定の plan を渡されたら、`%w` で包んだエラーを返し、センチネルエラーにはしない。競合のときの「アップロードで上書き」（仕様書 7 章）は M2 で扱う
- 判断理由: 競合の上書きを受け付けると、CLI でそれを選ぶ手段も決める必要がある。M1 の道は競合の行に当たらない。判定が Push でない plan を渡すのは呼び出し側の誤りであり、呼び出し側が振る舞いを分ける場面ではないので、センチネルエラーにしない

### 承認後に状況が変わったときのエラー

- 事項: 承認した後に状況が変わって Push をやめるとき、何を返すか
- 決定内容: センチネルエラー `ErrPlanStale` を 1 つ公開する。手順 3 で読み直した sha256 が manifest と違うときと、手順 5 で HEAD が承認した時点の世代から変わっているときの、両方でこれを返す。どちらで止まったかは、包んだメッセージに書く
- 判断理由: どちらの場合も、呼び出し側がすることは「判定からやり直す」の 1 つで、振る舞いを分ける必要がない。HEAD がない状態で承認した plan は、`Remote.Generation` が空の文字列なので、読み直した HEAD が空のままであることと文字列のまま比べられる（2026-10-27_03-07_manifest-and-status.md「Status が返す plan」）

### アップロードしながら sha256 を確かめる方法

- 事項: 手順 3 の「ファイルを読みながら sha256 を計算し直し、manifest と違えば中止する」を、`io.ReadSeeker` を受け取る `Put` でどう行うか
- 決定内容: ファイルを全部メモリに読み、sha256 と size が manifest と一致することを確かめてから、`bytes.Reader` で `Put` する。一致しなければ `Put` せずに `ErrPlanStale` を返す
- 判断理由: 読みながらハッシュを計算して `Put` し、後で比べる方法では、違ったときに消す前に中断すると、`objects/{sha256}` のキーに違う中身が残る。object は書き換えない前提なので、以後の Push は「リモートにある」とみなしてアップロードを省き、壊れた object を参照し続ける。一時ファイルにコピーしてから `Put` する方法でもこれは防げるが、作業領域の後始末が増える。セーブファイルは小さいことが多く、メモリは最大で「転送の並列数（8）× ファイルの大きさ」で済む。S3 のサーバー側の sha256 チェックサムに任せる方法は、SDK のチェックサムに頼らずコアが sha256 で確かめるという決定（2026-10-23_01-53_objstore.md）と合わない

### アップロードの並列

- 事項: 手順 3 のアップロードを並列にするか、1 つが失敗したときにどうするか、並列数をどう確かめるか
- 決定内容: M1 から、errgroup の `SetLimit` で 8 並列にする。並列数は syncore の定数にし、`Config` には入れない。アップロードする前に、sha256 で重複を除く。1 つが失敗したら（`ErrPlanStale` を含む）、errgroup の ctx をキャンセルして最初のエラーを返し、アップロードし終えた object は消さない。並列数そのものはテストせず、競合状態は `-race` で確かめる
- 判断理由: 転送の並列数は AGENTS.md「構成」で 8 と決めてある。M1 から並列にすると、objstore と memstore の同時呼び出しの問題を `-race` で早く出せる。中身が同じファイルは同じキー（`objects/{sha256}`）になるので、重複を除かないと同じ転送を 2 回行う。S3 の PUT は最後まで届いたときにだけ object が見えるので、キャンセルで途中の object が残ることはない。アップロードし終えた object はどの世代からも参照されず、仕様書 5 章の「3〜5 で中断した」と同じ状態になり、GC（M2）で消える。並列数は判定やリモートの中身を変えない内部の調整で、仕様書の行に当たらない。確かめるには memstore に同時呼び出しの数を数える仕組みが要る

### 時刻・世代 ID・deviceName の渡し方

- 事項: manifest の `createdAt`・`deviceName` と、世代の UUIDv7 を、コアがどこから得るか
- 決定内容: `syncore.New` の引数を `Config` 構造体（`Remote`・`Local`・`Logger`・`Now`・`NewGeneration`・`DeviceName`）にする。`Now` と `NewGeneration` は、nil なら実際の時刻と `uuid.NewV7` を使う。M1 の CLI は、`os.Hostname()` で得たホスト名を `DeviceName` に渡す
- 判断理由: コアのテストでは、時刻と ID の採番を差し替える（AGENTS.md「テスト」）。引数を足していくと、呼び出し側で順番を取り違えやすい。deviceName は DB の設定に置き、初期値をホスト名にする（仕様書 3 章）が、変更する手段は GUI（M4）までないので、M1 では初期値と同じホスト名を配線から渡す。DB の設定に置くのは、変更する手段を作る作業で行う

### base を書く操作

- 事項: 手順 7 で base を書く操作をどこに置くか
- 決定内容: store に `SetBase(ctx, gameID, hash)` を足し、syncore の `LocalStore` インターフェースにも足す。syncore のテストで、DB に SQL を直接書いて base を作っていた箇所も `SetBase` に置き換える
- 判断理由: syncore は必要な操作だけのインターフェースを定義し、store がそれを実装する（2026-10-23_00-30_package-structure.md）。テストの SQL は、base を書く操作がなかったための代わりである（2026-10-27_03-07_manifest-and-status.md「結果 / 影響」）

### 「base を記録」の行で base を書く操作

- 事項: 判定が「base なし・local あり・remote あり（local と同じ）→ 変更なし（base を記録）」の行に当たったとき、どの操作が base を書くか
- 決定内容: syncore に `RecordBase(ctx, plan)` を公開する。判定が「base を記録」の plan だけを受け付け、`plan.Local.Hash` を base に書く。ほかの判定の plan を渡されたら、`%w` で包んだエラーを返す。リモートは読み直さず、`ErrPlanStale` も返さない。CLI の `status` と `push` は、`Status` が返した plan が「base を記録」なら、確認を取らずに `RecordBase` を呼ぶ
- 判断理由: 判定そのものは副作用を持たず、base の記録は判定とは別の操作で、ユーザーの確認は取らない（仕様書 4 章）。この行は Push の手順 6 と 7 の間で中断したときの復旧も担う（仕様書 4 章）ので、書く操作がないと、中断した PC の base がいつまでも直らない。`Push` にこの plan を受け付けさせる案は、データを転送しない操作を Push と呼ぶことになり、`Push` が受け付ける判定の決定（「Push が受け付ける判定」）とも合わない。承認の後に状況が変わっていても、`Status` の時点で local と remote が同じハッシュだったので、そのハッシュを base にするのは正しい。その後に local が変われば次の判定は Push、remote が変われば Pull、両方が変われば判定表どおりに決まるので、読み直して止める必要がない

### 進捗の通知

- 事項: アップロードの進捗を通知するか
- 決定内容: この作業では通知せず、コールバックを受け取る口も作らない。M2 で作る
- 判断理由: 進捗は直列化したコールバックで通知する（AGENTS.md「構成」）が、M1 の CLI には進捗を出す場所がない。使う側がないまま口を作ると、形を確かめられない

### Push の後の `status`

- 事項: Push で base が書かれた後、同じ PC の `status` をどうするか
- 決定内容: base があるゲームの `Status` は、引き続き「未実装」のエラーを返す
- 判断理由: M1 の道で `status` を呼ぶのは、別のフォルダで `pull` する前（base なし）だけである。base ありの 8 行は M2 で、検査できる項目に ID を振ってから書く（2026-10-27_03-07_manifest-and-status.md「判定する行の範囲」）

### `push` コマンドの形

- 事項: CLI の `push` の引数・確認・出力・終了コード
- 決定内容: `cloudlaunch-cli push --game <gameId> [--data-dir <dir>]` とする。`status` と同じ内容を出し、判定が Push なら確認を取らずに Push する。判定が Push でなければ、アップロードしない旨を出して終了コード 0 で終わる。`ErrPlanStale` が返ったら、もう一度実行するよう出して終了コード 1 で終わる
- 判断理由: CLI では、`push` を実行したこと自体を承認とみなす。これは仕様書 7 章の「確認を取ってから行う」の解釈の範囲であり、確認のダイアログは GUI が出す。判定が Push でないのは誤りではなく、同期の必要がない状態なので、成功として終える。`ErrPlanStale` は、実行した時点の状態では Push できなかったことを表すので、失敗として終える

## 結果 / 影響

- `syncore.New` の引数が変わるので、CLI の配線と syncore のテストの補助を書き換える
- M1 の Push は手順 8 を行わないので、M2 で手順 8 を作るまでは、古い世代と不要な object がリモートに残り続ける
- 大きなセーブファイルでは、アップロードの間のメモリが増える。問題になったら、一時ファイルにコピーする方法に変える
- 受け入れの条件の 15 ケースが通る
- versitygw を相手に CLI で、`push` の後に別のフォルダの `status` が Pull になることを確かめた。中身が同じ 2 つのファイルは、object 1 つにまとまった。同じ PC でもう一度 `push` すると、base ありの `Status` が「未実装」のエラーを返す（「Push の後の `status`」のとおり）
- `Push` は、セーブフォルダのパスを plan から取らず、store から読み直す。plan に持たせると公開 API の型が増えるうえ、承認の後にパスが変わっても、手順 3 の sha256 の確かめで食い違いとして止まるためである
- 行数は約 780 行（テスト約 410 行、本体約 270 行、ADR 約 100 行）で、見込みの約 700 行を超えた。テストの補助を、2 つ目の PC を作れる形とリモートを読む関数に書き換えた分が増えた
- R2 を相手に CLI で、リモートと同じ中身を持つ別のフォルダの `status` と `push` が base を記録し、次の `status` が base ありの経路に進むことを確かめた。`RecordBase` の追加で、行数は約 110 行増えた（テスト約 60 行、本体約 30 行、ADR 約 10 行）
- M1 では、base を記録した後の同じ PC の `status` は「未実装」のエラーを返す（「Push の後の `status`」と同じ）
