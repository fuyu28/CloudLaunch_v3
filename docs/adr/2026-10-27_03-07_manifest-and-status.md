# manifest-and-status

- 日時: 2026-10-27 03:07 (JST)

## 当初の要求 / 背景

M1（walking skeleton）の 3 つ目の作業として、ゲームの状態が分かるようにする。セーブフォルダから manifest を計算し、リモートの HEAD が指す manifest と比べて、次に行うべき操作を判定する（仕様書 2・4 章）。M1 では `game add` → `status` → `push` → 別のフォルダで `pull` を一度通し、判定は「base なし」の行だけを扱う（AGENTS.md「開発の進め方」）。

syncore の公開 API は、副作用なしで plan を返す `Status` から始まり、`Push` / `Pull` が plan を受け取る形にする（AGENTS.md「構成」）。ゲームの登録（2026-10-23_00-53_store-and-game-add.md）とリモートの読み書き（2026-10-23_01-53_objstore.md）は、すでにできている。

manifest ハッシュの正規化 JSON と HEAD の形式は、この作業の前に仕様書 2 章で定めた。

## 仕様

## 決定事項

### 判定する行の範囲

- 事項: 判定表のどの行を実装するか
- 決定内容: 「base なし」の 5 行だけを実装する。base があるゲームの `Status` は、`%w` で包んだ「未実装」のエラーを返す。センチネルエラーにはしない
- 判断理由: M1 の道で `status` を呼ぶのは、`game add` の直後と、別のフォルダで `pull` する前だけで、どちらも base がない。base ありの 8 行は M2 で、検査できる項目に ID を振ってから書く（AGENTS.md「開発の進め方」）。「未実装」は M2 で消えるエラーで、呼び出し側が振る舞いを分ける必要がないので、センチネルエラーとして公開しない

### ハッシュキャッシュ

- 事項: manifest の計算でハッシュキャッシュ（`hash_cache`）を使うか
- 決定内容: 使わず、毎回すべてのファイルの sha256 を計算する
- 判断理由: キャッシュが消えても全ファイルを計算し直すだけで、判定の結果は変わらない（仕様書 3 章）。後から足しても振る舞いは変わらないので、M1 の範囲を小さくするために M2 に回す

### 通常のファイル以外

- 事項: セーブフォルダの中に、シンボリックリンクなどの通常のファイルでもディレクトリでもないものがあったとき
- 決定内容: エラーにして manifest の計算を止める。判別には `fs.DirEntry.Type()` を使い、通常のファイルでもディレクトリでもないものをまとめてエラーにする
- 判断理由: 仕様書ではこの扱いを未決事項としている（11 章）。黙って飛ばすと、リンク先のセーブが Push されないまま失われうる。reparse point の正確な判別は `internal/platform` が持つ予定だが、M1 では Go の標準ライブラリが返す種類で足りる

### 正規化 JSON の書き出し方

- 事項: manifest ハッシュのもとになる正規化 JSON を、どう書き出すか
- 決定内容: `encoding/json` を使わず、仕様書 2 章の規則どおりにバイト列を組み立てる関数を syncore に書く。既知の entries から計算したハッシュを固定値と比べる golden テストで、書き出しを固定する
- 判断理由: `encoding/json` は `SetEscapeHTML(false)` にしても U+2028・U+2029 を `\u2028` の形にエスケープし、仕様書の規則（JCS と同じエスケープ）と一致しない。entries の要素は文字列 2 つと整数 1 つだけなので、組み立てる関数は小さい。JCS のライブラリを入れる方法もあるが、キーの並べ替えなど、この形では使わない機能のために依存を足すことになる

### リモートの manifest の検査

- 事項: Status で、HEAD と manifest をどこまで検査するか
- 決定内容: HEAD が仕様書 2 章の形（小文字の UUIDv7 の 36 文字だけ）でなければエラーにする。HEAD が指す manifest がなければエラーにする。manifest は JSON として読めることと `version` が 1 であることだけを確かめ、`entries` から manifest ハッシュを計算する
- 判断理由: 仕様書 6 章の「不正な manifest」の検査は、Pull がファイルを書く前の手順（6 章の 2）であり、#10 で入れる。Status はハッシュを比べるだけで、ファイルを書かないので、不正な path があっても害がない

### Status が返す plan

- 事項: plan に持たせる情報
- 決定内容: gameId、判定の結果（`変更なし` / `Push` / `Pull` / `競合`）、base、local の manifest とハッシュ、remote の世代 ID と manifest とハッシュ（HEAD がなければ空）を持たせる。判定が「base を記録」の行に当たったことを示すフラグも持たせる。base・local・remote の「なし」は、どれもハッシュを空の文字列にして表し、remote もポインタにしない。base を記録する操作と、確認ダイアログに出す情報（追加・変更・削除の数、転送するサイズ、mtime の最大値）は、この作業では作らない
- 判断理由: Push と Pull は plan を受け取り、承認した時点の remote の世代と local のハッシュを使う（仕様書 5・6 章）ので、それらを plan に入れておく。base の記録は判定とは別の操作で行う（仕様書 4 章）。M1 の道では base の記録の行に当たらないので、M2 に回す。「なし」を空の文字列にそろえると、判定の入力が仕様書 4 章のとおり 3 つのハッシュになり、判定表の行と 1 対 1 で対応する。空 manifest の世代のハッシュも 64 文字なので、空の文字列が「HEAD なし」以外の意味になることはない。remote だけをポインタにすると、使う側が毎回 nil を確かめる必要があり、確かめ忘れると panic になる

### syncore が定義するインターフェース

- 事項: Status が依存する操作
- 決定内容: syncore は、リモートの `Get` と、gameId からセーブフォルダと base を返す操作だけのインターフェースを定義する。後者は store に `GameLocal` を足して実装する。Push や Pull で要る操作は、その作業でインターフェースに足す
- 判断理由: syncore が必要な操作だけのインターフェースを定義する（2026-10-23_00-30_package-structure.md）。使わない操作を先に入れると、まだ形の決まっていない操作にまで実装と偽物を用意することになる

### CLI の接続先と鍵

- 事項: CLI がリモートの接続先と鍵を受け取る方法
- 決定内容: 環境変数 `CLOUDLAUNCH_S3_ENDPOINT`・`CLOUDLAUNCH_S3_REGION`・`CLOUDLAUNCH_S3_BUCKET`・`CLOUDLAUNCH_S3_ACCESS_KEY_ID`・`CLOUDLAUNCH_S3_SECRET_ACCESS_KEY` から読む。`CLOUDLAUNCH_S3_REGION` は省いてよく、省くと objstore の既定（`auto`）になる
- 判断理由: 仕様書 3 章では、鍵を Windows 資格情報マネージャーに、バケットとエンドポイントを DB の設定に置く。どちらも M1 にはまだなく、M1 の目的は versitygw を相手につなぎ目を通すことなので、設定を保存する仕組みは M2 以降に回す

### `status` コマンドの形

- 事項: CLI の `status` の引数と出力
- 決定内容: `cloudlaunch-cli status --game <gameId> [--data-dir <dir>]` とし、1 回に 1 ゲームを見る。出力は、判定の結果と base・local・remote のハッシュ（ないものは `-`）を 1 行ずつ書いたテキストにする。全ゲームの一覧と JSON の出力は作らない。判定の結果は内部の用語（`Push` など）のまま出す
- 判断理由: v1 の CLI は同期コアを確かめるための道具であり、表示は最小限でよい。内部の用語を画面に出さない決まり（仕様書 1 章）は、CLI を対象から外している

## 結果 / 影響

- 受け入れの条件の 19 ケースが通る。Linux ではシンボリックリンクのケースも走り、Windows ではリンクを作る権限がなければ skip する
- versitygw を相手に、`game add` の直後の `status` が「変更なし」、セーブを置いたあとの `status` が「Push」になることを CLI で確かめた
- manifest ハッシュの golden テストの固定値は、仕様書の規則どおりに手で組み立てたバイト列から、Go とは別の実装（Python の hashlib）で求めたものである。size に 2^53 を超える値を入れ、浮動小数点を経由しないことも固定した
- 行数はテストを含めて約 840 行で、見込みの約 800 行を少し超えた。テストが約 440 行、本体が約 400 行である
- 不正な UTF-8 を含む path は、バイト列のまま書き出す。Windows のファイル名は UTF-16 から変換されるので不正な UTF-8 にならないが、Linux では起こりうる。Linux は開発用なので扱わない
- syncore のテストは、base を書く store の操作がまだないため、DB に直接 SQL を書いて base ありの状態を作っている。Push（#9）で store に base を書く操作を足したら、そちらに置き換える
- `Core` が受け取る `*slog.Logger` は、Status ではまだ使っていない
