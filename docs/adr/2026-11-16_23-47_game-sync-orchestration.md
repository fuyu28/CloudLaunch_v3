# game-sync-orchestration

- 日時: 2026-11-16 23:47 (JST)

## 当初の要求 / 背景

AGENTS.md の「構成」は、cmd には配線だけを書くと決めている。しかし、同期の振る舞いを決める手順が `cmd/cloudlaunch-cli/main.go` にある。

- `transfer`: 仕様書 8 章「セーブとメタ情報の同期」の順序（8-M1 ゲームの tombstone の確認 → セーブの同期 → 8-M2 メタ情報の同期、8-M3 メタ情報の同期の失敗をセーブの同期の結果に含めない）と、セーブの同期が失敗したときの tombstone の確かめ直し。テストがない
- `game set-image`: 登録の確認 → 画像のキャッシュ → DB への書き込み

GUI（M4、#141）も同じ手順が要る。cmd に置いたままでは、GUI の配線に同じ手順を書き直すことになる。

`2026-10-23_00-30_package-structure.md` は、syncore と metasync は互いに import せず、cmd で組み合わせると決めている。手順をコアに移すには、この決まりとの両立が要る。

GUI は「状態の確認 → 利用者の承認 → 転送」の順に進み、確認と転送の間に人が入る。CLI の `push`・`pull` は、コマンドの実行を承認とみなして一度に行う。M4 では、全ゲームの状態の確認とメタ情報の同期を並べて行うこと（#143）、ゲームの起動の前後の確認と同期（#146）も、syncore と metasync を組み合わせる。

## 決定事項

### 手順の置き場所

- 事項: 8-M1〜8-M3 の手順を、どこに置くか
- 決定内容: syncore と metasync を組み合わせる新しいパッケージ `internal/gamesync` に置く。syncore と metasync は、これまでどおり互いに import しない
- 判断理由: gamesync は両方のコアを知るので、セーブの同期の結果とメタ情報の同期の結果（`metasync.Result`）を 1 つの型で返せる。CLI と GUI は、それを表示するだけで済む。本物の 2 つのコアを偽のリモートでつないだテストで、確かめ直し（8-T7）とメタ情報の同期の前の確かめ（8-M5）の噛み合いを確かめられる。#143・#146 の組み合わせの置き場所にもなる。syncore がメタ情報の同期を `func(ctx) error` のコールバックで受け取る案は採らない。8-M3 でコールバックの失敗を戻り値に含められないので、メタ情報の結果と失敗を呼び出し側が自分の変数で持ち出すことになる。#143・#146 でも同じ形を取ると、syncore がセーブの同期のコアから手順全体の組み立て役になっていく

### パッケージの範囲

- 事項: gamesync に何を置くか
- 決定内容: 1 ゲームの同期の手順（8-M1〜8-M3）だけを置く。全ゲームを並べて行う処理（#143）と、起動の前後の同期（#146）を gamesync に置くかは、それぞれの Issue で決める
- 判断理由: 役割を絞って書いておかないと、両方のコアを知る場所に何でも入り、AGENTS.md が禁じる「何でも入る名前のパッケージ」に近づく

### 公開 API の形

- 事項: GUI の「確認 → 承認 → 転送」と、CLI の一度に行う形の両方に合う API
- 決定内容: 確認と、承認の後の操作の 2 段に分ける
  - `Check(ctx, gameID) (syncore.Plan, error)`: ゲームの tombstone を処理し（8-M1・8-T2）、なければ syncore の `Status` を呼ぶ。tombstone があれば `Plan.RemoteDeleted` を入れて返す。確認の後に置かれた tombstone を `Status` が見つけたときも、同じく処理して返す
  - `Push(ctx, plan, syncore.PushOptions) (Result, error)`・`Pull(ctx, plan, syncore.PullOptions) (Result, error)`: セーブを転送してから、`SyncMeta` を呼ぶ
  - `Skip(ctx, plan) (Result, error)`: 転送を見送る。`plan.RecordBase` なら base を記録してから（4 章）、`SyncMeta` を呼ぶ
  - `SyncMeta(ctx, gameID, saveErr) (Result, error)`: メタ情報を同期する（8-M2）。saveErr はセーブの同期のエラーで、返すエラーに含める。saveErr があれば、メタ情報を同期する前にゲームの tombstone を確かめ直す。tombstone があれば 8-T2 の扱いにし、メタ情報を同期しない。確かめ直しに失敗したときも、メタ情報を同期しない

  判定が Push・Pull でなければ見送る判断は、CLI の `push`・`pull` に固有なので cmd に残す。GUI は利用者の選んだ操作を呼ぶ。CLI は、`Check` の判定が失敗したときも、セーブの同期の失敗として `SyncMeta` を呼ぶ
- 判断理由: 確認と転送の間に人が入る GUI では、1 つの関数で通せない。確かめ直しは、承認の後にゲームが削除されたとき、セーブの同期が 8-T7 のほか、削除で消えた object を取得できずにも失敗するためである。確かめずにメタ情報を同期すると、削除したデータをリモートに戻す。`SyncMeta` を公開するのは、CLI では判定（`Status`）もセーブの同期の一部で、判定の失敗の後にも 8-M2 のとおりメタ情報を同期するためである。このとき確かめ直しを通さずにメタ情報を同期すると、tombstone が不正（8-T4〜8-T6）なときにも同期してしまう。metasync の `Sync` は、まだ同期の前に tombstone を確かめない（8-M5）。操作を引数（列挙）で渡す形は採らない。Push と Pull で options の型が違い、1 つの関数で受けると使わない options を渡すことになる

### 結果とエラーの分け方

- 事項: メタ情報の同期の結果・失敗と、セーブの同期の失敗の返し方
- 決定内容: `Result{RemoteDeleted *syncore.Tombstone; Meta *metasync.Result; MetaErr error}` を返す。`RemoteDeleted` は、確かめ直しで tombstone が見つかったときに入る。`Meta` はメタ情報の同期が成功したとき、`MetaErr` は失敗したときに入る。戻り値のエラーは、セーブの同期と tombstone の処理のエラーだけにする。8-M3 のログは gamesync が出す。表示の文言は cmd に残す
- 判断理由: 8-M3 はメタ情報の同期の失敗をセーブの同期の結果に含めないので、戻り値のエラーとは分ける。表示用の文言をコアに置かない決まり（`2026-10-23_00-30_package-structure.md`）に合わせる

### コアの受け取り方

- 事項: gamesync が syncore と metasync をどう受け取るか
- 決定内容: `gamesync.New(Config{Save *syncore.Core, Meta *metasync.Core, Logger *slog.Logger})` のように、具体的な型で受け取る
- 判断理由: gamesync を置く理由は、本物の 2 つのコアのつながりをテストで確かめられることである。インターフェースで受け取ると、テストで偽物を差し込む方向に流れやすい。失敗は、偽のリモート（memstore）に仕込んで起こす

### 画像の設定の置き場所

- 事項: `game set-image` の手順をどこに置くか
- 決定内容: `metasync.SetImage(ctx, gameID, r io.Reader, now time.Time) (string, error)` に置く。登録を確かめてから、画像をキャッシュし、DB に画像のハッシュを書いて、そのハッシュを返す。r が nil なら画像を外して空を返す。metasync の LocalStore に、画像のハッシュだけを書き換える操作を 1 つ足す
- 判断理由: 画像のキャッシュは metasync が持ち（`CacheImage`）、セーブの同期とは関係がないので、gamesync ではなく metasync に置く。登録の確認を先にするのは、登録していないゲームの ID を打ち間違えたときに、どこからも参照されない画像をキャッシュに残さないためである

### 決まりと既存の ADR の扱い

- 事項: AGENTS.md と `2026-10-23_00-30_package-structure.md` をどう直すか
- 決定内容: AGENTS.md の「構成」の図に `internal/gamesync/` を足し、「cmd で組み合わせる」を「gamesync で組み合わせる」に直す。「テスト」の方針で TDD と外部のテストパッケージで書く対象に gamesync を足す。`2026-10-23_00-30_package-structure.md` は本文を書き換えず、更新履歴に、この ADR で「依存の向き」の一部を置き換えたことを書く
- 判断理由: 決まりを変えずにパッケージを足すと、AGENTS.md と実際の構成が食い違う。古い ADR の本文を残せば、当時の前提と、それを覆した根拠の両方を追える

### テスト

- 事項: 何をどう検査するか
- 決定内容: gamesync のテストは `package gamesync_test` に置き、本物の syncore・metasync・store（SQLite）と memstore で書く。ケースは次の 9 つにする
  - `8-M1 ゲームの tombstone があれば、セーブもメタ情報も同期しない`
  - `8-M1 確認の後、判定の前にゲームの tombstone が置かれても、記録して判定しない`
  - `8-M2 Push を見送っても、メタ情報を同期する`
  - `8-M2 Push が失敗しても、メタ情報を同期する`
  - `8-M2 判定に失敗しても、メタ情報を同期する`
  - `8-M3 メタ情報の同期が失敗しても、セーブの同期の結果を返す`
  - `8-T7 承認の後にゲームが削除されたら、メタ情報を同期しない`
  - `8章/セーブとメタ情報の同期/セーブの同期の失敗の後に tombstone が見つかったら、メタ情報を同期しない`（削除で消えた object を取得できずに Pull が失敗した場合）
  - `8章/セーブとメタ情報の同期/tombstone を確かめ直せなかったら、メタ情報を同期しない`

  metasync には、次の 2 つを足す
  - `8章/画像/登録していないゲームには、画像をキャッシュに残さない`
  - `8章/画像/nil を渡すと画像を外す`
- 判断理由: 今は `transfer` にテストがなく、8-M1〜8-M3 と確かめ直しを CLI でしか確かめられない。確かめ直しの 2 つのケースは、8-T7 で止まる場合と、それ以外の失敗の後に tombstone が見つかる場合とで、通る道筋が違う

### 範囲外にすること

- 事項: この作業で扱わないこと
- 決定内容: 次を扱わない
  - push・pull の始めに、tombstone の処理と `Status` が deleted.json を続けて GET している重複（#160）
  - 全ゲームの確認とメタ情報の同期を並べて行う処理（#143）、起動の前後の同期（#146）
  - GUI からの呼び出し（#141）
- 判断理由: GET の重複は、`Status` が tombstone を扱う範囲の判断と一緒に #160 で決める。gamesync に移しても、呼ぶ順は変わらないので、後から片付けても振る舞いは変わらない

## 結果 / 影響

- `internal/gamesync` に `Check`・`Push`・`Pull`・`Skip`・`SyncMeta` を置き、CLI の `push`・`pull` はこれを呼んで表示するだけになった。`game set-image` は `metasync.SetImage` を呼ぶ
- 8-M1〜8-M3 と確かめ直しに、テストのケースが付いた。決定のときの 9 つに、`Status` が見つけた tombstone が確かめ直しで見えなくなったときに `Check` が `syncore.ErrRemoteDeleted` で止まるケース（8-M1）を足した。移す前の CLI と同じく、削除されたかどうか分からないので判定を止める
- 最初の tombstone の確認が読み取りの失敗で止まったときも、`Check` の失敗としてメタ情報の同期に進む。移す前の CLI は、このときメタ情報を同期しなかった。`SyncMeta` が確かめ直してから同期するので、削除したデータをリモートに戻すことはない
- `push`・`pull` の「アップロードしました」などの表示は、メタ情報の同期が終わってから出るようになった
- セーブの同期がエラーなく終わった後（見送り・成功した Push・Pull）は、メタ情報の同期の前に tombstone を確かめない。判定の後に別の PC がゲームを削除すると、メタ情報をリモートに戻す。移す前の CLI にもあった問題で、8-M5 の実装（#168）で塞ぐ
