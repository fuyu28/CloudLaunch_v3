# transfer-progress

- 日時: 2026-11-16 20:29 (JST)

## 当初の要求 / 背景

GUI では、承認した Push・Pull の進捗を、ゲームのカードと画面下の帯に出す（#140 の決めたこと 5、#141）。そのために、syncore が転送の進捗を呼び出し側に知らせる仕組みが要る。

AGENTS.md の「構成」は、並列実行を呼び出す側のコアが `errgroup` で制御し、進捗は直列化したコールバックで通知すると決めている。転送は 8 並列で行う。

GUI の試作（#113、`docs/adr/2026-11-15_01-56_gui-svelte-wails3.md`）では、Go から Wails の型つきのイベントで進捗の割合を送り、Svelte で表示した。

仕様書は進捗を扱わない。セーブの大きさは数十 MB 程度を想定する（仕様書 1 章「想定するセーブの大きさ」）。

## 仕様

- 進捗を知らせる処理
- 進捗の粒度
- 全体の数え方
- 知らせる値
- コールバックの渡し方
- 呼ぶ時機
- 呼び方の約束
- 遅いコールバックへの備え
- 転送の後の処理
- CLI の扱い

## 決定事項

### 進捗を知らせる処理

- 事項: どの処理の進捗を知らせるか
- 決定内容: syncore の Push のアップロード（`uploadMissing`）と、Pull のダウンロード（`downloadAll`）だけにする。ハッシュの計算（Status・転送の後の確かめ）、バックアップのコピー（Pull の手順 9・削除の 8-X4）、metasync のメタ情報の同期は対象にしない
- 判断理由: 数十 MB のセーブで目に見えて時間がかかるのは、ネットワーク越しの転送である。ほかは手元のディスクの処理か、10 MiB までの画像と小さい JSON の転送である。必要になったら、同じ形のコールバックを足せる

### 進捗の粒度

- 事項: どの区切りで知らせるか
- 決定内容: object を 1 つ転送し終えるごとに知らせる。転送の途中のバイト数は数えない
- 判断理由: Push は object をメモリに読んでから PUT し、失敗すると SDK が送り直す。読み書きした量を数える形では、送り直しのたびに数え直しになり、正しい値を出すには SDK の中の動きに頼ることになる。8 並列で転送し、セーブは数十 MB 程度なので、ファイルごとの区切りで足りる。大きいファイルが 1 つだけのゲームでは、そのファイルを送る間、進捗が止まって見える。これは受け入れる

### 全体の数え方

- 事項: 全体の数に何を数えるか
- 決定内容: 実際に PUT・GET する object の数と、そのバイト数にする。Push では、リモートにある object と、中身が同じで重複するファイルを数えない
- 判断理由: 送らないものを全体に入れると、最初から何割か済んだように見え、残りの時間の目安にならない

### 知らせる値

- 事項: コールバックに渡す値
- 決定内容: `Progress{FilesDone, FilesTotal int; BytesDone, BytesTotal int64}` にする。転送の向きは入れない
- 判断理由: 向きは、Push・Pull のどちらを呼んだかで呼び出し側が分かっている

### コールバックの渡し方

- 事項: コールバックをどこで渡すか
- 決定内容: `PushOptions`・`PullOptions` に `Progress func(Progress)` を持たせ、操作ごとに渡す。nil なら呼ばない。`PushOptions`・`PullOptions` は、上書き（7 章）のファイルから push.go・pull.go に移す。上書きと関係のない進捗の約束が 7 章のファイルに入らないようにするため
- 判断理由: GUI は進捗をゲームのカードごとに出す。操作ごとに渡せば、呼び出し側が、どのゲームの進捗かを自分で結びつけられる。`Config` に 1 つ持たせる案は、呼び出し側がゲーム ID で振り分けることになるので採らない

### 呼ぶ時機

- 事項: いつ呼ぶか
- 決定内容: 転送を始める前に、全体の数（済んだ分は 0）を 1 回知らせる。その後は、object を 1 つ転送し終えるごとに知らせる。転送するものがないとき（全部がリモートにある、上書きで local と remote が同じ（7-O5）、など）は、0/0 で 1 回だけ知らせる。転送の前に失敗したとき（同期ロック、リモートの一覧、stage の作成など）と、ctx がもう終わっているときは、1 回も呼ばない
- 判断理由: 最初に全体を知らせると、GUI が最初から全体の大きさを出せる。転送するものがないときも 1 回呼ぶと、成功する Push・Pull では、GUI は「進捗が来ない」場合を別に扱わずに済む。転送の前の失敗では進捗が来ないまま Push・Pull がエラーを返すので、GUI は戻り値で失敗を扱う

### 呼び方の約束

- 事項: コールバックをどう呼ぶか
- 決定内容: コアは、転送の goroutine の中から、ロックで直列にして呼ぶ（同時に 2 つ呼ばない）。コールバックには、すぐ戻ることを求め、`Progress` のフィールドのドキュメントに書く。呼んでいる間は、ほかの転送も、Push・Pull がエラーやキャンセルで戻るのも待つことも書く。失敗・キャンセルの後は呼ばない。済んだ分には、成功した object だけを数える。失敗・キャンセルの後に成功した object は、数えも知らせもしない。失敗の後かどうかは、errgroup の ctx ではなく、転送が失敗した goroutine がエラーを返す前にロックの中で立てる印で決める。キャンセルの後かどうかは、呼び出し側から渡された ctx で決める
- 判断理由: 直列に呼べば、呼び出し側は同時に呼ばれることを考えずに済む（AGENTS.md の「構成」）。直列に呼ぶ間はほかの転送が待つので、コールバックが長く戻らないと転送全体が遅くなる。失敗は Push・Pull の戻り値で伝わるので、失敗の後に進捗を知らせる必要はない。errgroup が自分の ctx を終わらせるのは、失敗した関数が戻った後なので、errgroup の ctx を見て止める作りでは、その間に成功したほかの転送が知らせてしまう。呼び出し側から渡された ctx は、ほかの転送の失敗では終わらないので、キャンセルの後かどうかを決めるのに使える。失敗の印だけを見る作りでは、転送を始めた後にキャンセルしても、その後に成功した転送が知らせてしまう

### 遅いコールバックへの備え

- 事項: コールバックが遅いときに転送を待たせない仕組みを、今作るか
- 決定内容: 作らない。コールバックを呼ぶ専用の goroutine を立て、転送の側は最新の値を置くだけにする形は、#141 で Wails のイベント送信がフロントの処理を待つと分かったときに、コアの中だけで替える
- 判断理由: 呼ぶ回数はセーブのファイルの数だけで、object 1 つの転送はネットワークの往復だけで数十ミリ秒以上かかる。イベントを送って戻るだけのコールバックなら、待たされる時間は転送の時間に比べて無視できる。専用の goroutine の形は、最後の値を渡し終えてから Push を戻す待ち合わせと、値を飛ばす振る舞いのテストが要り、30〜50 行ほど増える。コールバックの形（`Progress func(Progress)`）はどちらの作りでも同じなので、後から替えても呼び出し側は変わらない

### 転送の後の処理

- 事項: 全部済んだと知らせた後にも処理が続くことの扱い
- 決定内容: 受け入れる。Push は全部の object を送った後にも、ハッシュの計算し直し（5-P3）と manifest・HEAD の PUT を行う。Pull は全部を取得した後にも、stage の照合と入れ替えを行う。100% を知らせても、すぐには Push・Pull が戻らない
- 判断理由: 転送の後の処理は、ローカルの計算と小さい PUT・リネームで短い。GUI での見せ方（100% から戻るまでの表示）は #141 で決める

### CLI の扱い

- 事項: CLI に進捗を出すか
- 決定内容: 出さない。CLI は `Progress` を渡さない
- 判断理由: セーブは数十 MB 程度で、CLI では進捗がなくても困らない。v1 の CLI は同期コアを確かめる道具で、ゲームの管理は GUI で行う（AGENTS.md の「構成」）

### テスト

- 事項: 何をどう検査するか
- 決定内容: 次の 7 ケースにする。ケース名は「5章/Push/…」「6章/Pull/…」「7章/上書き/…」の形にする
  - Push: リモートにない object だけを全体に数え、最初の 1 回と object ごとに知らせる
  - Push: 転送するものがないときは、0/0 で 1 回だけ知らせる
  - Pull: 取得する object を全体に数え、最初の 1 回と object ごとに知らせる
  - Push の途中で PUT が失敗したら、失敗の後は知らせない。2 つの object の片方を、もう片方が PUT に入った後に失敗させ、もう片方は失敗の後に成功させる
  - Pull の GET が始まった後に呼び出し側がキャンセルしたら、その GET が成功しても知らせない
  - コールバックが同時に 2 つ呼ばれない
  - 上書きで local と remote が同じとき（7-O5）は、Push・Pull とも 0/0 で 1 回だけ知らせる
- 判断理由: 進捗は仕様書の項目ではないので、通る操作の章と項目をケース名に使う（AGENTS.md のケース名の規則）。並列の順は決まらないので、object ごとの呼び出しは、回数と、済んだ分が減らずに 1 つずつ増えて最後に全体と一致することで確かめる。失敗のケースで object を 1 つにすると、失敗の後に成功する転送がないので、約束の中心である並列の転送の振る舞いを確かめられない。ただし、失敗してから errgroup が ctx を終わらせるまでの短い間に成功が重なる場合は、テストから狙って起こせない

## 結果 / 影響

- syncore の Push・Pull が、`PushOptions`・`PullOptions` の `Progress` で転送の進捗を知らせるようになった。GUI（#141）は、このコールバックを Wails のイベントにつなげばよい
- CLI は `Progress` を渡さないので、振る舞いは変わらない
- 受け入れの条件の 7 ケースは、ロック・失敗の印・呼び出し側の ctx の確かめを 1 つずつ外すと、それぞれに当たるケースが失敗する
- 残る課題: コールバックが長く戻らないと、転送も、Push・Pull がエラーやキャンセルで戻るのも遅れる。#141 で Wails のイベント送信がフロントの処理を待つと分かったら、専用の goroutine で呼ぶ形に、コアの中だけで替える
- 見込みとの差: 差分は本番 +128 −21、テスト +215（ADR を除く）で、見込みの 150〜200 行に対して約 360 行になった。レビューで、errgroup の ctx を見る作りでは失敗の後にも知らせてしまうことが分かり、失敗の印とキャンセルの確かめを足した。テストも、失敗とキャンセルが並列の転送と重なる場合と、7-O5 の場合を足して 7 ケースになり、見込みの 2 倍に近くなった
