# no-hash-cache

- 日時: 2026-11-07 23:24 (JST)

## 当初の要求 / 背景

仕様書 3 章は、`(gameId, path)` ごとに size・mtime・sha256 を持つハッシュキャッシュを決めていた。size と mtime が一致するファイルは sha256 を計算し直さない。M1 では使わずに M2 に回し（2026-10-27_03-07_manifest-and-status.md「ハッシュキャッシュ」）、表だけを最初の migration に入れていた（2026-10-23_00-53_store-and-game-add.md「最初の migration に入れる表」）。

#28 で、キャッシュの使い方を仕様書に足し（#70）、実装した（#71）。実装には、計算の直後に書き換わったファイルを見落とさないための 2 秒の規則、古いかもしれない行を消す条件、読み書きに失敗したときの扱いが要り、約 800 行になった。また、size と mtime を保ったまま中身が変わったファイルを見落とすので、キャッシュを消して計算し直させる手段（CLI の `--rehash`）も要った。

その後、実際のゲームのセーブフォルダの大きさを確かめた。想定するゲーム（ノベルゲームなど）のセーブフォルダには、ゲームのシステムファイルと、セーブごとの場面のスクリーンショットしか入らず、クリアまで遊んでも 50MB 程度だった。

## 仕様

- ハッシュキャッシュを持つか
- 最初の migration にある `hash_cache` の表の扱い
- テーブル定義の正とするもの

## 決定事項

### ハッシュキャッシュを持つか

- 事項: local の manifest の計算で、ファイルの sha256 のキャッシュを持つか
- 決定内容: 持たない。local の manifest は、計算のたびにセーブフォルダの全ファイルを読む。仕様書 3 章からハッシュキャッシュの項目を消し、持たないことと理由を書く。#71 はマージせずに閉じ、#28 は作らないこととして閉じる
- 判断理由: 50MB（256KB × 200 ファイル）を全部読んで sha256 を計算すると、OS のファイルキャッシュに載った状態で約 0.06 秒だった。ディスクから読む場合は測っていないが、SSD なら 0.1〜0.2 秒程度、HDD でも 1 秒に満たないと見込む。判定では R2 から HEAD と manifest を読むのに約 0.3 秒かかる。Push はセーブフォルダを、判定・承認後の確かめ（5-P3）・アップロード中の計算（アップロードするファイルだけ）で読むので、キャッシュで縮むのは、そのうち判定と承認後の確かめの分である。縮む時間に比べて、#71 の実装の複雑さと、キャッシュを使う限り生まれる見落としのほうが大きい。数 GB のセーブを扱うことになったら、#71 のブランチ（`feat/hash-cache`）を出発点に作り直せる

### 最初の migration にある `hash_cache` の表の扱い

- 事項: 一度も読み書きしていない `hash_cache` の表を残すか
- 決定内容: 新しい migration（`00002_drop_hash_cache.sql`）で消す。down では元の表を作り直す
- 判断理由: 使わない表が残ると、テーブル定義を読む人が、キャッシュを持つと誤解する。表は一度も読み書きしていないので、行を移す必要はない

### テーブル定義の正とするもの

- 事項: 仕様書 3 章の「テーブル定義は最初の migration の SQL を正とする」をどうするか
- 決定内容: 「migration の SQL を順にすべて適用した結果を正とする」に改める
- 判断理由: 表を消す migration を足すので、最初の migration だけでは今のテーブル定義を表さなくなる

## 結果 / 影響

- 判定・承認後の確かめは、これまでどおり全ファイルを読む。数十 MB のセーブフォルダでは、リモートの読み込みより短い
- size と mtime を保ったまま中身が変わったファイルを見落とすことはない。`--rehash` のような逃げ道も要らない
- 次の ADR の決定と見込みを、この ADR で置き換えた: 2026-10-23_00-53_store-and-game-add.md（最初の migration に入れる表）、2026-10-27_03-07_manifest-and-status.md（ハッシュキャッシュを M2 に回す）、2026-11-04_15-45_push-rehash-local.md（#28 で読まずに済むようになる見込み）、2026-11-07_19-28_overwrite.md（キャッシュで中身だけが壊れた local を「同じ」と判定する問題を #28 で扱う）。テーブル定義の正の書き方は、2026-10-23_00-30_db-migration-goose.md と 2026-10-23_00-53_store-and-game-add.md の背景の記述を置き換えた
- #71 のブランチの CLI で開いたことのある DB には、#71 の `00002`（`hash_cache` の作り直し）が適用済みなので、`00002_drop_hash_cache.sql` は適用されず、`hash_cache` が残る。使わない表なので害はない。#71 は dev に入っていないので、CI と新しい DB には関係しない
