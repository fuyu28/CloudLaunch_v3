# ADR の書き方

ADR（Architecture Decision Record）は、意思決定の結論と、そこに至った根拠を残す文書である。後から「なぜこの設計や技術にしたのか」を追えるようにし、再検討するときに、当時の前提・制約・却下した案を判断材料として使えるようにする。

## いつ書くか

機能の追加・機能の変更・バグの修正では、ADR を書く。これらの作業の中では、決定の大小や巻き戻しやすさで対象を絞らない。作業中に行った意思決定の経緯を残すことが目的だからである。

設定・リンタ・CI・文書だけの変更では ADR を書かず、決定の理由は PR の説明に書く。

ADR は作業の進み具合に合わせて 3 回手を入れる。

1. 作業を始める前に、背景・仕様・決定事項（決定ごとの決定内容と判断理由）を書いて作る
2. 作業の途中で決定が変わったり、新しい決定が必要になったりしたら、その都度本文を直し、更新履歴に追記する
3. 作業が終わったら、実際の結果を「結果 / 影響」に書く。当初の見込みとずれた点があれば、その差も書く

## Issue との分担

ADR を書く作業では、GitHub Issue も作る。Issue には作業の管理に関わることを書き、同じことを ADR には書かない。

- Issue: 参照する ADR のファイル名、受け入れの条件（テストのケース名の一覧）、範囲外にすること、見込みの行数
- ADR: 何をどう決めたかとその根拠。置く場所・公開 API の形・採用するライブラリなど、実装の設計の決定も含む

ADR は作業の PR に含め、PR には `Closes #番号` を書く。

## 文書の構成

ADR は本文と更新履歴からなる。

- 本文: 「当初の要求 / 背景」「仕様」「決定事項」「結果 / 影響」の 4 節。意思決定の記録の実体であり、この文書で「ADR の内容」と言うときは本文を指す
- 更新履歴: 本文をいつ、なぜ変えたかを記すメタ情報。意思決定の記録そのものではない

## 本文の書き方

ADR は、意思決定をする側の視点で書く。作業を手伝うエージェントは道具であり、エージェントの視点や作業セッションの出来事は ADR の内容にならない。

- 決定・指示・指摘の主体（「ユーザー」「依頼者」「レビュアー」「Copilot」など）を書かない。ADR の書き手が決定者なので、決定者を三人称で書く必要がない。この規則は更新履歴にも適用する
  - 書かない例: 「判断理由: ユーザー指示による」「ユーザー判断で対応不要とした」「Copilot のレビュー指摘を反映」
- 作業セッションの出来事（指示や指摘を受けた、実装した、テストを実行した、レビューに対応した）を書かない。判断理由には、決定が妥当である根拠（制約、仕様、実測値、ログ、調査結果、関連する ADR や PR）を書く
- 指示や指摘は根拠ではなく、根拠が伝わってきた経路である。その内容から根拠を取り出して書く。根拠が示されない指示は確認し、確認できなければ「判断理由: 根拠未確認」と書き、推測で補わない
- 決定が変わったら、変わった後の決定とその根拠を書く。「当初は X としたが Y に変えた」と書くのは、X が劣ると判断した根拠を添えられる場合に限る。指摘やレビューがあったことは、きっかけであって根拠ではない
- テストの実行結果や作業手順を並べない

## 更新履歴の書き方

更新履歴は本文の変更記録であり、本文の書き方の規則は、主体を書かないことを除いて適用しない。

- 何を、なぜ変えたかを書く。「なぜ」には変えた後の決定の根拠を書き、きっかけだけで済ませない
- きっかけ（レビューで指摘されたこと、など）は書いてもよい。ただし主体は書かない（「レビュー指摘の反映」は可、「Copilot のレビュー指摘を反映」は不可）

## 過去の決定を覆すとき

別の作業で過去の ADR の決定を変えるときは、新しい作業の ADR に新しい決定とその根拠を書き、古い ADR のファイル名を参照する。古い ADR の本文は書き換えず、更新履歴に「{新しい ADR のファイル名} で置き換え」と追記する。本文を残しておけば、当時の前提と、それを覆した根拠の両方を追える。

## 置き場所とファイル名

ADR は `docs/adr/` に置き、コミットする。ファイル名は連番ではなく、作成した日時とタイトルにする。

```
%Y-%m-%d_%H-%M_{title}.md
```

- 日時は strftime の書式で、`%Y` が年 4 桁、`%m` が月 2 桁、`%d` が日 2 桁、`%H` が 24 時間制の時 2 桁、`%M` が分 2 桁である（月の `%m` と分の `%M` は大文字と小文字で区別する）
- 日付の中と時刻の中はハイフンで、日付と時刻の間と、時刻とタイトルの間はアンダースコアで区切る
- 日時には作成した時刻の実際の値を、Asia/Tokyo（JST）で使う。推測で書かず、`TZ=Asia/Tokyo date '+%Y-%m-%d_%H-%M'` などのコマンドで取得する
- タイトルは短い句にし、スペースを入れない。区切りが要るときはハイフンを使う

本文中の日時も JST で書く。

## テンプレート

```markdown
# {title}

- 日時: %Y-%m-%d %H:%M (JST)

## 当初の要求 / 背景

意思決定が必要になった経緯、解決したい課題、制約と前提を書く。

## 仕様

当初の要求から導かれる、決める必要のある事項を挙げる。要求全体に対して何を決めるかの見取り図にあたり、個々の決定内容はここに書かない。決定事項の節は、ここで挙げた事項ごとの決定として展開する。

## 決定事項

仕様の節で挙げた事項ごとに見出しを立て、次の 3 つを書く。決定の理由は独立した節にせず、各決定の判断理由に含める。

### {決定の見出し}

- 事項: 何についての決定か
- 決定内容: 採用した結論を断定の形で書く
- 判断理由: その結論にした根拠と、参照した情報・前提。却下した案があれば、却下した理由も書く。主体や作業の経過は書かない

## 結果 / 影響

決定によって生じる良い影響・悪い影響・トレードオフ・残る課題を書く。作業が終わったら、当初の見込みと実際の結果のずれを追記する。

## 更新履歴

- %Y-%m-%d %H:%M 何を、なぜ変えたか
```
