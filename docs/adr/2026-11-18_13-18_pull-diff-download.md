# pull-diff-download

- 日時: 2026-11-18 13:18 (JST)

## 当初の要求 / 背景

仕様書 6-L4 は、stage に manifest の全ファイルを置く。これまでの Pull は全ファイルをリモートから取得していたので、差分が小さくても remote のセーブ全体を転送していた。一方、7 章「確認ダイアログに出す情報」の「転送するサイズ」（`syncore.Plan.Changes` の `Bytes`）は追加と変更のファイルの大きさの合計で、ダウンロードの向きでは実際の転送量より小さく出ていた（#173）。

仕様書は #175 で次のように変わった。

- 6-L4: live に同じ中身のあるファイルは live からコピーし、残りだけをリモートから取得する
- 6-F1: mtime を `createdAt` にする対象に、コピーしたファイルも含める
- 6-F2: コピーの元は、承認した時点の local の manifest から sha256 だけで照合する。live にない object は sha256 ごとに 1 回だけ取得し、同じ sha256 のほかのエントリには stage の中でコピーする。ハードリンクにはしない
- 6-F3: コピーの元が承認の後に書き換わっていても手順 4 では確かめず、手順 5 の検証で中止する。コピーに失敗したら、取得に切り替えずに中止する（6-A1）
- 7 章: ダウンロードの「転送するサイズ」は、local にない sha256 ごとの大きさの合計で、同じ sha256 は 1 回だけ数える

進捗（`syncore.Progress`）は、全体にも済んだ分にも、実際に PUT・GET する object だけを数える約束である（`docs/adr/2026-11-16_20-29_transfer-progress.md`）。

## 決定事項

### コピーの元の引き当て方

- 事項: manifest のエントリごとに、live のどのファイルをコピーの元にするか
- 決定内容: plan の `Local.Entries`（承認した時点の local の manifest）から、sha256 → path の対応を作る。同じ sha256 のファイルが live に複数あれば、`Local.Entries` の順で最初のものを使う。Pull の中で live をハッシュし直してコピーの元を選ぶことはしない
- 判断理由: 6-F2 は「承認した時点の local の manifest」から照合すると定めている。中身が同じならどのファイルをコピーしても結果は同じで、`Local.Entries` は path の昇順に並ぶので、選び方が実行ごとに変わらない。Pull の中で live をハッシュし直すと、セーブフォルダ全体を余分に読むことになり、承認した時点と違う中身を元にする余地も生まれる。承認の後の変化は 6-L5・6-L6 が見つける（6-F3）

### stage を組み立てる順

- 事項: 取得とコピーをどの順で行うか
- 決定内容: 先に、live にない sha256 の object を、sha256 ごとに 1 回だけ、その sha256 の最初のエントリの path に取得する。取得は今の `downloadAll` と同じく 8 並列で行う。取得がすべて終わってから、残りのエントリを順にコピーする。コピーの元は、live にある sha256 なら live のファイル、そうでなければ stage に取得したファイルにする。コピーは並列にしない
- 判断理由: 取得を先に済ませると、残りのエントリはどれも「コピーの元のファイルから stage へ複製する」1 つの形で扱える。コピーを先にする案は、live の変化をネットワークの転送の前に見つけられるが、stage の中のコピーは取得の後にしかできないので、コピーが 2 回に分かれる。live が承認の後に変わるのはまれで、そのときに取得が無駄になっても数十 MB 程度である（仕様書 1 章「想定するセーブの大きさ」）。コピーは手元のディスクの処理で、数十 MB なら並列にしなくても転送に比べて短い。並列にすると、取得したファイルのコピーを、取得が終わるまで待たせる仕組みが要る

### コピーの書き方

- 事項: コピーをどう書き、失敗をどう扱うか
- 決定内容: コピーの元を開いて読み、取得と同じ関数（`writeStageFile`）で stage に書く。これにより、mtime を `createdAt` にすること（6-F1）と、ディスクへの書き出し（6-L4）を、取得したファイルと同じ処理で行う。コピーの途中では sha256 を計算せず、コピーの元がリンクに変わっていないかも確かめない。新しいセンチネルエラーは足さない
- 判断理由: 取得とコピーで書き方を分けると、mtime と書き出しの扱いが食い違うおそれがある。sha256 を確かめないのは 6-F3 のとおりで、6-L5 が stage 全体の manifest ハッシュを比べる。コピーの元が承認の後にリンクに変わっていれば、リンク先を読むことになるが、中身が違えば 6-L5 で、同じでも 6-L6 の local の計算（通常のファイル以外を拒否する、2 章）で止まるので、セーブは壊れない。承認の後にセーブフォルダをリンクに替えることはまれで、そのために開き方を変えるほどではない

### 手順 4・5 で止まったときのエラー

- 事項: live が承認の後に変わったために手順 4・5 で止まったとき（6-F3）、呼び出し側に何を返すか
- 決定内容: 手順 4・5 のどこかで失敗したら、live をハッシュし直し、承認した時点から変わっていれば、元のエラーに `ErrPlanStale` を `errors.Join` で足して返す。変わっていなければ、元のエラーだけを返す
- 判断理由: 仕様書 7 章は、承認してから実行するまでに local のハッシュが変わっていれば、中止して確認し直すと定めている。live が変わったときは、これまで 6-L6 で `ErrPlanStale` になり、GUI と CLI は確認し直すよう案内していた。コピーで手順 4・5 に止まる場所が早まっても、同じ案内を出すためである。Push も、承認の後にファイルが変わったときは `ErrPlanStale` にしている（5-P3）。ハッシュし直すのは失敗したときだけなので、成功する Pull は遅くならない

### 進捗の数え方

- 事項: Pull の進捗の全体と済んだ分に、何を数えるか
- 決定内容: 全体には、取得する object（live にない sha256 ごとに 1 つ）の数と、その大きさの合計を数える。済んだ分には、取得に成功した object だけを数える。コピーは数えず、知らせもしない。live にある中身だけで組み立てられるとき（取得する object がないとき）は、Push と同じく 0/0 で 1 回だけ知らせる
- 判断理由: `docs/adr/2026-11-16_20-29_transfer-progress.md` の「全体の数え方」の約束（実際に PUT・GET する object だけを数える）のままである。これで、確認ダイアログの「転送するサイズ」と進捗の全体のバイト数が一致する。コピーは数十 MB 程度の手元のディスクの処理なので、進捗に出さなくても止まって見える時間は短い

### 「転送するサイズ」の数え方

- 事項: `Plan.Changes` の `Bytes` をどう数えるか
- 決定内容: ダウンロードの向きでは、remote の entries のうち、sha256 が local の entries にないものの大きさを、sha256 ごとに 1 回だけ足す。アップロードの向きは変えず、追加と変更のファイルの大きさの合計のままにする。追加・変更・削除の数は、どちらの向きも path で数えるままにする。`Changes` の型と GUI（`cmd/cloudlaunch-gui/dialog.go`）は変えない
- 判断理由: 仕様書 7 章のとおりで、ダウンロードの `Bytes` が、Pull が実際に取得する量と、進捗の全体のバイト数に一致する。アップロードは #173 で範囲外にした（7 章では上限として扱う）。GUI は `Bytes` をそのまま出しているので、値の意味が変わるだけで、型とバインディングは変わらない

### テスト

- 事項: 何をどう検査するか
- 決定内容: 受け入れの条件は Issue #173 に挙げる。取得したかどうかは、偽のリモートの `Before` で object の GET を数えて確かめる。コピーしたことは、remote にその object を置かずに Pull が成功することでも確かめる。6-F3 の 2 ケースは、`ErrPlanStale` を返し、stage とジャーナルが消えることを確かめる。6-F1 のケースは、live からコピーしたファイルと、取得したファイルから stage の中でコピーしたファイルの両方の mtime を確かめる。既存の「7章/確認ダイアログ/転送するサイズは、追加と変更のファイルの大きさの合計にする」は、アップロードの向きのケースに名前と中身を絞る
- 判断理由: remote に object を置かない形だけでは、取得の回数（6-F2 の「sha256 ごとに 1 回だけ」）を確かめられない。6-F3 のケースは、手順 5 と手順 6 のどちらで止まったかを区別しない。どちらで止まっても、返すエラーと片付けの結果が同じになるようにしたためである（「手順 4・5 で止まったときのエラー」）。stage の中のコピーは live からのコピーと別の道筋なので、mtime を合わせ忘れても live からのケースだけでは見つからない
