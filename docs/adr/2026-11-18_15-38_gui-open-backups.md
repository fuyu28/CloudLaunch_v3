# gui-open-backups

- 日時: 2026-11-18 15:38 (JST)

## 当初の要求 / 背景

ローカルのバックアップは、Pull で退避したセーブ（仕様書 3 章、6-L9）と、ゲームをリモートから削除するときのコピー（8-X4）で作る。置き場所は `%LOCALAPPDATA%\CloudLaunch\backups\{gameId}\{UTC 日時}-{opId}\` で、ゲームごとに直近 3 個を残す。バックアップから戻す手順は仕様書になく、今は利用者がこの場所を自分で探してコピーするしかない（#130）。

M4 の計画（#140）は、v1 ではバックアップのフォルダを GUI から開けるようにして手で戻せるようにし、アプリの操作で戻すことは後に回すと決めている（#131）。

手で戻しても、同期の状態は壊れない。バックアップをセーブフォルダへ写すと local が base と異なるので、判定表（4 章）の「ローカルが変化 → Push」（4-D7）か競合の行に当たり、7 章の確認を通ってから Push される。そのため仕様書は変えない。

今の GUI には、ゲームごとの画面がなく、一覧のゲームのカード（タイトル・ブランド・確認ボタン・状態）だけがある（`docs/adr/2026-11-17_01-30_gui-skeleton.md`）。Wails v3 には、OS のファイルマネージャーでフォルダを開く `Env.OpenFileManager` がある。バックアップの置き場所を組み立てる関数は、syncore の非公開の `backupDir` だけである。

## 決定事項

### 操作を置く場所

- 事項: フォルダを開く操作を、画面のどこに置くか
- 決定内容: 一覧のゲームのカードの、「確認」ボタンの隣に「バックアップ」ボタンを置く。確認中・転送中も押せるようにする
- 判断理由: ゲームごとの画面はまだなく、置ける場所はカードだけである。#144（登録・編集）でゲームの画面ができたら、そちらへ移すかをそのときに決める。フォルダを開くだけで、セーブにも同期の状態にも触れないので、確認中・転送中に押しても困らない

### 開くフォルダ

- 事項: どのフォルダを開くか
- 決定内容: ゲームのバックアップのフォルダ（`{BackupsDir}/{gameId}`）を開く。個々のバックアップのフォルダは開かず、選んだ状態にもしない
- 判断理由: 中に `{UTC 日時}-{opId}` のフォルダが最大 3 つ並ぶので、利用者が日時で選べる。最新のバックアップを開く案は、戻したいのが 1 つ前とは限らないので採らない

### バックアップがないとき

- 事項: ゲームのバックアップのフォルダがないときの扱い
- 決定内容: ボタンはいつも出す。押したときにフォルダがなければ、開かずに、カードに「バックアップはまだありません。Pull で上書きする前のセーブが、ここに残ります」と出す。フォルダがあれば、中が空でも開く
- 判断理由: 一覧を読む時点で調べてボタンを無効にする案は、ゲームの数だけフォルダを調べることになり、押したときに調べれば足りる。バックアップは一度作れば直近 3 個が残り、0 個に減らす操作はないので、フォルダがあって中が空になることはまれで、開いても害はない

### 戻し方の案内

- 事項: 戻し方をどこに、どう書くか
- 決定内容: フォルダを開いたときに、カードの状態の行へ「戻すときは、ゲームを終了してから、戻したいバックアップの中身をセーブフォルダへ写し、『確認』を押してください。アップロードの確認が出ます」と出す。README には書かない
- 判断理由: 利用者向けの README は今なく、フォルダを開くその場で出すのが一番目に入る。手で戻した後は 4-D7 か競合に当たり、確認を通って Push されるので、「確認」を押すよう案内すれば足りる

### バックアップのフォルダのパスの組み立て

- 事項: ゲームのバックアップのフォルダのパスを、どこで組み立てるか
- 決定内容: syncore に `(*Core).BackupDir(gameID string) (string, error)` を足し、GUI はそれを使う。`Config.BackupsDir` が空ならエラーを返す。フォルダは作らない
- 判断理由: 置き場所の形（仕様書 3 章）はコアが持つ決まりで、GUI で `filepath.Join(dir, "backups", gameID)` と組み立て直すと、形が 2 か所に分かれる（AGENTS.md の「構成」）。#131 でアプリから戻す操作を作るときも、同じ関数を使える。空の `BackupsDir` のまま Join すると作業ディレクトリの下を指すので、既存の `makeBackupDir` と同じくエラーにする。フォルダを作らないのは、「まだない」を GUI が見分けるためである

### GUI の配線

- 事項: フロントから呼ぶ口と、結果の渡し方
- 決定内容: `cmd/cloudlaunch-gui/` に、syncore のコアを持つ `BackupService` を足し、`OpenBackups(gameID string) (string, error)` を公開する。フォルダがあれば `Env.OpenFileManager(dir, false)` で開いて案内の文を、なければ「まだありません」の文を返す。開けなかったときはエラーを返す。フロントは、返った文をカードの状態の行に、エラーをカードのエラーの行に出す。CLI は変えない
- 判断理由: 表示の文言は Go で決め、Svelte は受け取ったものを出すだけにする（AGENTS.md の「作る順番」）。一覧の組み立て（`HomeService`）と確認・転送（`SyncService`）のどちらとも責務が違うので、サービスを分ける。CLI は、ゲームの削除の後にバックアップの場所を出しており、#130 の範囲外である

### テスト

- 事項: 何をどう検査するか
- 決定内容: syncore の `BackupDir` に、次の 2 ケースを書く。GUI の配線にはテストを書かない
  - Pull で作ったバックアップが、`BackupDir` の返すフォルダの中にある
  - `BackupsDir` が空なら、エラーを返す
- 判断理由: syncore は TDD で書く（AGENTS.md の「テスト」）。Pull のバックアップの中にあることを確かめれば、置き場所の形が `backupDir` と食い違わないことを、公開 API から確かめられる。UI と Wails の配線にはテストを書かない
