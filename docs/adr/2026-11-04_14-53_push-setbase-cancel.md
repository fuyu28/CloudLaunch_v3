## 当初の要求 / 背景

Push は、手順 6（5-P6）で HEAD を PUT した後、手順 7（5-P7）で base を更新する。dev のコード全体のレビューで、base の更新が呼び出し側の ctx で行われていると分かった。HEAD を書いた直後にキャンセルされると、base の更新が失敗し、リモートは更新済みなのに Push が失敗と伝わる。

残った状態は、仕様書 5 章の「6 と 7 の間で中断した」（5-I2）に当たる。次の判定が「B / 変化 / 変化（local と同じ）」の行になり、base は更新されるので、セーブは失われない。ただし、ユーザーはアップロードに失敗したと受け取る。

Pull では同じ理由で、live を入れ替えた後の手順をキャンセルの効かない ctx で行うと決めた（2026-11-04_11-27_pull-backup-and-recover.md「ジャーナルの削除と、入れ替えの後の ctx」）。

## 仕様

- HEAD を書いた後の ctx

## 決定事項

### HEAD を書いた後の ctx

- 事項: 手順 6 の HEAD の PUT と、その後の base の更新を、どの ctx で行うか
- 決定内容: 手順 5 で HEAD を読み直して変わっていないと確かめた後は、HEAD の PUT から `context.WithoutCancel(ctx)` で行う。手順 8（古い世代の削除と GC、#31）を作るときも、同じ ctx を使う
- 判断理由: HEAD を書いた時点で、リモートでは Push が終わっている。その後にキャンセルで止めると、成功した Push を失敗と伝える。PUT の応答を待つ間にキャンセルされた場合も、リモートには HEAD が書けていることがあるので、PUT を始める時点から止めない。HEAD の PUT は世代 ID だけの小さな書き込みで、base の更新は DB への 1 回の書き込みである。DB が別の接続にロックされていても、待つのは `busy_timeout`（5 秒）までである。Pull の入れ替えの後と同じ扱いにそろえる

## 結果 / 影響

- HEAD を書く時点からキャンセルが効かないので、HEAD が書けたのに Push が失敗と伝わることはなくなった。その代わり、手順 5 を通った後は、R2 が応答しなくても SDK の再試行とタイムアウトが終わるまで取り消せない
- テストは、偽のリモートの Put が ctx を見ないことを使い、HEAD の PUT の直前にキャンセルして、HEAD と base が書けることを確かめる。本物のリモートで応答を待つ間にキャンセルされる場合は、テストでは再現していない
- CLI は ctx をキャンセルしないので、R2 を相手に CLI で確かめたのは、通常の Push が変わらず動くことだけである
- 「キャンセルされても最後まで進める」区切りは、Pull（`pull.go`）と Push の 2 か所にある。まとめるかは、M2 の終わりの `/simplify` で見る
- 行数は約 75 行（テスト約 25、本体約 5、ADR 約 45）で、見込みの約 80 行に収まった
