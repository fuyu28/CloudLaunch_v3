## 当初の要求 / 背景

仕様書 9 章「照合と取り込み」（9-K1〜9-K4）は、ゲームを登録するたびに、未紐付けの旧履歴と旧版のゲームのタイトルで照合し、確認を取ってから通常のプレイ履歴として取り込むとしている。取り込んだ履歴は、旧版のセッション ID のまま 8 章のとおり同期する。

前提は次のとおりである。

- 未紐付けの旧履歴は、2026-11-14_01-59_legacy-export-import.md で作った `legacy_sessions` に、旧版の gameId とタイトルとともに入っている。読み込み（9-L1〜9-L3）は `internal/legacy` の `Import` が持つ
- ゲームを登録する入口は、CLI の `game add` と、2026-11-14_02-46_remote-game-import.md で作った `game import`（8-N1〜8-N12）の 2 つである。後者の ADR は、9-K4 の照合を、この作業で両方の入口に足すとしている
- 通常のプレイ履歴は `play_sessions` に入り、8-S1 でローカルにだけあるセッションとして PUT される。取り込んだ履歴も同じ表に入れれば、同期の側を変えずにアップロードされる
- CLI は対話をせず、確認は `--overwrite` のようにコマンドとフラグで取る

## 決定事項

### 照合の入口

- 事項: 9-K4 の照合を、どの登録の入口で行うか
- 決定内容: `game add` と `game import` の両方で、登録が済んだ後に照合する。`game import` では、`ImportGame` が返したゲーム情報（登録の直前に読み直した game.json）のタイトルで照合する
- 判断理由: 9-K4 は、2 台目の PC での取り込みも照合の対象としている。照合は登録した後に DB だけを読む処理なので、入口がどちらでも同じ API を呼べば振る舞いが揃う。`game import` が登録するのは読み直した game.json のタイトルなので、一覧のときのタイトルではなく、それで照合する

### 公開 API の形

- 事項: legacy が何を公開し、store に何を求めるか
- 決定内容:
  - `Match(ctx, st, title string) (MatchResult, error)` を公開する。`MatchResult` は、提案する旧ゲーム（9-K1 で 1 件だけ一致したときだけ入る）と、旧ゲームの候補一覧（9-K2）を持つ。未紐付けの旧履歴がなければ、どちらも空になる
  - `Link(ctx, st, legacyGameID, gameID string) (LinkResult, error)` を公開する。`LinkResult` は、通常のプレイ履歴にした件数と、通常のプレイ履歴に同じ ID があったので取り込まずに消した件数を持つ
  - legacy の `Store` に、旧ゲームごとにまとめた一覧を返す `LegacyGames(ctx) ([]Game, error)` と、9-K3 を行う `LinkLegacySessions(ctx, legacyGameID, gameID string) (LinkResult, error)` を足す
  - 照合の比べ方と、提案するかどうかの判定は legacy に置き、トランザクションは store に置く
  - センチネルエラーは作らない
- 判断理由: 2026-11-14_01-59_legacy-export-import.md のとおり、9 章の規則は legacy で TDD の対象にし、2 つの表をまたぐ書き込みは store のトランザクションで行う。照合はタイトルの比べ方と件数で決まる規則なので、SQL に埋めずに legacy に置く。登録していないゲームの指定や DB の失敗で、呼び出し側が振る舞いを分ける必要はなく、CLI はエラーを出して終わるだけである。GUI で分ける必要が出たら M4 で足す

### 照合の比べ方

- 事項: 9-K4 の「前後の空白を除いた完全一致」の、空白の範囲と比べ方
- 決定内容: 旧ゲームのタイトルと v3 のゲーム名の両方に `strings.TrimSpace` をかけ、バイト列として完全に一致するものを一致とする。大文字小文字・全角半角・Unicode の正規化はそろえない。除いた後に空になるタイトルは、どれとも一致させない
- 判断理由: `strings.TrimSpace` は Unicode の空白（全角の空白を含む）を除くので、日本語のタイトルの前後に入りやすい全角の空白も除ける。仕様書は完全一致としているので、それ以上の正規化は入れない。正規化を入れると、別のゲームを提案する誤りが増え、9-K2 の候補一覧から選び直せば済む手間を減らすだけになる。空白だけのタイトルは、2026-11-14_01-59_legacy-export-import.md のとおり旧版が書きうるが、空同士を一致させると無関係なゲームを提案するので一致させない。そうした旧ゲームも 9-K2 の候補一覧から選べる

### 候補一覧の項目と並び

- 事項: 9-K2 の候補一覧に、旧ゲームごとに何を出し、どう並べるか
- 決定内容:
  - 旧版の gameId・タイトル・件数・合計時間（秒）・最後に遊んだ日時を出す
  - 旧ゲームは旧版の gameId でまとめる。同じ旧版の gameId で行ごとのタイトルが違うときは、`played_at` が最も新しい行のタイトルを、照合と表示に使う
  - タイトル順（同じなら旧版の gameId 順）に並べる
  - 件数は、通常のプレイ履歴に同じ ID がある行も含めて、未紐付けの旧履歴の行をそのまま数える
- 判断理由: 9-K2 は旧版の gameId で区別して選ばせるので、同名の旧ゲームを見分ける材料として、件数・合計時間・最後に遊んだ日時を出す。同じ旧版の gameId でタイトルが違う行は、旧版でタイトルを変えた後に別のエクスポートを読み込んだときにできる。新しいプレイ履歴を持つエクスポートほど新しいタイトルを持つので、最も新しい行のタイトルを使う。`played_at` は固定幅の形（3 章）で持つので、文字列の最大で最も新しい行を選べる。通常のプレイ履歴に同じ ID がある行は、読み込んだ後に別の PC が同じエクスポートを取り込んで同期したときにだけでき、9-K3 で取り込むときに消える。候補の段階で除くには 2 つの表を突き合わせる必要があり、まれな状態のために照合のたびに引く手間に見合わない。差は `Link` の結果で示す

### 1 件だけ一致したときに返すもの

- 事項: 9-K1 で提案するときに、候補一覧も返すか
- 決定内容: 提案と一緒に、候補一覧（提案した旧ゲームを含む全件）も返す
- 判断理由: 仕様書は、提案を断ったときにどうするかを書いていない。同名の旧ゲームが別物だったときに、断った後で一覧から別の旧ゲームを選べるようにする。API が返す情報を増やすだけで、提案するかどうかの規則（9-K1・9-K2）は変えない

### 取り込みのトランザクション

- 事項: 9-K3 を、store の 1 つのトランザクションでどう行うか
- 決定内容: 1 つのトランザクションで、次の順に行う
  1. `INSERT INTO play_sessions … SELECT … FROM legacy_sessions WHERE legacy_game_id = ? ON CONFLICT (id) DO NOTHING` で、選んだ旧ゲームの行を、指定した gameId の通常のプレイ履歴にする。入った件数を、通常のプレイ履歴にした件数とする
  2. `DELETE FROM legacy_sessions WHERE legacy_game_id = ?` で、選んだ旧ゲームの行をすべて消す。消した件数から 1 の件数を引いたものを、取り込まずに消した件数とする
  3. 指定した gameId が `games` になければ、エラーを返してロールバックする

  `legacy_sessions` の ID と日時は、入れるときに検証しているので、取り込むときには検証し直さない
- 判断理由: 9-K3 は、通常のプレイ履歴への追加と未紐付けの旧履歴からの削除を、1 つのトランザクションで行うことを求めている。`ON CONFLICT DO NOTHING` で入らなかった行は、別のゲームのものを含めて通常のプレイ履歴に同じ ID がある行であり、9-K3 のとおり取り込まずに消す。最初に書き込みを行うのは、WAL で読みから書き込みへの格上げが busy_timeout を待たずに失敗するのを避けるためである（`ImportSessions`・`AddLegacySessions` と同じ）。登録の確かめを最後にするのはこのためで、旧履歴がある場合は 1 の外部キーでも止まるが、旧履歴がない場合は 1 も 2 も何も書かないので、3 で確かめないと登録していない gameId が 0 件の結果として通ってしまう

### 取り込む時点の制限と、登録した後に読み込んだ旧履歴

- 事項: `Link` を、ゲームを登録した直後にだけ呼べるようにするか
- 決定内容: 呼べる時点を制限しない。登録済みのゲームならいつでも取り込める。「旧版のエクスポートを、ゲームを登録した後に読み込んだとき、登録済みのゲームと照合するか」を、仕様書 11 章「未決事項」に挙げる。11 章への追記は、振る舞いを変えない文書の変更として、この作業の PR に含める
- 判断理由: 9-K4 は「ゲームを登録するたびに」照合するとしているので、ゲームを先に登録してからエクスポートを読み込むと、そのゲームはどこでも照合されない。GUI では旧履歴を取り込む入口がなくなる。どの時点で照合し直すかは仕様書の判断であり、この作業では決めない。`Link` の時点を制限しなければ、仕様書がどう決めても API を変えずに済み、CLI の `legacy link` でいつでも取り込める

### 排他と、ゲームの tombstone の記録があるゲーム

- 事項: 取り込みで同期ロックを握るか。ゲームの実行中や、ゲームの tombstone の記録があるゲームへの取り込みを拒否するか
- 決定内容: 同期ロックは握らず、ゲームの実行中でも取り込める。DB にゲームの tombstone の記録があるゲームへの取り込みも拒否しない。登録していない gameId はエラーにする
- 判断理由: 取り込みは DB の 1 つのトランザクションだけで行い、セーブフォルダにもリモートにも触れない。同期ロック（3 章「排他」）が守るのはセーブフォルダとリモートの手順なので、握る理由がない。ゲームの tombstone の記録があるゲームのプレイ履歴は、8-M4 のとおり DB にだけ残り、上げ直せば新しい gameId の下にアップロードされる。取り込んだ履歴も同じ扱いになるので、拒否する理由がない

### 取り込む旧履歴がないとき

- 事項: 選んだ旧版の gameId に未紐付けの旧履歴が 1 件もないときに、エラーにするか
- 決定内容: エラーにせず、どちらの件数も 0 の結果を返す
- 判断理由: 取り込み済みの旧ゲームを選び直したときや、別のプロセスが先に取り込んだときに起きる。どちらも、望んだ状態（その旧ゲームの旧履歴が残っていない）にすでになっているので、冪等に 0 件を返せば足りる。エラーにすると、呼び出し側が「取り込み済み」と「失敗」を見分ける必要が出る

### CLI

- 事項: 照合と取り込みを、CLI でどう出し、どう確認を取るか
- 決定内容:
  - `game add` と `game import` は、1 行目にこれまでの出力をそのまま出す（`game add` は gameId、`game import` は `gameId<TAB>"title"`）。2 行目以降に照合の結果を出す。1 件だけ一致したときは、提案と、取り込むコマンドの例を出す。一致しないか複数あるときは、候補一覧を出す。未紐付けの旧履歴がなければ何も足さない
  - 提案と候補の行は `旧版の gameId<TAB>"タイトル"<TAB>件数<TAB>合計秒<TAB>最後に遊んだ日時` の形にし、旧版のタイトルは Go の引用符つきの表記（`%q`）で出す
  - 取り込みは `legacy link --game <gameId> --legacy-game <旧版の gameId> [--data-dir D]` とし、このコマンドを実行することを確認とみなす。通常のプレイ履歴にした件数と、取り込まずに消した件数を出す
  - 照合はリモートを使わない。登録が済んだ後に照合だけが失敗したときは、登録を取り消さずにエラーを出して終わる
- 判断理由: 1 行目を変えないので、gameId を取り出す既存の使い方が崩れない。CLI は対話をしないので、9-K1 の確認は、提案を見て `legacy link` を実行することで取る。コマンド名は AGENTS.md の CLI の一覧に合わせる。旧版のタイトルは手で書き換えたエクスポートから来ることがあり、タブ・改行・端末の制御文字を含みうるので、2026-11-14_02-46_remote-game-import.md の `game remote` と同じく引用符つきで出し、列と行を崩さない。照合の失敗で登録を取り消すと、`game import` ではリモートを読み直して登録したものまで巻き戻すことになるが、照合は `legacy link` で後からやり直せるので取り消さない

### テスト

- 事項: どう確かめるか
- 決定内容: legacy は `package legacy_test` で、本物の SQLite（store）を使い、`Import` で旧履歴を入れてから `Match`・`Link` を呼んで確かめる。ケースは Issue の受け入れの条件のとおりにする。9-K3 のロールバックは、旧履歴がある旧ゲームを登録していない gameId に取り込もうとして外部キーに当て、旧履歴が残ることで確かめる。取り込んだ履歴が次の同期で PUT されることは、legacy のテストでは確かめず、8-S1 の既存のテストと R2 での CLI の確認に任せる。cmd の配線にはテストを書かない
- 判断理由: AGENTS.md のテストの方針（コアのテストは本物の SQLite、仕様書の ID をケース名に入れる、配線にはテストを書かない）に従う。本物の SQLite では、旧履歴の削除まで済んだ後に失敗する状態を作れないので、制約に当たる入力でロールバックを確かめる。取り込んだ履歴は `play_sessions` の行で、ほかのプレイ履歴と区別がつかないので、8-S1 のテストがそのまま当てはまる。legacy のテストで metasync を動かすと、legacy のテストが 8 章の振る舞いまで背負うことになる
