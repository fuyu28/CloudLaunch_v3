# game-image-sync

- 日時: 2026-11-14 01:52 (JST)

## 当初の要求 / 背景

仕様書 8 章「画像」は、ゲームの画像を `games/{gameId}/images/{sha256}` に置き、変換せずに保存するとしている。画像を変えるときは、新しい画像を PUT してから game.json を PUT する（8-I1）。10 MiB を超える画像と、PNG・JPEG・WebP でない画像は、設定するときに拒否する（8-I2）。game.json の `imageSha256` が指す画像がキャッシュになければ、取得してキャッシュに入れる（8-I3）。取得した画像が不正（8-V12〜8-V14）なら、キャッシュに入れず、画像なしとして表示する。古い画像は削除しない。

ゲーム情報の後勝ちの同期は、2026-11-14_00-43_game-info-sync.md で作った。`imageSha256` は、そこで game.json と DB の間で値として受け渡すだけにし、画像そのものの扱いをこの作業に回した。10 MiB の定義は、仕様書の変更 PR（#117）で書く。

メタ情報の同期は同期ロックを握らない（仕様書 3 章「排他」）。objstore は Get / Put / List / Delete の汎用の契約で、HEAD を持たない（AGENTS.md「構成」）。

## 決定事項

### 扱う仕様書の ID の範囲

- 事項: この作業で、8 章のどの項目を満たすか
- 決定内容: 8-I1〜8-I4 と 8-V12〜8-V14 を扱う。8-I4 は、仕様書の変更 PR（#118）で足す。上げ直しのときの画像の扱い（8-U5）は #103、使われていない画像の削除（10 章）は v1 の後に扱う
- 判断理由: 8-U5 は上げ直しの手順の一部で、上げ直しと一緒に確かめる方がよい

### 画像を PUT する時点

- 事項: 8-I1 の「画像を PUT してから game.json を PUT する」を、どこで行うか
- 決定内容: `game set-image` は、画像を検証してキャッシュに入れ、DB の `imageSha256` と `updatedAt` を書き換えるだけにし、リモートに触れない。画像の PUT は、メタ情報の同期で game.json を PUT するとき（8-G1・8-G2）に、その直前に行う。画像の PUT が失敗したら、game.json を PUT せずにエラーを返す
- 判断理由: game.json の PUT の直前に画像を確かめれば、どの経路で `imageSha256` が変わっても、8-I1 の順番を同期の中で必ず守れる。`game edit` と同じく、設定の操作をオフラインでも行える。画像の PUT の失敗は通信の失敗なので、2026-11-14_00-43_game-info-sync.md と同じく、プレイ履歴の同期もしない

### リモートに画像があるかの確かめ方

- 事項: game.json を PUT する前に、画像を PUT する必要があるかをどう確かめるか
- 決定内容: `games/{gameId}/images/` を List し、`imageSha256` の画像がなければ PUT する。List するのは、`imageSha256` を持つ game.json を PUT するときだけにする
- 判断理由: 毎回 PUT すると、game.json を PUT するたびに最大 10 MiB を送ることになる。objstore は HEAD を持たず、HEAD を足すには契約と memstore・契約テストから変えることになる。画像は書き換えない object なので、キーがあれば中身は同じとみなせる

### PUT したい画像がキャッシュにないとき

- 事項: game.json を PUT したいのに、`imageSha256` の画像がキャッシュにもリモートにもないときの扱い
- 決定内容: 画像を PUT せずに、`imageSha256` を入れたまま game.json を PUT し、Warn のログを残す（仕様書 8-I4）。ゲーム情報の結果は「アップロードした」、画像の結果は「リモートになかった」とする。キャッシュの画像の中身が sha256 と違うときも、キャッシュから消して、キャッシュにないものとして扱う。リモートにあれば、キャッシュになくても game.json を PUT する
- 判断理由: キャッシュのフォルダを消したときや、使われていない画像の削除（10 章）の後に、古い game.json が後勝ちで画像を参照し直したときに起きる。画像は必須の項目ではないので、game.json の PUT を止めると、title・brand の編集までリモートに上がらなくなる。`imageSha256` を外して PUT する案は、同期が設定を黙って消し、後勝ちでほかの PC にも広がるので採らない。ほかの PC は 8-I3 で取得できず画像なしとして表示し、正しい画像をキャッシュに持つ PC が次に game.json を PUT するときに、画像も PUT されて直る

### 画像を取得する時点と失敗の扱い

- 事項: 8-I3 の取得を、いつ行い、失敗したらどうするか
- 決定内容: ゲーム情報の同期の後に、DB の `imageSha256` が指す画像がキャッシュにあるかを毎回確かめ、なければ GET する。結果ごとの扱いは次のとおりにする
  - GET が `fs.ErrNotExist` を返す: Warn のログを残し、画像なしのまま進める
  - 不正（8-V12〜8-V14）: キャッシュに入れず、Warn のログを残して進める
  - それ以外のエラー: エラーを返し、プレイ履歴は同期しない
  - game.json が不正（8-V7〜8-V11・8-V15）でゲーム情報の同期を止めたときは、画像も扱わない
- 判断理由: 8-G3 で取り込んだときに限らず確かめるので、前の同期で取得に失敗した画像も取り直せる。リモートにない画像と不正な画像は、データの状態によるもので、同期を止めても直らないので進める。不正な game.json の `imageSha256` は信用できないので、それを使って GET しない

### キャッシュの置き場所と書き方

- 事項: 画像のキャッシュをどこに、どう書くか
- 決定内容: `{データのフォルダ}/images/{sha256}` に置く。metasync の `Config` にフォルダのパスを渡し、metasync が直接ファイルを読み書きする。書くときは、同じフォルダの一時ファイルに書いてからリネームし、fsync はしない。キャッシュに同じ sha256 の画像があれば書き直さない。キャッシュから PUT する前に中身の sha256 を確かめ、違えばキャッシュから消して、キャッシュにないものとして扱う
- 判断理由: syncore がセーブフォルダを直接扱うのと同じ形で、新しいパッケージは要らない。キャッシュはリモートから取り直せるので、電源断で消えても取り直せば済む。リネームにしておけば、途中まで書いたファイルが sha256 の名前で残り、正しい画像として読まれることはない。Windows では、表示や同期で開かれているファイルへのリネームが失敗するので、同じ画像を書き直さない。同期ロックを握らないので、2 つのプロセスが同じ画像を同時に書くこともある。そのときのリネームの失敗は、宛先がもうあれば成功とする。中身は sha256 で決まり同じだからである。リモートの画像はキーがあれば中身は同じとみなすので、壊れた中身を一度 PUT すると、どの PC も 8-V12 で画像なしになり、正しい画像を持つ PC が同期しても直らない

### 大きさの上限

- 事項: 8-I2・8-V13 の「10 MiB」をどう判定するか
- 決定内容: 10,485,760 バイトちょうどは受け入れ、それを超えれば拒否する。読むときは上限の 1 バイト先までしか読まない
- 判断理由: 仕様書の定義（#117）に従う。上限の 1 バイト先まで読めば、超えたかどうかが分かり、大きな object を最後まで読まずに済む

### 形式の判定

- 事項: 8-I2・8-V14 の「PNG・JPEG・WebP でない」をどう判定するか
- 決定内容: 先頭のバイトだけで判定する。PNG は `89 50 4E 47 0D 0A 1A 0A`、JPEG は `FF D8 FF`、WebP は `RIFF` の 4 バイトの後に任意の 4 バイト、続いて `WEBP` で始まるものとする。画像として最後まで解読できるかは確かめない
- 判断理由: 画像は変換しない（8 章）ので、デコーダを入れる必要がない。`http.DetectContentType` は、判定の規則が標準ライブラリの版に依存し、3 つ以外の形式も返すので使わない

### キャッシュの掃除

- 事項: 使われなくなったキャッシュの画像を消すか
- 決定内容: 消さない。掃除の仕組みは作らない
- 判断理由: リモートの使われていない画像の削除（10 章）と同じく、v1 の後に回す。画像は 1 枚 10 MiB までで、ゲームごとに変える回数も少ない

### API の形

- 事項: metasync と store に何を足すか
- 決定内容:
  - `metasync.Config` に `ImageDir string` を足す。`LocalStore` と `ObjectStore` には何も足さない
  - `Core.CacheImage(r io.Reader) (string, error)` を足す。上限の 1 バイト先までしか読まずに 8-I2 を検証し、キャッシュに書いて sha256 を返す
  - store の `GameEdit` に `ImageSha256 *string` を足す。空文字は画像を外す。sha256 の形でない値は拒否する
  - 大きすぎる・形式が違うエラーは、センチネルエラーにせず `%w` で包んで返す
- 判断理由: `GameInfo.ImageSha256` と List・Get・Put で、同期に要る操作は足りる。今は、エラーの種類で振る舞いを分ける呼び出し側がない。GUI で分ける必要が出たら M4 で足す

### 結果と CLI の表示

- 事項: `Sync` の結果に何を返し、CLI に何を出すか
- 決定内容: `Result` に画像の結果を表す値（なし・変更なし・アップロードした・取得した・不正で入れなかった・リモートになかった）を足す。ゼロ値は「なし」で、画像を扱わなかったこと（画像がない・同期を飛ばした・game.json が不正）を表す。CLI は「ゲーム情報: …」の次の行に「画像: …」と出す。画像を持たないゲームでは「画像: なし」と出す。game.json が不正なときは「なし」と出さず、画像を扱わなかったことを出す
- 判断理由: ゲーム情報と同じく、1 ゲームに 1 つなので、毎回出しても表示が膨らまない。ゼロ値を「なし」にすると、画像を持たないゲームの既存のケースの期待値を変えずに済む。game.json が不正なときも DB には画像があるので、「なし」と出すと外れたと誤解させる

### CLI の入口

- 事項: 画像の同期を CLI で確かめるため、何を足すか
- 決定内容: `game set-image --game ID --file PATH [--data-dir D]` で画像を設定し、`--clear` で外す。`--file` と `--clear` は、どちらか一方だけを指定させる。画像をキャッシュに入れる前に、ゲームが登録されているかを確かめる
- 判断理由: 外す操作がないと、一度設定した画像を CLI から消せない。`game edit` と同じく、リモートへの反映は次の `push`・`pull` に任せる。キャッシュの掃除は作らないので、ID を打ち間違えたときに、どこからも参照されない画像を残さないようにする

### テスト

- 事項: どう確かめるか
- 決定内容: metasync は `package metasync_test` で、本物の SQLite・一時フォルダ・memstore を使い、8-I1〜8-I4 と 8-V12〜8-V14 を書く。8-I2 は上限ちょうどと 1 バイト超え、3 つの形式の受け入れと、それ以外の拒否を書く。8-I4 は、画像がどこにもないときと、キャッシュの画像が壊れているときを書く。ほかに、リモートにない画像を飛ばすこと、キャッシュにある画像を書き直さないこと、GET の失敗でプレイ履歴を同期しないこと、古い画像を削除しないこと、2 台の PC で設定した画像が相手のキャッシュに入ることを書く。store には `EditGame` の `ImageSha256` のテストを足す。cmd の配線にはテストを書かない
- 判断理由: AGENTS.md のテストの方針（本物の SQLite とファイルシステム、偽のリモート、仕様書の ID をケース名に入れる、複数 PC のシナリオは同じ偽のリモートを共有させる）に従う。8-I1 の順番は、memstore の PUT の記録の順で確かめる

## 結果 / 影響

- CLI の `push`・`pull` のたびに、game.json が指す画像が同期される。CLI は「画像: なし／変更なし／アップロードしました／取得しました／…」と出す
- `imageSha256` が指す画像がキャッシュにもリモートにもないときも、game.json は PUT される（8-I4）。リモートには、ない画像を指す game.json が残り、正しい画像をキャッシュに持つ PC が次に game.json を PUT するまで、どの PC でも画像なしとして表示される
- リモートの画像が不正（8-V12〜8-V14）だと、キャッシュに入れないので、同期のたびに最大 10 MiB を GET し直す。2026-11-12_00-47_play-session-download.md の不正なセッションと同じく、データの異常でまれにしか起きず、起きている間はログに出続ける方が気づきやすいので受け入れる
- キャッシュに書いている途中でプロセスが落ちると、一時ファイル（`.tmp-*`）がキャッシュのフォルダに残る。キャッシュの掃除は作らない（「キャッシュの掃除」）ので、v1 の後に掃除を作るときに一緒に消す
- キャッシュから PUT する画像は、sha256 を確かめるために、最大 10 MiB をメモリに読む
- R2 を相手に CLI で確かめた。PNG でないファイルの `set-image` は `8-I2: image is not PNG, JPEG or WebP` で拒否された。PC A で PNG を設定して `push` すると、画像とゲーム情報をアップロードした。PC B で `pull` すると画像を取得し、キャッシュの中身は元のファイルとバイト単位で一致した。A で画像を変えて `push` し、B で `pull` すると、新しい画像を取得した。A で最初の画像に戻して `push` すると「画像: 変更なし」で、古い画像がリモートに残っていた。A で `--clear` して `push` すると、B の `pull` でも「画像: なし」になった。A でリモートにない画像を設定し、A のキャッシュからその画像を消して `push` すると、「ゲーム情報: アップロードしました」「画像: リモートにもキャッシュにもないので同期しませんでした」で、B の `pull` はゲーム情報を取り込んだ（8-I4）。その状態のまま A で title を変えて `push` すると、B にも新しい title が届いた
- 行数は約 1,030 行（テスト約 480、metasync 約 270、store 約 20、CLI 約 80、ADR 約 170）で、見込みの約 800 行を超えた。8-I2 の形式と境界のケース、壊れたキャッシュとキャッシュの書き直しのケースを足し、ゲーム情報の同期を、PUT と画像の取得をそれぞれ 1 か所で行う形に組み直したため
