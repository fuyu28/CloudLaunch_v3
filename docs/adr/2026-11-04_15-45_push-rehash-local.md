# push-rehash-local

- 日時: 2026-11-04 15:45 (JST)

## 当初の要求 / 背景

仕様書 7 章は、承認してから実行するまでに local のハッシュが変わっていれば、実行せずに中止すると決めている。Push は手順 3（5-P3）でアップロードするファイルだけを読み直し、manifest と違えば `ErrPlanStale` で止める。しかし、リモートの `objects/` に既に object があるファイルは読み直さない。そのため、承認の後にそうしたファイルが書き換わっても、承認時の entries のまま manifest を書いて HEAD を進める（#56）。#25（同期ロック）のレビューで見つかった、前からある不具合である。

仕様書 5-P3 に「アップロードを終えたら、local をハッシュし直し、承認した時点から変わっていれば中止する」を足した（#58）。

## 仕様

- ハッシュし直す時機と比べ方
- アップロード中の検証との関係

## 決定事項

### ハッシュし直す時機と比べ方

- 事項: Push のどこで local をハッシュし直し、何と比べるか
- 決定内容: 手順 3 のアップロードを終えた後、手順 4 で manifest を PUT する前に、セーブフォルダを `localEntries` でハッシュし直す。`localHash(entries, plan.Base)` を `plan.Local.Hash` と比べ、違えば `ErrPlanStale` を返す
- 判断理由: アップロードの前に比べると、比べた後のアップロードの間にファイルが変わりうる。後に比べれば、manifest と HEAD を書く時点に近い状態を確かめられる。Pull が、ダウンロードの後（手順 6）に live をハッシュし直しているのと同じ並びにする。`localHash` と `plan.Base` を使うのは、`Status` が `plan.Local.Hash` を同じ規則で計算しているからである（2026-11-04_11-59_pull-empty-manifest-base.md）

### アップロード中の検証との関係

- 事項: アップロードするファイルを読みながら確かめる今の検証を残すか
- 決定内容: 残す
- 判断理由: ハッシュし直す確認は「セーブフォルダが承認の時点と同じか」を確かめ、アップロード中の検証は「アップロードした object の中身が manifest のハッシュと一致するか」を確かめる。後者がないと、アップロードの途中でファイルが変わり、後でまた元に戻った場合に、`objects/{sha256}` に違う中身が残りうる。費用として、Push のたびにセーブフォルダを 1 回多く読む。#28（ハッシュのキャッシュ）で、変わっていないファイルは読まずに済むようになる

## 結果 / 影響

- 承認の後に、リモートに object があるファイルが変わったり消えたり、ファイルが増えたりしても、Push は manifest も HEAD も書かずに `ErrPlanStale` で止まる。比べ方は Pull の手順 6 と同じで、`ensureLocalUnchanged` にまとめた
- ハッシュし直した後にも、manifest の PUT・HEAD の読み直し・HEAD の PUT の間に、ファイルが変わりうる隙間は残る。確かめる位置を HEAD の読み直しの後に移しても、狭まるのは manifest の PUT と HEAD の GET の分だけで、隙間はなくならない。仕様書 5-P3 の並び（アップロードを終えたら）のままにする。この隙間で変わったファイルは、次の `Status` で Push になる
- Push のたびに、セーブフォルダを 1 回多く読む。アップロードしたファイルは、アップロード中の検証と合わせて 2 回読む。#28（ハッシュのキャッシュ）で、変わっていないファイルは読まずに済むようになる
- R2 を相手に CLI で、`small.sav` を v1 で Push した後、v2 にして 100 MB の `big.bin` を足して Push し、アップロードの途中で `small.sav` を v1（リモートに object がある中身）に戻した。Push は「状況が変わりました」で止まり、もう一度 Push すると成功して「変更なし」になった
- 行数は約 170 行（テスト約 80、本体約 25、ADR 約 60）で、見込みの約 150 行を少し超えた。レビューで、ファイルが消えたケースと、アップロード中の検証を守るアサーションを足したため
