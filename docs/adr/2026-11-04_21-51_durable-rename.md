# durable-rename

- 日時: 2026-11-04 21:51 (JST)

## 当初の要求 / 背景

仕様書 1 章は、中断を「同期の途中でプロセスが異常終了すること。電源断を含む」と定め、中断してもセーブフォルダが同期前か同期後のどちらかと一致することを保証している。OS の異常終了（フリーズからの強制再起動など）も、ディスクから見れば電源断と同じである。

OS は、ファイルの書き込みとリネームをメモリにためてから、あとでディスクに書く。一方、SQLite はコミットのたびにディスクへ届ける。今の実装は、ファイルとリネームを書き出さずに、次の DB の書き込みへ進む。そのため、電源断の後には次の状態が起こりうる（#53）。

- Pull: stage のファイルの中身が空のまま、stage → live のリネームだけが残る。あるいはリネームが消えて、base（remote の値）とジャーナルの削除だけが残る。どちらも判定は「ローカルが変化」になり、壊れたセーブか古いセーブの Push を提案する
- 復旧の 6-R2: old → live のリネームが消えて、ジャーナルの行の削除だけが残る。セーブフォルダがなくなったまま、復旧されない
- バックアップ: 別のボリュームへのコピーで移すとき、コピーと最終の名前へのリネームがディスクに届く前に old を削除しうる。ボリュームが違うと、ファイルシステムのジャーナルは順序を守らない

電源断で危ないのは、Pull やバックアップの直後の数秒（OS がためた書き込みを書くまで）である。仕様書 3 章「ディスクへの書き出し」と 6-L4・6-L7・6-L9・6-R2 に、書き出す時機を定めた（#62）。

## 決定事項

### ファイルの中身の書き出し方

- 事項: stage に取得したファイルと、バックアップへコピーしたファイルの中身を、どうディスクへ書き出すか
- 決定内容: 書いたハンドルを閉じる前に `(*os.File).Sync` を呼ぶ。テストで差し替えられるよう、`Config.SyncFile func(*os.File) error` を置き、nil なら `(*os.File).Sync` を使う
- 判断理由: `(*os.File).Sync` は、Windows では `FlushFileBuffers`、Linux では `fsync` を呼ぶ。`FlushFileBuffers` は `GENERIC_WRITE` のハンドルを要求するが、書いたハンドルはそれを持つ。開き直さずに済み、OS ごとの分岐も要らないので、syncore の中に置ける

### Windows でのリネームの書き出し方

- 事項: Windows で、リネームをディスクへ届けてから次へ進む方法
- 決定内容: `MoveFileExW` に `MOVEFILE_WRITE_THROUGH` を付けてリネームする。親ディレクトリは別に書き出さない。`MOVEFILE_REPLACE_EXISTING` は付けず、移す先があれば失敗させる
- 判断理由: `MoveFileExW` の文書は、`MOVEFILE_WRITE_THROUGH` について「ファイルが実際にディスク上で移動するまで戻らない」と述べ、ディレクトリの移動（同じドライブの中）にも使える。ただし、同じ文書の続く文はコピーと削除で移す場合の保証だけを述べ、同じボリュームの中のリネームを明言してはいない。この点は文書の記述を根拠にし、電源断を起こして確かめてはいない
  - 却下した案 1: 親ディレクトリを `CreateFile(GENERIC_WRITE | FILE_FLAG_BACKUP_SEMANTICS)` で開いて `FlushFileBuffers` をかける。ディレクトリのハンドルで効くかの文書がない。Lucene.NET は、このときのアクセス拒否を無視している
  - 却下した案 2: NTFS のメタデータのジャーナルに任せる。バックアップの置き場所が別のボリュームにあると、順序が守られない
  - 移す先を上書きしないのは、Pull も復旧も、移す先がないことを確かめてからリネームするためである。あれば何かが食い違っているので、上書きせずに止めたほうが安全である

### Linux でのリネームの書き出し方

- 事項: Linux（開発用）で、リネームをディスクへ届ける方法
- 決定内容: `rename(2)` の後に、移した元と移した先の親ディレクトリを `fsync` する。stage やバックアップの中に作ったディレクトリの書き出しは行わない
- 判断理由: Linux では、ディレクトリを `fsync` すればその中の名前の変更がディスクへ届く。製品として保証するのは Windows で、Linux は開発用の最小限にとどめる（AGENTS.md）。中に作ったディレクトリまで書き出すには木をたどる処理が要り、Windows では不要（NTFS のジャーナルは同じボリュームの中では順に書かれ、`MOVEFILE_WRITE_THROUGH` のリネームより前の作成も一緒に届く）なので行わない

### 置き場所と配線

- 事項: OS ごとのリネームをどこに置き、syncore へどう渡すか
- 決定内容: `platform.Rename(oldpath, newpath string) error` を `rename_windows.go`・`rename_linux.go` に置く。`Config.Rename` は、`Locker`・`Processes` と同じく cmd が platform の実装を渡す必須の項目にし、nil のときに `os.Rename` を使う既定を消す。nil なら Pull と Recover は何も変える前にエラーにする
- 判断理由: Windows の API を呼ぶので、OS 固有の処理を置く platform に置く（AGENTS.md の「構成」）。nil のときに `os.Rename` を使う既定を残すと、GUI の配線で渡し忘れても黙って書き出さなくなる。`Locker` がないときに、ロックなしで黙って動く道を作らなかったのと同じ考えである（2026-11-04_15-21_sync-lock.md）

### 書き出しに失敗したときの扱い

- 事項: 書き出しに失敗したとき、どこまで戻すか
- 決定内容: 既存のエラーの道筋に乗せ、新しい復旧表の行は作らない
  - 6-L4 の stage のファイルの書き出しで失敗したら、6-A1 として stage とジャーナルを削除する
  - 6-L7 で live → old のリネームに失敗し、live が残っていれば、6-A1 と同じく stage とジャーナルを削除する
  - 6-L7 のそれ以外のリネームか書き出しの失敗では、ジャーナルを残してエラーにする。残った状態は 6-R2 か 6-R3 に当たり、Recover が片付ける
  - 6-L9 で失敗したら、old を移せなかったときと同じく、ジャーナルを残して中止する（6-R3）。リネームが済んでから書き出しに失敗したとき（old がもうない）は、コピーに進まない
  - 6-R2 で失敗したら、行を残してエラーにする
- 判断理由: `platform.Rename` は、リネームが済んでから書き出しに失敗しうる。それまでの 6-L7 は、live → old の失敗で stage とジャーナルを削除していた。リネームが済んでいれば、セーブフォルダがないまま復旧されない。live がなくなっていればジャーナルを残し、リネームが済んだかどうかを、Recover が残ったパスの状態から見分ける。一方、Windows では、セーブフォルダを開いているエクスプローラーやウイルス対策のせいで、リネームが実際に失敗する（何も移っていない）ことがよくある。live が残っていればリネームしていないので、片付けても失うものはない。片付けずに残すと、Recover を呼ばない CLI では、stage（セーブ全体のコピー）が Pull のたびに増える。live の有無を確かめられないときは、片付けずに残す

### テストの範囲

- 事項: 電源断は再現できない。何を検査するか
- 決定内容: syncore のテストで、記録用の `SyncFile` と `Rename` を渡して呼び出しの順を記録し、移すファイルの `SyncFile` が、6-L7 のリネームとバックアップの `.partial-` → 最終の名前のリネームより前に呼ばれることを確かめる。書き出しの失敗を仕込んで、上の扱いになることを確かめる。必須の項目（`Locker`・`Processes`・`Rename`・`BackupsDir`）がないときのテストは、テスト用の設定から 1 項目だけ外したコアで行う。platform のテストは、Windows と Linux の CI で、ディレクトリをリネームできることと、移す先があれば失敗することを確かめる
- 判断理由: 書き出しを忘れたり順序を取り違えたりしても、ふだんの動作では何も起きないので、テストでしか気づけない。リネームの後の書き出しは `platform.Rename` の中で閉じているので、syncore では `Config.Rename` を通ることだけが要る。必須の項目のテストで設定を手で組み立てると、新しく必須にした項目がないことで先に止まり、確かめたい項目を確かめないまま通る

### SQLite の `synchronous`

- 事項: DB のコミットがディスクへ届くことを、設定で明示するか
- 決定内容: DSN に `_pragma=synchronous(FULL)` を足す
- 判断理由: 書き出しの順序の保証は、ファイルとリネームを書き出した後の DB の書き込みがディスクへ届くことを前提にする。今は既定の FULL で動いているが、明示しないと、性能のために NORMAL へ変えたときに黙って保証が崩れる

## 結果 / 影響

- Pull・復旧・バックアップは、ファイルとリネームをディスクへ書き出してから、base の書き込みとジャーナルの削除へ進む。電源断や OS の異常終了の直後に、DB だけが新しくなって壊れたセーブの Push を提案することはなくなる（Windows では `MOVEFILE_WRITE_THROUGH` の文書の記述が正しい限り）
- R2 を相手に Linux で CLI を動かし、strace で、stage のファイルの `fsync` → `renameat2(RENAME_NOREPLACE)` と親ディレクトリの `fsync` → DB の `fsync` の順になることと、バックアップが別のボリューム（tmpfs）にあるときに、`EXDEV` の後にコピーしたファイルを `fsync` してから `.partial-` を最終の名前にリネームすることを確かめた
- Pull で、取得したファイルごとに書き出すので、ファイル数の多いセーブでは遅くなる。バックアップのコピーは 1 ファイルずつ書き出す。実際に使って遅さが問題になれば、書き出し方を見直す（コピーの並列化など）
- Windows の `MOVEFILE_WRITE_THROUGH` が同じボリュームの中のリネームでもディスクまで待つことは、文書の記述に頼っていて、確かめていない
- Linux では、stage やバックアップの中に作ったディレクトリの名前を書き出さないので、電源断の後に中のファイルが欠けうる。Linux は開発用なので受け入れる
- Linux の `RENAME_NOREPLACE` は、対応しないファイルシステム（NFS や一部の FUSE）では失敗し、Pull と復旧ができない。開発用なので受け入れる
- `platform.Rename` は Windows で `\\?\` を付けないので、パスが MAX_PATH を超え、かつ OS の長いパスの設定が無効なときは失敗する
- 行数は約 660 行（テスト約 470、本体約 120、ADR 約 90）で、見込みの約 400 行を超えた。順序を記録するテスト用の仕組みと、必須の項目のテストの設定を共通にする変更が、見込みより大きかった
