# game-running

- 日時: 2026-11-04 16:02 (JST)

## 当初の要求 / 背景

仕様書 7 章は、ゲームのプロセスが実行中なら Push も Pull も拒否すると決めている。実行中のセーブは、書き込みの途中かもしれないためである。プロセスはローカル設定の実行ファイルのパスで見つけ、CLI でも同じ判定をする。

M1 の Push と Pull は、この確認をしていない（2026-11-03_01-02_push.md・2026-11-03_17-44_pull.md「同期ロックとゲームの実行中の確認」）。M2 が終わると、実際のゲームのセーブで CLI を使い始める。#25（同期ロック）から分けた作業である。

前身の 2 つの版は、プレイ時間の記録のためにプロセスを監視していた。

- Electron 版（cloudlaunch）: PowerShell の `Get-Process` の出力を読み、失敗したら Node のパッケージ（ps-list）に切り替えた。Windows の API を呼ぶパッケージ（win32-api）も試したが、取り下げた（`ebd4878`・`2aaf950`）
- CloudLaunch_Go: Electron 版の方式のまま Wails に移り、PowerShell の `Get-Process` を実行し、失敗したら WMIC に切り替えた

どちらも、照合は同じ規則である。ファイル名が一致することを前提に、パスが完全に一致するか、どちらかがもう一方を含むか、プロセスのパスが登録した exe のフォルダを含めば一致とする。比べる前に小文字にし、Unicode の NFC に正規化する。パスが取れないプロセスは、パスの代わりに名前を入れるので、「含む」の判定で名前だけの一致になる。Electron 版の履歴では、「含む」と「フォルダを含む」は、外部コマンドの出力の文字化け（Shift-JIS と UTF-8 の取り違え）への手当てとして入った（`3d26afc`「ShiftJIS と UTF-8 の比較を行えるように変更」、`4341d90`「文字化けに対応するため、より柔軟なマッチング手法を使用」）。NFC は「日本語ゲーム対応」として入った。

## 決定事項

### コアが受け取る形と、エラー

- 事項: syncore がプロセスの実行状態をどう知り、実行中のときに何を返すか
- 決定内容: syncore に `ProcessChecker`（`Running(exePath string) (bool, error)`）を定義し、`Config.Processes` で受け取る。実装は `internal/platform` に置く。実行中なら、センチネルエラー `ErrGameRunning` を返す。`Config.Processes` が nil なら、`Push`・`Pull` は何も変える前にエラーを返す
- 判断理由: OS ごとの処理をコアの外に置き、コアのテストで偽物に差し替える（2026-10-23_00-30_package-structure.md）。呼び出し側（CLI・GUI）は「ゲームが実行中です」と出し分けるので、センチネルエラーにする。nil の扱いは `Locker` と同じにする（2026-11-04_15-21_sync-lock.md）

### 確かめる時機

- 事項: Push と Pull のどこで確かめるか
- 決定内容: 同期ロックを取った直後に 1 回、転送の後、承認後の確認（Push は 5-P3 のハッシュし直し、Pull は 6-L6）の直前にもう 1 回確かめる。2 回目で実行中と分かったときも `ErrGameRunning` で止め、Pull なら stage とジャーナルを消す（6-A1 と同じ扱い）
- 判断理由: ダウンロードやアップロードは長くかかることがあり、その間にゲームが起動されうる。2 回目は、Pull なら入れ替えの直前、Push なら manifest を書く直前に当たり、セーブフォルダを書き換える・公開する前の最後の確認になる。ハッシュし直す前に確かめるのは、転送の間に起動されたゲームがセーブを書くと、ハッシュし直す確認が先に `ErrPlanStale`（状況が変わりました）を返し、利用者に本当の理由が伝わらないため

### `Recover` で確かめるか

- 事項: `Recover` でも、ゲームの実行中を拒否するか
- 決定内容: 確かめない
- 判断理由: 仕様書 7 章が拒否すると決めているのは Push と Pull である。6-R2（old を live に戻す）をゲームの実行中に行うおそれはあるが、そのときゲームは live を開いているので、Windows ではリネームが失敗し、行が残ってエラーになるだけである

### 実行ファイルのパスの取り方

- 事項: syncore が、ゲームの実行ファイルのパスを store からどう受け取るか
- 決定内容: store の `GameLocal` の戻り値を、syncore が定義する構造体（`GameLocal`。セーブフォルダ・実行ファイルのパス・base を持つ）に変える
- 判断理由: 戻り値が 3 つ以上になると読みにくく、#27 などで項目がさらに増える。型を syncore に定義して store が返す形は、`ListPullOperations` と同じである（2026-11-04_11-27_pull-backup-and-recover.md「`ListPullOperations` が返す型」）

### プロセスの列挙のしかた

- 事項: OS ごとに、実行中のプロセスの名前と実行ファイルのパスをどう得るか
- 決定内容: Windows は、`CreateToolhelp32Snapshot` でプロセスを列挙して名前（`szExeFile`）を得て、`OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` と `QueryFullProcessImageName` で実行ファイルの完全なパスを得る。開けないプロセスは、パスなしとして扱う。Linux（開発用）は、`/proc/*/exe` を readlink してパスを得て、読めないプロセスは飛ばす
- 判断理由: 前身の版が PowerShell を使ったのは、Electron で要件を満たす Node のパッケージがなかったためで、Go では Windows の API を直接呼べる。PowerShell は起動に数百 ms〜1 秒かかり、出力の文字コードを推測する必要があり、実行方針やウイルス対策で止められうる。切り替え先の WMIC は、Windows 11 で既定から外されつつある。API なら文字列を UTF-16 のまま受け取れるので、文字化けが起きない。`PROCESS_QUERY_LIMITED_INFORMATION` なら、保護されたシステムのプロセスを除き、管理者で動くプロセスのパスも読める。Linux の `/proc/*/comm` は名前を 15 バイトで切るので、名前だけの照合には使わない

### 照合の規則

- 事項: 列挙したプロセスと、登録した実行ファイルのパスを、どう照合するか
- 決定内容: 次の規則にする。照合の判断は platform の関数に置き、同じファイルかの判定を差し替えられるようにする
  1. プロセスのパスが取れれば、登録した実行ファイルと**同じファイル**なら実行中とする。同じファイルかは、両方を `os.Stat` して `os.SameFile` で比べる（Windows ではボリュームの番号とファイルの番号、Linux では装置と inode）
  2. プロセスのパスが取れないか、そのパスを `Stat` できなければ（Windows で開けないプロセスなど）、ファイル名が一致すれば実行中とする。ファイル名は、Unicode の NFC に正規化し、`ToUpper` で大文字にそろえて比べる

  前身の版の「どちらかがもう一方を含む」と「プロセスのパスが登録した exe のフォルダを含む」は引き継がない
- 判断理由: 「含む」と「フォルダを含む」は、外部コマンドの出力の文字化けへの手当てとして入ったもので（Electron 版の `3d26afc`・`4341d90`）、API でパスを受け取る v3 では、その原因がない。仕様書 7 章は「ローカル設定の実行ファイルのパスで見つける」と決めており、目指すのは「登録した実行ファイルと同じファイルか」の判定である。パスの文字列で比べると、ジャンクションやシンボリックリンクを経由したパス、`subst` やネットワークドライブ、8.3 形式の短い名前（`PROGRA~2`）のように、同じファイルを別の書き方で指すときに見落とし、書き込みの途中のセーブを同期しうる。ファイルの同一性で比べれば、これらの違いをすべて吸収できる。費用は、プロセスごとに `Stat` を 1 回呼ぶことで、数百のプロセスでも数十 ms 以下である。パスが取れないときに名前で照合するのは、管理者で動くゲームを見落とさないためで、誤って「実行中」と判定しても同期を見送るだけで、セーブは失われない。ほかの利用者の同じ名前のプロセス（RPG ツクールの `Game.exe` など）で同期が止まることがあるが、この理由で受け入れる。NFC は「日本語ゲーム対応」として入ったもので、名前の濁点の表し方が違う場合に備えて残す。大文字にそろえるのは、Windows のファイル名の比べ方に合わせるためである（`validateEntries` と同じ）。ランチャー経由のゲーム（登録した exe が別の exe を起動して終わる）は検出しない

### 実行ファイルが見つからないとき

- 事項: 登録した実行ファイルが存在しないとき、どうするか
- 決定内容: syncore が、プロセスを確かめる前に実行ファイルを `Stat` し、存在しなければセンチネルエラー `ErrGameExeNotFound` を返して、Push・Pull を止める。CLI は「登録した実行ファイルが見つかりません」と出す
- 判断理由: 仕様書 7 章で、確かめられないときは拒否すると決めた（#60）。「実行中でない」として続けると、ゲームの更新や入れ直しでパスが変わったときに、確認が黙って効かなくなる。呼び出し側は「設定を直してもらう」と出し分けるので、センチネルエラーにする。platform が syncore のエラーを返すと platform が syncore に依存するので、`Stat` は syncore で行う

### テスト

- 事項: どう確かめるか
- 決定内容: 照合の関数は、同じファイルかの判定を差し替えて、規則ごとに表駆動のテストを先に書く（同じファイル、同じ名前で別のファイル、パスが取れないときの名前の一致と不一致、名前の大文字小文字と NFC の違い）。syncore は、偽の `ProcessChecker` で、Push・Pull のそれぞれについて、最初の確認で実行中なら何も書かずに止まること、転送の途中で起動されたら 2 回目の確認で止まること（Pull は stage とジャーナルを消す）、`Config.Processes` がなければエラーになることを確かめる。プロセスの列挙は実装した後で、テストのバイナリ自身を子プロセスとして起動し、そのパスで `Running` が真になること、kill した後は偽になること、存在しないパスは偽になることを、Ubuntu と Windows の CI で確かめる。Windows では、大文字小文字を変えたパスでも真になることも確かめる。シンボリックリンクを経由して登録したパスでも真になることを、リンクを作れる環境で確かめる。syncore では、実行ファイルが見つからなければ `ErrGameExeNotFound` で止まることも確かめる。ジャンクション・`subst`・短い名前は、PR をマージする前に Windows の実機で確かめる
- 判断理由: 照合は OS によらない純粋な関数なので、テストを先に書ける。プロセスの列挙のテストは実装した後で書き、Windows の振る舞いは Windows の CI で確かめる（AGENTS.md「テストの種類」）。テストのバイナリ自身を使えば、ほかの実行ファイルを用意せずに済む

## 結果 / 影響

- ゲームの実行中は、Push も Pull も `ErrGameRunning` で止まり、何も書かない。転送の途中で起動されても、セーブフォルダを書き換える・公開する前の 2 回目の確認で止まる。登録した実行ファイルがなければ `ErrGameExeNotFound` で止まる
- 照合はファイルの同一性で行うので、リンクを経由したパスや短い名前で登録しても見落とさない。ランチャー経由のゲームと、ほかの利用者の同じ名前のプロセスで止まる場合は、ADR の決定のとおり手当てしない
- Push・Pull のたびに、プロセスを 2 回列挙し、プロセスごとに `OpenProcess` と `Stat` を呼ぶ
- ゲームをアンインストールした PC では、実行ファイルが見つからないので Push も Pull もできない。確かめを飛ばす選択を用意するかは、GUI の段階で決める
- R2 を相手に CLI で、`/usr/bin/sleep` のコピーをゲームの実行ファイルとして登録して確かめた。起動している間は `push`・`pull` が「ゲームが実行中です」で止まり、Pull は stage を作らなかった。終了した後は成功した。リンクを経由したパスで登録し、実体のパスで起動しても、実行中と判定した。実行ファイルを消すと「登録した実行ファイルが見つかりません」で止まった
- Windows では、CI で列挙のテストを走らせる（一時ディレクトリが短い名前 `RUNNER~1` で渡されるので、同一性での照合を確かめられる）。ジャンクション・`subst`・短い名前で登録した場合と、管理者で動くゲームは、PR をマージする前に Windows の実機で確かめる
- 行数は約 700 行（テスト約 370、本体約 240、文書約 90）で、見込みの約 600 行を超えた。レビューを受けて照合をファイルの同一性に改め、実行ファイルが見つからないときの扱いとテストを足したため
