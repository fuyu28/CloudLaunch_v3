# default-logger

- 日時: 2026-11-16 19:33 (JST)

## 当初の要求 / 背景

`syncore.New` は、`Config` の `Now`・`SyncFile`・`NewGeneration` が nil なら既定の値を入れるが、`Logger` は入れない。`metasync.New` は `Config` をそのまま持ち、既定の値を何も入れない。どちらも、`Logger` を渡さずにコアを作ると、ログを出すところで nil の `*slog.Logger` を参照して panic する。

syncore の Push は HEAD と base を書いた後に、Pull は live を入れ替えた後にログを出す。そのため、同期は済んでいるのに呼び出し側にはクラッシュとして伝わり、Pull では old と Pull ジャーナルが残る（次の Recover で片付く）。metasync は、不正な game.json・画像・セッションを飛ばすときなどに Warn を出す。

今の CLI とテストは必ず `Logger` を渡すので起きない。M4 で Wails の配線を書くときに起きうる。

設定を `New` で確かめるかどうか（設定の検証全般）は、#161 で決める。

## 決定事項

### Logger が nil のときの扱い

- 事項: `Config.Logger` が nil のとき、`New` がどうするか
- 決定内容: `New` の中で `slog.New(slog.DiscardHandler)` を入れる。`New` のシグネチャは変えず、エラーも返さない。`Config` のコメントの既定の値の一覧に `Logger` を足す。ほかの設定（Remote・Locker・ImageDir など）の扱いは変えない
- 判断理由: ログを捨てても同期の結果は変わらないので、`Now`・`SyncFile`・`NewGeneration` と同じく、既定の値で済ませてよい種類の設定である。`New` でエラーにする案は、`New` のシグネチャが変わり、テストを含むすべての呼び出しを直すことになる。設定を `New` で確かめる形にするかは #161 で決めるので、その前に `Logger` だけをエラーにする形へ先に寄せない。#161 で `New` が設定を確かめる形になっても、既定の値を入れられる設定は今と同じく埋めればよく、この決定と食い違わない

### 対象にするコア

- 事項: どのコアを直すか
- 決定内容: syncore と metasync の両方を、同じ作業で直す。legacy・store・objstore はログを出さないので対象にしない
- 判断理由: どちらも同じ理由で panic し、GUI の配線ではどちらのコアも作る。片方だけ直すと、もう片方で同じ問題が残る

### テスト

- 事項: 何をどう検査するか
- 決定内容: それぞれのコアに、`Logger` を省いたコアで、ログを出す道を通る操作を最後まで終えることを確かめるケースを 1 つずつ置く。syncore は Push を成功させる（HEAD と base を書いた後にログを出す）。metasync は、リモートの game.json が不正なゲームを Sync する（8-V7 で game.json を飛ばすときに Warn を出す）。ログを出すことは仕様書の項目ではないので、ケース名は「コアの設定/…」の形にする
- 判断理由: 検査したいのは、ログを出す道を通っても panic しないことである。ログを出す行の数だけケースを並べても、既定の値を入れる場所は `New` の 1 か所なので、検出できる誤りは増えない
