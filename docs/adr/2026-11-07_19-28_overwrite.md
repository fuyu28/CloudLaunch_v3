# overwrite

- 日時: 2026-11-07 19:28 (JST)

## 当初の要求 / 背景

仕様書 7 章は、ゲーム単位で「アップロードで上書き」か「ダウンロードで上書き」を選べると決めている（7-O1〜7-O4）。上書きは競合のとき以外でも選べる。ローカルのセーブを捨てて、リモートのセーブを取り直したいときがあるためである。

今の `Push`・`Pull` は、`plan.Decision` が自分の判定でなければエラーを返す。CLI は、判定が Push・Pull でなければ何もしない。そのため、競合を解消する手段がない。M2 が終わると実際のゲームのセーブで CLI を使い始めるので、その前に競合を解消できるようにしておく必要がある。

## 仕様

- コアの API の形
- 上書きを拒否する場合と、そのエラー
- local と remote が同じときの上書き
- CLI での選び方
- リモートにある object の送り直し
- テスト

## 決定事項

### コアの API の形

- 事項: 上書きを、syncore の公開 API でどう表すか
- 決定内容: `Push(ctx, plan, PushOptions)`・`Pull(ctx, plan, PullOptions)` とし、どちらのオプションも `Overwrite bool` を持つ。`Overwrite` が false なら、今と同じく自分の判定の plan だけを受け付ける。true なら、どの判定の plan も受け付ける。手順と、承認した後の確かめ方（5-P3・5-P5・6-L6）、base の更新は、`Overwrite` によらず同じにする
- 判断理由: 上書きはどの判定でも選べるので、plan を受け付ける条件を「どの判定でも」に広げるだけにすると、呼び出し側が判定 Pull の plan を誤って `Push` に渡したときに、ほかの PC のセーブを確認なしに上書きする。上書きを明示する引数があれば、この誤りは判定の不一致として止まる。`ForcePush`・`ForcePull` を別に作る案は、手順が同じなのにメソッドが倍になるので採らない。手順を変えないので、承認した後に local や remote が変わったときは、今と同じく `ErrPlanStale` で止まる

### 上書きを拒否する場合と、そのエラー

- 事項: 上書きで転送するものがないときに、どうするか
- 決定内容: `Overwrite` が true で、local が「なし」（`plan.Local.Hash` が空）なら `Push` は、remote が「なし」（HEAD がない）なら `Pull` は、何も変える前に拒否する。センチネルエラー `ErrLocalMissing`・`ErrRemoteMissing` を公開する。`Overwrite` が false のときは、判定が Push・Pull の plan しか受け付けないので、この確かめは要らない
- 判断理由: 仕様書 7-O3・7-O4 による。local が「なし」の Push は空 manifest を HEAD に書き、どの PC でもセーブが消えたように見える。このケースはセーブフォルダの設定の誤りであることが多い。remote が「なし」の Pull は local のセーブをすべて消す。呼び出し側（CLI・GUI）は、「ローカルにセーブがありません」「リモートにセーブがありません」と出し分けるので、センチネルエラーにする

### local と remote が同じときの上書き

- 事項: `Overwrite` が true で、local と remote のハッシュが同じとき、どうするか
- 決定内容: `Push`・`Pull` とも何も転送せず、成功を返す。`plan.RecordBase` が真なら base を記録・更新する。ただし、ふつうの Push・Pull と同じく、同期ロックを取り、ゲームの実行中を確かめ、承認した後に local（ハッシュし直す）か HEAD が変わっていれば `ErrPlanStale` を返す。「同じ」の条件は `Plan.SameContent()` として公開し、CLI も同じ条件で表示を分ける
- 判断理由: 仕様書 7-O5 による。承認した後の確かめを飛ばすと、利用者が見た「同じ」がもう正しくないときに、頼んだ上書きが行われないまま成功と伝わる。base はほかの同期と同じくロックの中で書かないと、同じゲームを同時に Pull している別のプロセスと base を書き合う。条件を公開するのは、コアと CLI がそれぞれ条件を持つと、#64 で条件が変わったときに、転送したのに「転送しませんでした」と出るようなずれが起きるためである。ハッシュが同じなら path・size・sha256 がすべて一致するので、アップロードしても中身の同じ世代ができるだけで、ダウンロードしても同じ中身に入れ替えてバックアップが増えるだけである。上書きで効果が出るのはリモートの object が壊れているときだけで、それには object の送り直しが要る（#64）。#28 のハッシュキャッシュを入れると、中身だけが壊れた local を「同じ」と判定しうるが、これは判定の問題として #28 で扱う

### CLI での選び方

- 事項: CLI で上書きをどう選ぶか
- 決定内容: `push`・`pull` に `-overwrite` フラグを足す。フラグがあれば `Overwrite: true` で呼ぶ。フラグがなければ今と同じく、判定が違えば何もしない。CLI に確認ダイアログの情報（deviceName・日時・ファイル数など）は出さない
- 判断理由: フラグを付けずに `push` を打っただけで、相手側のセーブが消えることを防ぐ。CLI はコマンドの実行を承認とみなすので、フラグが上書きの承認に当たる。v1 の CLI は同期コアを確かめるための道具で、確認ダイアログは GUI（M4）で作る

### リモートにある object の送り直し

- 事項: アップロードで上書きのとき、リモートにある object も送り直すか
- 決定内容: 送り直さない。Push の手順 5-P3 のとおり、リモートにない object だけを送る。送り直す選択（local と remote が同じときの送り直しを含む）（CLI の `-force`）は別の Issue（#64）で扱う
- 判断理由: 送り直すには 5-P3 に例外を足す仕様書の変更が要り、上書きなしでも使えるか、Pull 側にも要るかなど、決めることが残っている。リモートの object の欠けや壊れは、Pull の検証（6-L5）で見つかるので、送り直さなくても壊れたセーブを live に入れることはない

### テスト

- 事項: どう確かめるか
- 決定内容: `package syncore_test` で、7-O1・7-O2 を、上書きで転送が起きる判定（Push・Pull・競合）ごとに 1 ケースずつ書き、上書きした後のリモートの HEAD と manifest、live の中身、base を確かめる。7-O3・7-O4 は、`ErrLocalMissing`・`ErrRemoteMissing` で止まり、何も書かないことを確かめる。7-O3 は、base がある状態（競合）とない状態（判定 Pull）の両方から確かめる。7-O5 は、アップロードとダウンロードのそれぞれで、世代も live も変わらず、base が記録されること、base も同じなら何も書かないこと、承認した後に local か HEAD が変わっていれば `ErrPlanStale` で止まること、ほかの同期が実行中なら `ErrSyncInProgress` で止まることを確かめる。あわせて、上書きでも承認した後にセーブフォルダか HEAD が変わっていれば `ErrPlanStale` で止まることを確かめる
- 判断理由: 判定ごとに出発点の状態（リモートの世代・local・base）が違い、どの状態からでも同じ手順で上書きできることを確かめる必要がある。`Overwrite` が false のときに判定の不一致で止まることと、承認した後の確かめ方は、既存の Push・Pull のテストで確かめているので、上書きの道筋で効いていることを 1 ケースずつ確かめれば足りる

## 結果 / 影響

- 判定によらず、`push --overwrite`・`pull --overwrite` で競合を解消でき、リモートのセーブを取り直すこともできる。`--overwrite` を付けなければ、今までと同じく判定が違えば何もしない
- `Push`・`Pull` のシグネチャが変わり、既存の呼び出し（テストの 75 か所と CLI の 2 か所）にオプションを足した
- local と remote が同じときの上書きは転送しないので、リモートの壊れた object を直す手段は、まだない（#64）
- R2 を相手に CLI で、2 つのデータディレクトリを 2 台の PC に見立てて確かめた。remote なしの `pull --overwrite` と、セーブフォルダがない状態での `push --overwrite` は、それぞれ「リモートにセーブがない」「ローカルにセーブがない」で止まった。競合のとき `push` はフラグがなければ何もせず、`--overwrite` で local を HEAD にした。判定 Pull の PC での `push --overwrite` は、リモートを自分のセーブに戻した。判定 Push の PC での `pull --overwrite` は、live をリモートのセーブにし、元のセーブをバックアップに移した。競合と判定 Pull での `pull --overwrite` も live をリモートのセーブにした。local と remote が同じときは、どちらも「転送しませんでした」と出て、バックアップは増えなかった
- 行数は約 740 行（テスト約 360、既存の呼び出しの書き換え約 80、本体と CLI 約 160、文書約 90）で、見込みの約 550 行を超えた。レビューを受けて、7-O5 の道筋でもロックと承認後の確かめを行うようにし、そのテストを足したため
