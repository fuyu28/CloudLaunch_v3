# gui-game-register-edit

- 日時: 2026-11-27 01:21 (JST)

## 当初の要求 / 背景

GUI には、ゲームを登録・編集する画面がまだなく、ゲームは CLI の `game add`・`game edit`・`game set-image` でしか登録・編集できない。M4 の計画（#140）は、v1 の範囲に「ゲームの登録・編集・画像の設定」を入れ、次のことを決めている。

- 実行ファイルが見つからないときは、7 章のとおり Push も Pull も拒否し、確かめを飛ばす選択は用意しない。エラーからゲームの編集画面へ移り、パスを直せるようにする（#140 の決めたこと 8）
- ランチャーの exe を登録すると、計測も同期の判定も外れるので、登録の画面で本体の exe を選ぶよう案内する（#140 の決めたこと 14）。ランチャーが本体を起動してすぐ終わるゲームが実際にある（`docs/adr/2026-11-04_16-02_game-running.md` の「結果 / 影響」）

仕様書で関係するのは次の規則である。

- 8 章「ゲーム情報」: game.json の項目は `id`・`title`・`brand`・`imageSha256`・`createdAt`・`updatedAt`。衝突したら `updatedAt` の後勝ち（8-G1〜8-G4）
- 8 章「画像」: 10 MiB を超える画像と、PNG・JPEG・WebP でない画像は、設定するときに拒否する（8-I2）。画像はアプリデータフォルダに sha256 をキーにしてキャッシュし、リモートへは次の同期で game.json より先に PUT する（8-I1）
- 9 章「照合と取り込み」: ゲームを登録するたびに、未紐付けの旧履歴とタイトルで照合する（9-K4）。1 件だけ一致したら取り込みを提案し（9-K1）、一致がないか複数あるときは候補一覧から選ぶか、取り込まずに済ませる（9-K2）
- 4 章: セーブフォルダが存在しないことも local の「なし」として扱う

今のコードには次のものがある。

- store: `CreateGame`（新しいゲーム）・`RegisterGame`（`createdAt`・`updatedAt`・`imageSha256` を渡したとおりに書く）・`EditGame`（タイトル・ブランド・`imageSha256` を書き換え、`updatedAt` を進める）。セーブフォルダと実行ファイルのパスを変える操作はない
- metasync: `CacheImage`（8-I2 を検査してキャッシュに入れる）・`SetImage`（キャッシュに入れて DB の `imageSha256` にする）。検査だけをする公開の関数と、キャッシュの画像のパスを返す公開の関数はない
- legacy: `Match`（9-K4 の照合）・`Link`（9-K3 の取り込み）
- GUI: 一覧のゲームのカード（タイトル・ブランド・確認・バックアップ）と設定画面。カードに画像は出していない（`docs/adr/2026-11-17_01-30_gui-skeleton.md`）。実行ファイルが見つからないときは、確認の結果の行にエラーの文を出すだけである

旧版（CloudLaunch_Go）の登録の画面は、パスの入力欄と「参照」ボタン（OS のダイアログ）を並べ、入力を止めて 500 ms 待ってから、ファイル・フォルダがあるかを確かめて欄の下に出していた。この検査は TS に書いてあった。

## 決定事項

### 画面の形と置き場所

- 事項: 登録と編集の画面をどこに、どう出すか
- 決定内容: 一覧の上に「ゲームを登録」ボタンを置き、カードに「編集」ボタンを置く。登録と編集は、設定画面と同じく App の中で画面を切り替えて出し（`page` に `"game"` を足す）、モーダルにはしない。登録と編集は 1 つの Svelte の部品（`GameForm.svelte`）で出し分ける
- 判断理由: 設定画面と同じ形にすると、転送の帯と進捗を画面を切り替えても出し続けられる（`docs/adr/2026-11-17_01-30_gui-skeleton.md`）。モーダルにすると、Esc で閉じられたときの入力中の値の扱いを考える必要がある。登録と編集の項目はほとんど同じなので、部品を分けると同じ欄と検査の表示を 2 回書くことになる

### 登録の画面で入れる項目と検査

- 事項: 登録で入れる項目と、拒否・警告する条件
- 決定内容: 次の項目を入れる。前後の空白は取り除いてから検査し、保存する
  - タイトル（必須）: 空なら拒否する
  - ブランド（任意）: 空なら未設定にする
  - セーブフォルダ（必須）: 絶対パスでなければ拒否する。ファイルを指していれば拒否する。存在しなければ拒否せず、「フォルダがありません。まだ遊んでいないゲームなら、このまま登録できます」と警告する
  - 実行ファイル（必須）: 絶対パスでなければ、存在しないか通常のファイルでなければ、Windows で拡張子が `.exe`（大文字と小文字を区別しない）でなければ拒否する。欄の下に「ランチャーではなく、ゲーム本体の exe を選んでください。ランチャーを選ぶと、実行中かどうかを見分けられず、遊んでいる間のセーブを同期してしまうことがあります」と常に出す
  - 画像（任意）: 下記「画像の登録と編集」
  - パスは `filepath.Clean` で整えて保存する
- 判断理由: セーブフォルダが存在しないことは、4 章で local の「なし」として扱えるので、まだ遊んでいないゲームも登録できるようにする。旧版のように拒否すると、ゲームを一度起動してセーブを作るまで登録できない。ファイルを指すパスは、セーブフォルダとして使えないので拒否する。実行ファイルがなければ、7 章のとおり Push も Pull も拒否されるので、登録の時点で止める。拡張子を `.exe` に限るのは、ショートカット（`.lnk`）やバッチを選ぶと実行中の判定が外れるためである。Linux は開発用なので拡張子を問わない。ランチャーの案内は、選ぶ前に読めるよう、選んだ後ではなく常に出す。ゲーム ID は CLI と同じく UUIDv7 を新しく振り、登録の画面からは指定させない。ID を指定するのはリモートのゲームを取り込むとき（#145）だけである

### 編集の画面で変えられる項目

- 事項: 編集の画面で、どの項目を変えられるようにするか
- 決定内容: タイトル・ブランド・画像・実行ファイルのパスを変えられるようにする。検査は登録と同じにする。タイトル・ブランド・画像のどれも変えていなければ、`EditGame` を呼ばず、`updatedAt` を進めない。セーブフォルダのパスの変更は、この作業では扱わない。編集の画面には表示するだけにする
- 判断理由: #140 の決めたこと 8 が編集の画面に求めるのは、実行ファイルのパスを直すことである。実行ファイルのパスは同期の判定に使わず、実行中の判定（7 章）にだけ使うので、変えても base と食い違わない。セーブフォルダのパスは同期の判定に使うので、変えたときに base をどう扱うかを仕様書で先に決める必要がある。base を残したまま変えると、新しいフォルダの中身が 4-D7（ローカルが変化）と判定され、判定どおりの同期としてアップロードが出る。それまでの間にセーブフォルダを変えたいときは、この PC の登録を解除して（#147）、リモートから取り込み直せる（#145）。セーブフォルダの変更は #144 の範囲外に挙げて残す
- 判断理由（`updatedAt`）: 実行ファイルのパスは同期しないローカル情報（仕様書 3 章）である。それだけを変えたときに `updatedAt` を進めると、game.json の中身が変わらないのに PUT し直し、ほかの PC の編集と後勝ちで競うことになる

### パスと画像の選び方

- 事項: セーブフォルダ・実行ファイル・画像をどう入れさせるか
- 決定内容: 旧版と同じく、パスの入力欄と「参照…」ボタンを並べる。ボタンは Go から Wails の `Dialog.OpenFile()` を開き、選んだパスを返す。セーブフォルダはフォルダを、実行ファイルは `*.exe` の絞り込みを、画像は `*.png;*.jpg;*.jpeg;*.webp` の絞り込みを付けて開く。欄に今の値があれば、そこから親へたどって最初にあるフォルダから開き、どれもなければ既定の場所から開く。Windows の Wails は、開くフォルダがないとダイアログを出さずにエラーを返すためである。キャンセルしたら空を返し、欄を変えない。Windows の Wails はキャンセルをエラー（`cancelled by user`）で返し、その値は Wails の internal のパッケージにあって `errors.Is` で比べられないので、エラーの文で見分けて空にそろえる。入力欄には直接書いてもよい。画像は URL では受け付けず、ファイルだけにする
- 判断理由: パスを直接書けると、ほかのアプリからパスを貼れる。ダイアログを Go から開くので、画像のファイルを Go がパスから読める。WebView の `<input type="file">` で選ぶと、最大 10 MiB の中身を Wails の呼び出しで Go へ送ることになる。絞り込みは選びやすくするためだけのもので、拒否は検査で行う。URL を受け付けるには、取得のタイムアウトや取得先の扱いを決める必要があり、8-I2 もファイルを前提にしているので範囲外にする

### 検査の時点

- 事項: 入力の検査をいつ、どこで行うか
- 決定内容: 検査は Go に置く。Svelte は、欄からフォーカスが離れたときと、「参照…」でパスを選んだときに、フォームの値を Go の `CheckForm` に渡し、欄ごとに返ってきたエラーと警告を欄の下に出す。Go はフォーム全体を検査するが、Svelte は離れたか選んだ欄の結果だけを出し、「登録」を押したらすべての欄の結果を出す。入力の途中では検査しない。応答には番号を振り、新しい呼び出しを始めた後に届いた古い応答は捨てる。「登録」「保存」を押したときも、Go が同じ検査をし直し、エラーがあれば何も書かずに欄ごとのエラーを返す
- 判断理由: 同期の状態と判定、画面に出すデータの組み立ては Go に置き、Svelte は表示と表示のための状態だけを持つ（AGENTS.md の「作る順番」）。v3 では、ファイルの存在も画像の形式も Go でしか確かめられない。欄が 4 つあり、セーブフォルダがないときの警告もあるので、保存を押してからまとめて知らせるより、欄を離れたときに知らせるほうが、どの欄を直せばよいかが分かる。入力を止めて一定の時間がたったときに検査する案は採らない。パスはたいてい「参照…」で選ぶか貼り付けて入れ、1 文字ずつ打つことは少ないので、打つ途中で知らせても得るものが少ない。打ちかけのパスに「存在しません」が出たり消えたりし、Svelte にタイマーも要る。まだ触っていない空の欄に「入れてください」を出すと、入れる前から間違いを指摘することになるので、触った欄の結果だけを出す。古い応答を捨てる番号は、選んだ直後に保存を押すと、検査の応答が保存の後に届くことがあるので要る。保存のときに検査し直すのは、検査の後にファイルが消えたり、古い応答を捨てたりした分を拾うためである。保存のボタンは検査の結果にかかわらず押せるようにし、エラーは保存の応答で出す。押せなくすると、検査が終わるまで待たせることになる

### 画像の登録と編集

- 事項: 画像を、登録と編集の画面からどう設定するか
- 決定内容: 画像の欄にパスがあれば、入力中の検査では Go がファイルを読み、8-I2 を検査する（キャッシュには入れない）。登録では、Go が `CacheImage` でキャッシュに入れてから、`RegisterGame` に `imageSha256` を入れて 1 回で書く（`createdAt` と `updatedAt` は登録した時刻にそろえる）。キャッシュに入れられなければ、ゲームを登録しない。編集では、画像の欄に新しいパスを入れたら差し替え、「画像を外す」を選んだら外す。どちらでもなければ今の画像を残す。差し替えるときは、`CacheImage` の後に、タイトル・ブランドの変更と合わせて `EditGame` を 1 回呼ぶ
- 判断理由: 登録してから `SetImage` を呼ぶと、画像が 8-I2 で拒否されたときに、画像のないゲームだけが登録された状態で失敗を伝えることになる。先にキャッシュに入れれば、画像で失敗したら何も登録しない。`CacheImage` に失敗してもキャッシュに残るのは検査を通った画像だけで、どのゲームからも参照されなくても、同期にも表示にも影響しない。入力中の検査でキャッシュに入れると、選び直すたびに使わない画像がキャッシュに増えるので、検査だけにする。編集でタイトル・ブランドと画像を別々に書くと、片方だけ書けたところで失敗しうるので、`EditGame` の 1 回にまとめる

### 画像の表示

- 事項: 設定した画像を、どこにどう出すか
- 決定内容: 一覧のカードと、編集の画面に、今の画像を出す。Wails の AssetServer に Middleware を足し、`/images/{sha256}` の要求に、キャッシュの画像を返す。`{sha256}` が sha256 の表記でなければ 404 を返す。Content-Type は中身から判定し、PNG・JPEG・WebP のどれでもなければ 404 を返す。カードには、キャッシュに画像があるときだけ画像の URL を渡す。登録の画面と、編集の画面で選び直した画像は、保存するまで表示しない
- 判断理由: 画像を設定しても、表示がなければ設定した結果を確かめられない。`data:` URL で一覧に埋め込むと、画像の数だけ最大 10 MiB を Wails の呼び出しで送る。AssetServer から返せば、WebView が普通の画像として読み込み、キャッシュも効く。パスに `{sha256}` 以外を受け付けると、キャッシュのフォルダの外のファイルを返しうるので、表記を確かめる。8-I4 のとおり、キャッシュの画像の中身が sha256 と違うことがあるので、画像でないものを WebView に渡さないよう中身で確かめる。8-I3 で取得する前の画像（キャッシュにない画像）は、URL を渡さず画像なしとして出す。保存前の画像を表示するには、キャッシュの外の任意のパスを返す口が要るので、範囲外にする

### 実行ファイルが見つからないエラーから編集の画面へ移る

- 事項: 実行ファイルが見つからないときに、どう編集の画面へ移らせるか
- 決定内容: 確認と転送の結果が `syncore.ErrGameExeNotFound` のとき、`CheckView` と `TransferView` に `ExeNotFound` を立てる。カードは、エラーの文の隣に「実行ファイルを直す」ボタンを出し、押すとそのゲームの編集の画面を開いて、実行ファイルの欄にフォーカスを置く
- 判断理由: どのエラーで編集へ移らせるかは同期の判断なので、Go が決めて渡す（AGENTS.md の「作る順番」）。エラーの文を Svelte で見分けると、文言を変えたときに壊れる。確認の後に実行ファイルが消えれば転送でも同じエラーになるので、転送の結果にも同じ印を付ける

### 旧履歴の照合の提案

- 事項: 登録した後の 9-K4 の照合を、GUI でどう出すか
- 決定内容: 登録の応答に `legacy.Match` の結果を入れる。候補が 1 件もなければ何も出さず、一覧に戻る。候補があれば、登録の画面を「旧版のプレイ履歴の取り込み」の表示に切り替える。1 件だけ一致したとき（9-K1）は、そのゲーム（タイトル・旧版の gameId・件数・合計時間・最後に遊んだ日時）を提案として先に出し、「取り込む」と「取り込まない」を置く。ほかの候補も、その下に選べる形で出す。一致がないか複数あるとき（9-K2）は、候補一覧から 1 つを選んで「取り込む」か、「取り込まない」を選ぶ。「取り込む」は `legacy.Link` を呼び、結果の件数を出してから一覧に戻る。照合に失敗しても登録は取り消さず、「ゲームは登録しましたが、旧版のプレイ履歴との照合に失敗しました」と出す
- 判断理由: 9-K1 は確認を取ってから取り込むことを求めるので、提案を出して押させる。提案の他の候補も出すのは、CLI と同じく、提案を断って別の旧ゲームを選べるようにするためである。9-K2 は一致がなくても候補一覧を出すことを求めている。照合は登録の後に行うので、照合の失敗で登録を巻き戻すと、登録できたゲームを失う。旧版のエクスポートの読み込み（9-L1）と、登録済みの全ゲームとの照合（9-K5）は #148 で扱う

### 同じセーブフォルダを複数のゲームに登録すること

- 事項: 2 つのゲームに同じセーブフォルダ、または一方がもう一方の中にあるセーブフォルダを登録しようとしたときの扱い
- 決定内容: #144 では検査せずに登録する。仕様書 11 章の未決事項に挙げる
- 判断理由: そのまま登録すると、片方の Pull がもう片方のセーブを上書きし、片方の Push がもう片方のセーブを含んでしまう。拒否するかどうか、入れ子まで見るか、大文字と小文字やリンクをどう比べるかは、同期の保証範囲に関わる判断で、仕様書で決めることである（AGENTS.md の「設計と実装の分担」）。CLI の `game add` も今は検査しておらず、GUI だけで検査すると振る舞いが食い違う

### コアの変更

- 事項: 登録と編集のために、内部のパッケージに何を足すか
- 決定内容: 次の 3 つを足す
  - metasync: `CheckImage(r io.Reader) error`。8-I2 の検査だけを行う、コアを持たない関数にする。`CacheImage` もこれを使う。拒否した理由は、センチネルエラーの `ErrImageTooLarge`（10 MiB を超える）と `ErrImageFormat`（PNG・JPEG・WebP でない）で返す
  - metasync: `(*Core).CachedImage(sha string) (string, error)`。キャッシュの画像のパスを返す。sha が sha256 の表記でなければエラーを返し、キャッシュになければ `fs.ErrNotExist` を包んで返す
  - store: `(*Store).SetExePath(ctx, gameID, exePath string) error`。`game_locals` の実行ファイルのパスだけを書き換え、`games` の `updated_at` は変えない。登録していないゲームはエラーにする
- 判断理由: 8-I2 の検査とキャッシュの置き場所の形は metasync が持つ決まりで、GUI で組み立て直すと形が 2 か所に分かれる（`BackupDir` と同じ理由、`docs/adr/2026-11-18_15-38_gui-open-backups.md`）。拒否した理由は、画面で「10 MiB を超える」と「形式が違う」を分けて伝えるので、センチネルエラーにする（AGENTS.md の「構成」）。GUI がファイルの大きさを測り直して理由を推測すると、上限の定数を二重に持つことになり、検査とずれうる。登録ではキャッシュへの書き込みの失敗も同じ呼び出しから返るので、それを画像の問題と取り違えないためにも、理由を見分けられる形にする。実行ファイルのパスは同期しないローカル情報（仕様書 3 章）なので、game.json の `updatedAt` を進める `EditGame` には入れない。セーブフォルダのパスを変える関数は、上記のとおりこの作業では扱わないので足さない

### GUI の配線

- 事項: フロントから呼ぶ口
- 決定内容: `cmd/cloudlaunch-gui/game.go` に `GameService` を足し、次を公開する
  - `CheckForm(form GameForm) FormCheck`: 欄ごとのエラーと警告を返す
  - `Register(form GameForm) RegisterView`: 検査し直して登録し、ゲーム ID と旧履歴の照合の結果を返す
  - `LoadEdit(gameID string) EditView`・`SaveEdit(gameID string, form GameForm) SaveGameView`: 編集の画面の値と保存
  - `LinkLegacy(gameID, legacyGameID string) LinkView`: 旧履歴の取り込み
  - `PickSaveFolder(current string) string`・`PickExe(current string) string`・`PickImage(current string) string`: OS のダイアログ
  - `HomeService` のカード（`GameCard`）に `ImageURL` を足す。画像を返す Middleware は `main.go` で組み立てる
  - `GameService` は、store と、リモートにつながない metasync のコア（画像のキャッシュの置き場所だけを使う）を持つ。設定を保存しても作り直さない
- 判断理由: 登録と編集は、一覧の組み立て（`HomeService`）とも確認・転送（`SyncService`）とも責務が違うので、サービスを分ける。画像のキャッシュの置き場所は接続情報で変わらないので、`BackupService` と同じく設定の保存で作り直さない。表示の文言は Go で決め、Svelte は受け取ったものを出す

### テスト

- 事項: 何をどう検査するか
- 決定内容: 内部のパッケージに足した 3 つにテストを書く。GUI の配線にはテストを書かない
  - metasync の `CheckImage`: 8-I2 の各条件（10 MiB ちょうどは受け入れ、1 バイト超えたら `ErrImageTooLarge` で拒否する。PNG・JPEG・WebP は受け入れ、それ以外を `ErrImageFormat` で拒否する）。`CacheImage` の既存のテストと同じ表を使い、2 つが同じ検査をすることを確かめる。`CheckImage` はコアを持たない関数なので、キャッシュに書かないことは形から分かり、テストを書かない
  - metasync の `CachedImage`: キャッシュに入れた画像のパスを返すこと、キャッシュになければ `fs.ErrNotExist`、sha256 の表記でなければエラー
  - store の `SetExePath`: 実行ファイルのパスだけを書き換え、`updated_at` を変えないこと、登録していないゲームはエラーにすること
- 判断理由: metasync は TDD で書く（AGENTS.md の「テスト」）。store も既存のテストに合わせて書く。UI と Wails の配線にはテストを書かない
