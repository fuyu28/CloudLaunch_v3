# gui-skeleton

- 日時: 2026-11-17 01:30 (JST)

## 当初の要求 / 背景

M4 で最初に通す一番細い道として、「GUI を起動 → 一覧 → 1 ゲームの Status → 確認ダイアログ → Push / Pull の進捗 → 完了」を、本物の syncore を相手に端から端まで通す（#140 の進め方 5、#141）。起動時には Recover を呼ぶ（仕様書 6 章「起動時の復旧」）。

フロントエンドは Svelte + Wails v3 で、同期の状態・判定・画面に出すデータの組み立ては Go に置く（`2026-11-15_01-56_gui-svelte-wails3.md`）。この ADR は、次の 2 つを #141 で決めるとしていた。

- Linux で GUI のコードを検査するのに要る `-tags gtk3` を、lefthook と CI でどう扱うか
- 古い呼び出しの結果が後から届いて表示を巻き戻す競合を、Svelte でどう防ぐか

関係する現状は次のとおりである。

- 仕様書 7 章「確認ダイアログに出す情報」のうち、追加・変更・削除されるファイルの数、転送するサイズ、local の最終更新日時は、`syncore.Plan` にない。local の entries は mtime を持たない
- 仕様書 8 章は、GUI のメタ情報の同期を、状態を確認するタイミングに判定と並べて行うとしている。転送の後にメタ情報を同期する `gamesync.Push`・`Pull` は CLI の順序（8-M1〜8-M3）に合わせたものである
- Pull ジャーナル（`pull_operations`）は `game_id` が UNIQUE で、ジャーナルが残っているゲームの Pull は、ジャーナルを書く手順（6-L3）で失敗する
- Windows の Wails v3 は cgo を使わない。Linux の Wails v3 は WebKitGTK を cgo で使う

## 決定事項

### PR の分け方

- 事項: #141 をいくつの PR に分けるか
- 決定内容: 次の 3 つに分ける。どれも #141 の作業とし、最後の PR で #141 を閉じる
  1. Wails v3 + Svelte の雛形、ツール（mise・lefthook・CI）、起動時の Recover、ゲームの一覧
  2. 1 ゲームの確認から転送まで: 確認 → 確認ダイアログ（方向、remote の deviceName と createdAt）→ 判定どおりの Push・Pull → 進捗とキャンセル
  3. 確認ダイアログの情報の残り（ファイルの数・転送するサイズ・local の最終更新日時）、上書き（7-O1〜7-O5）、競合のときに local と remote を並べる表示
- 判断理由: 1 つの PR ではオーナーが全行を読める量（数百行）を超える。3 は syncore に手を入れて TDD で書く部分と、それを表示する画面をまとめたもので、層ではなく仕様書 7 章の項目で縦に切っている

### 確認ダイアログの情報の作り方

- 事項: ファイルの数・転送するサイズ・local の最終更新日時を、どこで作るか
- 決定内容: syncore で作る。`LocalState` に、ファイルの mtime の最大値を足す。方向ごとの差分の要約（追加・変更・削除の数と、転送するサイズ）を返すメソッドを `Plan` に足す。どちらも `status.go` に置き、テストは `status_test.go` に足す。サブパッケージは作らない
- 判断理由: 差分の数え方は、Push・Pull が実際に転送するものと一致させる必要があり、テストで守りたい。`cmd/cloudlaunch-gui` で数えると、テストを書かない場所に数え方が入る。足すのはメソッド 1 つと項目 1 つで、AGENTS.md の「独立して意味を持つ部分が育ったら切り出す」に当たらない。syncore の中の分け方は、M4 を閉じる前に dev 全体へ `/simplify` をかけるときに見直す

### メタ情報の同期と tombstone の扱い

- 事項: GUI の確認と転送で、ゲームの tombstone とメタ情報をどう扱うか
- 決定内容: 確認には `gamesync.Check` を使い、ゲームの tombstone があれば 8-T2 の扱いにして「リモートで削除されました」と出す。転送には `syncore.Push`・`Pull` を直接呼び、メタ情報は同期しない。メタ情報の同期は #143 で、状態の確認と並べて行う
- 判断理由: `gamesync.Push`・`Pull` は転送の後にメタ情報を同期する CLI の順序で、仕様書 8 章の GUI の書き方（確認と並べて同期する）と合わない。`Check` は tombstone の処理（8-M1・8-T2）と判定をまとめており、GUI でも同じ手順が要る。登録の解除・上げ直しの操作は #147 で足す

### 承認した plan と実行する plan の一致

- 事項: ダイアログで見せた plan と、承認の後に実行する plan をどう対応させるか
- 決定内容: plan は Go の側にゲームごとに持つ。確認のたびにトークンを振り、表示用のデータと一緒に返す。Svelte は承認のときにゲーム ID とトークンだけを返す。トークンが Go の持つ最新の plan と違えば、実行せずに確認し直しを求める
- 判断理由: plan を TS に往復させると、Go の型を TS で扱う層が要り、状態を Go と TS の両方に持つことになる（`2026-11-15_01-56_gui-svelte-wails3.md`「Go とフロントの分担」）。トークンで比べれば、確認し直した後に古いダイアログから承認しても、利用者が見ていない plan を実行しない。承認の後に local・remote が変わったときは、これまでどおり syncore が `ErrPlanStale` で止める（7 章）

### 古い結果による表示の巻き戻しの防ぎ方

- 事項: 同じゲームへの呼び出しが重なったときに、古い結果で表示が巻き戻らないようにする方法
- 決定内容: Go の側が、ゲームごとに「今の操作」とその cancel を持つ。同じゲームに新しい確認を頼まれたら、前の確認の ctx を打ち切る。転送中のゲームには確認を受け付けない。キャンセルのボタンは、転送の ctx を打ち切る。別々のゲームの転送が重なったときは、同期ロックで「別の同期が実行中です」として止める（3 章「排他」）
- 判断理由: 試作では、前の呼び出しを cancel して Go の ctx まで打ち切る形で防げた（`2026-11-15_01-56_gui-svelte-wails3.md`「結果 / 影響」）。それを Go の側でゲームごとにまとめて持てば、Svelte は表示のための状態だけを持てばよい。PC 全体の排他はすでに同期ロックが担うので、GUI の側で重ねて排他しない

### 進捗の通知

- 事項: 転送の進捗をフロントへどう届けるか
- 決定内容: Wails のイベント（`application.RegisterEvent[T]`）で、ゲーム ID と `syncore.Progress` を送る。Go の側で間引き、100 ms に 1 回までにする。全体の数を知らせる最初の 1 回と、最後の 1 回は必ず送る
- 判断理由: `syncore` は object を 1 つ転送するごとに進捗を知らせる（`2026-11-16_20-29_transfer-progress.md`）。小さなファイルの多いセーブでは、そのまま送るとイベントが詰まる。最初と最後を必ず送れば、全体の数と完了の表示は欠けない。`RegisterEvent[T]` はイベントの型を TS に生成するので、中身の型を手で書かずに済む

### 起動時の Recover の見せ方

- 事項: 起動時の復旧の結果をどう見せるか
- 決定内容: 一覧を出す前に Recover を呼ぶ。復旧した行はログにだけ残す。失敗した行があれば、画面の上に「起動時の復旧に失敗したゲームがあります」と帯を出す。失敗したゲームの同期を止める仕組みは作らない
- 判断理由: 復旧した行は、利用者が何かをする必要がない。失敗した行が残ったゲームは、仕様書と DB の制約ですでに守られている。Pull は `pull_operations.game_id` の UNIQUE でジャーナルを書く手順（6-L3）で失敗し、セーブフォルダに触らない。live がない状態（6-R2 で止まった場合）では、local が「なし」なので判定が競合（4-D11）になり、Push は提案されない

### Linux での GUI のコードの検査

- 事項: 手元の Linux で GUI を動かす GTK と、Linux の lefthook と CI で `cmd/cloudlaunch-gui` をどう検査するか
- 決定内容: 手元の Linux では、Wails v3 の既定の GTK4（WebKitGTK 6.0）で動かし、`gtk3` のタグは使わない。リント（`.golangci.yml` の `build-tags`）と CI のテスト（`go test -tags purego`）には `purego` のタグを付け、Linux では Wails の cgo を使わない実装で GUI のコードをビルドする。CI に WebKitGTK を入れる手順は足さない。GUI は `mise run gui` でフロントをビルドしてから起動し、`wails3 dev` は使わない
- 判断理由: Wails v3.1 の Linux の既定は GTK4 で、GTK3 はタグで選ぶ古い実装である。GTK4 にすれば、wails3 のインストール・ビルドのどれにもタグが要らない。必要なのは手元に一度 GTK4 版の WebKitGTK を入れることだけである。Wails v3.1 の `purego` の実装は、システムのライブラリを実行時に読み込むので、ビルドに C のヘッダが要らない。そのため WebKitGTK のない CI の Ubuntu でも、Linux 向けの GUI のコードを型検査し、ビルドできる。`go test ./...` はテストのないパッケージもビルドするので、テストにもタグが要る。タグが変えるのは Wails の Linux の実装だけで、Windows と同期コアには影響しない。`cmd/cloudlaunch-gui` を Linux のリントから外す案は、Linux 向けの GUI のコードを検査できなくなるので採らない。CI の Ubuntu に WebKitGTK を入れる案は、依存を含めて大きく、ジョブごとに時間が延びるので採らない。`wails3 dev` は `wails3 init` の雛形が作る Taskfile と設定を前提にし、それらは取り込んでいない（`2026-11-15_01-56_gui-svelte-wails3.md`）。`2026-11-15_01-56_gui-svelte-wails3.md` の「結果 / 影響」にある「lefthook と CI の Ubuntu のジョブにタグを足すか、GTK4 のライブラリを入れる」と、「ツールの管理」の `tags = "gtk3"` は、この決定で置き換える

### データの場所・接続情報・ログ

- 事項: GUI が使う DB・リモートの接続情報・ログの出力先
- 決定内容: データディレクトリは CLI と同じ既定の場所にし、同じ DB を使う。リモートの接続情報は CLI と同じ環境変数から読む。ログは `log/slog` で、データディレクトリの下の `logs/gui.log` に追記する。ローテーションはしない
- 判断理由: CLI と GUI が同じ DB を使えば、どちらで登録・同期したゲームも、もう一方から見える。設定画面と資格情報マネージャーは #142 で足し、そのときに CLI も同じ場所から読むようにする。ログは同期 1 回で数行なので、当面は大きくならない。大きくなったらローテーションを Issue にする

### 一覧に出すもの

- 事項: #141 の一覧に何を出すか
- 決定内容: ゲームごとに、タイトル・ブランド・確認のボタン・最後に確かめた判定を出す。画像・検索・並び替え・起動時の全ゲームの確認は出さない
- 判断理由: 一番細い道を先に通し、つなぎ目の問題を先に出す（#140 の進め方 5）。全ゲームの確認は #143、画像は #144 で足す

### 範囲外にすること

- 事項: #141 で扱わないこと
- 決定内容: 次を扱わない
  - メタ情報の同期と、全ゲームの自動の確認（#143）
  - 画像・検索・並び替え（#143・#144）
  - 設定画面と資格情報マネージャー（#142）
  - ゲームの tombstone があるゲームの登録の解除・上げ直しの操作（#147）
  - フロントの CI（#21）
- 判断理由: どれも一番細い道を通すのに要らず、それぞれの Issue で決めることがある
