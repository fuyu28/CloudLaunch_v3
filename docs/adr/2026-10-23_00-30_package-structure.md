# package-structure

- 日時: 2026-10-23 00:30 (JST)

## 当初の要求 / 背景

v3 の Go のコードを、どの単位でパッケージに分け、パッケージ間の依存をどの向きにするかを決める必要がある。

前身の CloudLaunch_Go は、Clean Architecture の 4 層（domain / infrastructure / services / app）で構成していた。層を種類で分けたため、業務ロジックはすべて services に入り、同期のサービス（`internal/services/content_sync_service.go`）は 1 ファイルで約 1,500 行になった。また services が DB の具象実装と表示用の型（`result.ApiResult`）に直接依存しており、CloudLaunch_Go 自身の移行計画書（`docs/CLEAN_ARCHITECTURE_MIGRATION_PLAN.md`）でも問題として挙げられていた。

v3 では、同期コアを TDD で書き、テストは公開 API 経由で書く（AGENTS.md）。同期コアのテストでは、リモートを偽物に差し替え、中断を再現できる必要がある。

## 仕様

- パッケージをどの単位で分けるか
- 1 つのパッケージが大きくなったとき、どう分けるか
- パッケージ間の依存の向き
- OS 固有の処理をどう分けるか

## 決定事項

### パッケージの分け方

- 事項: パッケージを分ける単位
- 決定内容: 層の種類ではなく責務で分ける。`cmd/cloudlaunch-cli`（配線）、`internal/syncore`（セーブ同期）、`internal/metasync`（メタ情報の同期）、`internal/store`（SQLite）、`internal/objstore`（S3 互換オブジェクトストア）、`internal/platform`（OS 固有の処理）、`internal/synclock`（同期ロック）とする。`services`・`domain`・`util` のような、何でも入る名前のパッケージは作らない
- 判断理由: 種類で分けると、新しい処理の置き場が「業務ロジック」の層 1 つしかなくなり、CloudLaunch_Go の services のように 1 か所に集まる。責務で分ければ、仕様書の章（同期は 2・4〜7 章、メタ情報は 8 章）とパッケージが対応し、置き場に迷わない。`objstore` は、特定のサービス名（R2）を避け、S3 互換であることを表す名前にした

### 大きくなったパッケージの分け方

- 事項: syncore のように 1 つのパッケージが大きくなったときの扱い
- 決定内容: 最初はパッケージの中を仕様書の章に合わせてファイルで分ける。独立して意味を持つ部分（最初の候補は manifest）が育ったら、サブパッケージに切り出し、それ自身の公開 API でテストしてよい
- 判断理由: syncore は、テストを除いて 1,500〜2,500 行の見込みである。最初からサブパッケージに分けると、まだ境界の定まらない部分にも公開 API を作ることになる。ファイルで分けておけば、境界が見えてから切り出せる

### 依存の向き

- 事項: コアとアダプタの依存関係
- 決定内容: syncore と metasync が必要な操作だけのインターフェースを定義し、store・objstore・platform がそれを実装する。syncore と metasync は互いに import せず、cmd で組み合わせる。表示用の型（`ApiResult` など）はコアに置かず、Wails の境界で変換する
- 判断理由: コアがインターフェースを持てば、テストでリモートを偽物に差し替え、任意の手順で失敗を仕込める。コアが SQLite や S3 の実装を知らないので、アダプタを替えてもコアは変わらない。syncore が metasync を import しないよう、ゲームの tombstone の問い合わせも syncore が定義する小さなインターフェースで行う。表示用の型をコアに置くと、`errors.Is` による判別や `%w` で包んだ原因の連鎖が使えなくなり、CLI と GUI で変えたい文言がコアに入る

### OS 固有の処理

- 事項: Windows 固有の処理の置き方
- 決定内容: `internal/platform` に置き、同じパッケージの中でファイル名の接尾辞（`_windows.go` / `_linux.go`）で分ける。製品として保証するのは Windows で、Linux には開発用の最小限の実装（flock、シンボリックリンクの検出、`/proc` の走査）を置く。macOS は扱わない
- 判断理由: Go では OS の違いをファイル名の接尾辞で分けるのが慣例で、OS ごとのサブパッケージにすると呼び出し側がビルドタグで import を切り替えることになる。開発は Linux で行うため、Linux で CLI を R2 につないで試せる実装が要る。macOS と Linux で動く PC ゲームは少なく、それらを製品として保証する必要は小さい

## 結果 / 影響

- 仕様書の章とパッケージが対応するので、変更の置き場が決まりやすい
- コアがインターフェースを定義するため、インターフェースとその実装の 2 か所を保守する手間が増える
- Linux の実装は製品として保証しないので、Linux だけで起きる不具合は放置されうる
