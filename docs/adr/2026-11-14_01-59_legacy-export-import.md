# legacy-export-import

- 日時: 2026-11-14 01:59 (JST)

## 当初の要求 / 背景

仕様書 9 章は、旧版（CloudLaunch_Go）から引き継ぐのはプレイ履歴だけとし、旧版の「データエクスポート」が書き出す `cloudlaunch_export_*.json` をそのまま読み込むとしている。この作業では、読み込み（9-L1〜9-L3）を作る。ゲームとの照合と取り込み（9-K1〜9-K4）は #105 で扱う。

旧版のエクスポートは、旧版の `internal/services/maintenance_service.go` の `GameExportPayload` を `json.MarshalIndent` で書いたものである。ゲームは `games[]`（`domain.Game`）、プレイ履歴は `sessions[]`（`domain.PlaySession`）に入る。

- ID は、旧版の DB の既定値 `lower(hex(randomblob(16)))` で採番した 32 桁の小文字 16 進である
- `playedAt` は Go の `time.Time` をそのまま書いたもので、RFC3339Nano の形になる。時差は旧版を動かした PC の地域時刻のまま（`+09:00` など）で、秒未満の桁数は値によって変わる
- `duration` は秒の整数である
- `games` は、旧版の DB が空のとき `null` になりうる。旧版はゲーム一覧を `nil` のスライスから組み立てるためである

DB の `legacy_sessions` は最初の migration で作ったが、旧版の gameId を持たず、まだどのコードも書き込んでいない。

## 決定事項

### 置き場所

- 事項: 読み込みの処理をどのパッケージに置くか
- 決定内容: `internal/legacy` を新しく作り、9 章（読み込みと、#105 の照合・取り込み）を持たせる。syncore・metasync と同じく TDD で書き、`package legacy_test` で公開 API 経由でテストする。DB の操作は legacy が必要な分だけのインターフェースを定義し、store が実装する。AGENTS.md の「構成」と「テスト」の方針に legacy を足す
- 判断理由: 9 章は、セーブの同期（syncore）にも、リモートとのメタ情報の同期（metasync）にも当たらない。metasync に入れると、metasync の責務が「リモートと同期する」から「ローカルのプレイ履歴を扱う」に広がる。store と cmd だけで済ませると、9-L2・9-L3 の規則が TDD の対象から外れる。legacy はリモートを使わないので、`ObjectStore` は持たない

### 公開 API の形

- 事項: legacy が何を公開するか
- 決定内容: `Import(ctx, r io.Reader, st Store) (Result, error)` を公開する。`Store` は `AddLegacySessions(ctx, []Session) (int, error)` だけを持つ。`Session` は `{ ID, GameID, GameTitle, PlayedAt, DurationSec }` で、`GameID`・`GameTitle` は旧版のものである。`Result` は、保持した件数（`Added`）、同じ ID がすでにあって保持しなかった件数（`Existing`）、`games` にない gameId を持つ件数（`Orphaned`、9-L2）を持つ
- 判断理由: 呼び出し側が振る舞いを分ける必要のあるエラーはないので、センチネルエラーは作らない。不正なエクスポートも、DB の失敗も、CLI はエラーとして出して終わるだけである。`Existing` を返すのは、同じファイルを読み直したときに、保持が 0 件である理由を CLI で示すためである

### 不正なエクスポートの範囲

- 事項: どういうエクスポートをエラーにし、何も書かずに止めるか
- 決定内容: 次のどれか 1 つにでも当たれば、何も書かずにエラーを返す
  - JSON として読めない。最上位がオブジェクトでない
  - 最上位に `games` か `sessions` の項目がない。どちらかが配列でも `null` でもない（`null` は空の配列として扱う）
  - 配列の要素がオブジェクトでない
  - ゲームの `id`・`title` か、プレイ履歴の `id`・`gameId`・`playedAt`・`duration` が、ないか `null` か、型が違う（`duration` は整数として読める JSON の数、ほかは文字列）
  - ゲームの `id` か `title` が空文字
  - プレイ履歴の `id` が 32 桁の小文字 16 進でない
  - `playedAt` が RFC3339 として読めないか、UTC に直した年が 4 桁に収まらない
  - `duration` が負
  - ファイルの中で、ゲームの `id` か、プレイ履歴の `id` が重複している

  項目名は大文字小文字まで含めて比べる。知らない項目は無視する。この範囲は仕様書に書かず、この ADR だけに書く
- 判断理由: 旧版が書いたエクスポートは、どれにも当たらない。当たるのは、別のファイルを選んだか、手で書き換えたものである。その一部だけを読み込むと、どこまで取り込んだかが利用者に分からず、直したファイルを読み直したときに、先に読み込んだ行と混ざる。全体を止めれば、直して読み直すだけで済む。`games` の `null` を許すのは、上の背景のとおり、旧版が書きうる形だからである。項目名を大文字小文字まで比べるのは、Go の encoding/json が構造体の項目名を大文字小文字を区別せずに当て、`ID` のような項目を `id` として通すためである（2026-11-12_00-47_play-session-download.md と同じ）。9-L1〜9-L3 の範囲内での入力の検証なので、仕様書の行は足さない

### `playedAt` の直し方

- 事項: 旧版の `playedAt` を、3 章の日時の形にどう直すか
- 決定内容: `time.RFC3339Nano` で読み、UTC に直して、ミリ秒に切り捨てる
- 判断理由: 旧版は RFC3339Nano で書き、時差は旧版を動かした PC の地域時刻のままである。RFC3339Nano の読み込みは、秒未満の桁がない形と、`Z` と時差の両方を受け入れる。切り捨ては、DB に書くときの store の `formatTime` と同じ扱いである

### 9-L3 の判定と DB への入れ方

- 事項: 未紐付けの旧履歴か通常のプレイ履歴に同じ ID があるものを、どこで判定し、どう入れるか
- 決定内容: store の `AddLegacySessions` が、1 つのトランザクションの中で、1 件ずつ `INSERT … SELECT … WHERE NOT EXISTS (play_sessions に同じ ID) ON CONFLICT (id) DO NOTHING` で入れ、入った件数を返す。入れる前に ID と日時を検証し、1 件でも当たれば何も入れずにエラーを返す。legacy は、入れた件数との差を `Existing` にする
- 判断理由: 2 つの表をまたいだ ID の存在は DB で引かないと分からず、入れるのと同じトランザクションで確かめないと、確かめた後に別の接続が入れる隙間ができる。最初に書き込みを行うのは、WAL で読みから書き込みへの格上げが busy_timeout を待たずに失敗するのを避けるためである（`ImportSessions` と同じ）。ID と日時を store でも検証するのは、`CreateSession` と同じく、DB に入れる時点で形を保証するためである

### migration

- 事項: `legacy_sessions` に旧版の gameId をどう足すか
- 決定内容: 3 つ目の migration で `legacy_sessions` を消して作り直し、`legacy_game_id TEXT NOT NULL` を足す。`legacy_game_id` と `legacy_game_title` には空文字を禁じる CHECK を付ける。タイトルは今と同じく行ごとに持ち、旧ゲームの表は作らない。行は移さない
- 判断理由: この表にはまだどのコードも書き込んでいないので、行を移す必要がない（`hash_cache` を消した 2 つ目の migration と同じ扱い）。`ALTER TABLE ADD COLUMN` で NOT NULL の列を足すには既定値が要り、意味のない空文字の既定値が残る。旧ゲームの表に分けると、旧版でタイトルを変えた後に読み直したときにタイトルがそろうが、9-L3 で既にある行は保持しないので、そういう読み直しで足されるのは新しいプレイ履歴だけであり、表を分ける手間に見合わない

### CLI

- 事項: CLI のコマンドの形と表示
- 決定内容: `legacy import <ファイル>` とし、「旧版のプレイ履歴を N 件保持しました（既にある M 件、games にない K 件は保持していません）」と出す。`--data-dir` はほかのコマンドと同じく受け付ける
- 判断理由: コマンドの名前は AGENTS.md の CLI の一覧のとおりである。9-L2 は件数を出すことを求めている

### テスト

- 事項: どう確かめるか
- 決定内容: legacy は `package legacy_test` で、本物の SQLite（store）を使って、次のケースを書く。`9-L1 エクスポートのプレイ履歴を未紐付けの旧履歴として持つ`（`playedAt` の時差と秒未満の桁を含める）、`9-L2 games にない gameId のプレイ履歴は持たず、件数を返す`、`9-L3 同じファイルを 2 回読み込んでも結果は変わらない`、`9-L3 通常のプレイ履歴に同じ ID があるものは持たない`、`9章/読み込み/games が null でもエラーにしない`、`9章/読み込み/形の違う JSON はエラーにし、何も書かない`（上の範囲を表にする）、`9章/読み込み/知らない項目は無視する`。store には、migration を空の DB に最後まで適用できること（既存のケース）と、`AddLegacySessions` の検証（ID か日時が不正なら何も入れない）のケースを足す。cmd の配線にはテストを書かない
- 判断理由: AGENTS.md のテストの方針（コアのテストは本物の SQLite、仕様書の ID をケース名に入れる、配線にはテストを書かない）に従う

## 結果 / 影響

- CLI の `legacy import` で、旧版のエクスポートのプレイ履歴を未紐付けの旧履歴として持てる。照合と取り込みは #105 で作る
- 実際に使っていた旧版の DB の写しから、旧版と同じく `time.Time` を `json.MarshalIndent` で書いてエクスポートを作り、読み込んだ。`playedAt` は `2026-11-07T23:26:39.4171982+09:00` の形で、20 件を保持した。同じファイルの 2 回目は「0 件保持（既にある 20 件）」だった
- 空白だけのタイトルは不正にしない。旧版の DB の CHECK は空文字だけを禁じているので、旧版が書きうるタイトルである。9-K4 の照合では空になって一致しないが、9-K2 の候補一覧から旧版の gameId で選べる
- 9-L3 の確かめは、旧履歴に入れる時点だけで行う。読み込んだ後に、別の PC が同じエクスポートを取り込んで同期すると、同じ ID が未紐付けの旧履歴と通常のプレイ履歴の両方に入る。この状態は、同期のたびに確かめなくても、9-K3 が取り込むときに旧履歴から消すので、通常のプレイ履歴を入れる側（`CreateSession`・`ImportSessions`）では旧履歴を見ない。#105 で候補を示すときに、こうした ID をどう数えるかは #105 で決める
- 先頭に BOM のあるファイルは、JSON として読めないものとして拒否する。旧版は BOM を書かないので、BOM があるのは保存し直したファイルである
- ID の形・日時の検証・`played_at` の読み出しが、metasync と store のプレイ履歴の処理と重なる。重複の整理は #108 で扱う
- 行数は約 720 行（テスト約 280、legacy 約 200、store と migration 約 100、ADR 約 100、CLI 約 40）で、見込みの約 400 行を超えた。不正なエクスポートの範囲を項目ごとに検証し、表のケースを分けたため
