## 当初の要求 / 背景

仕様書 8 章「プレイ履歴」は、1 セッションを `games/{gameId}/sessions/{sessionId}.json` に置き、ローカルとリモートの和集合を取ると決めている。このうち、ローカルにだけあるセッションを PUT する（8-S1）のが最初の作業である。CLI では `push`・`pull` のたびに、セーブの同期の後でメタ情報を同期する（8-M2）。メタ情報の同期に失敗しても、セーブの同期の結果は変えない（8-M3）。

M3 の進め方（#94）では、`internal/metasync` の骨格だけの PR は作らず、この作業で要る分だけを作る。syncore と metasync は互いに import せず、cmd で組み合わせる（2026-10-23_00-30_package-structure.md）。

## 決定事項

### 扱う仕様書の ID の範囲

- 事項: この作業で、8 章のどの項目を満たすか
- 決定内容: 8-S1・8-S3・8-S6・8-M2・8-M3・8-M4 を扱う。8-M1（ゲームの tombstone の確認）は #100 で扱い、この作業の時点では、tombstone を確かめずにセーブの同期の後でメタ情報を同期する。8-S2・8-S4・8-S5（リモートにだけあるセッションの取り込みと、中身の食い違い）は #96 で扱う
- 判断理由: 8-M4 は `game_locals.remote_deleted_at` を読むだけで満たせ、tombstone の記録を書く #100 より前に入れておけば、記録が書かれた時点で PUT が止まる。8-M1 は `deleted.json` の検証（8-T1〜8-T6）と配下の削除を含み、#100 の範囲である。tombstone を書く操作（#101）は #100 より後に作るので、この作業の時点のリモートには tombstone がなく、確かめなくても削除したデータを戻すことはない

### metasync の公開 API

- 事項: cmd と GUI が metasync をどう呼ぶか
- 決定内容: `metasync.New(Config) *Core` と、`Config{ Remote, Local, Logger }` を置く。`(*Core).Sync(ctx, gameID) (Result, error)` を、1 つのゲームのメタ情報の同期をまとめて行う入口にする。この作業では、プレイ履歴の PUT だけを行う。`Result` には、アップロードしたセッションの件数 `UploadedSessions` を持たせる。取得・ゲーム情報・画像（#96〜#98）は、`Sync` の中に足す
- 判断理由: 仕様書 8 章は、メタ情報の同期を、セーブの判定とは別の 1 つの操作として、確認なしで行うとしている。操作ごとに公開すると、cmd と GUI の両方が呼ぶ順番（画像を PUT してから game.json を PUT する、8-I1 など）を知る必要が出る

### store とのインターフェース

- 事項: metasync がローカルの DB から何を読み、store がどう実装するか
- 決定内容: metasync に `Session{ ID, GameID string; PlayedAt time.Time; DurationSec int64 }` と、`LocalStore{ Sessions(ctx, gameID) ([]Session, error); RemoteDeleted(ctx, gameID) (bool, error) }` を定義する。store がこれを実装する。`RemoteDeleted` は、`game_locals` に行がなければエラーを返す。CLI の `session add` が使う `CreateSession` は store に足し、インターフェースには入れない。store は、syncore と同じく metasync を import する
- 判断理由: 必要な操作だけのインターフェースをコアの側に置く方針である（2026-10-23_00-30_package-structure.md）。登録していないゲームをエラーにするのは、syncore の `Status` がゲームのローカル情報を読めなければエラーにするのと揃えるためである。黙って 0 件として扱うと、gameId の打ち間違いに気づけない

### リモートのインターフェースとテストの偽物

- 事項: metasync がリモートのどの操作を使い、テストで何を偽物にするか
- 決定内容: metasync の `ObjectStore` には `Put` と `List` だけを置く。テストでは既存の `internal/objstore/memstore` を使い、失敗は `Before` フックで仕込む
- 判断理由: この作業で使う操作はその 2 つだけである。memstore は objstore と同じ契約テストを通っており（2026-10-23_01-53_objstore.md）、syncore のテストでも同じ仕込み方を使っている

### キャンセル済みの ctx でのリモートの操作

- 事項: リモートの操作（Get・Put・List・Delete・DeleteMany）が、終わった ctx を受けたときに何をするか
- 決定内容: 呼ばれた時点で ctx が終わっていれば、リモートに触れずに ctx のエラーを返すことを、objstore の実装の契約にする。objstoretest に操作ごとのケースを足し、objstore と memstore の両方に走らせる。objstore（S3）は SDK に任せず、各操作の入口で ctx を確かめる。memstore は `Before` を呼ぶ前に確かめ、`Before` の中でキャンセルされた操作はそのまま実行する。2026-10-23_00-30_remote-object-store.md の「並列実行の分担」に、この契約を足す
- 判断理由: errgroup はキャンセルした後も、入れた関数を空いた枠で動かす。契約がないと、失敗の後に残りの転送を始めないことを、コアが並列の転送ごとに `Put` などの前で確かめることになる。コアで確かめても、確かめてから `Put` を呼ぶまでの間のキャンセルは防げず、保証は実装の入口で確かめるのと変わらない。ctx を受け取る関数がキャンセルを見て止まるのは Go の慣例で、S3 の実装は SDK を通じて元から満たしており、満たしていなかったのは memstore だけである。S3 の入口でも確かめるのは、契約を SDK の内部の振る舞いに預けないためである。`Before` の中でのキャンセルで操作を止めないのは、syncore のテスト（5-P7 など）が、操作の直前にキャンセルされても操作が済んだ場合の振る舞いを、そうして作っているためである

### PUT の並列と失敗

- 事項: 複数のセッションを PUT するときの並列数と、1 件が失敗したときの扱い
- 決定内容: errgroup の `SetLimit(8)` で並列に PUT する。1 件が失敗したら残りをキャンセルし、そのエラーを `%w` で包んで返す。キャンセルの後に回る残りの PUT は、「キャンセル済みの ctx でのリモートの操作」の契約により、PUT せずに ctx のエラーを返す。呼び出し側のキャンセルでも、残りの PUT がエラーを返すので、成功とは返さない。先に PUT できた分はリモートに残す
- 判断理由: AGENTS.md の並列実行の方針（転送は 8 並列、1 つが失敗したら残りをキャンセルし、再試行は SDK に任せる）に従う。DB には同期済みのフラグがなく（仕様書 3 章）、次の同期でリモートの一覧と突き合わせるので、途中まで PUT した状態が残っても、次の同期で残りが PUT される。失敗した後も続けると、オフラインのときに件数分の失敗を待つことになる

### ID が 8-S6 に合わないローカルのセッション

- 事項: DB にある ID が、UUIDv7 の形でも 32 桁の小文字 16 進でもないときの扱い
- 決定内容: store の `CreateSession` は、8-S6 に合わない ID と、UTC の年が 4 桁に収まらない `PlayedAt` を DB に書かずにエラーにする。ID の検証は metasync の `ValidSessionID` を使う。同期では、それでも DB にある、8-S6 に合わない ID のセッションを 1 件だけ PUT せず、Warn のログを出して、残りの同期を続ける
- 判断理由: 8-S6 は、そういう ID をキーにも DB にも使わないとしているので、DB に入れる時点で止める。年が 4 桁を超える日時は 3 章の固定長の形で書けず、読み戻せない。DB に入ると、そのゲームのセッションの読み込みが毎回失敗して、ほかのセッションもアップロードできなくなる。同期の側でも飛ばすのは、DB を直接書き換えられたときに、1 件のために残りのアップロードを止めないためである。検証の規則は、キーの形を持つ metasync に置き、store はそれを呼ぶ

### リモートの一覧で数えるキー

- 事項: `sessions/` の一覧から、どのキーを「リモートにあるセッション」として数えるか
- 決定内容: `games/{gameId}/sessions/` を一覧し、`{ID}.json` の形で、かつ ID が 8-S6 に合うキーだけを数える。ほかのキー（`{sessionId}.deleted.json` など）は数えず、ログも出さない。数えたキーの中身は読まず、ID が一覧にあれば PUT しない
- 判断理由: 8-S3 により、tombstone などはセッションとして数えない。`{ID}.deleted.json` は `.json` で終わるので、末尾の形だけで判定すると、ID が `{ID}.deleted` のセッションとして数えてしまう。ID を 8-S6 で検証すれば、これを外せる。ログを出さないのは、10 章の tombstone が置かれると、同期のたびに出るためである。中身の食い違い（8-S4）は、リモートのセッションを読む #96 で扱う

### セッションの JSON の書き方

- 事項: PUT するセッションの本文の形
- 決定内容: `{"id":…,"gameId":…,"playedAt":…,"durationSec":…}` の順に、構造体から `encoding/json` で書く。`playedAt` は仕様書 3 章の形（`2026-10-22T12:00:00.000Z`）で書く。末尾に改行を付けない
- 判断理由: 項目は仕様書 8 章のとおりである。manifest ハッシュと違い、本文からハッシュを計算して比べることはないので、正規化の規則は要らない

### ロックとゲームの実行中

- 事項: メタ情報の同期で、同期ロックとゲームの実行中の確認を行うか
- 決定内容: どちらも行わない
- 判断理由: 仕様書 3 章「排他」は、メタ情報の同期ではロックを握らないとしている。セッションは書き換えない object なので、同時に書いても壊れない。ゲームの実行中に拒否するのは、セーブフォルダを読み書きする Push・Pull のためで（7 章）、メタ情報の同期はセーブフォルダに触れない

### CLI の `push`・`pull` での呼び方

- 事項: CLI のどの時点で `Sync` を呼び、結果をどう出すか
- 決定内容: `push`・`pull` は、セーブの同期の結果によらず、そのあとに `Sync` を呼ぶ。`Status` の失敗（オフラインなど）・判定が合わないための見送り・Push や Pull の失敗のどの場合も呼ぶ。成功したら「プレイ履歴を N 件アップロードしました」と出す。失敗したら、slog で Warn を出し、標準出力に「メタ情報の同期に失敗しました: …」と出す。終了コードと返すエラーは、セーブの同期の結果だけで決める。`status` では呼ばない
- 判断理由: 8-M2 は、セーブの同期を見送ったときや失敗したときも、メタ情報を同期するとしている。8-M3 により、メタ情報の同期の失敗はセーブの同期の結果に影響させない。`status` は読み取りだけを行う（8 章）

### プレイ履歴を足す CLI

- 事項: R2 で振る舞いを確かめるために、プレイ履歴をどう DB に入れるか
- 決定内容: `cloudlaunch-cli session add --game <gameId> --played-at <RFC3339> --duration <秒> [--data-dir <dir>]` を足す。ID は UUIDv7 で新しく振り、標準出力に出す。`--played-at` を省くと今の時刻にする。どのタイムゾーンで渡しても受け付け、UTC のミリ秒にして保存する。リモートには触れない
- 判断理由: AGENTS.md の CLI の一覧に `session add` がある。v3 で作るセッションの ID は UUIDv7 である（8 章）。アップロードを `push`・`pull` に任せるのは、GUI でもプレイ履歴の記録と同期が別の時点で起こるためで、CLI でも同じ道筋を確かめられる

### テスト

- 事項: どう確かめるか
- 決定内容: metasync は `package metasync_test` で、本物の SQLite（store）と memstore を使って、次のケースを書く。`8-S1 ローカルにだけあるセッションを PUT する`、`8-S1 リモートにもあるセッションは PUT しない`、`8-S3 sessions/ の一覧で .deleted.json を数えない`、`8-S6 形に合わない ID のローカルのセッションは PUT しない`、`8-S6 形に合わない ID のキーはリモートにあるセッションとして数えない`、`8-M4 ゲームの tombstone の記録があれば PUT しない`、`8章/プレイ履歴/PUT に失敗したら、残りを止めてエラーを返す`、`8章/プレイ履歴/一覧に失敗したら、PUT せずにエラーを返す`、`8章/プレイ履歴/PUT する JSON の形`、`8章/プレイ履歴/登録していないゲームはエラーにする`。PUT の失敗のケースは、並列数を超える 20 件を置いてすべての PUT を失敗させ、PUT を始めた数が並列数（8）を超えないことを確かめる。store には、`CreateSession` と `Sessions` の往復、`CreateSession` が 8-S6 に合わない ID と 4 桁に収まらない年を書かないこと、`RemoteDeleted` の真偽のテストを足す。cmd の配線にはテストを書かない
- 判断理由: AGENTS.md のテストの方針（コアのテストは本物の SQLite と偽のリモート、仕様書の ID をケース名に入れる、配線にはテストを書かない）に従う。JSON の形を本文のバイト列で比べるのは、#96 で別の PC が読む形であり、項目名や日時の形の取り違えを、往復のテストでは見落とすためである。PUT の失敗のケースで件数を並列数より多くするのは、並列数に収まる件数では、止めなくても全部が同時に始まり、止めたかどうかが結果に表れないためである

## 結果 / 影響

- CLI の `push`・`pull` のたびに、この PC にだけあるプレイ履歴がリモートに上がる。セーブの同期の見送り・失敗・オフラインでも行い、オフラインの間に記録した分は次の同期で上がる
- `8-S6 形に合わない ID のキーはリモートにあるセッションとして数えない` は、この作業の範囲では「そういうキーがあってもエラーにせず、ローカルの分を PUT する」ことしか確かめられない。この作業ではリモートの中身を読まないので、数えたかどうかが結果に表れないためである。リモートのセッションを取り込む #96 で、数えないことが結果に表れる
- 8-M4 で同期を飛ばしたときも、CLI は「プレイ履歴を 0 件アップロードしました」と出し、飛ばしたことを区別しない。#100 の後は、tombstone の記録があるゲームの `push`・`pull` が 8-M1 で止まり、ここに来ないためである。GUI での表示は M4 で決める
- 日時の形・並列数・UUIDv7 の正規表現が、syncore と metasync（日時の形は store にも）に重複している。syncore と metasync は互いに import しないためで、整理するかどうかはマイルストーンを閉じる前の `/simplify` で扱う
- R2 を相手に CLI で確かめた。セッションを足して `push` すると、Push が実行ファイルの検査で失敗しても、プレイ履歴は 4 件アップロードされた。続く `push` では 0 件だった。判定が合わずに見送った `pull` でも 1 件アップロードされた。接続先を偽にしてオフラインにすると、Warn のログと「メタ情報の同期に失敗しました」を出し、終了コードは `Status` の失敗による 1 だった。そのとき足した分は、次の `push` で上がった。もう 1 台に見立てた PC で同じ gameId を登録して `pull` すると、その PC のセッションが 1 件上がった。最後に、`sessions/` に 7 件の `{ID}.json` が揃っていた。`+09:00` で渡した日時が UTC のミリ秒の形になっていることも確かめた
- 行数は約 930 行（テスト約 470、metasync 約 180、store 約 60、CLI 約 100、ADR 約 110）で、見込みの約 450 行を超えた。テストの環境の組み立てと DB に直接書く補助、並列数を超える件数で止めたことを確かめるケース、ID と日時を DB に入れる時点で検証するテストを足したため
