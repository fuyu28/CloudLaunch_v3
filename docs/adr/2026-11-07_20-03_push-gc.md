# push-gc

- 日時: 2026-11-07 20:03 (JST)

## 当初の要求 / 背景

仕様書 2 章「世代の保持と GC」と 5-P8 は、Push が HEAD を差し替えた後に、直近 10 個の世代を残して古い世代を削除し、残った世代のどれからも参照されない object を削除すると決めている。HEAD が指す世代は、新しい 10 個に入らなくても削除しない。手順 8 で失敗しても Push は成功とし、途中で中断しても次の Push で消える（5-I3）。

M1 の Push は手順 8 を行わず（2026-11-03_01-02_push.md）、リモートに世代と object が溜まり続ける。M2 が終わると実際のゲームのセーブで CLI を使い始めるので、その前に作る。

## 決定事項

### 行う時機とロック

- 事項: GC をいつ、どの状態で行うか
- 決定内容: `Push` が HEAD を差し替えて base を書いた後に、同期ロックを持ったまま行う。上書きの Push でも行う。Pull と、上書きで local と remote が同じため転送しなかったとき（7-O5）は行わない。GC だけを走らせる公開 API と CLI のコマンドは作らない
- 判断理由: 仕様書 5-P8 は、Push の最後の手順として GC を置いている。世代が増えるのは Push だけなので、Push の後に行えば足りる。ロックを持ったまま行えば、同じ PC のほかの同期と重ならない。GC だけのコマンドは仕様書になく、必要になったら別に決める

### 失敗の伝え方

- 事項: GC が失敗したときに、何を返すか
- 決定内容: `slog` で Warn を出し、`Push` は nil を返す。戻り値やセンチネルエラーで GC の失敗を伝えない
- 判断理由: 仕様書 5-P8 により Push は成功である。残った世代と object は次の Push で消えるので（5-I3）、利用者にできることはない。表示すると、Push が失敗したと誤解させる

### キャンセル

- 事項: GC の途中でキャンセルされたら、どうするか
- 決定内容: GC は、`Push` が受け取った、キャンセルできる `ctx` で行う。キャンセルされたら GC をやめ、`Push` は nil を返す
- 判断理由: HEAD を書いた後にキャンセルを無視するのは、成功した Push を失敗と伝えないためで（2026-11-04_14-53_push-setbase-cancel.md）、GC には当てはまらない。止めても 5-I3 のとおり次の Push で片付くので、Ctrl-C で終われないより止めるほうがよい

### 残す世代の manifest が読めないとき

- 事項: 古い世代を削除した後、残した世代の manifest が読めない・解釈できないときに、object を削除するか
- 決定内容: 残した世代の manifest が 1 つでも読めない・解釈できなければ、object の削除を飛ばし、Warn を出す
- 判断理由: どの object が参照されているか分からないまま削除すると、残した世代を Pull できなくなる。消し損ねても、溜まるだけでセーブは失われない

### 想定しない名前のキー

- 事項: `manifests/` と `objects/` の下に、自分が書く形でないキーがあったら、どうするか
- 決定内容: `manifests/` の下で `{UUID}.json` の形でないキーと、`objects/` の下で 64 桁の小文字の 16 進でないキーは、世代の数にも削除の対象にも入れずに残す
- 判断理由: 自分が書いていないものを消さない。数に入れると、残す 10 個の世代が想定しないキーに押し出される

### 削除の並列数と失敗

- 事項: 削除をどう並べ、失敗したらどうするか
- 決定内容: 世代の削除と object の削除は、それぞれ errgroup の `SetLimit` で 8 並列にする。1 つでも失敗したら残りをやめる。世代の削除に失敗したら、object の削除にも進まない
- 判断理由: AGENTS.md の並列実行の方針（転送は 8 並列、1 つが失敗したら残りをキャンセル）に合わせる。世代の削除に失敗したときに object の削除へ進むと、削除できなかった古い世代が参照する object を消し、その世代が壊れたまま残る

### リモートの操作のインターフェース

- 事項: syncore がリモートの削除をどう呼ぶか
- 決定内容: syncore の `ObjectStore` に `Delete(ctx, key) error` を足す。objstore と memstore は、既に同じシグネチャで実装している
- 判断理由: 必要な操作だけをインターフェースに置く方針で（2026-10-23_00-30_package-structure.md）、M1 は削除を使わなかったので置いていなかった。存在しないキーの削除がエラーにならないことは、契約テスト（objstoretest）で確かめてある

### テスト

- 事項: どう確かめるか
- 決定内容: `package syncore_test` で、偽のリモートに世代と object を置いてから Push し、次を確かめる。新しい 10 個を残して古い世代を削除すること、HEAD が指す世代は新しい 10 個に入らなくても残すこと、残した世代のどれからも参照されない object だけを削除すること、想定しない名前のキーを残すこと、残す世代の manifest が読めなければ object を削除しないこと。中止は、偽のリモートで List・Delete・Get に失敗を仕込み、Push が nil を返し、HEAD と base が更新されていることを確かめる（5-P8）。キャンセルも同じく確かめる。中断（5-I3）は、古い世代と不要な object が残った状態を作り、次の Push で消えることを確かめる。ケース名は「2章/世代の保持と GC/…」と、5-P8・5-I3 にする
- 判断理由: 仕様書 2 章の GC の各項目には ID を振らない。AGENTS.md で ID を振ると決めた項目（判定表の行、手順、中断、復旧表の行、不正な manifest の条件）に含まれないため
