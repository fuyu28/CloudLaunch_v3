## 当初の要求 / 背景

仕様書 8 章「ゲーム情報」は、`games/{gameId}/game.json` を文書全体の `updatedAt` の後勝ちで同期するとしている（8-G1〜8-G4）。不正な game.json の条件は 8-V7〜8-V11 で、当たったらそのゲームのゲーム情報の同期だけを止め、DB を書き換えず、ローカルのもので上書きする PUT もしない。

プレイ履歴の同期は 2026-11-11_15-15_play-session-upload.md と 2026-11-12_00-47_play-session-download.md で作った。この作業では、同じ `metasync.Core.Sync` にゲーム情報の同期を足す。画像（8-I1〜8-I3・8-V12〜8-V14）は #98 で扱う。

メタ情報の同期は同期ロックを握らない（仕様書 3 章「排他」）。ゲーム情報の同時更新は、1 章「保証しないこと」に挙げてある。objstore は、キー指定で Get / Put / List / Delete を行う汎用のオブジェクトストアとして扱う（AGENTS.md「構成」）。DB の `games` は `brand` と `image_sha256` を NULL で未設定として持つ。

## 決定事項

### 扱う仕様書の ID の範囲

- 事項: この作業で、8 章のどの項目を満たすか
- 決定内容: 8-G1〜8-G4 と 8-V7〜8-V11 を扱う。`imageSha256` は、game.json と DB の間で値として受け渡すだけにし、画像の取得・設定（8-I1〜8-I3・8-V12〜8-V14）は #98 で扱う。8-M1（ゲームの tombstone の確認）は #100 で扱う
- 判断理由: `imageSha256` は game.json の項目なので、後勝ちで置き換えるときに値は運ぶ必要がある。画像の object を扱う部分は、ゲーム情報の後勝ちとは独立して足せる

### 1 回の `Sync` での順番と失敗の扱い

- 事項: ゲーム情報とプレイ履歴の同期を、どう組み合わせるか
- 決定内容: ゲーム情報 → プレイ履歴の順に行う。game.json の GET・PUT・DB の書き込みが失敗したら、プレイ履歴を同期せずにエラーを `%w` で包んで返す。不正な game.json（8-V7〜8-V11）は失敗に数えず、Warn のログを残してプレイ履歴の同期に進む
- 判断理由: 2026-11-12_00-47_play-session-download.md と同じく、オフラインならどちらも失敗するので、片方の失敗の後にもう片方を試す意味は薄い。不正なデータは、仕様書 8 章「不正なリモートのデータ」により、その単位の同期だけを止め、ほかの単位は続ける。互いに独立させてエラーを `errors.Join` でまとめる案は、失敗のたびに同じ通信の失敗を 2 回待つことになるので採らない

### game.json がないときと、GET に失敗したとき

- 事項: game.json の GET の結果ごとの扱い
- 決定内容: GET が `fs.ErrNotExist` を返したら、8-G1 としてローカルのものを PUT する。それ以外のエラーなら、上の決定のとおりエラーを返す。DB にゲームの tombstone の記録があれば、今と同じく game.json にも触れずにゼロ値を返す（8-M4）
- 判断理由: tombstone を書いた直後で game.json が消えている状態に PUT し直す重なりは、1 章「保証しないこと」（ゲームの削除と重なった書き込み）に含まれ、次に tombstone を見つけたときに消える（8-T2）

### 不正な game.json の検証

- 事項: 8-V7〜8-V11 を、どう判定するか
- 決定内容: 2026-11-12_00-47_play-session-download.md のセッションの検証に揃え、次のとおりにする
  - 8-V7: 本文が 64 KiB を超えるものは、JSON として読めないものとして扱う。上限より先は読まない
  - 項目名は大文字小文字まで含めて比べる。項目は 1 つずつ読み、型の違う値は、その項目の ID で不正とする（`"title": 5` は 8-V9、`"id": 5` は 8-V8）
  - 8-V10: 日時は、3 章の形（`2006-01-02T15:04:05.000Z`）に完全に一致するものだけを通す
  - 8-V11: `imageSha256` は、2 章の形（小文字の 16 進 64 文字）だけを通す
  - `brand`・`imageSha256` は、ないか `null` なら未設定とする。`brand` が空文字のときも未設定とする
  - `brand` が文字列でも `null` でもないときは、8-V7 に含める
  - 知らない項目があっても、不正としない
  - `createdAt` が `updatedAt` より後でも、不正としない
- 判断理由: 構造体に読むと、encoding/json が項目名を大文字小文字を区別せずに当てるので、仕様書の項目名を持たない本文が検証を通る。知らない項目を不正にすると、後の版で項目を足したときに、古い版の PC がゲーム情報を同期できなくなる。`brand` の型の違いには 8 章に ID がないが、期待する形で読めない本文という点で 8-V7 と同じであり、ID を足すための仕様書の変更を挟むほどの違いはない。DB は空文字の brand を NULL として持つ（`CreateGame`）ので、空文字と未設定を区別すると、取り込んで PUT し直すたびに表記が変わる。`createdAt` と `updatedAt` の前後は、後勝ちの比較に使わず、PC の時計のずれで逆になりうるので検査しない

### PUT する game.json の形

- 事項: ローカルのゲーム情報を、どういう JSON で PUT するか
- 決定内容: 項目の順を `id, title, brand, imageSha256, createdAt, updatedAt` に固定する。未設定の `brand`・`imageSha256` は項目ごと省き、`null` は書かない。`version` は持たない
- 判断理由: 仕様書 8 章の `brand?`・`imageSha256?` の書き方に合わせる。順を固定すれば、同じ内容から同じ本文が作られ、リモートの中身を比べて確かめやすい

### PUT の条件

- 事項: 8-G1・8-G2 の PUT に、条件（If-Match など）を付けるか
- 決定内容: 条件を付けずに上書きする
- 判断理由: 古い game.json を読んだ PC が新しい game.json を上書きする競合は、1 章「保証しないこと」に挙げてある。objstore は汎用の Get / Put / List / Delete の契約で、条件つきの PUT を足すには、その契約と memstore・契約テストから変えることになる

### DB を置き換えるときの条件

- 事項: 8-G3 で DB をリモートのもので置き換えるとき、GET から書き込みまでの間のローカルの編集をどう守るか
- 決定内容: DB の `updated_at` がリモートの `updatedAt` より小さいときだけ全項目を書き換える、条件つきの UPDATE にする。条件に合わなければ何も書かず、ゲーム情報の結果は「変更なし」とする
- 判断理由: 同期ロックを握らないので、GET の後に同じ PC で `game edit` が走ることがある。条件がないと、その編集を古いリモートの内容で消してしまう。条件に合わなかったときは、ローカルの方が新しいので、次の同期で 8-G2 として PUT される

### `updatedAt` が等しいときのログ

- 事項: 8-G4 のとき、何を残すか
- 決定内容: 中身が違えば Info のログを残し、同じならログを残さない。どちらでも DB とリモートには触れない
- 判断理由: 8-G4 は、次にどちらかの PC で編集すれば解消する状態で、異常ではないので Warn にはしない。中身の食い違いが続いていることは、ログから追えるようにする

### 編集したときの `updatedAt`

- 事項: ゲーム情報を編集したときの `updatedAt` をどう決めるか
- 決定内容: 今の時刻と、今の `updatedAt` に 1 ms を足した時刻の、大きい方にする
- 判断理由: PC の時計が遅れていると、リモートから取り込んだ `updatedAt` より古い時刻で編集することになり、その編集が 8-G3 で消えるか、等しければ 8-G4 で同期されない。この決め方なら、編集した PC の中では、編集が必ず直前の内容より新しくなる。PC 間の時計のずれで、別の PC の新しい編集に負けることは、後勝ちの前提として受け入れる

### インターフェースと型

- 事項: metasync と store に何を足すか
- 決定内容:
  - metasync に `GameInfo { ID, Title, Brand, ImageSha256 string; CreatedAt, UpdatedAt time.Time }` を置く。`Brand` と `ImageSha256` は空文字を未設定とする
  - `LocalStore` に `GameInfo(ctx, gameID) (GameInfo, error)` と `ReplaceGameInfo(ctx, GameInfo) (bool, error)` を足す。`ReplaceGameInfo` は、`updated_at` の比較と書き換えを 1 つの UPDATE 文で行い、書き換えたときに true を返す。title が空か、sha256 の形が合わないか、UTC の年が 4 桁に収まらない日時があれば、何も書かずにエラーを返す。登録していない ID は、書き換える行がないので false を返す
  - sha256 の表記の判定は `metasync.ValidSHA256` として公開し、store もそれを使う
  - `ObjectStore` には何も足さない
  - store に、CLI 用の `EditGame(ctx, gameID, GameEdit, now)` を足す。今の `updated_at` の読み出しと、上の規則で決めた新しい `updated_at` の書き込みを、1 つの UPDATE 文で行う。今の `updated_at` が日時の上限（`9999-12-31T23:59:59.999Z`）なら、1 ms 足せないので `updated_at` を変えない。metasync のインターフェースには入れない
- 判断理由: 2026-11-11_15-15_play-session-upload.md と同じく、DB に入れる時点でも形を検証する。metasync が検証してから渡すので、ここで当たるのは呼び出し側のバグであり、エラーにする。sha256 の判定を 1 か所にするのは、metasync の検証を通った値を store が拒むような食い違いを防ぐためである。編集は同期の操作ではないので、metasync を通さない。読み出しと書き込みを 1 つの文にすれば、間に入った同期の書き込みを基準にでき、トランザクションの中で読んでから書くときの、WAL での書き込みへの格上げの失敗（store の `ImportSessions` のコメント）も起きない。日時の上限は、リモートから取り込みうる値であり、そのときに編集が NOT NULL 制約で失敗し続けると、どの PC からもゲーム情報を直せなくなる。上限より大きい日時は 3 章の形で書けないので、`updated_at` を据え置くほかない

### 結果と CLI の表示

- 事項: `Sync` の結果に何を返し、CLI に何を出すか
- 決定内容: `Result` に、ゲーム情報の結果を表す値（`GameInfoUnchanged`・`GameInfoUploaded`・`GameInfoDownloaded`・`GameInfoInvalid`）を足す。ゼロ値は `GameInfoUnchanged` とする。CLI は、プレイ履歴の行の前に「ゲーム情報: アップロードしました／取り込みました／変更なし／リモートの game.json が不正なので同期しませんでした」と出す。8-M4 で同期を飛ばしたときは「変更なし」になる
- 判断理由: game.json は 1 ゲームに 1 つなので、不正なときに同期のたびに出しても表示が膨らまず、気づきやすい。プレイ履歴の不正をログだけにした 2026-11-12_00-47_play-session-download.md とは、件数が増えない点で事情が違う

### CLI の入口

- 事項: ゲーム情報の同期を CLI で確かめるため、何を足すか
- 決定内容: `game edit --game ID [--title T] [--brand B] [--data-dir D]` を足す。指定した flag だけを変え、どれも指定しなければエラーにする。`--brand ""` で brand を消す。DB だけを書き換え、リモートへは次の `push`・`pull` で反映する。`imageSha256` は扱わず、`game set-image` として #98 で足す
- 判断理由: flag を指定したかどうかは `flag.FlagSet.Visit` で分かるので、空文字の指定と未指定を区別できる。`session add` と同じく、リモートへの反映は 8-M2 の時点に任せる

### テスト

- 事項: どう確かめるか
- 決定内容: metasync は `package metasync_test` で、本物の SQLite（store）と memstore を使い、8-G1〜8-G4 を 1 ケースずつ、8-V7〜8-V11 を表記の揺れごとに表で書く。ほかに、未設定の項目を省いた PUT の形、知らない項目、取り込んだ後の再同期で PUT しないこと、不正な game.json でもプレイ履歴を同期すること、GET の失敗でプレイ履歴を同期しないこと、2 台の PC で後に編集した方が両方に残ることを書く。8-M4 の既存のケースに、game.json に触れないことの確認を足す。store には `ReplaceGameInfo` と `EditGame` のテストを足す。cmd の配線にはテストを書かない
- 判断理由: AGENTS.md のテストの方針（本物の SQLite と偽のリモート、仕様書の ID をケース名に入れる、複数 PC のシナリオは 2 つのコアに同じ偽のリモートを共有させる、配線にはテストを書かない）に従う。再同期で PUT しないことを確かめれば、PUT する形と読み込む規則が噛み合っていることが分かる

## 結果 / 影響

- CLI の `push`・`pull` のたびに、game.json が後勝ちで同期される。CLI は「ゲーム情報: アップロードしました／取り込みました／変更なし／リモートの game.json が不正なので同期しませんでした」と出す
- 2 台目の PC で `game add --id` で同じ gameId を登録すると、`createdAt`・`updatedAt` がその時刻になるので、最初の同期で 8-G2 に当たり、1 台目の game.json を上書きする。game.json を取り込んで登録する道（8-N3）は #99 で作る
- ゲームの tombstone を確かめる前に同期するので、別の PC がリモートから削除して game.json が消えた後でも、8-G1 で game.json を作り直すことがある。8-M1 の確認を #100 で足せば、同期の前に止まる
- 不正な game.json のログには、項目の生の値を入れる。本文は 64 KiB までしか読まず、game.json は 1 ゲームに 1 つなので、ログの大きさは限られる
- game.json の GET が終わってからプレイ履歴の一覧を始めるので、メタ情報の同期は、リモートへの往復 1〜2 回分だけ長くなる。並列にすると、ゲーム情報の失敗でプレイ履歴を止める決定（「1 回の `Sync` での順番と失敗の扱い」）が込み入るので、受け入れる
- プレイ履歴の検証（`parseSession`）は、日時の検証だけを `parseTimestamp` に揃え、項目がないか `null` かを調べる処理は今の書き方のまま残す。検証の書き方の整理は、#108 で扱う
- R2 を相手に CLI で確かめた。PC A で登録して `push` すると「ゲーム情報: アップロードしました」だった。PC B で `game edit --title Final` の後に `pull` すると、セーブをダウンロードし、ゲーム情報をアップロードした。続けて A で `push` すると、ゲーム情報を取り込み、A の title も「Final」になった。`--brand ""` で消した brand も相手の PC で消え、取り込んだ後にもう一度 `pull` すると「変更なし」だった
- 行数は約 1,130 行（テスト約 570、metasync 約 230、store 約 120、CLI 約 65、ADR 約 150）で、見込みの約 650 行を超えた。8-V7〜8-V11 のケースを表記の揺れごとに分け、store の `ReplaceGameInfo`・`EditGame` のケース（条件つきの書き換え、時計の戻り、日時の上限）を足したため
