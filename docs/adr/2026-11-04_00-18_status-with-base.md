# status-with-base

- 日時: 2026-11-04 00:18 (JST)

## 当初の要求 / 背景

M2 の最初の機能の作業として、base があるゲームを判定できるようにする（仕様書 4 章の判定表の `4-D6`〜`4-D13`）。M1 では「base なし」の 5 行だけを作り、base があると `Status` は「未実装」のエラーを返す（2026-10-27_03-07_manifest-and-status.md「判定する行の範囲」）。このため、同じ PC で Push か Pull をした後の `status` が止まり、CLI を続けて使えない。

「base を記録」の行は、`Plan.RecordBase` と `Core.RecordBase` で扱っている（2026-11-03_01-02_push.md「「base を記録」の行で base を書く操作」）。Pull の手順 9（バックアップ）と起動時の復旧は、まだない（2026-11-03_17-44_pull.md「6 章の手順の範囲」）。

## 仕様

- 判定する行の範囲と、base が空 manifest のときの local の扱い
- 「base を更新」の行で base を書く操作
- 「ローカルにセーブが見つかりません」の警告の伝え方
- base ありの Pull で old ができる問題
- 複数 PC のシナリオのテスト
- CLI の変更

## 決定事項

### 判定する行の範囲と、base が空 manifest のときの local の扱い

- 事項: 判定表のどの行を作り、4 章の「なし」の規則をどこまで入れるか
- 決定内容: 判定表の残りの 8 行（`4-D6`〜`4-D13`）を `Status` に足し、判定表の 13 行すべてを判定する。base が空 manifest のハッシュなら、ファイルが 1 つもない local を「なし」ではなく空 manifest のハッシュとして比べる規則も入れる。テストは 1 行 1 ケースで書き、空 manifest の規則には ID がないので「4章/…」の名前のケースを 1 つ足す
- 判断理由: 判定表は 1 行 1 ケースで全行を書く（AGENTS.md「テスト」）。空 manifest の規則がないと、セーブを空にして Push した後に、毎回 `4-D11`（競合）に当たる（仕様書 4 章）

### 「base を更新」の行で base を書く操作

- 事項: `4-D9`（変更なし（base を更新））で、どの操作が base を書くか
- 決定内容: `4-D4`（base を記録）と同じく `Plan.RecordBase` を true にし、`Core.RecordBase` で書く。名前は変えない。CLI は、plan に base がなければ「base を記録」、あれば「base を更新」と出し分ける
- 判断理由: どちらも、local と remote が同じハッシュなので、それを base に書く操作で、確認を取らない点も同じである（仕様書 4 章）。操作を分けても、呼び出し側が振る舞いを分ける場面がない。承認の後に状況が変わっても読み直さなくてよい理由も、`4-D4` と同じである（2026-11-03_01-02_push.md）

### 「ローカルにセーブが見つかりません」の警告の伝え方

- 事項: `4-D11`（base あり・local なし → 競合）の警告を、呼び出し側にどう伝えるか
- 決定内容: `Plan` に `LocalMissing bool` を足し、`Status` が `4-D11` の行のときだけ true にする。CLI はこれを見て警告を出し、GUI（M4）も同じ値を使う
- 判断理由: 呼び出し側が `Decision`・`Base`・`Local.Hash` から組み立てる案では、判定表の規則が CLI と GUI に 1 つずつ写される。判定表の行を知っているのをコアだけにしておけば、規則が変わったときに直す場所が 1 つで済む

### base ありの Pull で old ができる問題

- 事項: `4-D8`（Pull）では、セーブフォルダにファイルがあるので毎回 old ができ、ジャーナルが残る。これをこの作業で直すか
- 決定内容: 直さず、次の作業（#24、手順 9 と `Recover`）で直す。それまでは、同じゲームを CLI で 2 回 Pull すると、2 回目はジャーナルの書き込みで失敗する
- 判断理由: 手順 9 と `Recover` を入れると、PR がオーナーの読める量（数百行）を超える。この作業の後に実際のセーブで使い始めるわけではないので、間の制約で困る場面がない

### 複数 PC のシナリオのテスト

- 事項: base ありの判定を、Push と Pull が書く base とつないで確かめるか
- 決定内容: 2 つのコアに同じ偽のリモートを共有させ、「A が Push → B が Pull → A が書き換えて Push → B の判定が Pull（`4-D8`）」の 1 ケースを書く。ID には当たらないので、名前は「4章/複数 PC/…」にする
- 判断理由: 判定表の各行のテストは base を直接書いて作るので、Push と Pull が書く base と判定がかみ合うことは確かめられない

### CLI の変更

- 事項: CLI の `status`・`push`・`pull` をどう変えるか
- 決定内容: コマンドの形は変えない。「未実装」のエラーがなくなり、判定と、「base を記録 / 更新」の出し分け、`4-D11` の警告を出す
- 判断理由: 判定の行が増えるだけで、コマンドが受け付ける操作は変わらない

## 結果 / 影響

- この作業から #24 までは、base ありの Pull の後にジャーナルと old が残り、そのゲームの次の Pull が失敗する
