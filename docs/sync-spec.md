# セーブ同期仕様

このファイルが同期の振る舞いの唯一の正である。振る舞いを変えるときは、実装より先にこのファイルを変える PR を通す。

---

## 1. 目的と範囲

CloudLaunch は、PC ゲームのセーブデータを複数の PC 間でリモート（R2）経由で持ち運ぶツールである。同期の対象はセーブフォルダ配下の全ファイルで、v1 では除外パターンを持たない。

### 保証すること

ユーザーが明示的に上書きを選ばない限り、どの PC のセーブも失われない。

同期が途中で中断しても、ローカルとリモートは中途半端な状態にならない。ローカルのセーブフォルダの内容は、同期前か同期後のどちらかと一致する。リモートの HEAD は同期前か同期後の世代を指し、その世代が参照する object はすべてリモートにある（例外は次の「保証しないこと」に挙げる）。

### 保証しないこと

- 同時 Push の排他。2 台の PC がほぼ同時に Push すると、後から HEAD を書いた側の世代が最新になり、先に書いた側の世代は最新でなくなる
- 同時 Push と GC が重なったときの object の存在。このとき最新の世代が、リモートにない object を参照することがある（5 章）。Pull は検証でこれを検出して中止するのでローカルは壊れず、どれかの PC がもう一度 Push すれば直る

### 対象外（v1）

- 過去の世代への巻き戻し、ブランチ、世代の履歴閲覧、ファイル単位のマージ
- 既存のローカル登録を、リモートにあるゲームへ後から紐付けること（gameId の付け替え）
- ゲーム情報の項目単位の後勝ち
- 画像の縮小・サムネイル生成
- 削除したゲームの取り消し、削除済みの gameId の再利用
- プレイ履歴の編集・削除、セーブのリセット、使われていない画像の削除（10 章。v1 の後に実装する）
- OneDrive などのクラウド同期のフォルダの中にあるセーブ

### 用語

- **manifest**: ある時点のセーブフォルダの内容一覧。ファイルごとに相対パス・sha256・サイズを持つ（2 章）
- **空 manifest**: ファイルを 1 つも含まない manifest
- **manifest ハッシュ**: manifest のファイル一覧（`entries`）だけから計算するハッシュ。同期状態の比較はすべてこれで行う
- **object**: リモートに置くファイル実体。sha256 をキーにして保存し、書き換えない
- **世代**: リモートに保存した 1 つの manifest。UUIDv7 で識別する
- **HEAD**: リモートの最新の世代を指すポインタ
- **base**: この PC で、ローカルとリモートが一致したと最後に確認できた manifest ハッシュ
- **local**: 現在のセーブフォルダから計算した manifest ハッシュ
- **remote**: HEAD が指す世代の manifest ハッシュ
- **判定**: base / local / remote から、そのゲームで次に行うべき操作を決めること（4 章）
- **中断**: 同期の途中でプロセスが異常終了すること。電源断を含む
- **tombstone**: リモートのデータが削除されたことを示す記録。ゲーム全体の tombstone（8 章）と、プレイ履歴 1 件の tombstone（10 章）がある

Push・Pull・HEAD・base・manifest・世代・object は、この仕様書と実装の中だけで使う用語である。GUI の表示とユーザーに向けたメッセージには使わず、7 章の言い方（アップロード / ダウンロードなど）で表す。CLI は同期コアを確かめるための開発用の道具なので、この決まりの対象外とする。

## 2. リモートのデータ構造

sha256 の値は、どこでも小文字の 16 進数 64 文字で表す。キー名（`objects/{sha256}`・`images/{sha256}`）、manifest の `sha256`、manifest ハッシュ、game.json の `imageSha256` のすべてが対象である。同じ値が場所によって違う文字列になると、キーの一致や manifest ハッシュの比較が成り立たなくなるためである。

### キーのレイアウト

```
games/{gameId}/HEAD                              最新の世代の UUIDv7（テキスト）
games/{gameId}/manifests/{UUIDv7}.json           manifest（書き換えない）
games/{gameId}/objects/{sha256}                  セーブファイルの実体（書き換えない）
games/{gameId}/game.json                         ゲーム情報（8 章）
games/{gameId}/sessions/{sessionId}.json         プレイ履歴 1 件（書き換えない、8 章）
games/{gameId}/images/{sha256}                   ゲーム画像（書き換えない、8 章）
games/{gameId}/deleted.json                      ゲームの tombstone（8 章）
games/{gameId}/saves-reset.json                  セーブのリセット記録（10 章、v1 の後）
games/{gameId}/sessions/{sessionId}.deleted.json プレイ履歴の tombstone（10 章、v1 の後）
```

### HEAD

HEAD の中身は、最新の世代の UUIDv7 を、ハイフンで区切った小文字の 36 文字で書いたものだけにする。末尾に改行や空白を付けない。読んだ HEAD がこの形でなければ、エラーとして扱う。

### manifest

```json
{
  "version": 1,
  "createdAt": "2026-10-22T12:00:00.000Z",
  "deviceName": "Desktop",
  "entries": [{ "path": "slot1.sav", "sha256": "...", "size": 1234 }]
}
```

- `path` はセーブフォルダからの相対パスで、区切りを `/` に正規化する。大文字と小文字は区別する
- `entries` は `path` の昇順に並べる。昇順は UTF-8 のバイト列の辞書順とする
- mtime は含めない
- 対象は通常のファイルだけで、空ディレクトリは保存も復元もしない
- セーブフォルダの中に通常のファイル以外があれば、manifest を計算せずにエラーにして止める。通常のファイル以外とはシンボリックリンクやジャンクション、OneDrive のファイルのような Windows の reparse point と、デバイスなどである。セーブフォルダそのものがリンクのときも同じとする。通常のファイル以外を飛ばすと、リンク先のセーブが同期されないまま失われうるためである。Windows Server の重複除去で置き換わったファイルは、中身を通常どおり読めるので、通常のファイルとして扱う
- `createdAt` と `deviceName` は、確認ダイアログに表示するためだけに持つ

### manifest ハッシュ

manifest ハッシュは、`entries` だけを正規化 JSON にした sha256 である。`version`・`createdAt`・`deviceName` は含めない。このため、別の PC が同じ内容を Push すれば、作成日時やデバイス名が違っても同じハッシュになる。

正規化 JSON は、次の規則で書き出したバイト列である。書き出しが PC や実装によって 1 バイトでも違うと、同じ内容でもハッシュが変わり、全 PC で全ゲームが変化したと判定されるためである。

- `entries` を `[{"path":"slot1.sav","sha256":"...","size":1234}]` の形の配列で書く。要素の順は manifest の `entries` と同じにする
- 各要素のキーは `path`・`sha256`・`size` の順に並べ、空白と改行を入れない
- 文字列は UTF-8 のまま書き、`"`・`\`・制御文字（U+0000〜U+001F）だけをエスケープする。エスケープの書き方は RFC 8785（JCS）に従う
- `size` は 10 進数の整数で書く
- 空 manifest は `[]` と書く

### 世代の保持と GC

- 世代は直近 10 個を保持する。新しさは世代のキー（UUIDv7）の順で決める
- HEAD の差し替えに成功したら、`manifests/` を一覧し、新しい 10 個を残して残りを削除する
- HEAD が指す世代は、新しい 10 個に入らなくても削除しない。時計のずれた PC が Push すると、その世代のキーが実際より古い順に並び、最新の世代を消してしまうため
- GC（ガベージコレクション）として、古い世代の削除後に、残った世代のどれからも参照されない object を削除する

## 3. ローカルの状態

### 保存先

- DB: SQLite のファイル `%LOCALAPPDATA%\CloudLaunch\cloudlaunch.db` を 1 つだけ置き、GUI と CLI で共有する。同時に開けるよう WAL モードにし、busy_timeout を設定する
- R2 のアクセスキー: Windows 資格情報マネージャーに保存する。秘密でないバケット名とエンドポイントは DB の設定に置く
- 日時: RFC3339 の UTC・ミリ秒の固定長（`2026-10-22T12:00:00.000Z`）で保存する。リモートの JSON も同じ形式にする。固定長なので、文字列の大小比較が日時の前後と一致する

### DB に持つもの

テーブル定義は最初の migration の SQL を正とする。ここでは何を持ち、いつ書くかだけを定める。

- ゲーム情報: game.json と同じ項目。同期しない項目とは別の表に置く
- ゲームのローカル情報（同期しない）
  - セーブフォルダと実行ファイルのパス
  - base。初回は未設定で、判定表の「base なし」に当たる
  - ゲームの tombstone を見つけたときの記録（deletedAt・deviceName）
- プレイ履歴: `{ id, gameId, playedAt, durationSec }`。同期済みかどうかのフラグは持たず、同期のたびにリモートの一覧と突き合わせる
- ハッシュキャッシュ: `(gameId, path)` ごとに、size・mtime（ナノ秒）・sha256 と、その sha256 の計算を始めた時刻を持つ。size と mtime が一致するファイルは sha256 を計算し直さない。キャッシュが消えても全ファイルを計算し直すだけなので、判定の結果は変わらない
  - mtime が、計算を始めた時刻の 2 秒前より新しいファイルは、size と mtime が一致しても計算し直す。計算の直後に同じ size のまま書き換わると、mtime の刻みが粗いファイルシステム（FAT32 は 2 秒）では mtime も同じになり、変化を見落とすためである
  - local の manifest を計算するときは、いつもキャッシュを使う。判定と、5-P3・6-L6 のハッシュし直しを含む。判定と確かめで計算の仕方が違うと、判定では変わっていないと見て、確かめでは変わったと見て、何度やり直しても中止になりうるためである。5-P3 のアップロード中の計算と、6-L5 の stage の検証は、ファイルの中身を確かめるものなので、キャッシュを使わない
  - local の manifest を計算するたびに、そのゲームの行を、今あるファイルの分だけで置き換える
  - size と mtime を保ったまま中身が変わったファイル（mtime を戻すツールでの書き換えや、ビット化け）は、キャッシュを使う限り見落とす。そのため、ユーザーがキャッシュを消して計算し直させる手段を用意する
- Pull ジャーナル: 実行中の Pull 1 件につき 1 行（6 章）。ジャーナルが残っているゲームは削除できない
- 旧版の未紐付けの履歴（9 章）
- 設定: deviceName など。deviceName の初期値は OS のホスト名で、ユーザーが変更できる。同期はしない
- v1 の後に追加するもの（10 章）: 最後に見たセーブのリセット日時、削除したプレイ履歴の記録

ゲームを削除すると、そのゲームのローカル情報・プレイ履歴・ハッシュキャッシュも消える。

### ファイルシステム上の作業領域

Pull では、次の名前のディレクトリを使う。`{opId}` は Pull 1 回ごとに振るランダムな ID である。

- **live**: ユーザーが設定したセーブフォルダそのもの
- **stage**: リモートから取得したファイルを置く `.cloudlaunch-stage-{opId}`
- **old**: 入れ替えで退避した元のセーブを置く `.cloudlaunch-old-{opId}`

stage と old はセーブフォルダの親ディレクトリに作る。リネームによる入れ替えは、同じボリュームの中でしか行えないためである。セーブフォルダの中には作業用のファイルを置かない。

Pull で退避したセーブは、`%LOCALAPPDATA%\CloudLaunch\backups\{gameId}\{UTC 日時}-{opId}\` にバックアップとして移し、ゲームごとに直近 3 個を残す。

- `{UTC 日時}` は Pull を始めた時刻（Pull ジャーナルを書いた時刻）で、`20261022T120000.000Z` の形にする。RFC3339 の形は `:` を含み、Windows のファイル名に使えないためである。固定長なので、名前の順が日時の順と一致する
- 直近 3 個は名前の順で決める。この形の名前でないディレクトリやファイルは、数えも削除もしない
- その Pull で作ったバックアップは、新しい 3 個に入らなくても削除しない。PC の時計が戻ると、作ったバックアップの名前が既存のものより古い順に並び、直前まで使っていたセーブを消してしまうため
- バックアップの置き場所がセーブフォルダと別のボリュームにあり、リネームで移せないときは、old をコピーしてから削除する。old は、コピーしたファイルとバックアップの名前をディスクへ書き出してから削除する

### ディスクへの書き出し

OS は、ファイルの書き込みとリネームをメモリにためてから、あとでディスクに書く。一方、DB への書き込みはコミットのたびにディスクへ届く。そのため、書き出さずに次へ進むと、電源断（1 章の中断）の後に、DB の記録（base・ジャーナルの削除）だけが残り、セーブフォルダが前の状態に戻ったり、中身が空のファイルになったりする。このとき判定は「ローカルが変化」になり、壊れたセーブの Push を提案してしまう。

これを防ぐため、Pull（6 章）・起動時の復旧（6 章）・バックアップへの移動では、ファイルとリネームを、次の手順へ進む前にディスクへ書き出す。どの手順で書き出すかは、6 章の各手順に書く。

### 排他

Push と Pull の実行中は、`%LOCALAPPDATA%\CloudLaunch\sync.lock` を OS のファイルロックで握る。同時に実行できる同期は PC 全体で 1 つだけで、ロックが取れなければ「別の同期が実行中です」として中止する。プロセスが異常終了すれば OS がロックを解放するので、ロックが残り続けることはない。

## 4. 状態判定

判定の入力は base / local / remote の 3 つの manifest ハッシュで、出力は `変更なし` / `Push` / `Pull` / `競合` の 4 値である。判定の前にゲームの tombstone を確認し、あれば判定しない（8 章）。

判定表の「なし」は、次の意味で使う。

- remote の「なし」は、HEAD が存在しないことだけを指す。HEAD が空 manifest の世代を指していれば「あり」である
- local の「なし」は、セーブフォルダにファイルが 1 つもないことを指す。セーブフォルダが存在しない場合も含む
- ただし、base が空 manifest のハッシュなら、ファイルが 1 つもない local は「なし」ではなく、空 manifest のハッシュとして比べる。セーブを空にして Push した後で、毎回競合と判定されるのを防ぐためである

### 判定表

| ID | base | local | remote | 結果 |
|---|---|---|---|---|
| 4-D1 | なし | なし | なし | 変更なし |
| 4-D2 | なし | あり | なし | Push |
| 4-D3 | なし | なし | あり | Pull |
| 4-D4 | なし | あり | あり（local と同じ） | 変更なし（base を記録） |
| 4-D5 | なし | あり | あり（local と異なる） | 競合 |
| 4-D6 | B | B | B | 変更なし |
| 4-D7 | B | 変化 | B | Push |
| 4-D8 | B | B | 変化 | Pull |
| 4-D9 | B | 変化 | 変化（local と同じ） | 変更なし（base を更新） |
| 4-D10 | B | 変化 | 変化（local と異なる） | 競合 |
| 4-D11 | B | なし | B または変化 | 競合（「ローカルにセーブが見つかりません」と警告） |
| 4-D12 | B | B または変化 | なし | Push |
| 4-D13 | B | なし | なし | 変更なし |

「base を記録」「base を更新」の行は、中断からの復旧も担う。Push の HEAD 差し替え後や、Pull の入れ替え後に、base を書く前に中断すると、local と remote が一致して base だけが古い状態が残る。次の判定はこの行に当たり、base が正しい値になる。

判定そのものは副作用を持たない。base の記録と更新は判定とは別の操作で行い、データを転送しないのでユーザーの確認は取らない。

## 5. Push 手順

1. **5-P1** local の manifest を計算し、HEAD を読んで判定し、ユーザーに確認する
2. **5-P2** 承認した時点の remote の世代と local のハッシュを控える
3. **5-P3** リモートにない object をアップロードする。存在の確認は `objects/` の一覧で行う。アップロードではファイルを読みながら sha256 を計算し直し、manifest と違えば中止する（manifest を計算した後にファイルが書き換わった場合）。アップロードを終えたら、local をハッシュし直し、承認した時点から変わっていれば中止する。リモートに object があってアップロードしなかったファイルは、前者の確認を通らないため
4. **5-P4** `manifests/{UUIDv7}.json` を PUT する
5. **5-P5** HEAD を読み直し、2 で控えた世代から変わっていれば中止して、判定からやり直す
6. **5-P6** HEAD を PUT する
7. **5-P7** base を更新する
8. **5-P8** 古い世代の削除と GC を行う。ここで失敗しても Push は成功とする

5 は排他ではない。他の PC の Push と重なりうる時間を短くするだけである。

### 中断したときに残るもの

- **5-I1** 3〜5 で中断した: 参照されない object と manifest が残るだけで、次の GC で消える。HEAD は同期前の世代を指したままである
- **5-I2** 6 と 7 の間で中断した: 次の判定が「B / 変化 / 変化（local と同じ）」の行に当たり、base が更新される
- **5-I3** 8 で中断した: 古い世代と不要な object が残るだけで、次の Push で消える

### GC と同時 Push

同時 Push と GC が重なると、次の順で、最新の世代がリモートにない object を参照することがある。

1. PC-B が、object X はリモートにあると確認してアップロードを省く
2. PC-A の GC が、どの保持世代からも参照されなくなった X を削除する
3. PC-B が、X を参照する世代を HEAD に書く

PC-B が X をアップロードした場合も、manifest を書く前（5-P3 と 5-P4 の間）に PC-A の GC が走れば、X はまだどの世代からも参照されていないので削除される。そのあと PC-B が X を参照する世代を HEAD に書くと、同じ状態になる。

同時 Push は保証の外とする。この状態でも、Pull は検証で X の欠損を検出して中止する。

## 6. Pull 手順

1. **6-L1** HEAD と manifest を取得して判定し、ユーザーに確認する
2. **6-L2** manifest が不正でないことを検証する（下記「不正な manifest」）。不正なら中止する
3. **6-L3** Pull ジャーナルに `{ opId, gameId, live のパス, stage のパス, old のパス }` を書く
4. **6-L4** stage に全ファイルを取得し、ディスクへ書き出す
5. **6-L5** stage を検証する。全エントリの sha256 と size が manifest と一致し、manifest にないファイルがないこと
6. **6-L6** live をハッシュし直し、HEAD を読み直す。live が承認した時点から変わっているか、HEAD が承認した世代から変わっていれば中止する
7. **6-L7** live を old にリネームし、続けて stage を live にリネームする。live が存在しなければ、前半のリネームは行わない。2 つのリネームは、それぞれディスクへ書き出してから次へ進む。live を old にリネームできず、live が残っていれば、6-A1 と同じく stage を削除してからジャーナルを削除して中止する。それ以外のリネームか書き出しの失敗では、ジャーナルを残して中止する（残った状態は復旧表の 6-R2 か 6-R3 に当たる）
8. **6-L8** base を書き込む
9. **6-L9** old をバックアップへ移し（3 章）、移した結果をディスクへ書き出す。古いバックアップを削除して 3 個に保つ。old がなければ行わない。old を移せなければ、ジャーナルを残して中止する（残った状態は復旧表の 6-R3 に当たる）。古いバックアップを削除できなくても、Pull は成功とする
10. **6-L10** ジャーナルを削除する

**6-A1** 4〜6 で中止したときは、stage を削除してからジャーナルを削除する。

### 不正な manifest

Pull は `entries` の `path` に従って stage にファイルを書く。path がステージングの外を指すと、セーブフォルダと無関係な場所に書き込んでしまう。そのため、いずれかのエントリの `path` が次のどれかに当たれば、その manifest を不正として拒否する。

- **6-M1** 空である
- **6-M2** 絶対パスである（`/` や `\` で始まる、ドライブレター `X:` を含む、UNC パスである）
- **6-M3** `/` で区切った要素に、`..`・`.`・空の要素がある（`a..b.sav` のように要素の一部に `..` を含むだけなら正当）
- **6-M4** `\` を含む（区切りは `/` に正規化してあるはずなので、含んでいれば不正）
- **6-M5** 大文字小文字の違いだけで重複する path がある（Windows では同じファイルになるため）

### 起動時の復旧

起動時に、Pull ジャーナルに残っている行ごとに、記録されたパスの状態を見て復旧し、終わったらその行を削除する。

| ID | 残っているもの | 処理 |
|---|---|---|
| 6-R1 | stage があり、old がない | 入れ替えの前に中断した。stage を削除する。live は変わっていない |
| 6-R2 | old があり、live がない | 2 つのリネームの間で中断した。stage を削除し、old を live に戻してディスクへ書き出す |
| 6-R3 | old と live があり、stage がない | 入れ替え後に中断した。old をバックアップへ移す。base が書けていなくても、ここでは書かずに次の判定で記録させる |
| 6-R4 | stage も old もない | 4 より前で中断したか、9 まで終わっている。何もしない |
| 6-R5 | old・live・stage がすべてある | 2 つのリネームの間で中断した後に、ゲームなどが live を作った。どれが正しいセーブか決められないので、行を残してエラーにし、ユーザーに直してもらう |

記録されたパスの状態を確かめられない（存在しない以外のエラーになる）ときも、6-R5 と同じく、行を残してエラーにする。

## 7. 確認フロー

- Push と Pull は、必ずユーザーの確認を取ってから行う
- 確認を出すタイミング
  - ゲーム起動前: 判定が Pull または競合のときだけ
  - ゲーム終了後: 判定が Push のときだけ
  - 手動: ゲーム一覧から、いつでも状態の確認・Push・Pull ができる
- 競合のときは、ゲーム単位で「アップロードで上書き」か「ダウンロードで上書き」を選ぶ。上書きは、競合のとき以外でも選べる（下記「上書き」）
- 承認してから実行するまでに、判定の結果や local・remote のハッシュが変わっていれば、実行せずに中止して確認し直す。ユーザーが見た内容と違うものを転送しないためである
- ゲームのプロセスが実行中なら、Push も Pull も拒否する。実行中のセーブは書き込みの途中かもしれないためである。プロセスはローカル設定の実行ファイルのパスで見つけ、CLI でも同じ判定をする。ローカル設定の実行ファイルが見つからなければ、実行中かを確かめられないので、Push も Pull も拒否し、設定を直すよう伝える

### 上書き

判定によらず、ゲーム単位で「アップロードで上書き」か「ダウンロードで上書き」を選べる。判定どおりの同期では足りないとき（ローカルを捨ててリモートのセーブを取り直したい、など）に使う。

- **7-O1** アップロードで上書きは、判定によらず Push の手順（5 章）で行う
- **7-O2** ダウンロードで上書きは、判定によらず Pull の手順（6 章）で行う
- **7-O3** local が「なし」なら、アップロードで上書きを拒否する。上書きすると、どの PC からもセーブが消えたように見えるためである。セーブを意図して空にするときは、10 章「セーブのリセット」を使う
- **7-O4** remote が「なし」なら、ダウンロードで上書きを拒否する。上書きすると、local のセーブがすべて消えるためである
- **7-O5** local と remote が同じなら、どちらの上書きでも何も転送しない。必要なら base を記録・更新する（4-D4・4-D9 と同じ）。中身が同じなので、転送しても結果が変わらないためである

承認した後の確かめ方（5-P3・5-P5・6-L6）と base の更新も、Push・Pull と同じである。「なし」の意味は 4 章と同じで、base が空 manifest のハッシュなら、ファイルが 1 つもない local は「なし」ではない。

### 確認ダイアログに出す情報

- 方向（アップロード / ダウンロード）
- 追加・変更・削除されるファイルの数
- 転送するサイズ
- remote の deviceName と createdAt
- local の最終更新日時（ファイルの mtime の最大値）

競合のときは、local と remote の情報を並べて出す。

### 見送り・オフライン

同期できないことを理由に、ゲームの起動は止めない。

- 起動前に Pull を見送った: 起動を続け、「このまま遊ぶと、終了後に競合になります」と警告する
- 起動前にオフラインで判定できない: 警告して起動を続ける
- 終了後に Push を見送った、またはオフラインだった: 何もしない。次の判定で再び Push になる

## 8. メタ情報の同期

ゲーム情報とプレイ履歴（メタ情報）は、セーブの判定とは別の操作として、確認なしで同期する。

- GUI: 状態を確認するタイミング（起動前・終了後・手動）に、判定と並べて同期する。セーブの Push を見送っても、プレイ履歴はアップロードされる
- CLI: `push` と `pull` のときに同期する。`status` は読み取りだけを行い、同期しない

同期に失敗しても、セーブの同期の結果には影響させず、通知とログだけを残す。

### ゲーム情報

- `games/{gameId}/game.json` に `{ id, title, brand?, imageSha256?, createdAt, updatedAt }` を置く
- 衝突したら、文書全体で `updatedAt` が大きい方を採る（後勝ち）
- 総プレイ時間や最終プレイ日時などの集計値は持たず、プレイ履歴から計算する

### 画像

- `games/{gameId}/images/{sha256}` に置き、セーブの `objects/` とは別に扱う。セーブの GC は画像を対象にしない
- 画像を変えるときは、新しい画像を PUT してから game.json を PUT する
- 古い画像は削除しない。別の PC の game.json が後勝ちで古い画像を参照し直すことがあるためである。画像を削除するのは、ゲームのリモート削除と、使われていない画像の削除（10 章）のときだけである
- 画像は変換せずに保存する。上限は 10 MB、形式は PNG・JPEG・WebP とする
- ローカルでは、アプリデータフォルダに sha256 をキーにしてキャッシュする

### プレイ履歴

- 1 セッションを 1 オブジェクトとして `games/{gameId}/sessions/{sessionId}.json` に置き、書き換えない
- 同期では、ローカルにだけあるセッションを PUT し、リモートにだけあるセッションを取得する。これで両者の和集合になる

### ゲーム ID

ゲーム ID は UUIDv7 とする。ゲームを登録した PC が採番し、以後変えない。

### 2 台目の PC での取り込み

1. `games/` を区切り文字つきで一覧し、各ゲームの `game.json` を読む。ゲームの tombstone があるゲームは除く
2. この PC に未登録のゲームを一覧で出し、ユーザーが選ぶ
3. 同じ gameId でローカルに登録し、セーブフォルダと実行ファイルのパスを入力してもらう
4. base なしの状態から、通常どおり判定する

### ゲームの削除

ゲームを削除するときは、この PC の登録だけを解除するか、リモートのデータも削除するかを選ぶ。リモートも削除する場合は、次の順で行う。

1. ゲーム名の入力などの強い確認を取り、この PC のセーブをバックアップへ退避する
2. `games/{gameId}/deleted.json`（`{ deletedAt, deviceName }`）を PUT する。これがゲームの tombstone になる
3. `games/{gameId}/` 配下の、ゲームの tombstone 以外をすべて削除する
4. 3 が終わってから、この PC の登録を解除する

3 の途中で中断しても、ゲームの tombstone があるので、どの PC からも削除済みに見える。この PC の登録は残っているので、次にこの PC がゲームの tombstone を見つけたときに、消し残りの削除が再開される。ゲームの tombstone は削除せずに残し続ける。

### ゲームの tombstone を見つけた PC

- 確認なしで、`games/{gameId}/` 配下のゲームの tombstone 以外を削除する。tombstone がある以上、残りのデータを使う PC はないので、どの PC が削除しても安全である
- そのゲームは「リモートで削除されました（deviceName・deletedAt）」の状態になり、Push も Pull もできない。ゲームの起動はできる
- ユーザーが次のどちらかを選ぶ。どちらも自動では行わない
  - この PC でも登録を解除する。セーブフォルダには手を触れない
  - 新しいゲームとして上げ直す。新しい UUIDv7 を振り、ゲーム情報とプレイ履歴を引き継ぎ、base なしから始める

## 9. 旧版からのプレイ履歴取り込み

旧版（CloudLaunch_Go）から引き継ぐのはプレイ履歴だけで、ゲーム一覧と旧版のリモートのデータは引き継がない。

- 旧版の「データエクスポート」が書き出す JSON（`cloudlaunch_export_*.json`）を、そのまま読み込む
- 読み込んだプレイ履歴は、ローカル DB に「未紐付けの旧履歴」として保持し、ゲームを登録するたびに照合する
- 照合では、旧版の `games[].title` と v3 のゲーム名を、前後の空白を除いた完全一致で比べる
  - 1 件だけ一致したら、取り込みを提案し、確認を取ってから取り込む
  - 一致がないか、複数あるときは、旧ゲームの候補一覧から手動で選ぶか、取り込まずに済ませる
- 取り込んだ `sessionRows` は通常のプレイ履歴になり、8 章のとおり同期する
- セッション ID は旧版のものを使い、同じ ID がすでにあれば取り込まない。このため、同じファイルを何度取り込んでも結果は変わらない

## 10. リモートのデータの削除（v1 の後に実装）

この章の機能は v1 では実装せず、v1 の同期コア・CLI・GUI がそろった後の最初の追加として実装する。使うキーは 2 章で予約してある。

### セーブのリセット

セーブのリセットは、どの PC のローカルのセーブも消さずに、リモートのセーブだけを捨てる操作である。

1. 確認を取る
2. `games/{gameId}/saves-reset.json`（`{ resetAt, deviceName }`）を PUT する。リセットのたびに上書きする
3. `HEAD`・`manifests/`・`objects/` を、この順に削除する
4. この PC の base を消し、`resetAt` を記録する

他の PC は、判定の前に `saves-reset.json` を確認する。`resetAt` がその PC の記録より新しければ、base を消して `resetAt` を記録してから判定する。base を消した PC の判定は「base なし」の行に当たるので、リセット後に最初に Push した PC のセーブがリモートの新しい内容になり、内容の違う PC では競合になる。

3 の途中で中断して object が残っても、次の Push の GC で消える。

### プレイ履歴の削除

- プレイ履歴は、確認を取ってから 1 件ずつ削除する
- `games/{gameId}/sessions/{id}.deleted.json`（`{ deletedAt, deviceName }`）を PUT してから、セッション本体を削除する
- 同期で和集合を取るとき、tombstone のあるセッションは、ローカルとリモートのどちらにあっても削除する。ローカルにも削除の記録を持ち、後から届いた本体を取り込まない
- プレイ履歴は編集できない。時間を直すときは、削除してから新しい ID で追加する

### 使われていない画像の削除

- 手動の操作として、現在の game.json が参照していない `images/` 配下の画像を削除する
- 別の PC の古い game.json が後勝ちで、削除済みの画像を参照し直すことがある。その場合はエラーにせず、画像なしとして表示する。この操作の確認ダイアログで、このことを警告する

## 11. 未決事項

- 3 章のバックアップで、今の時刻より新しい名前（時計が進んでいた間に作ったもの）をどう扱うか。今の規則では、そういう名前が 3 個あると、そのあとの Pull で守られるのはその Pull で作ったものだけになる。1 つ前の Pull のバックアップは名前の順で古い側に並ぶので消え、実際のバックアップは 1 個しか残らない。案は、今の時刻より新しい名前を数えない、または消す対象にする、など
- Push でも、6 章「不正な manifest」の規則で local の entries を検証するか。今は検証しないので、ほかの PC の Pull が拒否する manifest を HEAD に書きうる。例えば、Linux や大文字小文字を区別する設定のフォルダで、大文字小文字の違いだけで重複するファイルを Push すると、6-M5 に当たる世代が最新になり、どの PC も Pull できなくなる
- Pull で、manifest の形をどこまで検証するか。今は `version` だけを確かめている。そのため、`entries` が欠けた manifest が空 manifest として通り、Pull するとセーブがすべて消える（元のセーブはバックアップに移る）。また、sha256 が 64 桁の小文字の 16 進でない場合や、entries が path の順に並んでいない場合は、manifest ハッシュが local の計算と一致しない。その結果、判定は「変化」になり、Pull は手順 5 の検証で必ず失敗する
- 6 章「不正な manifest」に、Windows でファイルとして書けない path を足すか。予約されたデバイス名（`CON`・`NUL`・`COM1` など。`aux.sav` のように拡張子が付いていても当たる）と、要素の末尾が `.` か空白のものが当たる。今の規則は、これらを拒否しない。そのため、デバイスに書き込んだり、名前が変わって手順 5 の検証で必ず失敗したりする
- path が正しい UTF-8 でないファイル（Linux の任意のバイト列や、Windows の対になっていないサロゲート）をどう扱うか。manifest ハッシュの計算は path のバイト列をそのまま使う。一方、Push で JSON にするときには U+FFFD に置き換わる。そのため、同じファイルでも local と remote のハッシュが一致しない
- HEAD に載らなかった世代を、GC でどう扱うか。5-I1 は、3〜5 で中断した Push が残した manifest は「次の GC で消える」としている。一方 2 章「世代の保持と GC」は、HEAD に載ったかを区別せずに、キーの新しい 10 個を残す。そのため、5-P5 で中止した Push や中断した Push の manifest は、キーが新しいので残す 10 個に入り、その後の最大 10 回の Push の間残る。その分だけ、HEAD に載った世代が早く消える。その manifest だけが参照する object も残る。案は、5-I1 を「残す 10 個から外れたときに消える」に直す、または GC で HEAD に載った世代を区別する（世代に 1 つ前の世代を書くなど、データ構造の変更が要る）、など
- Pull で取得したファイルの mtime をどうするか。manifest は mtime を持たないので、Pull で取得したファイルの mtime は取得した時刻になる。そのため、7 章の確認ダイアログに出す「local の最終更新日時（ファイルの mtime の最大値）」は、Pull した後は、セーブした時刻ではなく Pull した時刻を表す。例えば競合のときに、local と remote のどちらが新しいセーブかを、この日時では判断できない。案は、manifest の entries に mtime を持たせて Pull で戻す（manifest ハッシュの計算に含めるかも決める必要がある）、または確認ダイアログの項目を変える、など
