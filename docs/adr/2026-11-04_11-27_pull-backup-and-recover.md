# pull-backup-and-recover

## 当初の要求 / 背景

M1 の Pull（2026-11-03_17-44_pull.md）は、仕様書 6 章の手順 9（old をバックアップへ移し、3 個に保つ）と起動時の復旧（`Recover`）を作らなかった。old ができたときはジャーナルを残して成功とするので、そのゲームの次の Pull は、ジャーナルの書き込みが UNIQUE 制約で失敗する。M2 で実際のゲームのセーブで CLI を使い始めるには、手順 9 と `Recover` が要る。

仕様書は、バックアップ名の日時の形、手順 9 で失敗したときの扱い、復旧表のどの行にも当たらない「old・live・stage がすべてある」状態を決めていなかった。これらは先に仕様書で決めた（#36）。

作業は、仕様書の節に沿って 2 つの PR に分ける。見込みの行数が合わせて約 850 行で、1 つの PR では全行を読める量を超えるため。

- 手順 9（6-L9）: バックアップへの移動と、3 個に保つ処理。Pull は手順 10 まで進めてジャーナルを消す
- 起動時の復旧（6-R1〜6-R5）: `Recover`、store の `ListPullOperations`、CLI の `recover`。6-R3 は手順 9 の移動を使うので、手順 9 の後に作る

## 仕様

## 決定事項

### バックアップの置き場所の渡し方

- 事項: 仕様書 3 章の `%LOCALAPPDATA%\CloudLaunch\backups\` を、コアがどう知るか
- 決定内容: `Config` に `BackupsDir string` を足し、配線の側が渡す。CLI は `{data-dir}/backups` を渡す。コアはその下の `{gameId}/` に置く。`BackupsDir` が空なら、Pull はジャーナルを書く前にエラーを返す
- 判断理由: 置き場所は DB と同じく配線の側で決める（DB のパスも CLI の `--data-dir` から作っている）。テストでは一時ディレクトリを渡せる。設定の誤りを手順 9 で見つけると、live を入れ替えた後なので old とジャーナルが残る。何も変える前に止めれば、残るものがない

### ボリュームをまたぐときの移動

- 事項: old とバックアップの置き場所が別のボリュームにあるとき（例: セーブが D:、`LOCALAPPDATA` が C:）、どう移し、途中で中断したらどうなるか
- 決定内容: まずリネームを試す。失敗したら、次の順で移す
  1. `backups/{gameId}/.partial-{名前}` が残っていれば削除し、そこへ old をコピーする
  2. `.partial-{名前}` を最終の名前にリネームする
  3. old を `RemoveAll` する

  移す前に最終の名前のバックアップがすでにあれば、コピーし直さずに old だけを削除する。コピーするのは通常のファイルとディレクトリだけで、それ以外があればエラーにする。コピーはファイルごとに ctx のキャンセルを確かめ、途中で失敗したら `.partial-{名前}` を削除してからエラーを返す
- 判断理由: 途中で失敗した `.partial-` は 3 個に保つ処理の対象にならないので、消さないと残り続け、セーブと同じ大きさのディスクを使い続ける。コピーは大きなセーブで時間がかかるので、ほかの転送やハッシュの計算と同じく取り消せるようにする。リネームは別のボリュームへは行えない。リネームの失敗の理由を見分けずにコピーへ切り替えるのは、ボリュームの違いを OS ごとのエラーで判定せずに済み、リネームがほかの理由で失敗したときもコピーが同じ理由で失敗するだけだからである。この順にすると、どこで中断しても、完全なコピーを途中まで消えた old で上書きしない。最終の名前は同じボリュームの中のリネームで現れるので、最終の名前があれば中身は完全である。old を消している途中で中断すると、次の 6-R3 は最終の名前を見つけて old の残りを消すだけになる。通常のファイル以外の扱いは、仕様書 2 章のセーブフォルダの規則と揃える

### バックアップ名に使う時刻

- 事項: 仕様書 3 章の `{UTC 日時}` に、どの時刻をどこから取るか
- 決定内容: ジャーナルの `created_at` を使い、`20261022T120000.000Z` の形にする。Pull の中では、ジャーナルを書くときに `Config.Now` から作った時刻をそのまま使う
- 判断理由: 仕様書 3 章で Pull を始めた時刻と決めた（#36）。Pull の中と 6-R3 で同じ名前になるので、「最終の名前があるか」で前の移動が終わったかを確かめられる

### 3 個に保つ処理の対象

- 事項: `backups/{gameId}/` の下の何を数え、どう選んで削除するか
- 決定内容: 名前が `{UTC 日時}-{opId}` の形に合うディレクトリだけを数え、名前の順で新しい 3 個を残して残りを `RemoveAll` する。その Pull で作ったバックアップは、3 個に入らなくても削除しない。削除に失敗したら警告のログを出し、Pull は成功とする
- 判断理由: 仕様書 3 章と 6-L9 で決めた（#36・#39）。`.partial-` で始まるものやユーザーが置いたものを数えると、意図しないものを消すか、本物のバックアップを先に消すことになる。PC の時計が戻っていると、作ったばかりのバックアップの名前が一番古くなり、名前の順だけで選ぶと、直前まで使っていたセーブを Pull の成功と同時に消す

### ジャーナルの削除と ctx

- 事項: 中止（6-A1）や手順 10 でジャーナルを削除するとき、どの ctx を使い、失敗したらどうするか
- 決定内容: 中止のときの stage とジャーナルの削除は `context.WithoutCancel(ctx)` で行う。手順 10 の削除に失敗したら、警告のログを出して Pull は成功とする。store の `DeletePullOperation` は、該当する行がなければエラーを返す
- 判断理由: キャンセルで中止したときに呼び出し側の ctx で削除すると、削除そのものが失敗してジャーナルが残り、6-A1 に反する。手順 10 の時点では入れ替え・base・バックアップが終わっているので、エラーを返すと、成功した Pull を失敗と伝えることになる。残った行は stage も old もない状態で、6-R4 が消す。行がないのに成功と返すと、opId の取り違えに気づけない

### テストでリネームの失敗を起こす方法

- 事項: ボリュームをまたぐ経路と、移動に失敗したとき（6-L9）を、テストでどう起こすか
- 決定内容: `Config` に `Rename func(oldpath, newpath string) error` を足す。nil なら `os.Rename` を使う。コアの中のリネームはすべてこれを通す
- 判断理由: テストの中で別のボリュームを用意する方法は、CI の Ubuntu と Windows で揃えられない。`Now` と `NewGeneration` と同じく、差し替えられる依存として扱う

### `Recover` の API と、失敗した行の扱い

- 事項: `Recover` の形と、ある行の復旧に失敗したときの扱い
- 決定内容: `Recover(ctx) ([]Recovery, error)` とする。`Recovery` は `OpID`・`GameID`・`Case` を持ち、`Case` は 6-R1〜6-R4 のどれに当たったかを表す型にする。ジャーナルの全行を処理し、ある行で失敗しても残りの行を続ける。失敗した行はジャーナルを残し、エラーは `errors.Join` でまとめて返す。6-R5 と、パスの状態を確かめられないときも、失敗として扱う。store に `ListPullOperations` を足し、syncore の `LocalStore` にも足す。センチネルエラーは足さない
- 判断理由: 行どうしは別のゲームで、互いに影響しない。1 行の失敗で残りを止めると、関係のないゲームの Pull まで止まる。呼び出し側がすることは、どの行で失敗しても「表示してユーザーに直してもらう」の 1 つなので、振る舞いを分けるためのセンチネルエラーは要らない。`Case` を返すと、CLI がどの行で復旧したかを出せる

### CLI で `Recover` を呼ぶ時機と、`recover` コマンドの形

- 事項: 仕様書 6 章の「起動時」を CLI でどう扱い、`recover` が何を出すか
- 決定内容: `cloudlaunch-cli recover [--data-dir <dir>]` でだけ呼ぶ。`status`・`push`・`pull` は自動では呼ばない。処理した行ごとに gameId・opId・行の ID（6-R1 など）を出し、1 行でも失敗すれば終了コード 1 で終わる。GUI で起動時に自動で呼ぶことは、GUI の段階で決める
- 判断理由: v1 の CLI は同期コアを動かして確かめるための道具で（AGENTS.md「構成」）、復旧が起きたことを見て確かめられる形のほうがよい

### 同期ロックとゲームの実行中の確認

- 事項: `Recover` が仕様書 3 章の `sync.lock` を握るか
- 決定内容: この作業では入れず、#25 で Push・Pull と合わせて入れる
- 判断理由: Push と Pull もまだロックを握っていない。CLI を手で 1 回ずつ実行する間は、`Recover` と同期が重ならない

## 結果 / 影響

### 手順 9（#24）

- Pull は old ができても手順 10 まで進めてジャーナルを消すので、セーブフォルダがあるゲームでも繰り返し Pull できる
- バックアップへ移せなかったときは、ジャーナルと old が残る。#37 で `Recover` を作るまでは、そのゲームの次の Pull はジャーナルの書き込みで失敗する
- 古いバックアップの削除に失敗したときのテストはない。削除を失敗させる手段が OS ごとに違うためで、警告を出して成功とする振る舞いはコードで読むしかない
- R2 を相手に CLI で、セーブフォルダを tmpfs、データディレクトリを btrfs に置いて Pull を繰り返した。リネームが別のファイルシステムへ行えずにコピーの経路を通り、バックアップに元のセーブが入り、`.partial-` と old とジャーナルは残らなかった。4 回目の Pull の後、バックアップは名前の新しい 3 個（v2・v3・v4）だった
- 行数は約 520 行（テスト約 250、本体約 170、ADR 約 100）で、見込みの約 450 行を超えた。ボリュームをまたぐコピーの処理（コピー・mtime の設定・通常のファイル以外の拒否）と、リネームを差し替えるテストの補助が見込みより増えた
