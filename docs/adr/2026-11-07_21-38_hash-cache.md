# hash-cache

- 日時: 2026-11-07 21:38 (JST)

## 当初の要求 / 背景

今の syncore は、local の manifest を計算するたびに、セーブフォルダの全ファイルを読んで sha256 を計算する。判定はゲームの起動前と終了後に行い（仕様書 7 章）、Push・Pull は承認した後にもう一度ハッシュし直す（5-P3・6-L6）。セーブの大きいゲームでは、ここが一番待たされる。

仕様書 3 章は、`(gameId, path)` ごとに size・mtime（ナノ秒）・sha256 と、計算を始めた時刻を持つハッシュキャッシュを決めている。size と mtime が一致するファイルは計算し直さない。mtime が計算を始めた時刻の 2 秒前より新しいファイルは計算し直す。判定と 5-P3・6-L6 のハッシュし直しではキャッシュを使い、5-P3 のアップロード中の計算と 6-L5 の stage の検証では使わない。計算するたびに、そのゲームの行を今あるファイルの分だけで置き換える。キャッシュを消して計算し直させる手段を用意する（#70）。

最初の migration（00001_init.sql）には、計算を始めた時刻を持たない `hash_cache` の表がある。M1 から今までのコードは、この表を読み書きしていない。

この作業では、Pull の後にキャッシュを書くことと、セーブフォルダのパスを変えたときにキャッシュを消すことは扱わない。後者は、パスを変える手段（GUI）ができたときに扱う。キャッシュの行は `(gameId, path)` で引くので、パスを変えた先に、同じ相対パス・size・mtime のファイルがあると、前のフォルダのファイルの sha256 を使ってしまうためである。

## 決定事項

### `Status` がキャッシュを書くこと

- 事項: 「`Status` は副作用なしで plan を返す」（AGENTS.md）と、`Status` がキャッシュを書くことの関係
- 決定内容: `Status` もキャッシュを書く。「副作用なし」は、同期の状態（base・リモート・セーブフォルダ・Pull ジャーナル）を変えないことを指し、キャッシュは含めない。AGENTS.md の `Status` の説明も「同期の状態を変えずに plan を返す。ハッシュキャッシュは書く」に改める
- 判断理由: キャッシュは、消えても判定の結果が変わらない（仕様書 3 章）。`Status` が書かないと、キャッシュが効くのは Push・Pull の後だけになり、一番回数の多い起動前と終了後の判定で、毎回全ファイルを計算する

### キャッシュを使う計算と、使わない計算の分け方

- 事項: 今の `localEntries` は、判定（`Status`）、承認後の確かめ（`ensureLocalUnchanged`）、stage の検証（6-L5）で共有されている。どれにキャッシュを使うか
- 決定内容: ゲームのセーブフォルダの manifest を計算する関数（判定と承認後の確かめが呼ぶ）と、キャッシュを使わない関数（stage の検証が呼ぶ）に分ける。ファイルの一覧の取り方（通常のファイル以外とディレクトリの reparse point をエラーにする規則、仕様書 2 章）と、並列のハッシュ計算（キャッシュの行を渡さなければ、すべてのファイルを読む）は共有する。5-P3 のアップロード中の計算は、今までどおりファイルを読む
- 判断理由: 仕様書 3 章による。stage の検証はファイルの中身を確かめるもので、stage のファイルは Pull ごとに新しく作られるので、キャッシュに当たることもない

### 計算を始めた時刻の持ち方と、表の作り直し

- 事項: 計算を始めた時刻を、どの形で、どの単位で持つか。既存の表をどう変えるか
- 決定内容: 新しい migration で `hash_cache` を作り直し、計算を始めた時刻の列（`hashed_at`）を足す。形は仕様書 3 章の日時の形（RFC3339 の UTC・ミリ秒の固定長の文字列）にする。計算を始めた時刻は、1 回の manifest の計算の始めに 1 回取り、その計算で書く行すべてに使う。時刻は、コアの `Now` で差し替えられるようにする
- 判断理由: 既存の表は一度も書いていないので、作り直しても失うものはない。列を足す（`ALTER TABLE ADD COLUMN`）には、`NOT NULL` の列に既定値が要り、意味のない既定値を入れることになる。キャッシュは消えても計算し直すだけなので（仕様書 3 章）、仮に行があっても作り直してよい。日時は 3 章で形が決まっている。2 秒の規則にはミリ秒で足りる。mtime をナノ秒の整数で持つのは、ファイルシステムの値と完全に一致するかを比べるためで、日時の比較に使う `hashed_at` とは役割が違う。時刻を差し替えられれば、2 秒の規則をテストで確かめられる

### コアとストアの間のインターフェース

- 事項: syncore がキャッシュをどう読み書きするか
- 決定内容: syncore の `LocalStore` に、ゲームのキャッシュの行をすべて返す操作と、ゲームの行を渡したものだけで置き換える操作（1 つのトランザクションで、消してから書く）、ゲームの行を消す操作を足す。行の型は syncore に定義し、store が返す。ファイルを stat して、size と mtime が一致し、mtime が `hashed_at` の 2 秒前より古ければ、キャッシュの sha256 を使う。そうでなければ計算し、新しい行の `hashed_at` はその計算の始めの時刻にする
- 判断理由: 必要な操作だけをコアの側で定義し、store が実装する（2026-10-23_00-30_package-structure.md）。行の型を syncore に置いて store が返す形は、`ListPullOperations` と同じである（2026-11-04_11-27_pull-backup-and-recover.md）。置き換えを 1 つのトランザクションにするのは、GUI と CLI が同じ DB を開いても（仕様書 3 章）、途中の状態を読ませないためである。キャッシュの sha256 を使った行の `hashed_at` は、前の値を引き継ぐ。列の意味を「その sha256 の計算を始めた時刻」（仕様書 3 章）に保つためである

### キャッシュを消す手段

- 事項: キャッシュを使わずに計算し直させる手段（仕様書 3 章）をどう作るか
- 決定内容: コアに、ゲームのキャッシュの行を消すメソッド（`ForgetHashes(ctx, gameID)`）を足す。CLI の `status`・`push`・`pull` に `--rehash` を足し、付いていれば判定の前にこのメソッドを呼ぶ。`Status` のシグネチャは変えない
- 判断理由: キャッシュを消せば、次の計算はすべてのファイルを読む。`Status` にオプションの引数を足す案は、呼び出し側をすべて書き換えることになる。中身だけが壊れた local を「同じ」と判定して、上書きでも転送されない場合（7-O5）は、`--rehash` で判定し直せば、壊れたことが変化として見える

### 古いかもしれないキャッシュと、読み書きの失敗

- 事項: キャッシュが古いかもしれないと分かったとき、キャッシュの読み書きに失敗したとき、どうするか
- 決定内容: 次のときは、そのゲームのキャッシュを消す。消せなければログに出して続ける
  - Push のアップロードで、ファイルの中身が plan の sha256 と違ったとき（`ErrPlanStale` で止まる前に消す）
  - Pull で stage を live に入れ替えて base を書いた後

  キャッシュを読めなければ、ログに出してすべてのファイルを読む。書けなければ、ログに出して続ける。計算した行がキャッシュと同じなら書かない
- 判断理由: キャッシュは、消えても判定の結果が変わらない（仕様書 3 章）ので、消すことと、なしで続けることは、判定を変えない。アップロードで中身の違いが分かるのは、承認した後に書き換わったか、キャッシュが古い（size と mtime を保ったまま中身が変わった）ときである。後者でキャッシュを残すと、やり直しても同じ plan になり、毎回 `ErrPlanStale` で止まる。Pull で入れ替えた後のキャッシュには、入れ替える前のファイルの行が残る。mtime の粗いファイルシステムでは、取得したファイルの size と mtime がその行に一致し、前のファイルの sha256 を使いうる。Pull の後に取得したファイルの行を書く案は、この作業の範囲外にしたので（背景）、消すだけにする。読み書きの失敗で判定を止めないのは、GUI と CLI が同じ DB を開いて書き込みが待たされたときなどに、なくても済むキャッシュのために判定や Push を失敗させないためである。同じ行を書かないのは、判定のたびに全行を消して書き、ディスクへ書き出す（synchronous は FULL）費用を避けるためである

### テスト

- 事項: どう確かめるか
- 決定内容: `package syncore_test` で、次を確かめる。size と mtime が一致するファイルは読まずにキャッシュの sha256 を使うこと（キャッシュに入れた sha256 を実際と違う値にしておき、判定に現れることで確かめる）。size か mtime が違えば計算し直すこと。mtime が `hashed_at` の 2 秒前より新しければ計算し直すこと。消えたファイルの行を消すこと。`Status` がキャッシュを書くこと。承認後の確かめでもキャッシュを使うこと。`ForgetHashes` の後はすべて計算し直すこと。アップロードで中身の違いを見つけたときと、Pull で入れ替えた後に、キャッシュを消すこと。キャッシュの読み書きに失敗しても判定すること（store を包んで失敗を仕込む）。行が変わらなければ書かないこと。store では、置き換えと読み込み、ゲームの削除で行が消えることを確かめる。ケース名は「3章/ハッシュキャッシュ/…」にする。stage の検証でキャッシュを使わないことは確かめない
- 判断理由: キャッシュを使ったかどうかは、判定の結果からは見えない（正しいキャッシュなら同じ結果になる）。キャッシュの sha256 をわざと違う値にすれば、使ったかどうかを公開 API の結果で確かめられる。stage のファイルは Pull ごとに新しく作られ、mtime を前もって知れないので、キャッシュを使っていても当たらず、公開 API の結果に違いが出ない

## 結果 / 影響

- 変わっていないファイルは、判定でも承認後の確かめでも読まない。R2 を相手に CLI で、1.5 GB のファイルを含むセーブフォルダの `status` を続けて実行すると、1 回目が約 1.7 秒、2 回目が約 0.4 秒（ほぼリモートの読み込みの時間）だった。`--rehash` を付けると約 1.7 秒に戻り、その後はまた約 0.3 秒になった。この計測は OS のファイルキャッシュに載った状態のもので、ディスクから読むときの差はもっと大きい
- Pull した直後の判定は、全ファイルを読む（Pull の後にキャッシュを消すため）
- Push のアップロードで中身の違いが分かると、キャッシュを消すので、次の判定は全ファイルを読む
- size と mtime を保ったまま中身が変わったファイルは、アップロードされない限り見落とす。`--rehash` で計算し直せる
- セーブフォルダのパスを変えたときのキャッシュの扱いは、パスを変える手段（GUI）ができたときに決める
- 行数は約 800 行（テスト約 450、本体約 200、文書約 150）で、見込みの約 600 行を超えた。レビューを受けて、古いかもしれないキャッシュを消すこと、読み書きの失敗で判定を止めないこと、同じ行を書かないことと、それらのテストを足したため
