# gui-svelte-wails3

- 日時: 2026-11-15 01:56 (JST)

## 当初の要求 / 背景

`docs/adr/2026-10-23_00-30_gui-frontend.md` は、GUI の枠組みを Wails とし、フロントエンドの第一候補を Go のテンプレート + htmx、次点を Svelte とした。どちらにするかは、GUI に着手するときに、進捗の表示と確認ダイアログを含む 1 画面を試作して決めるとしていた。Wails は安定版の v2 を前提とし、v3 の安定度は GUI に着手するときに確かめるとしていた。

試作は次の 5 つを作った。同期は偽物で、ゲームの一覧と登録だけ本物の store を使った。

| 試作 | 作った範囲 | 手で書いた量（CSS と偽の同期を除く） |
|---|---|---|
| html/template + htmx（Wails v2） | ホーム（一覧・検索・並び替え・追加）だけ | 371 行 |
| templ + htmx + Alpine.js（Wails v2） | ホーム + 確認ダイアログ + 進捗 + キャンセル | 約 525 行 |
| templ + Datastar（Wails v2） | 同上 | Go のハンドラが templ + htmx 版より約 120 行多い |
| Svelte（Wails v2） | 同上 | 約 550 行 |
| Svelte（Wails v3） | 同上 | v2 版を載せ替えたもの |

Svelte + Wails v3 は、Windows 11（Build 26200、WebView2 157）でビルドと操作を確かめ、結果を #113 に記録した。ほかの試作は Linux でだけ動かした。

M4 の範囲と進め方は #140 で決めた。

## 決定事項

### フロントエンドの方式

- 事項: Wails の中のフロントエンド
- 決定内容: Svelte を使う。Go のテンプレート + htmx（templ・Alpine.js・Datastar との組み合わせを含む）は採らない
- 判断理由: GUI には、転送の進捗、キャンセル、ゲームの終了を受けて出す確認のように、Go からの通知や非同期の結果で変わる表示が多い。試作では、イベントと非同期の扱いに次の差が出た
  - Svelte では、Go がイベントで送った表示用のデータを受けて、変数に入れるだけで表示が変わった。templ の 2 つの版では、イベントは「変わった」としか伝えられず、それを DOM のイベントに変えて HTML を取り直す往復が要った
  - Svelte では Go の呼び出しが Promise になり、「承認 → 結果 → 失敗ならトースト」が `await` と `try/catch` の 1 つの関数に収まった。htmx では、エラーの応答をトーストに振り向けるのに `HX-Retarget` の工夫が要った
  - htmx は差し替える要素を丸ごと作り直すので、進捗を更新するたびにキャンセルのボタンも作り直され、フォーカスが外れる。一覧を差し替えると `<img>` も作り直される。Svelte は変わったテキストと属性だけを書き換えるので、要素がそのまま残る。htmx の idiomorph で差を縮められる見込みはあるが、試していない
  - Datastar は SSE で HTML を流し続ける方式だが、Wails の Windows の AssetServer は v2・v3 とも応答を最後までためてから画面に渡すので、製品の環境では流し続けられない。SDK の `NewSSE` は `Flush` のない応答の書き手で panic し、何もしない `Flush` で包む回避策が要った
  - html/template + htmx は、テンプレートの間違いが画面を開くまで分からず、ダイアログを閉じる処理などの素の JS が散らばり始めた

  古い ADR が htmx を第一候補にした理由の、Go の型を TS で書き直す層が要らないことは、Wails v3 のバインディングの生成で満たせる（下記「Go とフロントの分担」）。Node の道具が入ることは懸念だが、実行時には要らず、配布物に入るのはビルドした JS（約 75 KB）と CSS だけである。開発の依存（`node_modules` 約 106 MB・42 パッケージ）は、すべてビルドの道具（Vite・Svelte・TypeScript・svelte-check）だった

### Wails のバージョン

- 事項: Wails v2 と v3 のどちらを使うか
- 決定内容: Wails v3（3.1.0）を使う
- 判断理由: Svelte を v2 で使うと、試作で次の 2 つが残った。v3 ではどちらも解消した
  - v2 はイベントの型を生成しないので、進捗のイベントの中身の型を TS に手で書いた。v3 は `application.RegisterEvent[T]` で登録したイベントの型を生成し、試作では、型の違う代入とフィールド名の打ち間違いを `svelte-check` がエラーにした
  - v2 の `wails dev` は、Go 1.27 で内部エラー（`package "context" without types`）になった。v3 の `wails3 dev` は Go 1.27.3 で動いた

  v3 は 2026-10-26 に 3.0.0、2026-11-01 に 3.1.0 が出たばかりで、Windows の不具合の情報はまだ少ない。これについては、Windows 11 で v3.1.0 のビルド・起動・操作が通ったことで足りるとした（#113）

### Go とフロントの分担

- 事項: 状態と画面の組み立てをどちらに置くか、Go と TS の橋渡しをどう書くか
- 決定内容: 同期の状態、判定、画面に出すデータの組み立ては Go に置く。Svelte は、Go が返したデータの表示と、表示のための状態（ダイアログの開閉、入力中の値、進捗の表示など）だけを持つ。Go の型と API は `wails3 generate bindings` で生成した TS をそのまま使い、Go の型を TS で書き直す層や、Go の API を包む層は作らない
- 判断理由: CloudLaunch_Go も Wails が生成した型を使っていたが、手書きの `types/`・`bridge/`（約 1,800 行）ができた。原因は 3 つで、生成された型が使いにくかったこと（`time.Time` が中身のない型になる、取りうる値が union にならない）、戻り値を `{success, message}` に包み直す層があったこと、起動前に同期するかの判断のような判断が TS にあったことだった。v3 は Go の定数を TS の enum にし、`time.Time` も扱える形で生成するので、1 つ目は生成で済む。2 つ目と 3 つ目は、生成した関数を直接呼び、判断を Go に置くことで防ぐ。Svelte の試作では、Go が文言まで決めたデータを返し、Svelte は表示するだけという形を保てた

### コードの置き場所

- 事項: GUI のコードをどこに置くか
- 決定内容: Wails の配線と画面に出すデータの組み立ては `cmd/cloudlaunch-gui/` に、Svelte のフロントは `cmd/cloudlaunch-gui/frontend/` に置く。フロントのビルド結果は `//go:embed` で取り込み、git には `frontend/dist/.gitkeep` だけを入れる。生成したバインディングはコミットする。テストの要るロジック（ゲームの起動と終了の待機、プレイ時間の計測）は、`internal/` の新しいパッケージに置き、TDD で書く。そのパッケージの名前と形は #146 で決める
- 判断理由: AGENTS.md は `cmd/` を配線だけの場所とし、UI と Wails の配線にはテストを書かないとしている。仕様書 8 章「プレイ時間の計測」の規則は検査できる項目なので、`cmd/` に置くとテストのない場所に規則が入る。`//go:embed` は対象がないとビルドできないので、`go vet ./...` や `go test ./...` がフロントのビルドに依存する。`dist/.gitkeep` を置けば、フロントをビルドしなくても対象があり、試作では Node なしで Go の検査とテストが通った。CI のすべてのジョブで先にフロントをビルドする案は、同期コアのテストが Node に依存するので採らない。バインディングをコミットすると、Go の変更で TS がどう変わったかを差分で読め、CI で生成し直したものとの差分を確かめられる（#21）

### ツールの管理

- 事項: wails3 と bun をどう入れるか
- 決定内容: `mise.toml` の `[tools]` に、bun と、`go:github.com/wailsapp/wails/v3/cmd/wails3`（`tags = "gtk3"`）を足す。フロントの依存は bun で入れ、`bun.lock` をコミットする
- 判断理由: ツールのバージョンは `mise.toml` で固定する決まりで、clone して `mise install` すれば同じ環境になる。試作でも、この形で Windows のビルドが通った（#113）。Wails v3.1 の Linux の既定は GTK4（webkitgtk-6.0）で、`gtk3` のタグを付けると GTK3 の実装を使う。開発に使う Linux には GTK3 版の WebKitGTK しか入っていないので、タグを付ける

## 結果 / 影響

- フロントに Node の道具（bun・Vite・svelte-check）が入り、CI にフロントのジョブが要る（#21）
- Linux では、GUI のパッケージを含む `go vet`・`go test`・golangci-lint・ビルドのすべてに `-tags gtk3` が要る。試作ではサーバーモードのビルドでも GTK を読み込んだ。#141 で `cmd/cloudlaunch-gui/` を足すときに、lefthook と CI の Ubuntu のジョブにタグを足すか、GTK4 のライブラリを入れる。Windows には関係しない
- 画面の振る舞いの一部を TS（Svelte）に書くことになる。表示のための状態に限ることで、Go のコアと状態を二重に持たないようにする
- htmx の `hx-sync` が肩代わりしていた非同期の競合（古い呼び出しの結果が後から届いて表示を巻き戻す）は、Svelte では自分で防ぐ。試作では、前の呼び出しを `cancel()` して Go の `ctx` まで打ち切る形で防げた。どう揃えるかは #141 で決める
- 転送中のダイアログを Esc で閉じるのは、Chromium の仕様で止められない（#113）。進捗の出し方は #141 の範囲で、#140 で決めたとおりモーダルの外に出す
- `wails3 init` の雛形が作る Taskfile と各 OS 向けのパッケージングの設定は取り込んでいない。配布物の作り方（インストーラなど）は #140 の計画に入っておらず、扱う作業は未定
- 試作のうち push したのは Svelte + Wails v3（`fuyu28/GUI-svelte-v3`）だけで、ほかの試作のコードは残していない
