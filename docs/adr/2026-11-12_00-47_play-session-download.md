# play-session-download

- 日時: 2026-11-12 00:47 (JST)

## 当初の要求 / 背景

仕様書 8 章「プレイ履歴」は、ローカルとリモートのプレイ履歴の和集合を取るとしている。2026-11-11_15-15_play-session-upload.md で、ローカルにだけあるセッションを PUT する側（8-S1）を作った。この作業では、リモートにだけあるセッションを取得して DB に入れる側（8-S2）と、取り込むときの扱い（8-S4・8-S5）、不正なセッションの検証（8-V1〜8-V6）を作る。

8-S4 は、仕様書の変更 PR（#111）で「ローカルとリモートの両方にある ID のセッションは、同じものとして扱い、中身を比べない（GET しない）。どちらも書き換えない」に直した。この作業は、その変更を前提とする。

メタ情報の同期は同期ロックを握らない（仕様書 3 章「排他」）。objstore の実装は、呼ばれた時点で ctx が終わっていれば、リモートに触れずに ctx のエラーを返す（2026-11-11_15-15_play-session-upload.md「キャンセル済みの ctx でのリモートの操作」）。DB の `play_sessions.id` は、ゲームをまたいで一意な主キーである。

## 決定事項

### 扱う仕様書の ID の範囲

- 事項: この作業で、8 章のどの項目を満たすか
- 決定内容: 8-S2・8-S4・8-S5・8-V1〜8-V6 を扱う。8-M1（ゲームの tombstone の確認）は #100、プレイ履歴の tombstone（10 章）は v1 の後に扱う
- 判断理由: 8-S1・8-S3・8-S6・8-M2〜8-M4 は #95 で満たしている。この作業で足すのは、リモートのセッションを読む側だけである

### アップロードと取り込みの順番

- 事項: 1 回の `Sync` で、アップロードと取り込みをどう組み合わせるか
- 決定内容: `sessions/` の一覧を 1 回だけ取り、そこから PUT するもの（ローカルにだけある ID）と GET するもの（リモートにだけある ID）を決める。アップロード → 取り込みの順に行い、どちらかが失敗したら、その時点で `Sync` をエラーで返す
- 判断理由: 一覧を 2 回取らずに済む。オフラインなら両方とも失敗するので、片方の失敗の後にもう片方を試す意味は薄い。一覧の後に、取り込んだセッションを PUT し直すこともない（取り込んだものはリモートにある）

### 両方にある ID のセッション

- 事項: ローカルとリモートの両方にある ID のセッションを、どう扱うか
- 決定内容: GET せず、どちらも書き換えない（8-S4）
- 判断理由: 仕様書の 8-S4 のとおり。中身の違いを見つけるには、同期のたびに両方にあるセッションをすべて GET することになり、セッションは書き換えない object なので、その費用に見合わない

### GET の並列と失敗

- 事項: リモートにだけあるセッションを、どう取得し、失敗したらどうするか
- 決定内容: errgroup の `SetLimit(8)` で並列に GET する。消えていた（`fs.ErrNotExist`）以外の理由で 1 件が失敗したら、残りを止め、何も DB に入れずに、そのエラーを `%w` で包んで返す
- 判断理由: PUT と同じく、AGENTS.md の並列実行の方針に従う。残りの GET は、objstore の契約により、キャンセル済みの ctx を受けて取得せずに返る。何も入れずに返しても、次の同期でリモートの一覧と突き合わせ直すので、取り込み直せる

### 一覧の後に消えたセッション

- 事項: 一覧に出たのに、GET したら存在しなかったセッションの扱い
- 決定内容: その 1 件だけを飛ばしてログに残し、ほかの取り込みは続ける。同期は成功として扱う
- 判断理由: 一覧を取った後に別の PC がゲームを削除する（8-X6）と起きる。v1 にはプレイ履歴だけの削除はない。ゲームが削除されたことは、次のゲームの tombstone の確認（#100）で分かるので、ここでエラーにすると、正当な削除の途中で毎回失敗と出ることになる

### 不正なセッションの検証

- 事項: 8-V1〜8-V6 を、どう判定するか
- 決定内容: 当たったセッションは、その 1 件だけを取り込まずにログに残し、ほかの取り込みは続ける。判定は次のとおりにする
  - 8-V2: 4 つの項目のどれかが、ないか `null` なら不正とする
  - 8-V5: `playedAt` は、3 章の形（`2006-01-02T15:04:05.000Z`）に完全に一致するものだけを通す。`+09:00` などの別の書き方は不正とする
  - 8-V6: `durationSec` は、整数として読める JSON の数で、0 以上のものだけを通す。`1.5` や `1e3` は不正とする
  - 知らない項目があっても、不正としない
- 判断理由: 3 章の形でない日時を通すと、DB に入れるときに形を直すことになり、リモートとローカルで同じセッションの表記が分かれる。`1e3` は整数の値を表せるが、#95 の PUT は整数の表記でしか書かないので、それ以外の表記は別の書き手か手で書き換えたものである。知らない項目を不正にすると、後の版で項目を足したときに、古い版の PC がそのセッションをすべて取り込めなくなる

### DB への入れ方

- 事項: 取得したセッションを、いつ、どう DB に入れるか
- 決定内容: すべての GET と検証が済んでから、1 つのトランザクションで入れる。GET が 1 件でも失敗したら、何も入れない
- 判断理由: DB への書き込みが 1 か所になり、並列の goroutine から DB を書かずに済む。8-S5 の判定（別のゲームに同じ ID があるか）を、入れるのと同じトランザクションの中で行えるので、確かめた後に別のゲームに入る隙間ができない

### 同じゲームに同じ ID がすでにあるとき

- 事項: 一覧を取ってからトランザクションに入るまでの間に、同じゲームに同じ ID のセッションが入っていたときの扱い
- 決定内容: 何もせずに飛ばす。エラーにもログにもせず、取り込んだ件数にも数えない
- 判断理由: 同期ロックを握らないので、2 つのプロセスが同じゲームを同時に同期すると起きる。セッションは書き換えない object なので、先に入った方と中身は同じはずである

### インターフェースに足すもの

- 事項: metasync の `ObjectStore` と `LocalStore` に何を足すか
- 決定内容: `ObjectStore` に `Get(ctx, key) (io.ReadCloser, error)` を足す。`LocalStore` に `ImportSessions(ctx, gameID, []Session) (ImportResult, error)` を足す。`ImportSessions` は 1 つのトランザクションで入れ、別のゲームにすでにある ID（8-S5）は入れずに、その ID を `ImportResult` で返す。ログは metasync が出す
- 判断理由: 8-S5 は、ゲームをまたいだ ID の存在を DB で引かないと分からず、入れるのと同じトランザクションで確かめる必要があるので、store が判定する。ログを metasync が出すのは、store がログを持たず、何をどの重さで知らせるかは同期の側の判断であるため

### 結果と CLI の表示

- 事項: `Sync` の結果に何を返し、CLI に何を出すか
- 決定内容: `Result` に `DownloadedSessions`（DB に入れた件数）を足す。CLI は「プレイ履歴を N 件アップロードし、M 件取り込みました」と出す。不正（8-V）・別のゲームの ID（8-S5）・一覧の後に消えていたもので飛ばしたものは、ログだけに出し、件数に数えない
- 判断理由: 飛ばしたものはどれも、同期のたびに同じ理由で飛ばされうる。件数として毎回出すと、取り込みが進んでいないように見える。GUI に飛ばした件数を出すかは M4 で決める

### ログのレベル

- 事項: 飛ばしたものを、どのレベルでログに残すか
- 決定内容: 不正（8-V1〜8-V6）と、別のゲームの ID（8-S5）は Warn にする。一覧の後に消えていたものは Info にする
- 判断理由: 前の 2 つは、データの異常か操作の行き違いを示す。消えていたものは、ゲームの削除という正当な操作で起きる

### テスト

- 事項: どう確かめるか
- 決定内容: metasync は `package metasync_test` で、本物の SQLite（store）と memstore を使って、次のケースを書く。`8-S2 リモートにだけあるセッションを DB に入れる`、`8-S4 両方にある ID のセッションは、中身が違っても GET せず、どちらも書き換えない`、`8-S5 別のゲームに同じ ID があるセッションは取り込まない`、`8-V1`〜`8-V6`（表にする）、`8章/プレイ履歴/2 台の PC で同期すると、両方の DB が和集合になる`、`8章/プレイ履歴/一覧の後に消えたセッションは飛ばす`、`8章/プレイ履歴/GET に失敗したら、何も DB に入れずにエラーを返す`。2 台の PC のケースは、別々の DB を持つ 2 つのコアに、同じ memstore を共有させる。store には `ImportSessions` のテスト（入れる、同じゲームの同じ ID を飛ばす、別のゲームの同じ ID を返す）を足す。cmd の配線にはテストを書かない
- 判断理由: AGENTS.md のテストの方針（コアのテストは本物の SQLite と偽のリモート、仕様書の ID をケース名に入れる、複数 PC のシナリオは 2 つのコアに同じ偽のリモートを共有させる、配線にはテストを書かない）に従う。8-S4 のケースでリモートの中身をわざと違えるのは、GET していれば中身の違いが DB か結果に表れうるようにするためである
