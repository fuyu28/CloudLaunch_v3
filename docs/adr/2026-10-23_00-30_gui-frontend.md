# gui-frontend

- 日時: 2026-10-23 00:30 (JST)

## 当初の要求 / 背景

v3 の GUI で行うことは、画像とブランド名つきのゲーム一覧、確認ダイアログと進捗表示、ゲームの登録・取り込み・削除、設定、ゲームの起動と終了の待機である（仕様書 7〜9 章）。画面は 5〜6 枚で、状態の多くは Go 側にある。

CloudLaunch_Go のフロントエンドは React（Vite + TypeScript + Tailwind + DaisyUI + Jotai）で、162 ファイル・約 1 万 7 千行、依存は 262 パッケージだった。この中には、v3 では持たない機能（メモ、スクリーンショット、ErogameScape の連携、ルート）も含まれる。加えて、Go の型を TS で書き直す層（`types/`）、Go の API を包む層（`bridge/`・`wailsBridge.ts`）、それを呼ぶ hooks と状態の atoms があり、Go で機能を 1 つ足すたびに TS の複数か所を書く構造になっていた。React を採っていた理由は、書き慣れていることと、既存のライブラリに頼りやすいことだった。

## 決定事項

### GUI 全体の枠組み

- 事項: デスクトップアプリの枠組み
- 決定内容: Wails を使う。安定版の v2 を前提とし、v3 の安定度は GUI に着手するときに確かめる
- 判断理由: Wails は Go のライブラリと WebView2 のウィンドウからなり、Go のコアを同じプロセスから呼べ、配布物は exe 1 つで済む。WebView2 は Windows 11 に標準で入っている。画像の並んだ一覧を描くには Web の技術が安上がりである。Fyne と Gio は Go だけで完結するが、Fyne は見た目が Windows らしくなく、cgo と C コンパイラが要る。Gio は部品が少なく、一覧やダイアログを組む量が多い。Win32 を直接使うライブラリ（walk など）は保守が止まりがちである。Tauri と Electron は、Go のコアを別プロセスにすることになり、構成が合わない

### フロントエンドの方式

- 事項: Wails の中のフロントエンド
- 決定内容: 第一候補は Go のテンプレート + htmx、次点は Svelte とする。状態と画面の組み立ては Go に置き、Go の型を TS で書き直す層や、Go の API を包む層を作らない
- 判断理由: CloudLaunch_Go の肥大化の主な原因は、機能の範囲と、Go と TS の間の橋渡しの層である。機能の範囲は v3 で狭まるが、橋渡しの層は、状態を TS 側で持って Go を API として呼ぶ限り、React を Svelte や Preact に替えても残る。Go のテンプレート + htmx は、Go が HTML を組み立てて返し、htmx が画面の一部を差し替えるので、TS の型・橋渡しの層・状態管理が要らず、Node の道具も要らない。代わりに React の部品のライブラリと書き慣れた方式を手放し、Go から画面への通知（進捗など）は Wails のイベントと少しの JS で書く。Wails での htmx の利用は情報が少ないため、次点として Svelte を残す。Svelte はコンパイルされて小さく、状態管理のライブラリが要らず、この規模では書く量が少ない

### 最終的な決め方

- 事項: htmx と Svelte のどちらにするか
- 決定内容: GUI に着手するときに、進捗の表示と確認ダイアログを含む 1 画面を試作して決める
- 判断理由: htmx の懸念は、Wails の AssetServer に Go の `http.Handler` を渡す使い方と、Go から画面への通知が無理なく書けるかにあり、試作すれば確かめられる。同期コアと CLI は GUI に依存しないので、ここで決めなくても先に進められる

## 結果 / 影響

- フロントエンドのコードと依存は、CloudLaunch_Go より小さくなる見込み
- htmx を採ると、UI のロジックも Go に書くことになり、Go のテンプレートの保守が増える
- 試作の結果は、この ADR を置き換える ADR として記録する
