# pull

- 日時: 2026-11-03 17:44 (JST)

## 当初の要求 / 背景

M1（walking skeleton）の 5 つ目の作業として、別の PC が Push したセーブを取り込めるようにする（仕様書 6 章）。M1 の道は `game add` → `status` → `push` → 別のフォルダで `pull` で、判定は「base なし」の行だけを扱う（AGENTS.md「開発の進め方」）。base ありの判定は「未実装」のエラーを返すので、M1 で Pull になるのは「base なし・local なし・remote あり」の行だけであり、live にファイルはない。ただし、live が空のフォルダとして存在すれば、手順 7 で old ができる。

syncore の公開 API は、`Status` が返した plan を `Pull` が受け取り、承認した後に状況が変わっていればセンチネルエラーを返す形にする（AGENTS.md「構成」）。Push は 2026-11-03_01-02_push.md で作り、`ErrPlanStale` と `Config` を定めた。

仕様書 6 章の手順には HEAD を読み直すステップがなく、7 章の「承認してから実行するまでに remote のハッシュが変わっていれば中止する」と食い違っていた。このため、手順 6 で HEAD を読み直すよう仕様書を先に変えた（#19）。

## 仕様

- 6 章の手順のどこまでを作るか
- PC 全体の同期ロックと、ゲームの実行中の確認
- Pull が受け付ける判定
- 承認後に状況が変わったときのエラー
- 不正な manifest の検証
- stage への取得と、手順 5 の検証
- 作業領域の作り方
- 入れ替えの後に失敗したとき
- ジャーナルの書き方
- `pull` コマンドの形

## 決定事項

### 6 章の手順の範囲

- 事項: 仕様書 6 章の Pull の手順と、起動時の復旧（`Recover`）のどこまでを作るか
- 決定内容: 手順 1〜8 と 10 を作る。手順 9（old をバックアップへ移し、3 個に保つ）と `Recover` は M2 で作る。old ができたときは、ジャーナルの行を消さずに成功として終え、M2 の `Recover` が復旧表の「old と live があり、stage がない → old をバックアップへ移す」の行で片付ける
- 判断理由: M1 の目的はつなぎ目の問題を先に出すことである。M1 で old ができるのは、空のセーブフォルダがあるときだけで、old の中にファイルはない。手順 9 を作ると、`LOCALAPPDATA` とセーブフォルダのボリュームが違うときの移動も決める必要があり、M1 の道のつなぎ目を増やさないのに行数が倍近くになる。ジャーナルを残しておけば、後に残る状態は仕様書の復旧表の行に当たり、中断したときと同じ扱いで片付けられる

### 同期ロックとゲームの実行中の確認

- 事項: 仕様書 3 章の `sync.lock` と、7 章の「ゲームの実行中は Pull を拒否する」を、この作業で入れるか
- 決定内容: どちらも入れず、M2 で入れる
- 判断理由: Push と同じである（2026-11-03_01-02_push.md「同期ロックとゲームの実行中の確認」）。M1 の道では CLI を手で 1 回ずつ実行するので、同時の同期も、ゲームの実行中の同期も起こらない

### Pull が受け付ける判定

- 事項: `Pull` が、どの判定の plan を受け付けるか
- 決定内容: 判定が Pull の plan だけを受け付ける。ほかの判定の plan を渡されたら、`%w` で包んだエラーを返し、センチネルエラーにはしない。競合のときの「ダウンロードで上書き」（仕様書 7 章）は M2 で扱う
- 判断理由: Push の決定（2026-11-03_01-02_push.md「Push が受け付ける判定」）と揃える。判定が Pull でない plan を渡すのは呼び出し側の誤りで、呼び出し側が振る舞いを分ける場面ではない

### 承認後に状況が変わったときのエラー

- 事項: 手順 6 で live か HEAD が承認した時点から変わっていたとき、何を返すか
- 決定内容: stage を削除し、ジャーナルを削除してから、`ErrPlanStale` を返す。live は、計算し直した manifest ハッシュを `plan.Local.Hash` と比べる。HEAD は、読み直した世代を `plan.Remote.Generation` と比べ、HEAD が消えていた場合も「変わった」として扱う。取得する世代は plan の manifest のままにし、HEAD を読み直して取得し直すことはしない
- 判断理由: どちらの場合も、呼び出し側がすることは「判定からやり直す」の 1 つで、Push の `ErrPlanStale` と同じ意味である。manifest は書き換えないので、plan の manifest はユーザーが承認した内容そのものである

### 不正な manifest の検証

- 事項: 手順 2 の検証をどこまで作り、どう確かめるか
- 決定内容: 仕様書 6 章「不正な manifest」の規則をすべて作り、規則ごとにテーブル駆動のケースを書く。違反したら、ジャーナルを書く前に `%w` で包んだエラーを返し、センチネルエラーにはしない。ドライブレターは、path のどこかに「英字 1 文字と `:`」が並んでいれば当たるとする。大文字小文字の違いは `strings.ToUpper` で揃えて比べる。fuzz テストは M2 で足す
- 判断理由: path が stage の外を指すと、セーブフォルダと無関係な場所に書き込む。M1 の道でも、ほかの PC が書いた manifest を信じてファイルを書くことになるので、検証を後回しにできない。不正な manifest は判定からやり直しても直らないので、`ErrPlanStale` とは分ける。Windows のファイル名の比較は大文字に揃えて行われるので、`ToLower` ではなく `ToUpper` で揃える

### stage への取得と、手順 5 の検証

- 事項: 手順 4 で object をどう取得し、手順 5 で stage をどう確かめるか
- 決定内容: エントリごとに `objects/{sha256}` を GET して stage に書く。errgroup の `SetLimit` で 8 並列にし、1 つが失敗したら残りをキャンセルする。同じ sha256 のエントリも、まとめずにそれぞれ GET する。手順 5 は、stage を manifest の計算と同じ方法（`localEntries`）で計算し直し、manifest ハッシュを `plan.Remote.Hash` と比べる。object がないとき（仕様書 5 章の GC と同時 Push）や、stage が manifest と一致しないときは、中止して stage とジャーナルを削除し、`%w` で包んだエラーを返す
- 判断理由: 転送の並列数は AGENTS.md「構成」で 8 と決めてある。Push で重複を除いたのは同じキーへの PUT を避けるためだが、Pull ではエントリごとに書く先が違い、まとめるとローカルでのコピーが増えるだけである。manifest ハッシュの比較は、中身・サイズ・余分なファイルを 1 回で確かめられ、`Status` の local の計算と同じ道を通る。ファイルを 2 回読むことになるが、セーブは小さいことが多い。object がないことや中身の食い違いは、判定からやり直しても直らないので、`ErrPlanStale` とは分ける

### 作業領域の作り方

- 事項: opId の振り方、セーブフォルダの親ディレクトリがないとき、作るファイルの権限
- 決定内容: opId は `uuid.NewV7` で振り、`Config` で差し替えられるようにはしない。セーブフォルダの親ディレクトリがなければ `MkdirAll` で作る。ディレクトリは 0o755、ファイルは 0o644 で作り、mtime は取得した時刻のままにする
- 判断理由: opId は stage と old の名前に使うだけで、テストは親ディレクトリに `.cloudlaunch-` で始まるものが残っていないかで確かめられる。2 台目の PC では、ゲームを一度も起動しておらず、セーブフォルダの親もまだないことがある。manifest は mtime を含めないので、mtime を合わせても判定は変わらない

### 入れ替えの後に失敗したとき

- 事項: 手順 7 の 2 つ目のリネームや、手順 8 の base の書き込みに失敗したとき、どうするか
- 決定内容: エラーを返し、ジャーナルを削除しない。手順 7 の 1 つ目のリネーム（live → old）に失敗したときは、まだ入れ替えていないので、4〜6 で中止したときと同じく stage とジャーナルを削除する
- 判断理由: 入れ替えを始めた後に残る状態は、仕様書 6 章の復旧表の行（「old があり、live がない」「old と live があり、stage がない」）に当たり、`Recover` が片付ける。その場で戻そうとすると、復旧表と同じ処理を 2 か所に書くことになる。M2 で `Recover` を作るまでは、ジャーナルが残ったゲームの次の Pull は、ジャーナルの書き込みで失敗する

### ジャーナルの書き方

- 事項: 手順 3 と 10 のジャーナルを、どこにどう書くか
- 決定内容: store に `InsertPullOperation` と `DeletePullOperation` を足し、syncore の `LocalStore` にも足す。引数は store の型を使わずに文字列と時刻で渡す。`created_at` は `Config.Now` から作る。同じゲームのジャーナルが残っていれば、テーブルの UNIQUE 制約で失敗するので、`%w` で包んだエラーとして止める
- 判断理由: syncore が必要な操作だけのインターフェースを定義し、store がそれを実装する（2026-10-23_00-30_package-structure.md）。引数に store の型を使うと、syncore が store に依存する。ジャーナルが残っているのは前の Pull が終わっていないことを表し、M1 には片付ける手段がない

### `pull` コマンドの形

- 事項: CLI の `pull` の引数・確認・出力・終了コード
- 決定内容: `cloudlaunch-cli pull --game <gameId> [--data-dir <dir>]` とする。`status` と同じ内容を出し、判定が Pull なら確認を取らずに Pull する。判定が Pull でなければ、ダウンロードしない旨を出して終了コード 0 で終わり、「base を記録」の行なら base を記録する。`ErrPlanStale` が返ったら、もう一度実行するよう出して終了コード 1 で終わる
- 判断理由: `push` の決定（2026-11-03_01-02_push.md「`push` コマンドの形」）と揃える

## 結果 / 影響

- M1 では、空のセーブフォルダがあるところへ Pull すると、セーブフォルダの隣に `.cloudlaunch-old-{opId}` が残り、ジャーナルも残る。M2 で手順 9 と `Recover` を作るまで、そのゲームの次の Pull はジャーナルの書き込みで失敗する
