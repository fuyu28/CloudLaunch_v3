# game-delete

- 日時: 2026-11-14 20:30 (JST)

## 当初の要求 / 背景

仕様書 8 章「ゲームの削除」は、ゲームを削除するときに、この PC の登録だけを解除するか（8-X1）、リモートのデータも削除するか（8-X2〜8-X10）を選ぶとしている。リモートも削除するときは、同期ロックを握り、ゲームの実行中は拒否し、Pull ジャーナルの確認 → セーブのバックアップ → `deleted.json` の PUT と DB への記録 → 配下の削除 → 登録の解除、の順で行う。仕様書の変更 PR #126 で、既に tombstone があるときの拒否（8-X11）、セーブフォルダがないときにバックアップを飛ばすこと（8-X12）、実行ファイルがないときに実行中でないとして続けること（8-X13）を足した。

同期ロックとバックアップの処理は syncore にあり、外からは呼べない（`acquire`・`copyTree`・`pruneBackups`）。`deleted.json` の検証、DB への記録、配下の削除（`deleteGameData`）は metasync にある（2026-11-14_19-07_game-tombstone-check.md）。tombstone を書いた後で止まったときの消し残りの削除は、metasync の `HandleTombstone` が既に担う（8-X10）。syncore と metasync は互いに import しない（2026-10-23_00-30_package-structure.md）。store にはゲームを消す関数がなく、CLI にも `game delete` がない。DB の `pull_operations` は `ON DELETE RESTRICT` で、ジャーナルが残るゲームの削除を止める。

## 決定事項

### 扱う仕様書の ID の範囲

- 事項: この作業で、どの項目を満たすか
- 決定内容: 8-X1〜8-X13 を扱う。8-X1 の登録の解除は、store の関数と CLI の `game delete`（`--remote` なし）として作る。8-X10 の消し残りの削除は、既存の `HandleTombstone` に任せ、新しく作らない。リモートで削除されたゲームの登録の解除（8-U1、#102）は、同じ `game delete` で行えるので、#102 には残る作業だけを残す。上げ直し（8-U2〜8-U5、#103）は扱わない
- 判断理由: 8-X7 で登録を解除する関数が要るので、それを CLI から呼ぶ入口を足しても、増えるのは数十行である。8-U1 は 8-X1 と同じ操作なので、別に作ると同じ関数が 2 つになる

### syncore と metasync の分担と、ロックを握る範囲

- 事項: 8-X2 は 8-X3〜8-X7 の間ずっと同期ロックを握るとしている。ロックとバックアップは syncore に、tombstone の PUT と配下の削除は metasync にある。これをどうつなぐか
- 決定内容: syncore に `DeleteGame(ctx, gameID string, deleteRemote func(ctx context.Context) error) (DeleteResult, error)` を置き、ロックの取得から登録の解除までの手順を持たせる。tombstone の PUT・DB への記録・配下の削除は metasync の `DeleteRemoteGame` に置き、cmd がそれを閉包に包んで `deleteRemote` として渡す。tombstone の扱いを 1 つのパッケージに寄せるかは、別の Issue で検討する
- 判断理由: 手順と、途中で止まったときの扱い（8-X8〜8-X10）を syncore が持てば、syncore のテストで順番と止まり方を検査できる。syncore にロックを外から握る口を開けて cmd が手順を組む案と、cmd が `platform` のファイルロックを直接握る案は、手順が cmd に入り、AGENTS.md の方針では cmd にテストを書かないので採らない。閉包で渡すのは、2026-11-14_19-07_game-tombstone-check.md の `ReadTombstone` と同じ形である。tombstone を syncore に移す案は、2 台目の PC での取り込み（8-N7・8-N8・8-N12）も `deleted.json` を検証するので、metasync の側に注入が残る。決定済みの構造（AGENTS.md の構成、2026-11-14_19-07_game-tombstone-check.md）を変え、マージ済みのコードを移すことになり、この作業の PR がオーナーの読める量を超えるので、ここでは行わない

### syncore の手順と確認の順

- 事項: `DeleteGame` が、何をどの順で確かめ、どこで止まるか
- 決定内容: 次の順で行う
  1. 同期ロックを取る。取れなければ `ErrSyncInProgress` を返す（8-X2）
  2. `ListPullOperations` に同じゲームの行があれば、`ErrPullPending` を返す（8-X3）
  3. `Config.ReadTombstone` で tombstone を確かめ、あれば `ErrRemoteDeleted` を返す。読めない・不正ならそのエラーを返す（8-X11）
  4. ゲームのローカル情報を読み、実行中なら `ErrGameRunning` を返す。実行ファイルがなければ、実行中でないとして続ける（8-X13）
  5. セーブをバックアップへコピーする。セーブフォルダがなければ、作らずに Info のログを残す（8-X4・8-X12）
  6. 実行中と tombstone を確かめ直す。どちらかで止まったら、バックアップを残して 4・3 と同じエラーを返す（8-X8 の状態になる）
  7. `deleteRemote` を呼ぶ。失敗したら、登録を残して `ErrRemoteDeletionFailed` で包んで返す（8-X8〜8-X10）
  8. 登録を解除する（8-X7）。失敗したら `ErrUnregisterFailed` で包んで返す
  - 作ったバックアップのパスを `DeleteResult.BackupPath` で返す。作らなかったときは空にする
  - `deleteRemote`・`Config.ReadTombstone`・`Config.Locker`・`Config.Processes`・`Config.BackupsDir`・`Config.Rename` のどれかがなければ、ロックを取る前にエラーを返す
- 判断理由: 2〜4 は何も変えない確認なので、仕様書の「何も変える前に拒否する」を満たす。ジャーナルを tombstone より先に確かめるのは、仕様書の手順の順に合わせるためで、どちらで止まっても状態は変わらない。ジャーナルの確認をセンチネルエラーにするのは、CLI が `recover` を案内するためである。ジャーナルは `ListPullOperations` で確かめ、新しい問い合わせを足さない。行は実行中の Pull 1 件につき 1 行なので、全件を読んでも小さい。実行中の確認は、実行ファイルがなければ通し、あれば 7 章の `ensureGameNotRunning` を呼ぶ削除用の関数にする。`ensureGameNotRunning` に引数を足すと、Push・Pull の呼び出しにも 8-X13 の分岐が見えるためである。6 で確かめ直すのは、コピーが長くかかることがあり、その間にゲームが起動されると、書き込みの途中のセーブを写したバックアップだけを残して、リモートの正しいセーブを消すためである（Push・Pull が転送の後に確かめ直すのと同じ理由、7 章）。tombstone も読み直すのは、ほかの PC が先に書いた tombstone を上書きする間隔を、コピーの時間から PUT の往復だけに縮めるためである。条件付きの PUT（If-None-Match）で防ぐ案は、オブジェクトストアのインターフェースを変えることになり、仕様書 1 章が保証しないとした重なりと同じ程度に縮められれば足りるので採らない。登録の解除の失敗をセンチネルにするのは、リモートは削除済みなので、利用者がすべきことが「登録だけを解除し直す」になり、ほかの失敗と分ける必要があるためである。呼び出し側が閉包の成否で見分ける案は、GUI の配線でも同じ仕掛けを作り直すことになるので採らない。バックアップのパスを返すのは、8-X12 で作らなかったときに、ないバックアップの場所を表示しないためである。Pull と違い、ロックの後に設定の不足に気づくと、ロックだけを取って何もせずに終わることになるので、`Pull` と同じく何も変える前に確かめる

### バックアップの作り方

- 事項: 8-X4 のコピーを、Pull のバックアップ（3 章）とどう揃えるか
- 決定内容: 名前は `backupName(削除を始めた時刻, opId)` とし、`{UTC 日時}` はロックを取った後の `Config.Now()`、`{opId}` は UUIDv7 とする。コピーは `moveToBackup` のリネームで移せないときと同じく、`.partial-{名前}` に `copyTree` してから最終の名前に `Config.Rename` でリネームし、そのあと `pruneBackups` で、作ったものを除いて 3 個に保つ。コピーか最後のリネームに失敗したら `.partial-` を消して止まる。コピーの部分は `moveToBackup` と共有する関数に切り出す
- 判断理由: 仕様書は置き場所・名前の形・保持数・ディスクへの書き出しを Pull と同じとしている。`.partial-` の名前からリネームするので、最終の名前のバックアップは常に完全なコピーになる。途中で中断して `.partial-` が残っても、次の同じ処理（Pull の手順 9・復旧の 6-R3・削除）では名前が違うので消されず、保持数にも数えられない。削除のバックアップは呼ぶたびに名前を振るので、リネームに失敗した `.partial-` を残すと、次の削除でも消されずに残り続ける。そのためリネームの失敗でも消す。リネームが済んでから書き出しに失敗したときは `.partial-` がもうないので、消しても最終の名前のコピーは残る。Pull の経路では、次の呼び出しがコピーし直すので、消しても失うものはない

### metasync の tombstone の PUT と、止まった場所の伝え方

- 事項: 8-X5・8-X6 を metasync でどう行い、8-X8・8-X9・8-X10 のどれで止まったかを CLI がどう見分けるか
- 決定内容: metasync に `DeleteRemoteGame(ctx, gameID string, t Tombstone) error` を置く。`deleted.json` を `{ deletedAt, deviceName }` の形で PUT し、成功したら `RecordRemoteDeleted` で DB に記録し、`deleteGameData` で配下の `deleted.json` 以外を削除する。PUT に成功した後の失敗（記録・削除）は、センチネルエラー `ErrDeleteIncomplete` で包む。PUT の失敗は包まずに返す。`deletedAt`・`deviceName` は、cmd が閉包の中で今の時刻とホスト名から作る。CLI は、syncore の `DeleteGame` が返したエラーを次のように見分ける
  - `ErrDeleteIncomplete` を含む（8-X10）: リモートでは削除済みで、消し残りは次の `push`・`pull` で消え、登録は `game delete`（`--remote` なし）で解除すると出す
  - `deleteRemote` のそれ以外のエラー（8-X9）: リモートに届いたか分からないので、`status` で確かめてからもう一度実行するよう出す
  - それより前の手順のエラー（8-X8 を含む）: 何も消えていないので、そのまま返す
- 判断理由: 利用者がすべきことは止まった場所で変わるが、syncore は `deleteRemote` の中を知らない。metasync がセンチネルエラーで「tombstone は書いた」ことを伝えれば、syncore は `%w` で包むだけで済み、cmd が見分けられる。8-X9 と 8-X8 を分けるには、syncore が `deleteRemote` のエラーを別のセンチネルで包む必要があるので、`ErrRemoteDeletionFailed` を syncore に置く。時刻とホスト名を metasync の `Config` に足さないのは、ほかの操作が使わず、`DeleteRemoteGame` の引数で足りるためである。PUT の前に `deleted.json` を読み直さないのは、syncore の 3 で確かめた直後で、間にほかの PC が削除するのは仕様書 1 章「保証しないこと」の重なりと同じ扱いになるためである

### 登録の解除と Pull ジャーナル

- 事項: 8-X1 と 8-X7 の登録の解除を、store でどう行うか
- 決定内容: store に `DeleteGame(ctx, gameID) error` を置く。1 つのトランザクションで、同じゲームの `pull_operations` の行を先に確かめ、あれば `store.ErrPullInProgress` を返す。なければ `games` の行を消し、`ON DELETE CASCADE` でローカル情報とプレイ履歴を消す。登録していないゲームは `sql.ErrNoRows` で包んで返す。画像のキャッシュと、そのゲームのバックアップは消さない。同期ロックは握らない
- 判断理由: `ON DELETE RESTRICT` に任せると、返るのは SQLite の制約違反のエラーで、CLI が `recover` を案内できない。RESTRICT は最後の安全網として残す。画像のキャッシュは sha256 をキーにしてほかのゲームと共有しうる。バックアップは 8-X4 が「登録を解除しても消さない」としている。ロックを握らないのは、3 章「排他」が、登録の解除は DB の 1 つのトランザクションで済むので握らないとしているためである

### API の形

- 事項: 各パッケージに何を足すか
- 決定内容:
  - syncore: `Core.DeleteGame`（`DeleteResult` を返す）、`ErrPullPending`、`ErrRemoteDeletionFailed`、`ErrUnregisterFailed`。`LocalStore` に `DeleteGame(ctx, gameID) error` を足す
  - metasync: `Core.DeleteRemoteGame`、`ErrDeleteIncomplete`
  - store: `DeleteGame`、`ErrPullInProgress`
  - migration は足さない
- 判断理由: syncore の `ErrPullPending` と store の `ErrPullInProgress` は、どちらも Pull ジャーナルが残っていることを表すが、syncore が store を import しないので、それぞれに置く。syncore の 7 で store の `ErrPullInProgress` が返るのは、2 で確かめた後にロックを握ったまま Pull が始まることがないので、起きない

### CLI の振る舞い

- 事項: `game delete` の形と出力
- 決定内容:
  - `game delete --game <id> [--data-dir <dir>]`: 登録だけを解除する（8-X1）。リモートには接続しない
  - `game delete --game <id> --remote --confirm-title <タイトル> [--data-dir <dir>]`: リモートも削除する。`--confirm-title` が DB のタイトルと完全に一致しなければ、何も変える前に拒否する。`--remote` なしで `--confirm-title` を付けたときもエラーにする
  - 成功したら、削除したことと、作ったバックアップのパスを出す。8-X12 で作らなかったときは、作っていないと出す
  - `ErrUnregisterFailed` なら、リモートは削除済みなので、`--remote` なしで解除するよう出す
  - エラーは `explainSyncError` に、`ErrPullPending`・`ErrPullInProgress`（`recover` の案内）、`ErrRemoteDeleted`（`--remote` なしの案内）を足して説明する。止まった場所の出し分けは、前節のとおり
  - AGENTS.md の CLI の一覧には `game delete` が既にあるので、直さない
- 判断理由: CLI は対話をしないので、8-X4 の「ゲーム名の入力などの強い確認」を、タイトルを引数で打つことで取る。gameId の打ち間違いで別のゲームを消すことも防げる。照合を cmd が行い、syncore は確認済みとして受け取るのは、7 章の確認を GUI と CLI が持つのと同じ分担である。`--yes` だけで確認したことにする案は、gameId の打ち間違いを防げないので採らない

## 結果 / 影響

- CLI の `game delete` で、登録だけの解除（8-X1）と、リモートも含めた削除（8-X2〜8-X7）ができる。リモートで削除されたゲームの登録の解除（8-U1、#102）も、同じ `game delete`（`--remote` なし）で行える
- 8-X1〜8-X13 は、すべてテストのケース名に入った（`mise run spec-ids` の一覧から消えた）
- R2 を相手に CLI で確かめた。2 台の PC に見立てた別々の data-dir で、PC1 から `game delete --remote` を実行すると、タイトルが違えば何も変えずに拒否した。一致すれば、バックアップを作ってセーブフォルダを残し、登録を解除した。その後、3 台目の data-dir の `game remote` に、そのゲームは出ず、`game import` も拒否した（8-N7）。PC2 の `status` は「リモートで削除されました」を出し、PC2 からの `game delete --remote` は 8-X11 で拒否した。`--remote` なしでは、登録だけを解除した。同じ ID で別の data-dir に登録して `push` すると、tombstone で止まり、消し残りの削除のログは出なかった。配下に `deleted.json` しか残っていないことを表す
- 削除のたびに、tombstone の確認の GET が 2 回（バックアップの前と後）増える。コピーの間の削除と重なっても上書きする間隔を縮めるためで、削除はまれな操作なので費用は小さい
- 登録だけの解除は、仕様書 3 章のとおり同期ロックを握らない。同じゲームの `push` と重なると、`push` は base を書けずにエラーで終わる。登録を消すのは利用者の意図した操作なので、そのままにした
- 行数は約 1,130 行（テスト約 610、syncore 約 190、metasync 約 30、store 約 40、CLI 約 140、ADR 約 120）で、見込みの約 700 行を超えた。超えたのは主にテストと syncore で、コピーの後の確かめ直し、登録の解除の失敗、バックアップのリネームの失敗のケースと、その実装を、レビューの後に足したため
