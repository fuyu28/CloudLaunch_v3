# manifest-validation

- 日時: 2026-11-07 23:41 (JST)

## 当初の要求 / 背景

仕様書 6 章「不正な manifest」は、Pull の 6-L2 で拒否する manifest として、path の規則 6-M1〜6-M5 だけを決めていた。また、Push は local の entries を検証していなかった。そのため次のことが起きた。

- `entries` が欠けた manifest が空 manifest として通り、Pull するとセーブがすべて消える
- sha256 の形が崩れた manifest や、path の順に並んでいない manifest は、判定が「変化」になったうえで、Pull が手順 5 の検証で必ず失敗する
- Windows で書けない path（予約されたデバイス名など）を Pull すると、デバイスに書き込むか、名前が変わって手順 5 の検証で失敗する
- 6-M5 などに当たるファイルを Push すると、その世代が HEAD になり、どの PC も Pull できなくなる
- path が正しい UTF-8 でないファイルは、JSON に書くときに U+FFFD に置き換わり、local と remote の manifest ハッシュが一致しなくなる

これらは仕様書の変更（#73）で、6-M6〜6-M12 の追加と、2 章の local の検証として決めた。この ADR は、その実装の決定を記録する。M2 が終わると実際のセーブで CLI を使い始めるので、その前に作る。

## 決定事項

### 検証の置き場所

- 事項: Pull と local が共有する検証を、どのファイルに置くか
- 決定内容: `internal/syncore/pull.go` の `validateEntries`・`validatePath` を、新しいファイル `internal/syncore/validate.go` に移す。6-M2 のドライブレターを検出していた正規表現は消し、6-M12 の `:` の検査で拒否する。path の規則（6-M1〜6-M5・6-M10〜6-M12）を検査する関数と、path 以外の規則（6-M6〜6-M9）を検査する関数に分け、Pull は両方を、local は path の規則だけを呼ぶ
- 判断理由: ドライブレターは必ず `:` を含むので、6-M12 があれば正規表現は拒否の結果を変えない。仕様書 2 章の local の検証は、6 章の path の規則をそのまま参照する。規則を 1 か所に置けば、Pull と local で検査がずれない。AGENTS.md は syncore のファイルを仕様書の章に合わせて分けるとしているが、この規則は Pull の手順ではなく、2 章と 6 章の両方から参照されるものなので、独立したファイルにする。サブパッケージには切り出さない。公開 API を増やさずに済み、#29 の fuzz テストも外部テストパッケージから `Pull` と `Status` 経由で書けるため

### Pull の検証

- 事項: 6-M6〜6-M9 をどう検査するか
- 決定内容:
  - 6-M6: `Manifest.Entries` が nil なら拒否する。`encoding/json` は、`"entries"` がないときと `null` のときは nil のままにし、`[]` のときは長さ 0 の nil でないスライスを作るので、nil かどうかで区別できる
  - 6-M7: 64 文字で、各文字が `0-9a-f` であることを確かめる
  - 6-M9: 隣り合うエントリの path を `strings.Compare` で比べ、前が後ろより小さくなければ拒否する。等しい場合が重複に当たる
  - 検査の順は 6-M6 → 各エントリの 6-M7・6-M8・6-M9 → path の規則とする。path の規則は local と同じ関数で検査する
- 判断理由: 6-M6 で `json.RawMessage` などを使って欠けたことを見分ける案もある。しかし、nil かどうかで区別できるので、`Manifest` の型を変えずに済む。昇順は仕様書 2 章のとおり UTF-8 のバイト列の辞書順で、Go の文字列の比較はバイトの比較なので一致する

### local の検証

- 事項: local の manifest を計算するときに、どこで検証するか
- 決定内容: `localEntries` で、ファイルを列挙して相対パスを `/` 区切りにした後、ハッシュを計算する前に、`utf8.ValidString` と path の規則で検査する。6-M5 は列挙したすべての path に対して検査する。Pull の 6-L5 で stage を検証するときも `localEntries` を通るので、同じ検査がかかる
- 判断理由: ハッシュの前に検査すれば、大きなセーブフォルダでも計算を無駄にしない。stage は 6-L2 を通った manifest から作るので、検査に当たることはなく、分ける必要はない。Windows では、対になっていないサロゲートを含む名前を Go が正しくない UTF-8 にするか、U+FFFD に置き換えるかが、Go の版によって違う可能性がある。前者なら `utf8.ValidString` で止まり、後者なら置き換えた名前でファイルを開けず、ハッシュの計算がエラーになる。どちらでも manifest を計算せずに止まるので、仕様書 2 章を満たす

### エラーの返し方

- 事項: 検証に当たったことを、センチネルエラーで公開するか
- 決定内容: 公開しない。どの path がどの規則に当たったかを書いたエラーを `%w` で包んで返す
- 判断理由: AGENTS.md の方針では、センチネルエラーにするのは呼び出し側が振る舞いを分ける必要のあるものだけである。CLI はエラーを表示して止まるだけで、規則ごとに振る舞いを変えない。GUI で分ける必要が出たら、そのときに足す

### テスト

- 事項: Windows で作れない名前の local の検証を、どう確かめるか
- 決定内容: Pull の 6-M6〜6-M12 は、偽のリモートに manifest を直接書いて、どの OS でも確かめる。6-M6 は `entries` がない JSON と `null` の JSON を書く。local の検証（正しい UTF-8 でない path・6-M5・6-M10〜6-M12）は、そのファイルを作れない Windows では `t.Skip` で飛ばし、Linux で確かめる
- 判断理由: 大文字小文字だけが違う 2 つのファイルや、`:` と末尾が `.` の名前は、Windows のファイルシステムにはそもそも作れない。local の検証は、大文字小文字を区別するフォルダや Linux から来るファイルを止めるためのものなので、Linux で確かめれば足りる

## 結果 / 影響

- 決定事項のとおりに実装した。差分は本番が約 100 行、テストが約 170 行で、見込み（300 行前後）に収まった
- 6-M9 の「同じ path が 2 つある」は、6-M5 の大文字への揃えでも重複になるので、6-M9 を足す前から拒否されていた。ほかの 6-M6〜6-M12 は、足す前は Pull が手順 5 の検証まで進むか、成功していた
- R2 で、`entries` のない manifest を HEAD にした世代を Pull すると、何も変えずに止まることを確かめた。判定は Pull で、この変更の前なら、セーブがすべてバックアップに移って消えていた
- 次のことは、仕様書の判断が要るので、11 章「未決事項」に挙げた
  - 6-M5 が path 全体だけを大文字に揃えて比べるので、ディレクトリの部分だけが大文字小文字で違う path（`dir/a.sav` と `DIR/b.sav`）や、ファイルとディレクトリの名前の衝突（`a` と `a/b.sav`）を拒否しない
  - 6-M10 が最初の `.` より前の部分をそのまま比べるので、末尾に空白のある `aux .sav` を拒否しない。Windows は空白を取り除いてデバイス名として扱う
  - 6-M5 の大文字への揃え方（Go の `strings.ToUpper`）が NTFS の対応表と違い、Windows では別のファイルになる `ı.sav` と `i.sav` などを重複として拒否する
- 承認の後に、検証に当たるファイルがセーブフォルダに現れると、5-P3 と 6-L6 のハッシュのし直しが `ErrPlanStale` ではなく検証のエラーを返す。承認の後に通常のファイル以外が現れたときと同じ扱いで、どちらも何も変えずに止まるので、分けなかった
